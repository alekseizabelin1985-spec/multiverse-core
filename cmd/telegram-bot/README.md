# `cmd/telegram-bot` — Telegram-бот игрока

Клиент платформы поверх HTTP API шлюза (`internal/gateway/client`): long
polling `getUpdates`, разбор команд, доступ по приглашению, отправка ответов
игроку. Библиотека — `go-telegram/bot` (ADR-018). Персистентного хранилища у
бота нет: связка аккаунта с игроком — в `links.db` шлюза; состояние диалога и
кэш `chat_id → player_id` — в памяти бота с TTL (T-311).

Подробное поведение — `Docs/dev-team/architecture/components/gateway-and-bot.md`
§10, решения — ADR-018 (библиотека, long polling, reply-клавиатуры).

## Как устроен процесс

Две рабочие горутины и сервер `/health`:

- **Обработчик обновлений** — одна горутина на все чаты: `access.Gate` →
  разбор команды → `flow`. Пока он ждёт Telegram или шлюз, команды всех
  игроков стоят в очереди, поэтому у него короткие клиенты (таблица ниже).
- **Цикл доставки** (`internal/deliver`) — своя горутина: long-poll
  `GET /v1/clients/telegram-bot/deliveries` (`wait_ms=25000`, `limit=100`),
  доставки ответа отправляются по одной в порядке шлюза, затем один
  `POST …/deliveries/ack` на все отработанные. Порядок сообщений игрока
  держит шлюз (в лизинге одна доставка на игрока), бот ничего не
  переставляет. Механика и нарратив хода — разные доставки, а значит, разные
  сообщения; у нарратива строка-пометка источника текста. Цикл стартует после
  того, как Telegram принял токен (`getMe`): с отозванным токеном бот не берёт
  доставки в лизинг.

`X-Client-Id` бота — `telegram-bot` (константа, первый элемент
`MV_GATEWAY_CLIENT_IDS` по умолчанию); отдельной переменной для него нет.

| Кто ждёт | Клиент | Одна попытка | Повторы |
|---|---|---|---|
| `access` — ответ постороннему | свой HTTP-клиент Telegram | 5 с (`sender.BestEffortHTTPTimeout`) | нет |
| `flow` — ответ игроку | свой HTTP-клиент Telegram | 10 с | `sender.ReplyPolicy`: сеть и `5xx` — ещё один раз через 1 с; `429` ждётся один раз и только при `retry_after` ≤ 3 с: зависший Telegram держит остальных не дольше ~21 с |
| `flow` → шлюз | свой клиент шлюза | 6 с (обычный запрос шлюз обрывает через 5 с) | один повтор через 200 мс, только на сеть и `503`: одна команда держит остальных не дольше ~12 с |
| цикл доставки → Telegram | свой HTTP-клиент Telegram | 30 с (`sender.DefaultHTTPTimeout`) | `sender.DefaultPolicy`: `429` — пауза `retry_after` (до 60 с, до 5 раз), сеть и `5xx` — 3 попытки через 1 с |
| цикл доставки → шлюз, long-poll | свой клиент шлюза | 35 с (`client.DefaultHTTPTimeout`, дольше long-poll 25 с) | внутри клиента не повторяется — цикл опрашивает снова после паузы 1, 2, 4 … 30 с; так же после пустого ответа, пришедшего раньше половины ожидания (так шлюз отвечает при остановке) |
| цикл доставки → шлюз, `ack` | свой клиент шлюза (`deliver.NewAckClient`) | 6 с | один повтор через 200 мс на сеть и `503`: неудачный `ack` (после ответа и ещё раз перед следующим long-poll) держит цикл не дольше ~25 с — меньше лизинга 30 с, иначе шлюз выдал бы доставку снова |

Что делает цикл доставки с результатом отправки:

| Ответ Telegram | Ошибка `Sender` | Доставка |
|---|---|---|
| отправлено | — | подтверждается |
| `403` (бот заблокирован) | `ErrBlocked` | подтверждается: игрок недоступен, повтор не поможет; строка лога `reason=blocked` без ID |
| `400 chat not found` | `ErrChatNotFound` | подтверждается, `reason=chat_not_found` |
| другой `4xx` | `ErrRejected` | подтверждается, `reason=rejected` |
| сеть, `5xx`, `429` сверх политики | `ErrUnavailable` | **не** подтверждается: шлюз выдаст её снова через 30 с (`MV_GATEWAY_DELIVERY_LEASE`) |
| `401` (токен отозван) | `ErrUnauthorized` | **не** подтверждается, остаток ответа не отправляется; опрос обновлений получает тот же `401` и останавливает процесс с кодом 1 |

Доставка без маршрута Telegram (`route` пуст, другая платформа или
нечисловой `external_id`) подтверждается без сообщения: этот бот её никогда не
отправит, а неподтверждённая она 24 часа стояла бы перед остальными
сообщениями игрока.

Что живёт **только в памяти** и пропадает при перезапуске:

- курсор доставок: после рестарта бот опрашивает шлюз с пустым курсором, и всё
  неподтверждённое приходит снова (component §16 п. 5). Сообщение, которое
  ушло игроку, но чей `ack` не дошёл до шлюза, после рестарта придёт повторно.
  При остановке бот успевает подтвердить уже отправленное (до 5 с);
- шаг диалога онбординга и `player_id` чата: после рестарта `/start`
  восстанавливает всё по `links/resolve`;
- отметка «удаление не завершено» (`forget_incomplete`): если бот перезапустили
  между ответом «удаление не завершено» и повтором `/forget confirm`, повтор
  ответит «нечего удалять», хотя связка и её данные уже стёрты.

Ответ `flow` под флуд-баном Telegram дольше 3 с не ждётся и теряется: игрок
не видит ответа и повторяет команду, а команды других игроков в это время не
стоят.

## `/health` и подкоманда `health`

`GET /health` на `MV_TELEGRAM_HEALTH_ADDR` (умолчание `:8089`, в compose
опубликован только `127.0.0.1:8089`):

```json
{"status":"ok","details":{"bot_denied_total":0,"bot_not_private_total":0,"bot_too_often_total":0}}
```

`bot_denied_total` — отклонённые обновления не из allow-list,
`bot_not_private_total` — сообщения не из личного чата, `bot_too_often_total` —
команды сверх лимита; счёт с момента старта, только числа, без ID. `status` —
`ok`, пока процесс работает: доступность Telegram и шлюза он не отражает, их
отказы видны в логе (`deliveries not polled`, `answer not delivered`).

`telegram-bot health [--url <url>]` — healthcheck образа без оболочки и curl
(`docker-compose.bot.yml`). Без `--url` адрес строится из
`MV_TELEGRAM_HEALTH_ADDR`: пустой хост, `0.0.0.0` и `::` заменяются на
`127.0.0.1`. Код 0 — ответ 200 со `status: ok`; 1 — иначе (нет ответа, другой
статус); 2 — неверная командная строка. Прокси окружения проба не использует.

## Как получить токен

1. В Telegram открыть `@BotFather`, отправить `/newbot`, задать имя и
   username бота — BotFather выдаёт токен вида `<цифры>:<секрет>`.
2. Тому же боту отправить `/setjoingroups` → выбрать **Disable**: бота нельзя
   будет добавить в группы (см. «Ограничения» ниже, SEC-07).
3. Токен положить в `.env` (`MV_TELEGRAM_BOT_TOKEN=<токен>`) — **не** в код и
   не в `docker-compose.bot.yml`: в compose токен передаётся только через
   `environment:` сервиса `telegram-bot` (D-10, правило 4 `compose-lint`,
   `docker-compose.bot.yml`), не через `env_file`.
4. Ротация токена (компрометация, плановая замена) — `Docs/ops/runbook.md`
   §6.

Формат токена проверяется при старте (`config.Load`): значение, не похожее на
`<цифры>:<секрет>`, отклоняется без вывода самого значения. Без токена бот не
стартует (`ErrTokenMissing`, SEC-08).

## Allow-list

`MV_TELEGRAM_ALLOWED_USER_IDS` — список числовых Telegram user id через
запятую. Пустой список означает отказ всем (fail-closed, SEC-06) — это не
баг, это поведение по умолчанию для нового бота. Отправитель не из списка
получает **один** ответ «Доступ по приглашению.» на серию сообщений (не
больше 10 таких ответов на весь бот за 60 секунд суммарно, дальше — тишина и
только счётчик), а не по одному на каждое сообщение; `bot_denied_total`
считает каждое отклонённое обновление. Отказ никогда не называет id — ни в
ответе, ни в логе (`internal/access`, `internal/privacy`).

## Профиль compose `bot`

Сервис `telegram-bot` живёт в `docker-compose.bot.yml`, а не в основном
`docker-compose.yml` (см. комментарий в файле): интерполяция compose
разворачивает переменные всех файлов сразу, и обязательный
`MV_TELEGRAM_BOT_TOKEN` ломал бы `make up` даже тем, кто бота не поднимает.
Поднять вместе с остальным стеком:

```bash
make up PROFILES=<обычный набор>,bot   # например: make up PROFILES=memory,bot
```

`memory`/`legacy` — только пока allow-list состоит из владельца (У-2, «Данные
игроков» ниже). Для внешних игроков пример — `make up PROFILES=bot`.

Или добавить сервис к уже поднятому стеку, не трогая остальное (сначала
`export COMPOSE_ENV_FILES=.env,build/versions.env` — PowerShell:
`$env:COMPOSE_ENV_FILES = ".env,build/versions.env"` — иначе compose падает на
первой переменной образа, см. врезку `Docs/ops/runbook.md` перед разделом 1):

```bash
docker compose -f docker-compose.yml -f docker-compose.bot.yml up -d telegram-bot
```

Подробности профилей — `Docs/ops/runbook.md`, разделы «Профили» и §6.
Порт `/health` бота публикуется только на `127.0.0.1:8089` (`MV_TELEGRAM_HEALTH_ADDR`,
умолчание `:8089`).

## Переменные окружения

Только объявления `shared/env` (`shared/env/vars.go`), полные умолчания и
комментарии — там же и в `.env.example`.

| Переменная | Смысл |
|---|---|
| `MV_TELEGRAM_BOT_TOKEN` | токен от `@BotFather`; секрет, в логах и ошибках не печатается |
| `MV_TELEGRAM_ALLOWED_USER_IDS` | allow-list Telegram user id; пусто = отказ всем |
| `MV_TELEGRAM_GATEWAY_URL` | адрес HTTP API шлюза (в compose — `http://gateway:8088`) |

| `MV_TELEGRAM_HEALTH_ADDR` | адрес, на котором бот отдаёт `/health` |
| `MV_TELEGRAM_COMMANDS_PER_MIN` | лимит команд одного пользователя за 60 с (SEC-11) |
| `MV_TELEGRAM_ACTION_KEY_SALT` | ключ HMAC для `action_key`; без значения используется производная от токена (не логируется ни в каком виде) |

доставок и `X-Client-Id` — константы кода (раздел «Как устроен процесс»), не
переменные.

`MV_TELEGRAM_ACTION_KEY_SALT` и `MV_TELEGRAM_COMMANDS_PER_MIN` объявлены в
манифесте и есть в `.env.example`, но **не** переданы в
`docker-compose.bot.yml` — обе переменные читаются с умолчаниями манифеста,
пока эту строку не закроет
[карточка T-463](../../Docs/dev-team/epics/EPIC-001-foundation/tasks/T-463.md)
(EPIC-001, часть «в», статус `todo` на момент этой страницы).

## Коды выхода и `409 Conflict`

Код выхода выбирает `main`: остановка опроса обновлений переводится в код
через `updates.ExitCode`, ошибки конфигурации и старта дают код 1. Причина
уходит в stderr одной строкой `telegram-bot: …` и в лог — без токена.

| Код | Когда | Что означает |
|---|---|---|
| `0` | процесс остановлен сигналом (`SIGTERM`, `Ctrl+C`) | обычная остановка |
| `1` | `getMe` при старте или `getUpdates` во время опроса ответили `401 Unauthorized` (`ErrUnauthorized`; после первого `401` опрос не продолжается); пустой или не похожий на токен `MV_TELEGRAM_BOT_TOKEN`; неверная переменная `MV_TELEGRAM_*` или `MV_LOG_LEVEL`; адрес `/health` занят | токен отозван или недействителен — обновить `MV_TELEGRAM_BOT_TOKEN`; иначе исправить переменную из сообщения |
| `2` | неверная командная строка (неизвестная подкоманда, лишний аргумент `health`) | ошибка вызова |
| `3` (`updates.ExitConflict`) | `getUpdates` ответил `409 Conflict` (`ErrConflict`) | **другой экземпляр бота уже поллит тот же токен**, либо для него настроен webhook |

**Что делать при `409`:** проверить, не запущен ли бот где-то ещё с тем же
токеном (второй контейнер, локальный запуск для отладки, старый процесс,
который не остановился) и убедиться, что для токена не установлен webhook.
Токен нельзя подставлять в URL или в аргумент команды: он попадёт в историю
оболочки, в список процессов и в адресную строку браузера. Проверка через
`curl -K -` — конфигурация `curl` из stdin. Git Bash (токен вводится и не
отображается, не пишется в историю):

```bash
IFS= read -rs TG_TOKEN
printf 'url = "https://api.telegram.org/bot%s/getWebhookInfo"\n' "$TG_TOKEN" | curl -sS -K -
# при непустом "url" в ответе — снять webhook тем же приёмом:
printf 'url = "https://api.telegram.org/bot%s/deleteWebhook"\n' "$TG_TOKEN" | curl -sS -K -
unset TG_TOKEN
```

PowerShell (Windows PowerShell 5.1 и PowerShell 7) — именно `curl.exe`: в
Windows PowerShell 5.1 `curl` — псевдоним `Invoke-WebRequest`, и он не
понимает `-sS -K -`. Ввод `Read-Host` в историю PSReadLine не пишется, в
истории остаётся только литерал `$t`:

```powershell
$s = Read-Host -AsSecureString
$t = [System.Net.NetworkCredential]::new('', $s).Password
"url = `"https://api.telegram.org/bot$t/getWebhookInfo`"" | curl.exe -sS -K -
# при непустом "url" в ответе — снять webhook тем же приёмом:
"url = `"https://api.telegram.org/bot$t/deleteWebhook`"" | curl.exe -sS -K -
Remove-Variable s, t
```

Не выкладывать вывод `docker compose config` и `docker inspect telegram-bot`
— там токен виден открытым текстом. После выхода с кодом 3 `docker compose
restart` без устранения причины уйдёт в цикл рестартов с тем же кодом; при
ротации токена webhook проверяется до перезапуска (`Docs/ops/runbook.md`, §6,
шаг 3).

## Логи и токен

Токен и явно заданная `MV_TELEGRAM_ACTION_KEY_SALT` никогда не попадают в
лог: `internal/privacy` строит `slog.Handler`, который вырезает
`external_id`, `chat_id`, `username`, `text` на всех уровнях (включая
`debug`), а `Redact`/`Redactor` заменяют `bot<цифры>:<секрет>` на
`bot<redacted>` в любой строке, включая тела ошибок HTTP-клиента Telegram.
Проверка перед выпуском — по всему логу контейнера, без чтения глазами (утечка
при старте может уйти выше последних строк, которые смотрит оператор):

```bash
docker compose -f docker-compose.yml -f docker-compose.bot.yml \
  logs telegram-bot | grep -cE '[0-9]{5,}:[A-Za-z0-9_-]{30,}'   # ожидается 0
```

Шаблон ищет форму токена, а не сам токен, поэтому безопасен для команды и её
вывода. Он ловит обе формы — `bot<цифры>:<секрет>` из URL Bot API и голый
`<цифры>:<секрет>` (например, в тексте ошибки конфигурации); `bot<redacted>`
под него не попадает. Ненулевой счёт — повод для ротации токена, найденные
строки не выкладывать (см. также `Docs/ops/runbook.md`, раздел 6).

## Данные игроков

Текст первого сообщения `/start` (`FR-009`, задача T-318) обещает игроку, что
его записи под псевдонимом удаляются автоматически, а копия связки хранится
не дольше 30 дней; при этом в резервных копиях игры эти записи могут
храниться ещё до 30 дней сверх указанных сроков (У-1). Эти обещания правдивы
только при выполнении следующих правил оператора — они не проверяются кодом
бота, это ручная дисциплина эксплуатации:

- **Профили `memory` и `legacy` не включаются**, пока в
  `MV_TELEGRAM_ALLOWED_USER_IDS` есть кто-то, кроме владельца. Qdrant, Neo4j
  и ChromaDB (профили `memory`/`legacy`) пока не удаляют данные по сроку —
  удаление по возрасту появится в EPIC-005 (бэклог, условие включения этих
  профилей для внешних игроков).
- **Открытых копий тома `gateway-data` не оставлять.** Копия `links.db`
  делается только зашифрованной (`age`); открытая копия в томе удаляется
  сразу после `docker cp`.
- **Копии `links.db` и `gateway.db` не хранятся дольше 30 дней** — ротация
  сейчас не реализована (задача T-463, EPIC-001, статус `todo` на момент
  этой страницы): пока она не выполнена, копии старше 30 дней вручную не
  оставлять.
- **Архивы `make backup` не старше 30 дней** — та же задача T-463: на
  сегодня `make backup` копит архивы бессрочно, ручная чистка — до её
  выполнения обязанность оператора.
- **`mvctl report` по сессиям живых игроков — только после доработки в
  EPIC-005** (T-131/T-132): пока в `ops/metrics/*` может встретиться
  идентификатор игрока, «обезличенная статистика» из текста `/start`
  неточна для внешних игроков.
- Если срок хранения (30/90/180 дней) или срок хранения бэкапа меняется,
  `internal/render/notice.go` (текст `/start`, T-311) и его тест
  правятся в той же задаче, что и срок (FR-009) — иначе бот обещает то, чего
  не делает.

Источник правил — карточка
[tasks/T-318.md](../../Docs/dev-team/epics/EPIC-004-gateway-bot/tasks/T-318.md),
раздел «Условия правдивости У-1…У-9».

## Ограничения

- Порт `/health` бота публикуется наружу только на `127.0.0.1:8089`
  (`docker-compose.bot.yml`); правило 2 `scripts/compose-lint.sh` («каждый
  опубликованный порт привязан к `127.0.0.1`», SEC-13) проверяет это для всех
  сервисов, включая бота.
- Бот отвечает только в приватных чатах (`chat.type = private`, SEC-07): в
  группе он молчит и не читает сообщения группы — поэтому `/setjoingroups` у
  `@BotFather` должен быть выключен (Disable), иначе бота можно добавить в
  группу, где он всё равно ничего не сделает и никого не предупредит.
- При `SIGTERM` может потеряться одно обновление, уже взятое в обработку
  (long polling без буфера канала); Telegram отдаёт остаток пачки повторно,
  повтор гасится тем же `action_key` (риск записан в `Docs/ops/runbook.md` §6).
- Ответы отправляются без `parse_mode`: разметка Markdown/HTML в тексте
  игрока или в тексте бота не форматируется, а показывается буквально
  (SEC-10).
- Граница по `internal/*` платформы — правило depguard `cmd-telegram-bot`
  (`.golangci.yml`): только `internal/gateway/client` и `internal/gateway/api`,
  без `shared/eventbus`. Вторая линия — тест `go list -deps` в
  `cmd/telegram-bot/imports_test.go` (пакет бинарника).
