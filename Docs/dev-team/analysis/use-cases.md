### 0.2. Единицы и идентификаторы

- **Ход** — одно действие игрока, принятое game-service, с результатом механики и нарративом (или шаблоном). **Раунд** — в `solo` = ход; в `group` — закрывается, когда все `active` участники действовали или истёк таймаут (60 с по умолчанию из блупринта; в CI — явная команда закрытия). **Сессия** — серия ходов в scope с простоем ≤ 30 мин; `session.id = "{scope.id}:{started_at_unix}"`.
- **Идентификаторы** (строки, английские): `world_id` (`dark-forest-world`), `region_id` (`dark-forest-01`), `player_id` (псевдоним персонажа, например `player-A`), `npc_id` (`wolf-alpha`), `group_id`, `encounter_id`, `agent_id`, `event_id` (UUID), `correlation_id` (= `event_id` события-причины: действия игрока или `tick.fired`), `session_id`, `laws_version` (`v1`).
- **Scope** (`scope{id,type}`): `solo:{player_id}` (тип `solo`), `group:{group_id}` (`group`), `region:{region_id}` (`region`), `world:{world_id}` (`world`). Игрок ровно в одном игровом scope (`solo` или `group`); scope региона и мира — scope агентов, не игроков.
- **Позиция** персонажа: `outside:{world_id}` («Опушка») либо `region_id`. Группа всегда в одной позиции.
- **Фикстуры** (как в `user-stories.md`): мир `dark-forest-world` с `laws@v1`; регион `dark-forest-01`; NPC `wolf-alpha`; персонажи «Вася» `player-A`, «Лена» `player-B`, «Олег» `player-C`; блупринты `global-dark-forest-world`, `domain-dark-forest`, `player-gm`, `encounter-wolf` (или часть `domain-dark-forest` — архитектор).

### 0.3. Общие правила всех игровых сценариев

1. **Валидация до механики.** Действие проверяется на словарь, состояние персонажа, scope, цель — до Phase 1 и без вызова LLM. Отклонение возвращается синхронно клиенту с кодом (см. `api-contracts.md` §1.6) и фиксируется `analytics.turn.completed status=rejected`.
2. **Механика первична.** Результат Phase 1 публикуется как события (`dice.rolled`, `combat.decided`, `entity.update.proposed` → `entity.updated`) **до** запуска Phase 2. Нарратив ничего не меняет.
3. **Единственный писатель.** Состояние сущностей меняет только entity-manager по предложениям; конфликт — по версии сущности.
4. **Record-replay.** Все недетерминированные источники записываются до использования: `llm.output` (до применения ответа), `dice.rolled`, `tick.fired`, `round.closed`, TTL/таймауты. В replay они читаются, а не порождаются.
5. **Сквозная трасса.** `meta.correlation_id` проставляется gateway (действие, `round.closed`) или планировщиком (тик) и наследуется всеми событиями цепочки через `eventbus.Derive`; `meta.causation_id`/`causation_type` ссылаются на непосредственную причину (ADR-007; в v0.1 — `trigger.event`).
6. **Адресность.** Игрок получает только то, что адресовано его `player_id` (через его персональный GM). Ничего чужого.
7. **Приватность.** Внешние ID не покидают бота и хранилища связок; в шине, снапшотах, индексах, логах, промптах — только `player_id` и имя персонажа.
8. **Деградация.** Недоступность LLM никогда не блокирует механику; игрок получает шаблон с пометкой.

### Игрок: доступ и персонаж

## UC-001: Первый контакт — уведомление об ИИ, согласие, подтверждение 18+

Актор: игрок через бота · Предусловия: бот запущен; у аккаунта нет связки; **Telegram user id входит в allowlist бота (`MV_TELEGRAM_ALLOWED_USER_IDS`) и команда пришла из личного чата** (ADR-006/009 дополнения; иначе бот молча игнорирует или отвечает «доступ по приглашению», gateway не вызывается) · Триггер: `/start`

### Основной поток
1. Бот получает `/start` от внешнего аккаунта (`external_platform=telegram`, `external_id`).
2. Бот запрашивает у game-service разрешение связки (`resolve`) по внешнему ID; ответ: связки нет. При первом обращении gateway заводит запись связки с суррогатом `link_id` (ULID; только в `links.db`).
3. Бот показывает единое сообщение: контент создаётся ИИ; игра 18+ — подтвердите возраст; введённый текст обрабатывается для генерации (при облачном провайдере — передаётся ему); `/forget` удаляет связку. Предлагает явное подтверждение.
4. Игрок подтверждает.
5. Бот передаёт game-service факт согласия; game-service создаёт запись связки со статусом `consented` и полями `notice_shown_at`, `consent_at`, `age_confirmed_at` (одно и то же значение времени допустимо), `player_id` пока пуст.
6. Бот предлагает ввести имя персонажа и выбрать мир (UC-002).

### Альтернативные потоки
- **A1. Повторный `/start` с существующей связкой и живым персонажем.** Шаг 2 возвращает `player_id` и статус `alive` → бот показывает краткое состояние (UC-003) без повторного согласия. Повторный показ уведомления — по `/help` и после 30 дней неактивности (`last_seen_at` связки; Should).
- **A2. Связка есть, персонаж `dead`.** Бот предлагает создать нового персонажа (UC-002, A2).
- **A3. Связка есть, согласия нет (`pending_consent`).** Повтор шага 3.

### Исключения
- **E1. Игрок отвечает «нет» или игнорирует.** Связка остаётся `pending_consent` (или не создаётся); любая игровая команда → повтор сообщения подтверждения; событий в шину нет.
- **E2. game-service недоступен.** Бот отвечает «сервис недоступен, попробуйте позже»; ничего не сохраняется.

### Постусловия
Связка `consented` без персонажа; в шине событий нет (согласие — не событие мира).
Связь: US-008, US-009 · FR-009, FR-060 · NFR-045

## UC-002: Создание персонажа

Актор: игрок · Предусловия: связка `consented` без живого персонажа; мир существует · Триггер: бот получает имя персонажа и мир

### Основной поток
1. Бот проверяет имя: длина 2–32 символа, буквы/цифры/пробел/дефис; если имя совпадает с `username`/именем профиля аккаунта — предупреждает и просит подтвердить (проверка на стороне бота: game-service данных профиля не имеет).
2. Бот вызывает создание персонажа: `{external_platform, external_id, world_id, character_name, actor_kind}`.
3. game-service проверяет: связка `consented`; мир существует; у связки нет персонажа `alive`; идемпотентность — по `(link_id, action_key)` в `character_requests` (`links.db`): повтор возвращает прежний ответ и тот же `player_id` (внешний ID в ключе и в `gateway.db` не используется — SEC-03).
4. game-service генерирует `player_id = "player-" + ULID`, публикует предложение создания сущности `entity.create.proposed` (тип `player`, имя, `hp 10/10`, инвентарь пуст, позиция `outside:{world_id}`, статус `alive`, `scope solo:{player_id}`) — корневое событие (`meta.correlation_id = id`); до факта `entity.created` статус связки/персонажа — `creating`.
5. entity-manager создаёт сущность (версия 1), публикует `entity.created`.
6. game-service, дождавшись `entity.created` по `correlation_id` (ограниченное ожидание), связывает `player_id` со связкой и отвечает боту: `player_id`, состояние персонажа.
7. Бот показывает состояние и уведомление, что можно `enter dark-forest-01`.

### Альтернативные потоки
- **A1. У связки уже есть персонаж `alive`.** Шаг 3 возвращает существующий `player_id` и состояние (идемпотентность; второй персонаж не создаётся).
- **A2. Персонаж связки `dead`.** Создаётся новый персонаж с **новым** `player_id`; связка переключается на него; старый `player_id` остаётся в истории и графе, исключается из всех scope и целей NPC.

### Исключения
- **E1. Мир не найден** → ошибка `world_not_found`, сущность не создаётся.
- **E2. Нет согласия** → `consent_required`, бот повторяет UC-001 шаг 3.
- **E3. Имя отсутствует / бот подставил имя профиля** → `name_required` / `name_invalid`; game-service не может отличить имя профиля от введённого — запрет подстановки закреплён контрактом бота (см. `integrations.md` §1).
- **E4. Таймаут ожидания `entity.created`** → ответ `202 accepted` с `player_id` и статусом `creating`; бот повторяет запрос состояния (UC-003).

### Постусловия
Сущность `player` в хранилище состояния; связка ссылается на `player_id`; в шине — `entity.create.proposed`, `entity.created` без внешних ID.
Связь: US-001, US-009 · FR-001, FR-023, FR-060, A-7 · NFR-041

## UC-003: Возврат в мир и запрос состояния (`status`)

Актор: игрок · Предусловия: живой персонаж · Триггер: `/start` повторно, `status`

### Основной поток
1. Бот разрешает внешний ID → `player_id`.
2. Бот запрашивает состояние персонажа: HP, инвентарь, позиция, статус, scope (соло/группа, лидер), активная встреча, участники.
3. game-service отвечает из своей читающей модели состояния (проекция `entity.updated`) либо запросом к хранилищу состояния **[решение аналитика: `status` — запрос чтения, не ход; событий и LLM не порождает; в `analytics.turn.completed` не входит]**.
4. Бот показывает состояние.

### Альтернативные потоки
- **A1. Первое действие после паузы ≥ 30 мин** — не относится к `status`; граница сессии открывается первым *игровым* действием (UC-027).

### Исключения
- **E1. Персонаж `dead`** → состояние возвращается с `status=dead` и подсказкой создать нового (UC-002 A2).

### Постусловия
Состояние не изменилось.
Связь: US-001 · FR-001, FR-006

### Игрок: цикл «Тёмный лес» соло

## UC-004: Вход в регион (`enter`) и сводка «пока тебя не было»

Актор: игрок · Предусловия: персонаж `alive`, позиция `outside:{world}` или другой регион, вне встречи, в `solo` (в группе — UC-015); GM региона активен постоянно (UC-029) · Триггер: `enter <region_id>`

### Основной поток
1. Бот отправляет действие `{type: enter, target: dark-forest-01, action_key}`; game-service подтверждает приём (`202`, `action_id = correlation_id`, `turn.seq`).
2. game-service валидирует: регион существует в мире; персонаж не во встрече; не в группе (или лидер группы — UC-015). Открывает/продолжает сессию (UC-027).
3. game-service публикует `player.entered_region` (`entity{player}`, `target{region}`, `scope solo`, `correlation_id`) и `entity.update.proposed` (позиция → регион; `cause=move`).
4. entity-manager применяет, публикует `entity.updated changed:[position]`. Бот получает механический результат «Вы вошли в Тёмный лес» (`generated_by=rules`).
5. GM региона получает `player.entered_region`: добавляет игрока в наблюдаемый scope региона (контекст не пересоздаётся), переводит расписание тика региона в «активный» интервал (интервал обнаружения из блупринта).
6. Рантайм роя активирует персональный GM игрока (если не активен): `agent.spawned {level, blueprint player-gm, scope solo:{player_id}}`.
7. Персональный GM собирает сводку «пока тебя не было»: если у игрока есть предыдущая сессия в мире — выбирает из журнала событий/памяти фоновые события мира и региона (`world.*`, `region.*`, `npc.*` с `actor_kind=system`) за `(since_at = ended_at последней сессии игрока, now)`; берёт текущие атрибуты мира (погода, время суток) и региона из состояния.
8. Персональный GM выполняет Phase 2 (LLM, модель нарратива): контекст = описание региона из блупринта (слой `authored`), канон, текущее состояние мира/региона, сводка фона, `laws_version`. Записывает `llm.output` до использования ответа. Валидирует (UC-022). Публикует `narrative.output {recipients:[player], generated_by:llm, absence{since_at, background_events_count}, background_refs[]}`.
9. game-service доставляет нарратив боту; фиксирует `analytics.turn.completed` (`status=ok`, `absence{…}`, `narrative{generated_by, agent_level}`, `delivery{…}`).

### Альтернативные потоки
- **A1. Первый вход (предыдущей сессии нет).** Шаг 7 без сводки; `absence` отсутствует.
- **A2. Повторный вход после убийства волка в той же сессии.** Сводка/контекст содержит факт `wolf-alpha: dead`; нарратив не описывает волка живым (проверка канона/состояния при валидации — UC-022 A3).
- **A3. LLM недоступна/таймаут.** UC-021: шаблон входа с фактами сводки (без LLM), `generated_by=template`.
- **A4. Фоновых событий ≥ 1 и сводка не отражена.** Нарушения нет (доля измеряется), но `background_refs` пуст → метрика; в CI при `background_events_count ≥ 1` и `surfaced=0` — предупреждение теста.

### Исключения
- **E1. Регион не существует** → `unknown_target`, состояние не меняется, `turn.completed status=rejected`.
- **E2. Персонаж во встрече** → `in_encounter` («сначала выйдите из боя: flee»).
- **E3. Персонаж `dead`** → `character_dead`.
- **E4. Не-лидер группы** → `not_leader` (UC-015 E1).

### Постусловия
Позиция = регион; игрок в scope региона для GM; персональный GM активен; нарратив входа доставлен; сессия активна.
Связь: US-002, US-005, US-036 · FR-001, FR-002, FR-011, FR-016, FR-127 · NFR-001, NFR-002

## UC-006: Обнаружение NPC и начало встречи

Актор: GM региона (система), Task-агент встречи · Предусловия: игрок(и) в регионе, живой NPC региона, нет активной встречи с этим игроком · Триггер: тик GM региона в активном режиме (`tick.fired`, интервал обнаружения из блупринта) либо реакция на `player.entered_region` **[решение аналитика: обнаружение — на тике, чтобы вход и встреча были отдельными ходами, как в e2e-сценарии PRD]**

### Основной поток
1. Планировщик публикует `tick.fired {agent: domain-dark-forest, scope region, scheduled_at, tick_seq, mode: active}`; `correlation_id = event_id тика`.
2. GM региона (LOD 1, без LLM): проверяет таблицу обнаружения блупринта: для каждого игрока/группы в регионе и каждого живого NPC в радиусе восприятия — есть ли встреча; если нет — решает породить встречу (детерминированно по правилам блупринта; опциональный бросок `dice.rolled` на шанс встречи).
3. GM региона публикует `entity.create.proposed` для сущности `encounter` (`participants: [player_ids]`, `npcs: [wolf-alpha]`, `region`, `scope` игрока/группы, `state: active`) → entity-manager → `entity.created`.
4. GM региона публикует `encounter.started {encounter{id}, participants[], npcs[], scope, round{timeout, idle_after_missed}?}` (`meta.causation_type = tick.fired`; параметры раунда — из блупринта `encounter-*`, C-05 v1.1); рантайм роя порождает Task-агент встречи: `agent.spawned {level task, blueprint encounter-wolf, parent domain-dark-forest, scope = scope игрока/группы}`. Для scope `group` gateway по `encounter.started` открывает раунд 1 (`round.opened seq=1`, таймер из `round.timeout`) — ADR-020 п. 2.
5. Персональный GM игрока получает `encounter.started` (событие в видимости) → Phase 2: нарратив появления волка с подсказкой действий (атаковать, бежать) → `narrative.output` → доставка. Это **не ход** игрока: `analytics.turn.completed` не публикуется; доставка — как «событие мира» (`delivery.kind=world_event`).

### Альтернативные потоки
- **A1. NPC мёртв или в кулдауне возрождения** → встреча не создаётся; тик завершается «без изменений» (`tick.fired` записан; событий региона нет).
- **A2. Игрок в группе** → одна встреча на группу: `participants = все active участники`; персональные GM всех участников получают событие; нарратив — один на scope (UC-020).
- **A3. LLM недоступна** → шаблон «Из тени выходит волк. Действия: attack wolf-alpha / flee».

### Исключения
- **E1. Task-агент встречи не стартовал (ошибка рантайма)** → `agent.spawn_failed`; встреча остаётся `active` без агента; следующий тик региона повторяет спавн; действия игрока по встрече отклоняются с `encounter_unavailable` (временный код); оператору — ошибка в логе с `handled=true`.

### Постусловия
Сущность `encounter` активна; Task-агент живёт до её завершения; игрок уведомлён.
Связь: US-002 · FR-012, FR-124, BR-16

## UC-007: Атака (соло)

Актор: игрок; Task-агент встречи; механика · Предусловия: активная встреча, персонаж `alive`, цель — живой NPC этой встречи · Триггер: `attack <npc_id>`

### Основной поток
1. Приём (`202`), валидация: цель существует, жива, в этой встрече; персонаж во встрече.
2. game-service публикует `player.attacked {entity{player}, target{npc}, scope, encounter{id}, correlation_id}`.
3. Task-агент встречи запускает Phase 1 в режиме правил (`phase1_mode=rules`, LOD 1, без LLM). Механика: бросок попадания `dice.rolled roll_index=0 formula d20` (`seed = hash(event_id действия, 0)`); при `d20 + atk ≥ def` — бросок урона `roll_index=1 formula d6`; нат. 20 — урон ×2; нат. 1 — промах.
4. Механика публикует `combat.decided {attacker{player}, defender{npc}, hit, natural, damage, hp_before, hp_after (clamp 0..hp_max), rolls[event_ids], gm_path=agent, phase1_mode=rules, correlation_id, trigger{player.attacked}}` и `entity.update.proposed` (NPC `hp`, при `hp_after=0` — `status=dead`; `cause=combat`, `agent{level task}`).
5. entity-manager применяет по версии, публикует `entity.updated`. game-service доставляет механический результат («Попадание, урон 3; волк 7/10», `generated_by=rules`) — в пределах NFR-001.
6. Если NPC жив: ответ NPC (UC-008 шаги 1–3) в том же раунде (соло: раунд = ход).
7. Phase 2: персональный GM игрока генерирует нарратив хода из всех `combat.decided` раунда (числа обязательны к соблюдению) → `llm.output` → валидация → `narrative.output` → доставка. `analytics.turn.completed` после доставки нарратива/шаблона.

### Альтернативные потоки
- **A1. NPC погиб от удара** → UC-008 A1 (трофей, завершение встречи); ответа NPC нет.
- **A2. Нарратив расходится с числами** («волк убит» при HP 7) → состояние не меняется (нарратив ничего не пишет); расхождение фиксируется метрикой `narrative_mechanics_mismatch` (ручная разметка в MVP-1) — не ошибка конвейера.
- **A3. Повторная доставка `combat.decided`/`entity.update.proposed`** → идемпотентность по `event_id`: применяется один раз.

### Исключения
- **E1. Цель не существует / не в scope** (`wolf-999`) → `unknown_target` до Phase 1, LLM не вызывается.
- **E2. Цель мертва** → `target_dead` (в соло — отклонение; в группе — UC-016 A2).
- **E3. Нет активной встречи** → `not_in_encounter`.
- **E4. Дубликат `action_key`** → тот же `202` с тем же `action_id`, второй ход не создаётся.

### Постусловия
HP NPC уменьшен ровно на `damage` из `combat.decided`; все броски записаны; нарратив доставлен.
Связь: US-002, US-003, US-004 · FR-013, FR-018, FR-020…FR-022, FR-084 · NFR-001, NFR-060

## UC-008: Ответ NPC, смерть NPC, трофей

Актор: Task-агент встречи; механика · Предусловия: встреча активна; после действий игроков раунда NPC жив · Триггер: закрытие раунда (соло — сразу после действия игрока; группа — `round.closed`)

### Основной поток
1. Механика выбирает цель детерминированно: последний игрок, нанёсший NPC урон в этой встрече; иначе игрок с минимальным HP; при равенстве — по возрастанию `player_id`; `idle`, `out_of_combat`, `dead` — не цели.
2. Броски `dice.rolled roll_index=2 (d20 попадания), 3 (d4 урона)`, seed от `event_id` действия, закрывшего раунд (соло — действие игрока; группа — `round.closed`) **[решение аналитика: в группе причина бросков NPC — событие `round.closed`]**.
3. `combat.decided {attacker{npc}, defender{player}, …}` → `entity.update.proposed` (HP игрока; при 0 — `status=dead`) → `entity.updated`. Механический результат доставляется цели и (в группе) всем участникам.

### Альтернативные потоки
- **A1. NPC погиб в этом раунде** (HP ≤ 0 по применённому `entity.updated`): Task-агент публикует `entity.update.proposed` для игрока, нанёсшего последний удар: `inventory += {item: wolf-pelt, name: «волчья шкура», source: wolf-alpha}` (`cause=loot`), затем `encounter.ended {reason: npc_dead, killer{player}}`, `entity.update.proposed` для `encounter` (`state=resolved`), `agent.child_resolved {agent task, parent domain, reason: npc_dead}`. Регион запоминает `wolf-alpha.died_at` (атрибут NPC) для кулдауна возрождения (UC-019 A2).
- **A2. Нет допустимой цели** (все `out_of_combat`/`idle`/`dead`) → NPC не действует; если все участники вне боя — `encounter.ended reason: players_out`.
- **A3. Игрок погиб от ответа** → UC-009.

### Исключения
- **E1. Конфликт версии при применении** (два предложения на NPC) → `entity.update.rejected reason=version_conflict`; издатель повторяет с актуальной версией (максимум N попыток, N — конфигурация); порядок — по времени приёма entity-manager.

### Постусловия
Инвариант «трофей за NPC ≤ 1 раза» выполнен (проверяется по `source` в инвентаре); NPC `dead` не выбирается целью и не действует.
Связь: US-002, US-007 · FR-020, FR-023, FR-128, BR-03, BR-13 · NFR-020 (1, 3, 7)

## UC-009: Смерть персонажа

Актор: механика; game-service · Предусловия: HP игрока стал 0 · Триггер: `entity.updated changed:[hp,status] status=dead`

### Основной поток
1. entity-manager применяет `hp=0, status=dead` (терминально).
2. game-service помечает персонажа `dead` в читающей модели; в группе — исключает его из `expected` открытого раунда (пересчёт `expected`; если `expected ⊆ acted` — немедленное закрытие `all_acted`); если он лидер — лидерство переходит к **старейшему `alive` участнику по `joined_at`** (`entity.update.proposed group.leader_id` + `group.leader_changed cause=death`); живых нет — лидер не меняется, группа доживает до `disbanded`/`session.ended death` **[предложение закреплено архитектурно: ADR-020 п. 8, C-04; BA закрепляет в BR-13 — то же правило, что при выходе лидера]**.
3. Task-агент/персональный GM: нарратив гибели (Phase 2) адресован погибшему и (в группе) остальным в составе нарратива раунда; персонаж не описывается действующим.
4. Если персонаж был последним живым участником scope — встреча завершается `encounter.ended reason: players_out` (NPC остаётся), сессия завершается `analytics.session.ended end_reason=death`.
5. Бот показывает предложение создать нового персонажа (UC-002 A2).

### Альтернативные потоки
- **A1. Смерть в группе, остальные живы** → сессия продолжается; погибший остаётся членом группы формально до `group leave`/`/forget`, но не действует, не ждётся, не цель.

### Исключения
- **E1. Любое игровое действие от `dead`** → `character_dead` без событий.

### Постусловия
`status=dead` навсегда; персонаж остаётся в графе/истории; исключён из scope и целей.
Связь: US-002, US-007 · FR-023, DR-26 · NFR-020 (1)

## UC-012: Реплика (`say`)

## UC-014: Создание группы, присоединение, выход

Актор: игрок · Предусловия: `alive` · Триггер: `group create` / `group join <group_id>` / `group leave`

### Основной поток (create)
1. Валидация: игрок не в группе.
2. game-service публикует `entity.create.proposed` для сущности `group` (`leader = player`, `members=[player]`, `position = позиция игрока`, `scope group:{group_id}`) → `entity.created`; затем `group.created {group{id}, leader{player}, members[]}` и `entity.update.proposed` игрока (`scope → group:{id}`).
3. Ответ игроку: `group_id`, состав, лидер. Сессия scope `group` открывается при создании (`analytics.session.started kind=group`); соло-сессия создателя закрывается `end_reason=leave` **[решение аналитика]**.

### Основной поток (join)
1. Валидация: группа существует; ≤ 5 участников; группа **не во встрече**; игрок не в группе; персонаж `alive`.
2. `entity.update.proposed` группы (`members += player`) и игрока (`scope`, `position = позиция группы`) — атомарно как одно предложение с несколькими сущностями **[решение аналитика: entity-manager поддерживает пакетное предложение с атомарным применением; иначе — инвариант «позиция участника = позиция группы» нарушается между двумя событиями]** → `entity.updated` ×2 → `group.joined`.
3. Все участники получают уведомление о составе.

### Основной поток (leave, вне встречи)
1. `entity.update.proposed` группы (`members -= player`) и игрока (`scope → solo:{player_id}`, позиция сохраняется) → `group.left`.
2. Если ушёл лидер — лидер = старейший из оставшихся (по времени присоединения) → `group.leader_changed`.
3. Если участников не осталось — `group.disbanded`, сущность группы `state=disbanded`; сессия группы закрывается.
4. Ушедший больше не получает нарратив группы; сессия остальных продолжается.

### Альтернативные потоки
- **A1. `group leave` во встрече** → выполняется как `flee` (UC-017).
- **A2. Игрок `idle` покидает группу** — обычный выход.

### Исключения
- **E1. `join` во время встречи группы** → `group_in_encounter` («подождите конца боя»).
- **E2. Группа полна (6)** → `group_full`.
- **E3. Не в группе при `leave`** → `not_in_group`.
- **E4. Уже в группе при `create`/`join`** → `already_in_group`.
- **E5. Группа не найдена** → `unknown_target`.

### Постусловия
Инварианты: 1 ≤ участников ≤ 6; каждый участник ровно в одном scope; позиция участника = позиции группы.
Связь: US-006 · FR-005, BR-13 · NFR-020 (4, 5, 6)

## UC-015: Перемещение группы лидером

Актор: лидер группы · Предусловия: группа вне встречи · Триггер: `enter <region>` / `leave` от лидера

### Основной поток
1. Валидация: отправитель — лидер; группа не во встрече.
2. game-service публикует **одно** событие `group.entered_region {group{id}, leader{player}, members[]{player}, target{region}, position{from,to}}` (или `group.left_region`) в `player_events` — **единственный формат перемещения группы** (решено: C-04, ADR-007; `player.entered_region` для участников не издаётся) — и пакетное `entity.update.proposed atomic=true` (позиция группы и всех `alive` участников).

### Исключения
- **E1. `enter` от не-лидера** → `not_leader` («регион меняет лидер группы»).
- **E2. Группа во встрече** → `in_encounter`.

### Постусловия
Позиция всех участников = позиции группы.
Связь: US-006 · FR-005, BR-06, BR-13, DR-20

## UC-016: Групповой раунд боя с таймаутом и `idle`

Актор: участники группы; game-service (координатор раунда — ADR-020); Task-агент встречи; механика · Предусловия: встреча группы активна · Триггер: раунд 1 — `encounter.started` (UC-006 шаг 4); раунд N+1 — первое открывающее действие участника после закрытия предыдущего раунда

### Основной поток
1. Открывающее действие (`attack` / `flee` / `defend` / `group.leave`; **не `say`**) участника после закрытия предыдущего раунда → game-service публикует `round.opened {scope, encounter, round{seq}, expected[] = members ∩ alive ∩ active ∩ ¬out_of_combat, deadline_at = now + timeout}` **до** `202` на это действие и запускает таймер (`timeout` из `encounter.started.round`, по умолчанию 60 с; через `Clock` — в replay не срабатывает). Координатор — gateway (решено, ADR-020).
2. Каждое действие участника принимается (`202`), публикуется как `player.*`, Phase 1 применяется **сразу по приёму** (порядок — по времени приёма): `dice.rolled`, `combat.decided`, `entity.updated` — участники видят механические результаты по мере поступления.
3. Раунд закрывается, когда все `expected` действовали **или** истёк таймаут: game-service публикует `round.closed {scope, encounter, round_seq, close_reason: all_acted|timeout|explicit, acted[]{player, event_id}, auto_defended[]{player}, idle[]{player}}`. Молчавшие `active` участники получают авто-действие `defend` — game-service публикует `player.defended {cause: round_timeout}` за каждого (не GM; BR-06 соблюдён).
4. Task-агент: ответ NPC один раз (UC-008) с seed от `round.closed`.
5. Учёт пропусков: gateway ведёт `missed_rounds` (`group_participation`); при `missed_rounds ≥ idle_after_missed` (2) → `entity.update.proposed Group.members[player].participation=idle` (`cause=group`, с `expected_version`); `idle` не ждётся при закрытии, не цель (`NPCTarget`, C-03), но получает нарратив раунда; первое его действие → предложение `active`, `missed_rounds=0`, участник входит в `expected` следующего раунда.
6. Phase 2 — один нарратив на раунд (UC-020): нарратор раунда получает все `combat.decided`, `player.said`, `player.defended`, итоги бегства; `narrative.output recipients = все участники (включая idle и out_of_combat; dead — только нарратив своей гибели)`.
7. `analytics.turn.completed` — по одному на каждое действие участника (ход = действие); `narrative_at` для всех = момент доставки последнему адресату; `delivery.narrative_event_id` одинаков.

### Альтернативные потоки
- **A1. Два удара одновременно, первый убивает.** Применение последовательно по версии NPC: второй `combat.decided` вычисляется по актуальному состоянию → `target_dead: true, damage: 0`; трофей — нанёсшему последний удар (один раз).
- **A2. Тест-харнесс.** Вместо таймера — команда `round.close` (API, только `actor_kind=ci`) → `round.closed close_reason=explicit`.
- **A3. Replay.** Таймер не используется; `round.closed` читается из журнала.
- **A4. Участник погиб в раунде** → исключается из `expected` следующих раундов (UC-009).

### Исключения
- **E1. Действие участника после закрытия раунда до открытия нового** → открывающее действие открывает новый раунд (шаг 1); действие, пришедшее в состоянии `closing`, относится к следующему раунду (игрок опоздал — ожидаемо).
- **E2. Второе действие того же участника в открытом раунде** → `409 already_acted` («дождитесь конца раунда»). **`say` — не действие раунда**: не открывает раунд, не входит в `acted[]`, доставляется участникам сразу и попадает в контекст нарратора (закреплено C-04 и ADR-020; BA закрепляет в FR-025).
- **E3. Участник ∉ `expected` (`idle`/`out_of_combat`) действует** → действие принимается как обычный ход, в `acted[]` не входит (для `idle` — возврат в `active`, шаг 5).

### Постусловия
HP NPC = HP до раунда − Σ урона; NPC ответил один раз; все участники получили одинаковый нарратив; `round.closed` записан.
Связь: US-007 · FR-025, FR-013, FR-033, BR-04, BR-13 · NFR-005, NFR-012, NFR-013

## UC-017: Индивидуальное бегство и выход из группы в бою

Актор: участник · Предусловия: встреча группы активна · Триггер: `flee` / `group leave`

### Основной поток (`flee`)
1. Как UC-010; при успехе участник получает `out_of_combat=true` в сущности `encounter`, остаётся в группе и в позиции группы, не цель; при провале — свободная атака NPC, участник в бою.

### Основной поток (`group leave` в бою)
1. Исполняется как `flee`. Успех → участник покидает встречу и группу (`group.left`), переходит в `solo`, позиция → `outside:{world}` **[решение аналитика: вышедший из группы в бою оказывается на опушке, как и при соло-бегстве]**. Провал → свободная атака, участник остаётся в группе и в бою.

### Постусловия
Один NPC — одна встреча — один scope (нет NPC в двух scope одновременно).
Связь: US-007 · BR-13

## UC-018: Фоновый тик глобального GM

Актор: планировщик; глобальный GM · Предусловия: мир загружен; блупринт `global-*` с `trigger.type=timer`; глобальный GM активен (не удаляется по TTL) · Триггер: расписание (по умолчанию 60 мин)

### Основной поток
1. Планировщик публикует `tick.fired {agent{id, level global, blueprint}, scope world:{world_id}, scheduled_at, tick_seq, mode: background, actor_kind: system}`; `correlation_id = event_id`.
2. Глобальный GM выбирает режим: LOD 1 (таблица событий блупринта без LLM) или LOD 2 (малая модель), если бюджет фона не исчерпан (счётчик вызовов за скользящий час на мир < B, B=4 по умолчанию).
3. LOD 2: Phase «tick» → `llm.output {phase: tick, agent, actor_kind: system, laws_version}` → валидация (UC-022: только атрибуты мира; события только из белого списка уровня `global`).
4. Глобальный GM публикует события мира: `world.weather_changed {from, to}`, `world.time_advanced {time_of_day, day}` и/или `world.event_occurred {kind, summary}`; каждое — с `entity.update.proposed` атрибутов мира (`weather`, `time_of_day`, `day`) → `entity.updated`.
5. GM регионов получают `world.*` как контекст (вниз); семантическая память индексирует события.
6. Если решений нет — тик завершается без событий мира (`tick.fired` уже записан; допускается `tick.completed {events_count: 0}` — архитектор).

### Альтернативные потоки
- **A1. Бюджет исчерпан** → LOD 1; `llm.output.rejected reason=budget_exceeded actor_kind=system`.
- **A2. LLM недоступна** → LOD 1, ошибок нет.
- **A3. Активная сессия в мире в момент тика** → тик выполняется с низким приоритетом: LLM-вызов тика ставится в очередь после вызовов ходов; при ожидании дольше порога — LOD 1 (BR-10).
- **A4. Replay** → `tick.fired` читается из журнала; таймер не используется; `llm.output` тика читается.

### Исключения
- **E1. Вывод LLM меняет сущность чужого уровня** (NPC, игрока) → `level_violation`, остальное применяется.
- **E2. Рестарт во время тика** → после восстановления тик либо завершён по записанным событиям, либо помечен `tick.aborted`; события не применяются дважды (идемпотентность по `event_id`).

### Постусловия
Атрибуты мира изменены (или нет); события записаны с `actor_kind=system`; вызовов LLM за час по фону ≤ B.
Связь: US-036, US-037 · FR-124…FR-126, FR-128, BR-10 · NFR-007, NFR-053

## UC-020: Адресный нарратив: персональный GM и нарратор раунда

Актор: персональный GM; нарратор раунда · Предусловия: событие в видимости игрока (действие, `combat.decided`, `encounter.*`, адресованные scope события уровней выше) · Триггер: закрытие раунда scope (соло — ход; группа — `round.closed`) или событие мира вне хода (`encounter.started`, трансляция `world.*` при значимости — по правилу блупринта)

### Основной поток
1. Нарратор определяется по scope: `solo` — персональный GM игрока (`player-gm`); `group` — отдельный агент **`group-narrator`** (`level: task`, один на `group:{id}`, спавн по `group.created`, TTL 45 мин; решено C-11 v0.2 — вместо «персонального GM лидера» v0.1; контракт `narrative.output` одинаков). Персональные GM участников группы вызовов LLM не делают (`rule-only`).
2. Нарратор собирает контекст: события раунда (все `combat.decided`, `player.said`, `player.defended`, итоги `flee`), текущее состояние участников и NPC (числа), атрибуты мира (погода = текущая), канон и описание региона из блупринта (`authored` > `validated` > `generated`), `laws_version`, `locale=ru`.
3. Phase 2 (модель нарратива) → `llm.output {phase: narrative, attempt}` → валидация (UC-022) и `NarrativeFilter` (UC-023).
4. `narrative.output {recipients[]{player}, text, generated_by: llm, agent{level, blueprint}, correlation_id (действия/раунда), round{seq}?, background_refs[]?, absence{}?, filter{applied, status}}`.
5. game-service доставляет каждому адресату; чужим scope — ничего.

### Альтернативные потоки
- **A1. Один вызов, N адресатов** — в группе один `llm.output` на раунд; персональные GM участников не делают вызовов (A-13); их роль — контекст памяти игрока и доставка.
- **A2. Лидер `idle`/`dead`** → на нарратора не влияет (`group-narrator` привязан к scope группы, не к лидеру); v0.1-правило «персональный GM старейшего `active`» снято.
- **A3. Событие уровня выше во время хода** (`world.weather_changed`) → попадает в контекст следующего нарратива, отдельная доставка не требуется; блупринт может пометить типы событий как «немедленная трансляция» (тогда доставка как `delivery.kind=world_event`).

### Исключения
- **E1. Невалидный ответ после повторов** → шаблон (UC-021).
- **E2. Персональный GM публикует `player.*` или `entity.update.proposed`** → отклонение `player_agency`/`level_violation`; нарратив доставляется без них.

### Постусловия
Все адресаты получили одинаковый текст с одним `narrative_event_id`.
Связь: US-004, US-006, US-037 · FR-003, FR-013, FR-123, A-13

## UC-021: Деградация при недоступности LLM

Актор: конвейер агента; провайдер LLM · Предусловия: любой вызов LLM · Триггер: недоступность провайдера, таймаут, ошибка, невалидный ответ после повторов, лимит

Механика применена полностью; игрок получил текст; сессия продолжается.

## UC-022: Валидация вывода LLM стражем (отклонение)

Актор: страж (функция валидации конвейера); entity-manager (последняя линия) · Предусловия: получен ответ LLM, записан `llm.output` · Триггер: каждый ответ

### Основной поток (порядок проверок)
1. **Схема** фазы (structured output; строгий JSON) — иначе `schema_invalid` → повтор (до N) → шаблон.
2. **Язык** (Phase 2/tick с текстом): нет CJK-иероглифов; латиница ≤ порога (NFR-090) — иначе `language` → повтор → шаблон.
3. **Ссылки на сущности**: все `entity.id` в ответе существуют в реестре мира и видимы агенту — иначе `unknown_entity {entity{id}}`; событие в мир не публикуется, «призрачная» сущность не создаётся.
4. **Агентность игрока**: ответ не содержит событий `player.*` и действий персонажей, которых они не совершали, — иначе `player_agency`; событие отбрасывается, остальное применяется.
5. **Уровень**: предлагаемые изменения касаются только сущностей уровня агента (таблица владения — `data-model.md` §4) и типов событий из белого списка блупринта — иначе `level_violation`; отбрасывается элемент, остальное применяется.
6. **Законы/инварианты** (MVP-1 = инварианты NFR-020 как `laws@v1`): предложение не нарушает инварианты (HP в диапазоне, мёртвый не действует…) — иначе `law_violation` **[к BA: причина отсутствует в перечислении FR-034; предлагаю добавить]**; `laws_version` ответа = текущей.
7. **Фильтр (a)** — UC-023.
8. **Бюджет** — проверяется до вызова (UC-024).
9. Валидный остаток применяется: `llm.output.validation_status = valid | partially_rejected`; для каждого отклонённого элемента — `llm.output.rejected {reason, entity?, element_index, correlation_id, agent, actor_kind}`.
10. entity-manager при получении `entity.update.proposed` повторяет проверки 3, 5, 6 и версию → `entity.update.rejected {reason}` при провале.

### Постусловия
В состояние попали только валидные, разрешённые уровнем изменения; каждый отказ записан с причиной.
Связь: US-003, US-018, US-037 · FR-034, FR-042, FR-122, BR-06, BR-16 · NFR-021, NFR-022, NFR-090

## UC-023: Фильтр категории (a) на выходе — `quarantined` (решение G1, OQ-D-16 = B)

## UC-025: Снапшот, рестарт и восстановление (снапшот + replay без LLM)

Актор: оператор; каждый компонент с состоянием (entity-manager, рантайм роя, game-service) · Предусловия: стек работал; снапшоты пишутся периодически (интервал — конфигурация), по завершении сессии и при штатной остановке · Триггер: рестарт всех сервисов

### Основной поток
1. **Снапшот (до рестарта).** Каждый компонент с состоянием пишет снапшот: `{service, world, snapshot_id, taken_at, cursor (позиция в журнале: последний применённый event_id/offset по топикам), laws_version, state_hash, содержимое}`; публикует `snapshot.created`. entity-manager — все сущности мира с версиями; рантайм роя — экземпляры агентов (уровень, блупринт+версия, scope, состояние, `tick_seq`, счётчики бюджета, активные раунды/ожидания); game-service — сессии, открытые раунды, ключи идемпотентности, недоставленные сообщения (outbox).
2. **Старт.** Компонент загружает последний целостный снапшот (проверка `state_hash`), выставляет режим `replay=true`, читает журнал с `cursor`.
3. **Догон.** entity-manager повторно применяет `entity.updated`-факты после `cursor` (идемпотентно по `event_id` и версии) — **не** пересчитывает предложения; рантайм роя восстанавливает агентов и «проигрывает» события после `cursor`: на месте вызова LLM читает записанный `llm.output` по `meta.correlation_id`+`meta.agent.id`+`phase`+`attempt`, на месте броска — `dice.rolled` по `meta.causation_id`+`roll.index`, на месте таймера — `tick.fired`/`round.closed`; game-service восстанавливает сессии из `analytics.session.started` без парного `ended` (либо закрывает их `end_reason=error`), outbox — из недоставленных `narrative.output`.
4. По достижении конца журнала компонент снимает `replay`, публикует `analytics.replay.completed {run_id, mode: recovery, snapshot_id, events_replayed, llm_calls: 0, dice_rolled_new: 0, duration_ms, state_hash_before (из снапшота), state_hash_after, identical, events_hash_match, incomplete_record: false}`; `/health = ok`.
5. Игрок делает следующий ход; состояние соответствует последнему принятому действию/тику.

### Альтернативные потоки
- **A1. Рестарт между Phase 1 и Phase 2 хода.** `combat.decided`/`entity.updated` уже в журнале — не применяются повторно; нарратив достраивается: если `llm.output` хода записан — из него; иначе — шаблон с пометкой; `analytics.turn.completed status=degraded fallback_reason=restart`.
- **A2. Рестарт во время тика** → UC-018 E2.
- **A3. Недоставленный нарратив** → доставляется из outbox после восстановления связи с ботом (UC-008 бота) или доступен по `look`.
- **A4. Снапшота нет (первый запуск)** → объекты сущностей есть → восстановление из объектов (`cursor = End(system_events)`, `reason=no_snapshot`, `/health degraded`); объектов нет → мир пуст: оператор выполняет `mvctl world init --fixtures` (UC-036; снапшот `seq 0`, `reason=bootstrap`); блупринты состояние не создают (решение G2).

### Исключения
- **E1. Снапшот повреждён/отсутствует при непустом журнале** → `/health = fail {snapshot: corrupted}`, лог; сервис не поднимается с пустым состоянием молча; оператор выбирает более ранний снапшот или полный replay с начала журнала (команда оператора).
- **E2. В журнале нет `llm.output` для точки вызова в replay** → остановка с `incomplete_record=true` (в recovery-режиме — допускается шаблон с пометкой и продолжение; в test-режиме — ошибка).
- **E3. Журнал короче, чем нужно (retention)** → `/health = degraded {log_gap}`; состояние = снапшот; оператор уведомлён.

### Постусловия
Состояние идентично; вызовов LLM = 0; новых бросков = 0; тиков по часам = 0; `laws_version` из снапшота действует.
Связь: US-011, US-017 · FR-031…FR-033, FR-087, FR-100, BR-04 · NFR-010, NFR-011, NFR-014

## UC-036: Инициализация мира из фикстур (`mvctl world init --fixtures`)

Актор: оператор (в CI — харнесс e2e) · Предусловия: стек поднят (`make up`), State работает, объектное хранилище доступно; каталог `testdata/fixtures/{world,region,npc,players}.json` (владелец EPIC-001 F-10) · Триггер: первый запуск целевого стека; сброс стенда (`make reset`); подготовка e2e-прогона; добавление нового региона (UC-029 шаг 3)

Решение G2 (`journal.md`, `epics.md` §2): **единственный** способ первичного создания мира на MVP-1 — фикстуры; блупринты (`npc_table`, `## description`) состояние не создают; `mvctl world init --blueprints` — вне MVP-1.

### Основной поток
1. Оператор выполняет `mvctl world init --fixtures testdata/fixtures/ --world dark-forest-world`.
2. CLI читает фикстуры, проверяет их схему и ссылочную целостность (регионы ссылаются на мир, NPC — на регион, `stats_ref` NPC есть в `rules/dark-forest.yaml`, `laws_ref` мира существует).
3. CLI (через `internal/state/bootstrap.go`) публикует `entity.create.proposed` для мира, регионов, NPC и фикстурных персонажей `player-A/B/C` (`actor_kind = ci`) — `proposer=system`, `cause=bootstrap`, `meta.actor_kind=system`, корневой `correlation_id` на прогон.
4. State создаёт сущности (`entity.created`, версия 1), пишет объекты и снапшот `seq 0` (`snapshot.created component=state, reason=bootstrap`) с курсорами `End` по всем топикам.
5. CLI ждёт факты по `correlation_id` (таймаут конфигурации), выводит сводку (`mvctl world status`: число сущностей по типам, `laws_version`, `state_hash`); код возврата 0.
6. Рантайм роя (при старте или по сигналу) привязывает блупринты к созданным сущностям (UC-028 шаг 2); `region-gm` использует `npc_table` только для респауна после `respawn_ttl` (UC-019 A1).

### Альтернативные потоки
- **A1. Повторный запуск на непустом мире** → предложения для существующих `id` отклоняются `entity.update.rejected reason=duplicate_entity`; CLI считает это «уже есть» и завершается успешно (идемпотентно); новые сущности из фикстур (например, второй регион) создаются.
- **A2. `--dry-run`** → только проверка фикстур (шаг 2), событий нет.
- **A3. CI/e2e** → тот же `bootstrap.go` вызывается харнессом напрямую в `membus` с `--id-source=sequence` — детерминированные `event.id` и seed'ы.

### Исключения
- **E1. Фикстуры невалидны** (схема, ссылка, `stats_ref`) → CLI выводит файл/поле/причину, ничего не публикует, код возврата ≠ 0.
- **E2. State/шина недоступны** → CLI завершается ошибкой до публикации; частичного мира нет (первое предложение не отправлено), либо — при сбое посреди прогона — повторный запуск дозаполняет по A1.
- **E3. Расхождение `npc_table` блупринта с фикстурами** → обнаруживается тестом согласованности EPIC-003 I1b / `mvctl blueprint validate`, не `world init`.

### Постусловия
Мир, регионы, NPC и фикстурные персонажи существуют в State с версией 1; снапшот `seq 0`; журнал содержит `entity.created` без внешних ID; агенты роя могут стартовать.
Связь: US-010, US-015, US-017 · FR-080, FR-090, FR-120 · NFR-060, NFR-070

## UC-101: Пробой законов неординарным событием (эпик E-B)
Актор: глобальный/региональный GM в **фазе пробоя**; страж; ревьюер. Границы: (1) счётчик напряжения по законам (`law.strain_changed`); (2) фаза пробоя запускается только при напряжении ≥ порога или авторском триггере, LLM в фазе получает только события-причины и счётчик (не текст игрока); (3) `world.law_breach.proposed` → синхронная автопроверка стража (не трогает `immutable` — решение G1; непротиворечивость; `canon_invalidated` полный; нет формул механики; ссылки существуют) → `world.law_breach.rejected` **или** `world.law_breach.applied` + `world.laws.changed {from vN, to vN+1, status pending_review}`; (4) законы вступают в силу с границы следующего раунда во всех scope; трансляция в нарратив через глобальный → персональные GM; агенты перезагружают `laws_version`; (5) `world.law_breach.review_decided {decision approved|rolled_back, reviewer_kind human|timeout}` — по истечении окна без решения `approved` (решение G1); (6) откат = `world.law_breach.rolled_back` + `world.laws.changed {to vN+2 = содержимое vN}`, факты под vN+1 → `retconned`, числовое состояние не откатывается; (7) не более одного `pending_review` на мир; второй → `rejected reason=breach_pending`; (8) replay: фаза пробоя не вызывает LLM. Контракт событий — в MVP-1 (`api-contracts.md` §2.3.13), механика — эпик. Связь: US-020 · FR-041, FR-045, FR-046, BR-02 · NFR-025.

## UC-102: Утверждение канона (E-B)
Факт `generated` → предложение в канон → страж (конфликт с каноном → отклонение с указанием факта) / ревьюер → `canon.fact_validated {fact, version}`; конфликт оформляется `canon.retcon`. Использует пометку источника факта (FR-035) из MVP-1. Связь: US-021 · FR-043, FR-044.

## UC-103: Автономные сущности Entity-Actor (E-A)
Сущность с блупринтом актора действует на тике региона по своим целям через тот же контракт: `entity.actor.decided` → `entity.update.proposed` (уровень владения — как у `task`-агента своего региона; чужой регион → `level_violation`); события с `meta.causation_type ∉ player.*`. Резерв MVP-1 (C-13): уровень `object` в реестре уровней, блупринт `role: entity-actor` валидируется, спавн за флагом `MV_SWARM_OBJECT_AGENTS_ENABLED`, белый список событий `entity.actor.*`. Связь: US-022 · FR-110, FR-017.

## UC-104: Эволюция правил с ревью до применения (E-A)
Monitor-агент → `rule.change.proposed {formula diff, evidence}` → ревью человека → `rule.change.applied {rules_version}` → нарративное объявление; правила не меняют законы (`FR-046`). Резерв: `rules_version` в `combat.decided` **[к архитектору: добавить поле в MVP-1 — дёшево]**. Связь: US-023 · FR-115.

## UC-105: Культивация, Планы, Ω (E-C)
Ступени/прорыв (детерминированно, enum исходов), портрет дао (единственная LLM-оценка с enum-исходом, `llm.output phase=evaluation`), вознесение, `ascended_final` — терминальный статус наравне с `dead`. Резерв: статус `ascended_final` в машине состояний персонажа (MVP-1). Связь: US-024, US-025 · FR-111, FR-112.

## UC-106: Город и GM города (E-D)
GM города — `domain`-агент с родителем GM региона; леджер (валюта, предметы — сущности), квесты, репутация; события `city.*`; предложения вне города → `level_violation`. Резерв: scope-тип `city`, родительские ссылки в блупринте. Связь: US-026 · FR-113.

## UC-107: Генерация мира, законы вселенной, онтологии (E-E)
Законы вселенной `immutable`/`default` с версиями; генерация мира/регионов/блупринтов GM по описанию и seed; проверка наследования законов; мир недоступен игрокам до утверждения. Резерв: `laws_version`, реестр блупринтов, `entity.create.proposed` для миров/регионов. Связь: US-027…US-029 · FR-094, FR-114.

## UC-108: Публичный API с аутентификацией (E-H)
Токен на клиента, разделение аккаунт/персонаж, подписка на события своего игрока (`401` без токена). Резерв: API game-service уже адресует по `player_id`; связка расширяется полем `account_id`. Связь: US-030 · FR-008.

## UC-109: Реальный фильтр 18+ «стены» (E-H)
Та же точка вставки `NarrativeFilter`/`InputFilter`; политика по scope (приватный — только абсолютные запреты; групповой/публичный — полный); протокол вне игры для (e); журнал инцидентов и жалобы. Связь: US-031 · FR-053, FR-054.

## UC-110: Свободный текст → намерение с подтверждением (E-H)
`InputFilter` → распознавание намерения (LLM, `llm.output phase=intent`) → тип действия словаря → подтверждение перед необратимым → обычный ход. Резерв: словарь действий как перечисление в реестре. Связь: US-032 · FR-007.

## UC-111: LOD и бюджет на действие (E-G) — двухосный LOD: значимость события → желаемый LOD, бюджет → потолок; критические события (смерть) не понижаются. Резерв: поля `lod`, `agent.level` во всех событиях роя. Связь: US-033 · FR-017.

## UC-112: Дашборд и алерты оператора (E-G) — экспорт метрик из тех же событий; алерты по порогам. Связь: US-034 · FR-082.

## UC-113: Полное право на забвение (E-H) — крипто-шреддинг/удаление событий игрока, перестройка индексов, ссылки `redacted`. Резерв: все события игрока помечены `player_id` (есть); ключ шифрования на игрока — архитектор. Связь: US-035 · FR-062.
