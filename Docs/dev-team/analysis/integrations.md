## 1. Telegram-бот ↔ game-service

**Ответственность бота (тонкий клиент):** парсинг команд словаря FR-002 (`/enter`, `/look`, `/status`, `/attack`, `/flee`, `/say`, `/rest`, `/leave`, `/group create|join|leave`, `/start`, `/help`, `/forget`); показ уведомления и подтверждения (UC-001); проверка имени персонажа против `username`/имени профиля (предупреждение); вызовы API; доставка сообщений в чат; подтверждение приёма ≤ 300 мс (NFR-003).

**Режим получения обновлений** — long polling или webhook: нейтрально; влияет только на деплой (webhook требует публичного адреса).

**Данные, пересекающие границу бот → game-service:**
- `external_platform=telegram`, `external_id` (числовой user id) — **только** в вызовах `links/*` и создания персонажа; после разрешения бот использует `player_id`.
- `actor_kind=human`.
- Имя персонажа — введённый текст; текст `say`.
- Никогда: `username`, `first_name`, фото, `chat_id`, `update_id` в чистом виде (для `action_key` допустима односторонняя производная от `update_id` — не обратима).

**Данные game-service → бот:** `player_id`, состояние персонажа, ошибки с кодами, доставки (`Delivery`) с `external_id` для маршрутизации (из хранилища связок; только боту той же платформы).

**Отказы:**
- game-service недоступен → бот отвечает «сервис недоступен», не теряет команду в пределах разумного повтора (повтор с тем же `action_key`, идемпотентно).
- Бот недоступен для game-service → доставки копятся в outbox (`Delivery pending`), доставляются при восстановлении; `look` всегда даёт актуальное состояние.
- Telegram недоступен → бот повторяет отправку; сообщения не переупорядочиваются внутри одного игрока (последовательная доставка по `player_id`).

**ПДн и контент:** уведомление об ИИ, 18+, обработка текста, `/forget` — единый текст при первом контакте; повтор по `/help` и через 30 дней. Логи бота — уровень без пейлоадов обновлений; retention ≤ 7 дней; тест NFR-041 включает логи бота. Правила Telegram в отношении 18+ контента — внешний риск (`plan/risks.md`); ботом не решается.

**Групповая доставка:** по конфигурации — каждому участнику в личный чат (по умолчанию) либо в общий канал группы; в обоих случаях один `narrative_event_id`.

## 2. Провайдер LLM (абстракция)

**Интерфейс (логический):** `Generate(request{phase, model, system_prompt, messages/context, schema (structured output), params{temperature, max_tokens, thinking}, timeout, correlation_id}) → response{text|json, tokens{prompt, completion}, latency_ms, provider, model, finish_reason}`; `Health()`; `Models()` (проверка, что нужные модели загружены и резидентны).

**Реализации:** локальная (Ollama, по умолчанию; две модели одновременно: `qwen3:8b` — `phase1`/`tick`, `qwen3:30b-a3b` или `qwen3:32b` — `phase2`; `keep_alive` для резидентности; thinking off для `phase1`; structured output по JSON-схеме блупринта); облачные — через тот же интерфейс, ключи только из окружения.

**Данные в промпте:** блоки `<laws laws_version>`, `<canon source=authored|validated>`, `<state>` (числа из состояния), `<events>` (события раунда/сводка фона), `<player_text>` (реплики как данные, экранированы), `<absolute_limits>` (короткая позитивная формулировка BR-08), `locale=ru`. Нет внешних ID.

**Отказ и деградация:** таймаут фазы (конфигурация; ориентир: `phase1` 5 с, `phase2` 20 с, `tick` 30 с — уточняется замером); повторы N (блупринт) с записью каждой попытки `llm.output attempt=n`; после — шаблон/правила (UC-021); `/health llm: unavailable`; восстановление без рестарта. Холодный старт ≤ 20 с (NFR-004) — на время старта шаблон.

**Приоритет:** вызовы ходов (`actor_kind ≠ system`) впереди тиков; тик, ждущий дольше порога, — LOD 1 (BR-10).

**Учёт:** каждый вызов — `llm.output` с `tokens`, `cost_usd`, `provider`, `model`; сверка с отчётом провайдера ≤ 5 % (NFR-052).

**ПДн:** локальный провайдер — данные не покидают машину. Облачный: текст с `player_id` уходит за рубеж; по умолчанию недоступен при наличии игроков, кроме владельца (число связок с `alive`-персонажем > 1); включение — явный флаг + запись в журнал; юрист при внешних игроках (NFR-046).

**Секреты:** ключи облака только в окружении; отсутствие ключа — ошибка конфигурации при старте (UC-030 E1).

## 4. Шина событий

- Топики: существующие `player_events`, `world_events`, `game_events`, `system_events`, `scope_management` (мёртвый — кандидат на удаление), `narrative_output`; предлагаемые новые (**решение архитектора**): `analytics_events` (аналитика, не в replay, длинный retention), `llm_records` (`llm.output`, `llm.output.rejected`, `dice.rolled` — большие payload, отдельный retention). Карта «событие → топик» — `api-contracts.md` §2.2.
- Гарантии: at-least-once; ключ сообщения — `world.entity.id` (порядок внутри мира); потребители идемпотентны по `event_id`; версии схем — `payload.schema_version`.
- Реестр типов: событие неизвестного типа отклоняется издателем (библиотека) — Should; типы пробоя зарегистрированы без обработчиков.
- Отказ шины: `/health` всех сервисов ≠ ok ≤ 30 с; game-service отвечает клиенту `503 bus_unavailable`, действие не принимается (не 202) — чтобы не терять подтверждённые действия.
- Наблюдаемость: глубина очередей consumer-групп (Phase 2) — метрика `phase2_queue_depth_max`.

## 5. Планировщик тиков (внутренняя интеграция)

- Вход: блупринты с `trigger.type=timer` (`intervals{idle, active}`), состояние регионов (есть ли игроки).
- Выход: `tick.fired` на шину с `correlation_id = id`, `actor_kind=system`, `agent{…}`, `tick_seq` монотонно на агента; затем конвейер агента.
- Бюджет: единый счётчик фоновых вызовов на мир за скользящий час (`B`, по умолчанию 4); планировщик передаёт агенту разрешённый режим (`lod_allowed`).
- Приоритет: тики не блокируют ходы (очередь с приоритетом или отдельный воркер с уступкой).
- Ускорение в тестах: множитель времени/явный вызов «выполнить тик» (`actor_kind=ci`), записывается тем же `tick.fired`.
- Replay: планировщик отключён; `tick.fired` читаются из журнала.
- Рестарт: `next_tick_at` и `tick_seq` — из снапшота рантайма; пропущенные тики за время простоя **не** наверстываются пачкой (один тик после старта, если срок прошёл) — **[решение аналитика, уточняет архитектор]**.

## 6. Семантическая память (внутренняя интеграция)

- Вход: все доменные топики (включая фоновые события с `actor_kind=system`); каждый факт индексируется с меткой источника (`authored/validated/generated`) и слоя.
- Запросы агентов: «контекст scope за окно», «события региона за `(since_at, now)` с `actor_kind=system`» (сводка UC-004), «сущности рядом», «трасса по `correlation_id`».
- Приоритет фактов при конфликте: `authored > validated > generated`; факты состояния (погода из `World`) приоритетнее памяти нарратива.
- Деградация: недоступность → агент строит контекст из состояния и журнала за окно (без семантического поиска); ошибок игроку нет.
- ПДн: индексируются имя персонажа и текст `say` (игровые данные); внешних ID нет; целевое право на забвение требует удаления/перестройки (E-H).

## 7. Замечания по ПДн (сквозные)

1. Единственная копия связи «внешний ID ↔ `player_id`» — хранилище связок game-service; удаление физическое; после удаления обратный поиск невозможен по построению.
2. `notice_shown_at`, `consent_at`, `age_confirmed_at` обязательны для связки с персонажем (`ai_notice_coverage = 1.0`).
3. Бот не использует данные профиля мессенджера ни для чего, кроме доставки; имя персонажа — явный ввод; совпадение с `username` — предупреждение на стороне бота.
4. Логи всех сервисов и бота — без внешних ID; логи бота — без пейлоадов обновлений, retention ≤ 7 дней.
5. Облачный LLM — трансграничная передача; по умолчанию выключен при внешних игроках; включение с флагом и записью в журнал.
6. `analytics.*`, CSV, артефакты прогонов — только `player_id`, счётчики, идентификаторы; без текста.
7. `llm.output.response_raw` — единственное место хранения сгенерированного текста помимо `narrative.output`; при `quarantined` отсутствует.
8. Резервные копии хранилища связок — отдельная политика оператора (шифрование, срок) — **[к архитектору/оператору]**.
