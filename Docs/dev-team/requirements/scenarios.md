**Инициатива:** PROJECT — аудит платформы
**Этап:** A1 Discovery, шаг 1
**Дата:** 2026-09-09
**Автор:** бизнес-аналитик (dev-team)

Сценарии описаны без технических деталей: «актор → цель → шаги → результат».
Колонка «Проходит сегодня» — оценка по документам и коду (см. `inventory.md`),
без запуска стека. Сценарии — кандидаты; какие из них входят в MVP, решает
владелец продукта (см. `project/open-questions.md`, раздел «Требования и сценарии»).

## Роли

| Роль | Кто это | Что нужно |

| **Игрок** | Человек, действующий в мире через клиент (какой — не решено) | Понятный отклик на действия, память мира о нём, ощущение живого мира |

## Сценарии

### SC-01. Регистрация и вход в мир

**Актор:** игрок.
**Цель:** получить персонажа в выбранном мире и вернуться к нему позже.

1. Игрок выбирает мир из списка доступных.
2. Называет персонажа; система создаёт его в мире.
3. При следующем визите игрок входит и видит своего персонажа с сохранённым состоянием.

**Результат:** у игрока есть персонаж, привязанный к миру; состояние сохраняется между сессиями.

**Сегодня:** REST-регистрация и вход работают, сущность сохраняется, публикуется событие о создании. Нет списка миров, нет проверки, что мир существует, нет аутентификации (любой может войти под любым `player_id`).

### SC-02. Действие свободным текстом → ответ мира

**Актор:** игрок.
**Цель:** сказать миру, что я делаю, и получить осмысленный ответ с последствиями.

1. Игрок пишет: «Пытаюсь уговорить стражника пропустить меня».
2. Система понимает намерение (убеждение, ключевая характеристика — харизма).
3. Система разыгрывает механику (проверка навыка) и фиксирует результат как факт мира.
4. Система описывает произошедшее текстом в стиле мира.
5. Стражник «помнит» этот разговор при следующей встрече.

**Результат:** игрок получил текст и видимое изменение состояния (стражник пропустил / не пропустил, репутация изменилась).

**Сегодня:** распознавание намерения есть только как HTTP-эндпоинт entity-actor; WebSocket `/ws/actions` — TODO; текст нарратива рассылается всем подключённым клиентам без адресации; память NPC о конкретном игроке отдельно не хранится (только семантическая память событий).

### SC-03. Вход в регион, встреча, бой («Тёмный лес»)

**Актор:** игрок.
**Цель:** пройти через опасный регион и пережить столкновение.

1. Игрок входит в регион «Тёмный лес».
2. Регион «оживает»: появляется атмосфера, поблизости оказывается волк.
3. Игрок атакует; результат определяется правилами (попадание, урон, исход).
4. Игрок получает описание боя и его последствий (трофей, ранение, гибель).
5. После ухода игрока регион «засыпает» и не тратит ресурсы.

**Результат:** сквозная цепочка «вход → встреча → бой → нарратив → последствия» с предсказуемой механикой.

**Сегодня:** цепочка покрыта e2e-тестом в `shared/agent` (внутри процесса, с заглушками). Нет сервиса-оркестратора агентов, нет подключения к шине и game-service. Через narrative-orchestrator похожая цепочка воспроизводится только тест-харнессом `/run_test` без механики.

### SC-04. Развитие персонажа и вознесение

**Актор:** игрок.
**Цель:** расти в силе и в итоге перейти на следующий план бытия.

1. Игрок применяет навыки и предметы; прогресс культивации растёт.
2. По истории действий формируется «портрет Дао» персонажа.
3. При достижении порога игроку предлагается испытание вознесения, уникальное для его пути.
4. Успех открывает переход на следующий план; неудача имеет последствия.

**Результат:** персонаж перешёл на новый план, мир это отразил.

**Сегодня:** cultivation-module и plan-manager есть в compose, но подписаны на `player_events`, куда действия игрока не попадают; генерация испытания через оракул не связана с клиентом.

### SC-05. Совместная игра группы

**Актор:** несколько игроков.
**Цель:** действовать вместе в одном месте и видеть одно и то же.

1. Два игрока входят в один регион и объединяются в группу.
2. Действие одного видит другой; нарратив общий, но каждый получает свою точку зрения.
3. Один игрок уходит разведать — группа разделяется; при возвращении объединяется.

**Результат:** согласованная картина мира для всех участников группы.

**Сегодня:** merge/split GM реализован в narrative-orchestrator; нет входа для нескольких клиентов, нет адресации вывода по игроку, нет понятия сессии.

### SC-06. Создание вселенной и мира по описанию

**Актор:** автор мира.
**Цель:** получить играбельный мир из текстового описания и набора законов.

1. Автор задаёт вселенную: фундаментальные законы и базовые онтологии (или принимает предложенные).
2. Автор описывает мир («культивация, магические реки, летающие острова», ограничения).
3. Система порождает мир: регионы, водоёмы, города, стартовые NPC, канон.
4. Автор просматривает результат и правит (переименовать регион, убрать элемент).
5. Мир становится доступен игрокам.

**Результат:** мир с регионами и каноном, согласованный с законами вселенной.

**Сегодня:** генерация вселенной и мира работает по событиям `universe.genesis.request` и `world.generate` (публикуются вручную через Kafka); нет API автора, нет CRUD законов/онтологий (US-001/002), нет просмотра и правки результата, наследование законов мирами не проверяется.

### SC-07. Описание поведения региона блупринтом

**Актор:** автор мира.
**Цель:** задать, как ведёт себя регион или NPC, текстом без изменения кода.

1. Автор пишет Markdown-блупринт: цель, правила, ограничения, инструменты, память.
2. Система проверяет блупринт и сообщает об ошибках.
3. Блупринт подхватывается работающей системой без перезапуска.
4. Автор видит в логах/трассе, как агент принял решение.

**Результат:** поведение региона изменилось; автор понимает, почему агент поступил так.

**Сегодня:** парсер и валидатор блупринтов есть; исполняющего сервиса и горячей перезагрузки нет; форматы блупринта в двух документах различаются.

### SC-08. Контроль целостности и утверждение эволюции правил

**Актор:** автор / модератор мира.
**Цель:** мир не ломает свои законы, а новые механики появляются под контролем.

1. Игрок пытается сделать невозможное по законам мира (огненное дыхание в мире без огня).
2. Система не отказывает «ошибкой», а превращает действие в последствие в духе мира.
3. Система замечает устойчивую аномалию поведения (кролик 100 раз успешно прячется) и предлагает новое правило.
4. Модератор видит предложение, оценку баланса и безопасности, утверждает или отклоняет.
5. Утверждённое правило начинает действовать; журнал изменений доступен.

**Результат:** мир целостен, эволюция правил прозрачна и обратима.

**Сегодня:** ban-of-world и evolution-watcher есть в коде; ban-of-world не в compose; шаг 2 в README сервиса описан как наказание, а не последствие; шаг 4 (human review) не реализован; интерфейса модератора нет.

### SC-09. Запуск, наблюдение, восстановление, контроль LLM

**Актор:** оператор.
**Цель:** поднять стек на одной машине, убедиться, что он жив, и не разориться на LLM.

1. Оператор поднимает стек одной командой и видит, что все сервисы здоровы.
2. Видит очередь событий, латентность LLM, число активных GM/агентов, стоимость (или нагрузку GPU).
3. При недоступности LLM мир продолжает работать в упрощённом режиме (правила без нарратива).
4. При падении сервиса он восстанавливается из снапшота и дочитывает события.
5. Оператор ограничивает частоту вызовов LLM и получает предупреждение при превышении.

**Результат:** предсказуемая эксплуатация на одном хосте с GPU.

**Сегодня:** compose поднимает часть стека (нет ban-of-world, city-governor, reality-monitor, Redis); health есть не у всех; метрик/алертов нет; деградация без LLM описана, не проверена; восстановление подтверждено для entity-manager и narrative-orchestrator.

### SC-10. Воспроизводимый эксперимент с GM

**Актор:** разработчик-исследователь.
**Цель:** сравнить два варианта GM (или два промпта) на одном сценарии.

1. Исследователь выбирает сценарий и фиксирует seed (броски, порядок событий).
2. Прогоняет сценарий с вариантом A и вариантом B (например, scope-GM и Agent GM).
3. Получает оба нарратива, метрики (латентность, токены) и список порождённых событий.
4. Сохраняет результат как артефакт для сравнения.

**Результат:** обоснованный выбор варианта на данных, а не на впечатлении.

**Сегодня:** есть `/run_test` с набором сценариев для narrative-orchestrator; нет переключателя модели GM, фиксированного seed, сохранения и сравнения результатов.

## Наблюдения

1. Ни один игровой сценарий (SC-02…SC-05) не проходит сквозь систему: отсутствует
   вход действий игрока из клиента и адресный выход нарратива к игроку. Это общий
   блокер для любой модели GM.
2. Сценарии автора (SC-06…SC-08) сегодня требуют публикации событий в Kafka вручную;
   роль автора как пользователя системы в документах не описана.
3. Сценарии SC-03 и SC-02 представляют две разные концепции ввода (события против
   свободного текста); выбор одной из них или гибрида — решение владельца.
4. SC-09 и SC-10 — единственные сценарии, где актор реально существует сегодня
   (владелец = оператор = исследователь); разумно сделать их первыми в MVP, поскольку
   без них нельзя проверить остальные.
