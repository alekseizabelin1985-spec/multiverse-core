# Инвентаризация существующих требований

**Инициатива:** PROJECT — аудит платформы
**Этап:** A1 Discovery, шаг 1
**Дата:** 2026-09-09
**Автор:** бизнес-аналитик (dev-team)

## 1. Цель и метод

Собрать в одном месте всё, что уже сформулировано как требование к multiverse-core
(пользовательские истории, фичи, NFR, «технические хотелки»), оценить их статус по
документам о реализации и коду, найти пересечения и противоречия.

Оценка статуса — грубая, по документам и беглому чтению кода (без запуска):

| Статус | Значение |
|---|---|
| Описано | Есть текст требования/дизайна, кода нет или он не найден |
| Частично | Код есть, но сценарий не проходит сквозь систему или заявлены заглушки |
| Реализовано | Код есть и по документам покрывает требование |
| Расходится | Документ и код (или два документа) противоречат друг другу |
| Не найдено | На документ ссылаются, но файла нет |

Тип формулировки: **US** — пользовательская история (есть актор и ценность),
**Фича** — функциональное описание без актора, **Тех** — техническое решение,
выданное за требование, **NFR** — нефункциональное требование.

## 4. Пересечения и противоречия

### 4.1. Три конкурирующие модели «мозга мира»

| | A. Scope-GM (narrative-orchestrator) | B. Living Worlds (Entity-Actor) | C. Agent GM Core (shared/agent) |
|---|---|---|---|
| Единица | GM на scope (игрок/группа/локация/регион/мир) | Актор на сущность + общий Rule Engine | Агент по блупринту (Global/Domain/Task/Object) |
| Механика | Нет (LLM «придумывает, что дальше») | Кубики в Rule Engine, TinyML для состояния | Phase 1 LLM со строгой JSON-схемой, fallback на rule-engine |
| Вход игрока | Структурированные события (`player.used_skill`) | Свободный текст → Intent Recognition | События (`player.attack`, `player.entered_region`) |
| Конфигурация | `configs/gm_*.yaml` | Правила JSON в MinIO | MD-блупринты |
| Статус | Работает (тест-харнесс) | Код с заглушками, не подключён | Библиотека, сервиса нет |
| Судьба по документам | S6: отключить; S3: расширить | S3: production ready | S6: заменяет A |

Ни один документ не описывает, как A, B и C соотносятся. Это главный
блокирующий вопрос для PRD и архитектуры (см. OQ-R-13).

### 4.2. Прочие противоречия

1. **Коллизия идентификаторов.** US-001..US-005 существуют в двух независимых наборах
   (S1 и S2) с разным содержанием. При формализации нумерацию придётся переназначить.
2. **Статус Living Worlds.** «Production Ready: Yes» (04-05) против «Redis stub, тесты 20%,
   интеграции TODO» (02-23) и отсутствия топиков/Redis в compose. Чек-лист «все 34
   требования verified» датирован днём дизайна.
3. **Четыре стража целостности** с пересекающейся ролью: Overseer (S1), BanOfWorld (S4/S5),
   Rule Validator (S3), MonitorAgent (S2). Не определено, кто арбитр и на каком уровне.
4. **Два смысла «онтологии»**: полюса и взаимодействия (S1) против JSON-схем сущностей
   (ontological-archivist).
5. **Наказание vs последствия.** Философия S4 («мифологические последствия вместо
   наказаний») против `player.punished` в README ban-of-world.
6. **Форма ввода игрока**: свободный текст (B) против структурированных команд (A, C).
7. **Латентность**: <100 мс на LLM-вызов (C) и <50 мс инференс TinyML (B) — цифры
   разных механизмов смешаны в одном обещании «быстрого GM».
8. **Инфраструктура**: документы предполагают Redis, PostgreSQL, Kubernetes, Prometheus;
   реальность — docker-compose без них, один разработчик.
9. **Язык**: промпты, примеры и часть документов на русском, Living Worlds — на
   английском, `locale` заявлен, но не реализован.

### 4.3. Что сформулировано как история, а что — как техническое решение

- Настоящие пользовательские истории (актор + ценность): S1 US-001, US-002, S2 US-003
  (частично). Всего три.
- Технические хотелки, оформленные как истории: S2 US-001, 002, 004, 005 (актор —
  Router/Lifecycle/Worker, а не человек).
- Остальное — описания сервисов и чек-листы без актора.
- Роли «автор мира», «оператор», «исследователь» нигде не названы явно; роль «игрок»
  подразумевается, но ни один сквозной сценарий игрока не описан от входа до ответа.

## 5. Выводы для discovery

1. Единого источника истины по требованиям нет; три набора документов описывают три
   разных продукта на одной шине событий.
2. Ни один сценарий игрока не проходит сквозь систему без ручной публикации событий в
   Kafka или тест-харнесса `/run_test` (см. `scenarios.md`).
3. Все NFR — декларативные; ни одна цифра не подтверждена измерением.
4. Перед PRD нужно решение владельца по модели GM (OQ-R-13) и по статусу документации
   Living Worlds (OQ-R-12); без них формализация даст четвёртый противоречащий документ.
5. Кандидат на единый MVP-сценарий по документам — «Тёмный лес» (вход в регион →
   встреча → бой → нарратив): он назван критерием фазы 4 в S2 и покрыт e2e-тестом в
   `shared/agent`.
