## 1. Контекст и цель

multiverse-core — бэкенд-платформа «живых миров»: символическое состояние мира
(сущности, события, законы, канон) — источник истины; LLM принимает решения в
рамках правил и рассказывает; мир помнит действия игроков, живёт между сессиями,
восстанавливается после сбоя и эволюционирует. Игровые домены (культивация, города,
Планы) — расширения поверх платформы, не её ядро (раунд 1).

Сегодня в репозитории 15 сервисов и три поколения дизайна GM, но ни один игровой
сценарий не проходит сквозь систему из клиента (`requirements/scenarios.md`).
Цель этого PRD — задать проверяемые требования для двух горизонтов:

- **MVP-1 «Тёмный лес»** — первый играбельный инкремент: вход в регион → встреча →
  бой → нарратив, 30 ходов без поломки мира, соло и группой 2–6, через Telegram-бота;
  мир живёт между сессиями (фоновые события глобального и регионального GM);
- **целевое видение** — платформа с Living Worlds, эволюцией законов через пробой,
  культивацией и Планами, городами, генерацией миров и авторскими инструментами —
  как основа для декомпозиции на эпики.

### 1.1. Цели

| # | Цель | Как проверяем |
|---|---|---|
| G-1 | Сквозной играбельный цикл существует и проходит автоматически | e2e-тест «Тёмный лес» на поднятом стеке (US-002) |
| G-2 | Мир не ломается в сессии | 30 ходов без противоречий состояния (NFR-012) |
| G-3 | Мир переживает рестарт | восстановление из снапшота + replay без повторных вызовов LLM (US-011) |
| G-4 | В мир можно играть вдвоём-вшестером | групповая сессия из 3 игроков (US-006, US-007) |
| G-5 | Есть эталонный клиент | Telegram-бот (US-008) |
| G-6 | Одна архитектура GM — рой агентов | все GM (глобальный, региональный, персональный) — экземпляры Agent GM Core по блупринтам; legacy `GMInstance` выведен или рендер (FR-010, FR-120, US-037) |
| G-7 | Мир живёт без игроков | между сессиями в регионе происходят фоновые события, видимые игроку при входе (FR-124…FR-127, US-036) |
| G-8 | Основа для целевого видения зафиксирована | требования целевого горизонта (§4.2) достаточны для брифов эпиков; контракт пробоя законов зарезервирован (FR-045) |

### 1.2. Не-цели (этого цикла и MVP-1)

- Массовый мультиплеер, шардирование, «1000 игроков/шард» — снято из целей и NFR.
- Графический или веб-UI (`hasUI=false`); клиент — бот и API.
- Монетизация, публичный запуск, внешние разработчики фронтов.
- Обучение нейросетевых Entity-Actor (TinyML) в MVP; Entity-Actor как автономная сущность — эпик E-A (фоновая жизнь мира через GM-рой — уже в MVP-1, см. FR-124).
- Реальный фильтр контента 18+ («стены») и аутентификация внешних игроков в MVP (только точки вставки; в MVP-1 фильтр проверяет лишь категорию (a) — FR-050, решение G1).
- Механика пробоя законов (фаза пробоя, напряжение, ревью) в MVP-1 — только контракт (FR-045, эпик E-B).
- Очистка git-истории (`git filter-repo`) — отдельная задача по явной команде пользователя.
- Юридическая экспертиза (152-ФЗ, 436-ФЗ, 243-ФЗ) — только ориентиры из `domain-notes.md`.

| Роль | Кто это (MVP-1) | Что нужно | Истории |
|---|---|---|---|
| **Игрок (соло)** | Сам разработчик; затем 2–6 тестеров | Войти, действовать, получать механический результат и нарратив, чувствовать память и жизнь мира | US-001…US-005, US-009, US-036 |

| **Автор блупринтов / мира** | = оператор (допущение A-4, OQ-R-17/OQ-P-11): файлы в Git + CLI, без UI | Описать регион/NPC/тики блупринтом, получить ошибки валидации, увидеть трассу решений агента | US-015, US-016 |

| **Страж** (автомат) | Запрет Мира — автоматический валидатор предложений LLM и действий против законов/канона (DR-17) | — | FR-042, BR-02 п. 7 |
| **Внешний разработчик фронта** (целевое) | Не в MVP | Публичный API с аутентификацией | US-030 |

Термины «страж» (автомат) и «ревьюер» (человек) разведены по DR-17; в v0.1 они употреблялись как одна роль.

Аккаунт и персонаж в MVP-1 не разделяются: один внешний аккаунт (Telegram) ↔ один
**живой** персонаж ↔ один `player_id`; после смерти персонажа тот же аккаунт создаёт
нового персонажа с новым `player_id` (FR-023, A-7, DR-06); после `/forget` персонаж
становится **покинутым** (`abandoned`) и тот же аккаунт при новом входе получает новую
связку и нового персонажа (FR-061, G2). Доступ в MVP-1 — только по allowlist Telegram
user id и только из личных чатов (FR-130, FR-131). Разделение аккаунт/персонаж
как отдельных сущностей — целевое (US-030).

## 4. Объём по инкрементам

### 4.1. MVP-1 «Тёмный лес» (обязательное)

Один мир, один регион «Тёмный лес» (`dark-forest-01`), один тип NPC (волк), один
игрок или группа 2–6. Цикл: вход в регион → активация GM региона по блупринту →
встреча с волком (Task-агент) → бой (детерминированная механика, правила v0.1 как
данные) → нарратив (LLM, асинхронно, через персональный GM игрока) → последствия
(HP, трофей, смерть) → выход. 30 ходов подряд без поломки мира.

**Рой GM в MVP-1 (обязательно):** глобальный GM мира (погода и события мира по
тикам), GM региона «Тёмный лес» (наблюдает территорию, порождает события и встречи
по тикам — и с игроками, и без), персональный GM каждого игрока (события в
видимости игрока → его нарратив). GM города — целевое (E-D).

**Фоновая жизнь в MVP-1:** глобальный и региональный GM тикают по расписанию без
игроков в дешёвом режиме (без LLM или малая модель, лимит вызовов); мир меняется
между сессиями; игрок при входе видит последствия.

Клиент — Telegram-бот (Discord — следующий инкремент). Оператор поднимает стек
одной командой на целевой машине (RTX 4090 24 ГБ, 128 ГБ RAM, i9-13900),
восстанавливает после рестарта, работает без LLM в деградированном режиме, получает
отчёт по сессии. Исследователь воспроизводит прогон по seed и записанным выводам LLM.

**Контракты, зарезервированные в MVP-1 без механики:** пробой законов (`laws@v1`,
`laws_version`, типы событий пробоя — FR-045), точка вставки фильтра входа и выхода
(FR-050, FR-056), Entity-Actor (FR-110).

**Уточнения объёма по итогам G2 (2026-09-09):**

- **Семантическая память (эпик 005-memory: Qdrant + Neo4j, контракт C-09) — Should,
  отрезаемая:** решение «включать в MVP-1 или отложить» принимается на G3/G4 по
  фактическому ходу работ; все Must-требования MVP-1 (в т. ч. сводка «пока тебя не
  было» FR-127, контекст агента, US-005, US-036) выполняются без неё — из состояния и
  журнала событий (FR-035, ADR-004).
- **Сводка «пока тебя не было» (FR-127) — Must** и строится из журнала событий, не из
  семантической памяти.
- **Инициализация мира — фикстуры:** мир `dark-forest-world`, регион, законы `laws@v1`,
  NPC «Альфа-волк» и стартовые атрибуты создаются командой оператора
  `mvctl world init --fixtures` из файлов блупринтов/фикстур в Git (воспроизводимо,
  без LLM); генерация мира — целевое (E-E). `npc_table` блупринта региона используется
  **только для респауна** NPC фоновыми тиками после TTL (FR-128, `npc.spawned`), а не
  для первичного заселения.
- **Доступ тестеров:** allowlist Telegram user id и только личные чаты (FR-130,
  FR-131); лимиты частоты и размера — NFR-049.
- **Объектное хранилище:** MinIO собирается из исходников (ADR-021, OQ-A-20); для
  требований это прозрачно — используется только Put/Get/Stat/List/Delete.

## 6. Бизнес-правила

| ID | Правило | Область |
|---|---|---|
| BR-01 | **Слои консистентности.** (1) *Законы мира* (`laws@vN`) — неизменны в обычном игровом цикле; меняются только автором (новая версия `approved`) или пробоем (BR-02). (2) *Канон* — факты мира/региона; добавляются и меняются только через утверждение (страж или ревьюер), с версией. (3) *Сиюминутное* — атмосфера, реплики, детали сцены; LLM свободно, без утверждения, с TTL. Таблица «кто что меняет»: автор — все слои и `immutable`/`default`-законы вселенной; ревьюер (человек) — канон, решение по пробою и по правилам FR-115; страж (автомат) — только отклоняет/помечает; LLM — сиюминутное напрямую, канон и законы только предложением (пробой — только в фазе пробоя); механика — числовое состояние сущностей; **пробой** — законы мира и `default`-законы вселенной, не `immutable` и не формулы механики; **эволюция правил (FR-115)** — формулы механики с ревью до применения, не законы (DR-02, FR-046) | консистентность |
| BR-02 | **Пробой законов** (редакция по DR-01; механика — эпик E-B, в MVP-1 — только п. 12). (1) *Объект:* закон мира — декларативное ограничение слоя 1, документ `laws@vN`; *пробой* — событие, отменяющее ≥ 1 закон и/или вводящее ≥ 1 новый в обход авторской правки. (2) *Что пробивается:* законы мира и `default`-законы вселенной; `immutable` — нет (допущение A-10); формулы механики — нет (FR-046). (3) *Инициаторы:* (а) LLM-агент уровня `global`/`domain` — только в отдельной *фазе пробоя*, запускаемой по п. 4 (в Phase 1/2 схема ответа пробоя не содержит); (б) автор — вручную (сразу `approved`); (в) игрок — косвенно, действиями, повышающими напряжение; прямой команды нет (BR-06). Инициатор и события-причины записываются в предложение. (4) *Условие «неординарности» — напряжение закона:* по каждому закону ведётся счётчик (отклонённые стражем предложения против закона, аномалии Monitor-агента, нарушения игроков, авторские триггеры блупринта); фаза пробоя запускается только при напряжении ≥ порога автора или по авторскому триггеру; текст игрока фаза не читает (защита бюджета и от инъекций). (5) *Частота:* не более одного пробоя `pending_review` на мир; кулдаун после решения ≥ K ходов и ≥ T дней (по умолчанию 100 ходов, 7 дней). (6) *Контракт:* `world.law_breach.proposed {initiator, cause_event_ids[], strain, laws_removed[], laws_added[], canon_invalidated[], narrative_hook, laws_version_base}`; `canon_invalidated` обязательно. (7) *Автопроверка стража до применения (синхронно):* не трогает `immutable`; новые законы непротиворечивы между собой и с оставшимися; все конфликты с каноном перечислены; нет изменений формул; ссылки только на существующие сущности (FR-034). Провал → `world.law_breach.rejected` (записан, не применён, напряжение не сбрасывается). (8) *Применение:* прошедшее автопроверку предложение становится `laws@vN+1` со статусом `pending_review` и вступает в силу с границы следующего хода/раунда во всех scope мира (не ретроактивно); событие пробоя транслируется в нарратив всех активных scope с `reason` (BR-11) через глобальный GM → персональные GM; агенты перезагружают законы; промпты, `llm.output`, снапшоты несут `laws_version = vN+1`. (9) *Постфактум-контроль:* ревьюер (человек) получает diff законов, `canon_invalidated`, число ходов/фактов под vN+1 и решает `approved` / `rolled_back` в окне ревью T_r (по умолчанию 14 дней или 200 ходов — что раньше); по истечении без решения — `approved` автоматически (допущение A-11; альтернатива — автооткат). (10) *Откат = ретрокон:* создаётся `laws@vN+2` с содержимым vN (история не удаляется); факты под vN+1 получают статус `retconned` (не удаляются); числовое состояние сущностей (смерти, предметы, HP) не откатывается — компенсации только явными событиями мира (BR-11); откат — нарративное событие, видимое игрокам. (11) *Replay:* все шаги — события (`proposed → rejected \| applied → review_decided → rolled_back`); при replay фаза пробоя LLM не вызывает (BR-04). (12) **MVP-1:** фаза пробоя отключена; обязательны `laws@v1`, `laws_version` в контексте/`llm.output`/снапшоте, зарегистрированные типы событий, инварианты NFR-020 как первые законы (FR-045). | BR-10 | **Фоновая жизнь дёшева.** Без игроков LLM тратят только глобальный и региональные GM по расписанию и в бюджете FR-125 (без LLM или малая модель, ≤ B вызовов/час/мир); персональные GM и Task-агенты без игроков не живут; фоновый тик никогда не блокирует и не задерживает обработку действия игрока (приоритет — действию) | LLM/стоимость |
| BR-11 | **Последствия, не наказания.** Нарушение законов игроком превращается в событие в духе мира с видимой причиной (`reason`), не в отказ «ошибкой» и не в штраф вне мира | консистентность |
| BR-12 | **Одна архитектура GM — много агентов.** Все GM (глобальный, региональные, городские, персональные, Task) — экземпляры Agent GM Core по блупринтам; legacy `GMInstance` narrative-orchestrator выводится (или остаётся тонким рендером); фича-флаг сосуществования допустим только на период миграции и удаляется по её завершении. «Один GM» в видении = одна архитектура, не один агент (р5) | архитектура |
| BR-13 | **Группа и раунд.** Группа — 2–6 игроков в одном scope `group`; *лидер* — создатель группы; только его `enter`/`leave` перемещают группу (`enter` от не-лидера отклоняется с подсказкой); группа распадается с выходом последнего; группа всегда в одной позиции (для `alive` участников — NFR-020 инв. 4). **Передача лидерства (G2, UC-009):** при выходе (`group leave`), смерти (`dead`) или отвязке (`abandoned`, FR-061) лидера лидером становится старейший **живой** (`alive`) участник по `joined_at`; публикуется `group.leader_changed {leader, cause: leave|death|forget}`; если живых участников нет — группа остаётся **без лидера** (`leader_id = null`, перемещение недоступно): `enter`/`leave` группы при `leader_id = null` отклоняются с `409 no_leader` (сведение 3 З-4; ранее `not_leader`), кроме личного `group.leave` — он допустим и при отсутствии лидера — до `group.disbanded`; `dead`/`abandoned` участники остаются в `members[]` формально (история), но не в `active`, не в `acted[]`/`expected[]` и не в целях NPC. Раунд — по FR-025; действия внутри раунда — по времени приёма; NPC действует один раз в раунд. `flee` индивидуален (успех → `out_of_combat`, игрок остаётся в группе, не цель; провал → свободная атака NPC); `group leave` во время активной встречи = `flee`: при успехе участник покидает встречу и группу, переходит в `solo`, **позиция → опушка (`outside:{world}`, safe spot региона — как при соло-бегстве, UC-017)**, при провале — свободная атака, остаётся в группе и в бою; `group leave` вне встречи — `solo` в той же позиции; присоединение — только вне встречи; трофей — нанёсшему последний удар (один раз); выход участника не прерывает сессию остальных (DR-03) | игровой цикл |
| BR-14 | **Деградация без LLM.** Отсутствие LLM никогда не блокирует механику; игрок получает шаблонный текст с пометкой, а не ожидание | надёжность |
| BR-15 | **Локальный по умолчанию.** Базовая конфигурация — Ollama без внешних затрат; облачный провайдер включается явно, с лимитом и с записью в журнал; при наличии в мире игроков, кроме владельца, облако по умолчанию недоступно (NFR-046, DR-14) | LLM/стоимость |
| BR-16 | **Правила роя GM** (р5). (1) Каждый GM меняет состояние только своего уровня и только событиями-предложениями (FR-122); (2) события идут вверх и вниз по иерархии через шину, прямых вызовов между агентами нет (FR-121); (3) персональный GM игрока не публикует `player.*` и не действует за игрока (FR-123); (4) конфликт двух GM за одну сущность разрешает entity-manager по версии (BR-03), пересечение уровней — страж (`level_violation`); (5) один агент на (уровень, scope) — `max_instances = 1`; (6) фоновый тик уступает действию игрока (BR-10) | архитектура |
| BR-17 | **Сессия и учёт.** Сессия — серия ходов в scope с простоем ≤ 30 мин между ходами (FR-085); в критерии S7 считаются только сессии с `actor_kind = human` (допущение A-12, PA) | продукт/метрики |

## Приложение A. Правила боя «Тёмного леса» v0.1 (данные; предложение DR-04, допущение A-16)

| Параметр | Игрок | `wolf-alpha` |
|---|---|---|
| `hp_max` | 10 | 10 |
| `atk` (бонус попадания) | +2 | +3 |
| `def` (класс защиты) | 12 | 11 |
| `dmg` | d6 | d4 |
| `flee` (бонус бегства) | +2 | не бежит |

- **Атака:** `d20 + atk ≥ def цели` → попадание, урон `dmg`; натуральная 20 — урон ×2; натуральная 1 — промах. HP всегда в [0, hp_max] (clamp — инвариант NFR-020).
- **Ответ NPC:** после действий игроков раунда волк, если жив и есть цель, атакует один раз. Цель: последний игрок, нанёсший ему урон; иначе игрок с минимальным HP; при равенстве — по возрастанию `player_id`. `idle` и `out_of_combat` — не цели. Без вызовов LLM в Phase 1 боя (LOD 1).
- **Бегство:** `d20 + flee ≥ 10 + число живых противников` → игрок выходит из встречи в позицию `outside:{world}`; провал — волк немедленно атакует его вне очереди (свободная атака), игрок остаётся.
- **Смерть:** HP = 0 → `dead`. Игрок — терминально (FR-023). Волк — `dead`, трофей «волчья шкура» → нанёсшему последний удар; волк не возрождается в сессии и в течение TTL региона (FR-128).
- **Отдых:** `rest` вне встречи — HP до `hp_max`, занимает ход; во встрече недоступен (FR-024).
- **Броски на ход:** до 4 `dice.rolled` (попадание, урон, ответ волка: попадание, урон), `roll_index` 0…3, seed по FR-021.
- **Калибровка (ожидание):** шанс попадания игрока 0,60, средний урон 3,5 → волк падает за ~5 ходов; волка 0,60 × 2,5 → игрок за ~6,7 ходов; соло-победа ~60–65 %; группа из 3 — ~2 раунда, ≤ 1 укус на игрока. Замер на первых прогонах.
- **E2E «30 ходов соло»:** seed фиксирован и выбран так, чтобы игрок выжил (отмечено в тесте): `enter` → `look` → тик (встреча) → `attack`×k → волк мёртв → `look` → `leave` → `enter` (волк не появляется) → `rest` → …; отдельные прогоны: seed с гибелью игрока (FR-023) и с провальным `flee`.
