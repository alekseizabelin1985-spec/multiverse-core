# Нефункциональные требования

**Инициатива:** PROJECT · **Версия:** 0.3 · 2026-09-09 · бизнес-аналитик (dev-team)
**Статус:** утверждено на G1 2026-09-09 (без замечаний)

**Изменения v0.3 (G1, точечно):** NFR-048 — фильтр категории (a) принят в MVP-1 (OQ-D-16), условие «если выбран вариант B» снято, приоритет Must; NFR-007 — B = 4 переведено из допущения в стартовое значение G1 (OQ-R-20), порог по-прежнему после замера.

**Изменения v0.2 (кратко):** целевое железо RTX 4090 24 ГБ / 128 ГБ RAM / i9-13900 и две модели Qwen3 одновременно (NFR-073, NFR-076, «Что измерить первым»); бюджет фоновой жизни мира (NFR-007, NFR-053 переписано — допущение A-3 отклонено); бюджет LLM на *раунд* scope для группы (NFR-005, NFR-006, DR-12); инварианты «Тёмного леса» расширены и оформлены как первые законы (NFR-020, DR-18, DR-11); пробой без напряжения = 0 (NFR-025, DR-01); seed по броскам и независимость бросков (NFR-060, DR-05); логи бота и негативный случай «username = имя персонажа» (NFR-041, DR-10, DR-21); облако при внешних игроках и юрисдикция оператора (NFR-046, DR-14, DR-27); structured output при замере (NFR-022, DR-22); поле `handled` в логах и `actor_kind` в аналитике (NFR-033, NFR-036, PA §8); рой GM — лимит на число агентов (NFR-083).

Правила чтения:

- Пороги с пометкой **«после замера»** — допущение (OQ-R-09): цифра фиксируется после
  первого замера на целевой машине (RTX 4090 24 ГБ VRAM, 128 ГБ RAM, i9-13900 — р5)
  с выбранными моделями (OQ-D-13). До замера порог — ориентир для проектирования,
  не критерий приёмки.
- «Способ проверки» — как убедиться, что требование выполнено; если проверка
  требует инструмента, которого нет, это отмечено.
- Приоритет — MoSCoW для MVP-1; целевой горизонт отмечен в примечании.
- Неприменимые категории помечены явно (§10).
- Требования «1000 событий/с/шард», «10 000 акторов», «99.9 %», «<100 мс p95 на
  LLM-вызов» из старых документов **сняты** (раунд 1, OQ-A-04/OQ-P-03) и здесь
  не воспроизводятся.
- Определения: *ход*, *раунд*, *сессия*, *фоновый тик* — по `prd.md` (FR-025, FR-085, FR-124) и глоссарию.

## Что измерить первым (для фиксации порогов «после замера»)

Все замеры — на целевой машине (RTX 4090 24 ГБ, 128 ГБ RAM, i9-13900), ≥ 3 прогона,
результат — `ops/metrics/baseline.md` (дата, драйвер, модели, режимы). Протокол — `metrics.md` §7.

1. **Размещение двух моделей** (NFR-076): `qwen3:8b` + `qwen3:30b-a3b` и + `qwen3:32b` — помещаются ли обе в 24 ГБ с рабочим контекстом; скорость Phase 2 при частичной выгрузке в RAM.
2. Латентность Phase 1 (на правилах и с LLM) и Phase 2 при обеих загруженных моделях и включённых фоновых тиках (NFR-001, NFR-002, NFR-007) — соло и группа из 3 (один нарратив на раунд).
3. Холодный старт каждой модели и влияние `keep_alive` (NFR-004).
4. Доля валидных JSON с первой попытки в режиме structured output, thinking off для Phase 1 (NFR-022, DR-22) — по фазам и для фоновых тиков.
5. Доля ответов с иероглифами/латиницей у модели нарратива (NFR-090).
6. Время `make up` до всех `/health` = ok с двумя моделями и ресурсный след (NFR-070, NFR-073).
7. RTO восстановления с фоновыми событиями в логе (NFR-010).
8. Стоимость фоновой жизни: вызовы/токены за час без игроков при B = 4 и при LOD 1 без LLM (NFR-007) — для выбора режима тиков по умолчанию.
