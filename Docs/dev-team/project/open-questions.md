### OQ-R-01. Для кого продукт [блокирующий]

**Контекст.** `Docs/user-stories/README.md` называет продукт «бэкенд мультивселенной,
к которому можно подключить любой фронт». Living Worlds пишет об удержании игроков,
Agent GM — о 1000 игроках на шард. Фактически проект ведёт один разработчик, игроков нет.

**Варианты.**
- A. Личная исследовательская платформа владельца: цель — проверять идеи «живых миров», пользователь = автор.
- B. Backend-as-a-service для авторов миров / инди-разработчиков: они подключают свой клиент.
- C. Готовый продукт для конечных игроков со своим клиентом.

**Предполагаемый ответ по документам.** A сейчас, B как видение; C нигде не обоснован.
**Рекомендация.** Зафиксировать A для MVP с архитектурой, не закрывающей B.
**Статус.** решено — бэкенд-платформа живых миров, игровые домены как расширения; первый игрок — сам разработчик, затем узкий круг тестеров (2–6) (раунд 1).

### OQ-R-02. Какую боль решаем [блокирующий]

**Контекст.** Философия («мир не программируется, а рождается») есть; формулировки
проблемы пользователя нет. `agent-gm-research/README` описывает только техническую боль
(if-else, стоимость LLM). Аналоги (AI Dungeon, AI Game Master и др.) уже дают LLM-нарратив
с памятью.

**Варианты.**
- A. Консистентность и память мира: LLM-нарратив, который не противоречит фактам и законам мира.
- B. Эмерджентность: мир меняет собственные правила под действиями игроков (эволюция правил, Запрет Мира).
- C. Экономика: живой мир при стоимости LLM, приемлемой для локального GPU.
- D. Инструмент автора: описал мир текстом — получил играбельный мир.

**Предполагаемый ответ.** A + B (это отличает проект от аналогов); C — ограничение, не боль.
**Рекомендация.** Выбрать одну главную боль для MVP; остальные — в видение.
**Статус.** решено — A + B: мир, который не ломается в сессии (критерий успеха раунда 1), и эволюционирует (Living Worlds в целевом, пробой законов — раунд 2). C — ограничение (Ollama по умолчанию), D — целевой эпик авторских инструментов.

### OQ-R-03. Чем измеряем успех [блокирующий]

**Контекст.** Документы содержат цифры без источника (+31% удержания, −92% ручной
балансировки) и технические SLA без измерений. Метрик, которые можно снять сегодня, нет.

**Варианты.**
- A. Технические: сквозной сценарий проходит автоматически; p95 ответа игроку ≤ N с; стек поднимается одной командой.
- B. Продуктовые: число сессий, длина сессии, возвращаемость (требует игроков).
- C. Исследовательские: доля ответов LLM, прошедших валидацию схемы; число противоречий канону на 100 ходов (оценка человеком или LLM-судьёй); число порождённых системой правил, принятых автором.

**Предполагаемый ответ.** A + C; B недоступно без игроков.
**Рекомендация.** 3–5 метрик, по каждой — как измеряем и текущее значение («не измерено»).
**Статус.** решено — успех = регулярные сессии без поломок мира; для MVP: «Тёмный лес» 30 ходов без поломки (раунд 1). Формализовано: `prd.md` §1.1 (G-1…G-7), `nfr.md` NFR-012.

- C. SC-06 «мир по описанию»: законы → мир → регионы → канон.
- D. SC-09 + SC-10 (оператор и исследователь) как обязательная база, затем один из A–C.

**Предполагаемый ответ.** D + A: «Тёмный лес» назван критерием готовности в Agent GM и уже покрыт e2e-тестом библиотеки.

**Статус.** решено — D + A: «Тёмный лес» (вход → встреча → бой → нарратив, 30 ходов) + сценарии оператора и исследователя как база (раунд 1). См. US-002, US-010…US-019.

### OQ-R-05. Режим игры [блокирующий]

**Контекст.** Документы целятся в массовый мультиплеер (1000 игроков/шард, 10 000 акторов).
Аналоги на рынке — одиночная игра и группы до 6. Проект — один разработчик, один GPU.

**Варианты.**
- A. Только одиночный режим.
- B. Одиночный + малая группа (2–6) в общем scope.
- C. Массовый мультиплеер с шардированием.

**Предполагаемый ответ.** B — merge/split GM уже реализован, а C недостижимо без команды.
**Рекомендация.** B; C — как нефункциональное ограничение «архитектура не должна исключать», без обязательств.
**Статус.** решено — B, причём соло + группа 2–6 СРАЗУ в MVP (отклонение от рекомендации «только соло»); «1000/шард» снято из NFR (раунд 1). См. FR-005, NFR-080…082.

### OQ-R-06. Интерфейс игрока [блокирующий]

**Контекст.** `hasUI=false`. game-service даёт REST + WebSocket, но приём действий (`/ws/actions`)
не реализован, вывод рассылается всем клиентам. Без какого-либо клиента сценарии игрока
нельзя проверить.

**Варианты.**
- A. Только API (WebSocket + REST); клиент вне объёма.
- B. A + консольный тестовый клиент (инструмент разработчика).
- C. A + бот в Telegram/Discord как «клиент по умолчанию» (дёшево, даёт мультиплеер и адресацию из коробки).
- D. Веб-клиент.

**Предполагаемый ответ.** A по конфигу; практически нужен B или C.
**Рекомендация.** B для MVP; C — следующий шаг, если нужны внешние игроки.
**Статус.** решено — C: Telegram/Discord-бот как эталонный клиент в MVP (раунд 1). Допущение BA: первым — один мессенджер, второй — следующий инкремент (PRD A-6). См. FR-004, US-008.

### OQ-R-07. Форма ввода игрока [блокирующий]

**Контекст.** Living Worlds: свободный текст → Intent Recognition через LLM. narrative-orchestrator
и Agent GM: структурированные события (`player.used_skill`, `player.attack`). Аналоги используют
гибрид (AI Dungeon: Do / Say / Story + текст).

**Варианты.**
- A. Только структурированные команды (move / attack / talk / use) с параметрами.
- B. Только свободный текст; LLM извлекает намерение.
- C. Гибрид: тип действия + свободный текст; интент-распознавание применяется внутри типа.

**Предполагаемый ответ.** C — примиряет обе ветки кода.
**Рекомендация.** C; словарь типов действий — в глоссарий.
**Статус.** решено — C (раунд 4): в MVP-1 бот даёт команды `enter/look/attack/flee/say/leave` с опциональным текстом, распознавание свободного текста — целевое. Словарь дополнен по DR-17 (`status`, `rest`, `group create/join/leave`, `/start`, `/help`, `/forget`) — состав **принят на G1** как стартовое значение, уточняется по первым сессиям. См. PRD FR-002 (A-1 решено), FR-007, US-008, US-032.

### OQ-R-09. Латентность ответа игроку [блокирующий для NFR]

**Контекст.** Agent GM обещает Phase 1 <100 мс p95 (LLM-вызов), Living Worlds — инференс
<50 мс (TinyML). Локальный Ollama с 7B-моделью даёт секунды на ответ. Честной цели нет.

**Варианты.**
- A. «Чат»: полный ответ до 3–5 с на ход; допускается стриминг текста.
- B. «Реальное время»: механический результат ≤ 500 мс (правила/кэш, без LLM), нарратив асинхронно до 5 с.
- C. Пошагово без ограничения: важна консистентность, не скорость.

**Предполагаемый ответ.** B — соответствует двухфазной идее, но с реалистичными числами.
**Рекомендация.** B, с обязательным измерением на целевом железе до фиксации цифр.
**Статус.** допущение — B: механика ≤ 0,5 с без LLM, нарратив асинхронно ≤ 5 с; цифры фиксируются после замера на целевом GPU (допущение оркестратора; G1 пройден без замечаний — считается подтверждённым). См. NFR-001, NFR-002.

### OQ-R-10. Стоимость и источник LLM [блокирующий для NFR]

**Контекст.** Документы приводят цены облачных токенов ($0.0018/1000 действий, <$0.01/игрок-час),
стек — локальный Ollama с NVIDIA GPU. Какой GPU и допустимы ли облачные модели — не сказано.

**Варианты.**
- A. Только локальные модели; бюджет = железо; ограничение — GPU-время на ход.
- B. Локальные для механики, облачные для нарратива с лимитом $/месяц.
- C. Только облако.

**Предполагаемый ответ.** A.
**Рекомендация.** A + указать модель(и) и GPU; ввести метрику «LLM-вызовов на ход игрока» вместо долларов.
**Статус.** решено — облачные модели допустимы через абстракцию провайдера, локальный Ollama по умолчанию (раунд 2); железо названо (раунд 5): RTX 4090 24 ГБ VRAM, 128 ГБ RAM, i9-13900, две модели Qwen3 одновременно (`qwen3:8b` решения/тики + `qwen3:30b-a3b`/`32b` нарратив); пороги — после замера на этой машине. Метрика «вызовов на ход» вместо долларов — допущение оркестратора (G1 пройден без замечаний — считается подтверждённым). См. FR-070…072, NFR-007, NFR-050…053, NFR-076.

### OQ-R-11. Уровень строгости консистентности мира [блокирующий]

**Контекст.** Есть четыре механизма целостности (Overseer, BanOfWorld, Rule Validator,
MonitorAgent) и два подхода к нарушениям: «мифологические последствия» (architecture.md) и
`player.punished` (ban-of-world README). Не определено, что неизменно, что «канон», кто арбитр.

**Варианты.**
- A. Строгий: числовое состояние (HP, инвентарь, позиция) и законы вселенной меняет только механика; LLM описывает и предлагает, но не пишет факты напрямую.
- B. Мягкий: LLM может порождать факты и события; страж постфактум откатывает противоречия.
- C. Слоями: immutable-законы вселенной (только автор), канон мира (LLM предлагает, страж утверждает), сиюминутное (LLM свободно).

**Предполагаемый ответ.** C — соответствует US-001 (immutable/default) и философии.
**Рекомендация.** C; в PRD — таблица «что кто может менять».
**Статус.** решено — C (законы неизменны → канон с утверждением → сиюминутное свободно) ПЛЮС механизм «пробоя законов»: LLM может породить неординарное событие, разрушающее старые законы и образующее новые; контроль постфактум (страж/ревью) (раунд 2). См. BR-01, BR-02, FR-040…044, US-020, US-021.

### OQ-R-13. Какая модель GM — целевая [блокирующий]

**Контекст.** Три несовместимых модели: scope-GM (narrative-orchestrator, работает),
Entity-Actor (Living Worlds, заглушки), Agent GM (shared/agent, библиотека без сервиса).
MIGRATION.md отключает narrative-orchestrator, Living Worlds — расширяет его. См. `inventory.md` §4.1.
Вопрос общий с системным архитектором; здесь — продуктовая сторона.

**Варианты.**
- A. Оставить scope-GM, остальные ветки закрыть.
- B. Agent GM как единственный «мозг»; narrative-orchestrator и Entity-Actor выводятся.
- C. Комбинация: Agent GM — оркестрация и решения; Rule Engine — механика; narrative-orchestrator — генерация текста (Phase 2); Entity-Actor — не используется.
- D. Комбинация с Entity-Actor как хранителем состояния сущностей.

**Предполагаемый ответ.** C — переиспользует работающее и не требует TinyML.
**Рекомендация.** C; решение оформить как ADR.
**Статус.** решено — Agent GM Core единственный «мозг», narrative-orchestrator → тонкий рендер или выводится, Rule Engine — механика, временный фича-флаг на миграцию (раунд 1). ADR — за архитектором. См. FR-010, FR-014, BR-12, US-019.

### OQ-R-18. Модель раунда группы и формулировка S2 [уточняющий; решено на G1]

**Контекст.** Доменное ревью (DR-03) показало, что «30 ходов группой из 3» без модели раунда не тестируемо: неясно, когда действует NPC, что с молчащим игроком, кто ведёт группу. В PRD принята модель раунда (FR-025, BR-13): раунд закрывается, когда все `active` участники сделали действие или истёк таймаут (60 с); NPC действует один раз в раунд; молчащий — `defend`, после двух пропусков — `idle`; лидер перемещает группу; `flee` индивидуален.

**Варианты.**
- A. S2 = «30 раундов группы из 3 (≥ 60 действий игроков), включая раунд с молчащим игроком, индивидуальное бегство и выход участника»; таймаут 60 с, `idle` после 2 пропусков.
- B. S2 = «30 действий на каждого игрока» (90 действий, ~30+ раундов).
- C. Без раундов — NPC отвечает на каждое действие (штраф за размер группы).

**Рекомендация.** A (допущение A-15 PRD); C отклонить.
**Статус.** решено (G1) — A по рекомендации: S2 = «30 раундов группы из 3 (≥ 60 действий игроков)», таймаут 60 с, `idle` после 2 пропусков — стартовые значения, уточняются замером на этапе архитектуры. См. PRD A-15, FR-025, BR-13, US-007; формулировку S2 в `vision.md` обновляет PO.
**Уточнение после G2 (2026-09-09).** Семантика раунда закреплена по замечаниям системного аналитика (use-cases.md приложение Б п. 1, 3–5) и архитектора (consolidation G-6/G-7, C-04): `say`/`look` не открывают раунд и не входят в `acted[]`; второе раундовое действие в открытом раунде — `409 already_acted`; `status` — запрос чтения; лидерство при смерти лидера — старейший `alive` по `joined_at` (`group.leader_changed cause=death`), без живых — без лидера до `disbanded`; позиция после успешного `group leave` в бою — опушка; инвариант 4 — только `alive`. Внесено: PRD v0.4 FR-002/006/025, BR-13; NFR-020; US-006/007.

### OQ-P-01 · БЛОКИРУЮЩИЙ · Кто пользователь первого играбельного среза?
**Контекст.** В документах упомянуты игрок, «администратор» вселенной, геймдизайнер (блупринты), внешние разработчики фронтов, но целевая аудитория нигде не выбрана. От неё зависит, что считать MVP.

### OQ-D-01. LLM-выводы как события и политика replay [БЛОКИРУЮЩИЙ]

**Контекст.** Архитектура обещает «snapshot + replay», но rule-engine seed-ится от `time.Now()`, оракул работает с temperature 0.8–1.0 без seed, промпты/ответы LLM не сохраняются как события. При replay GM повторно вызовет LLM и породит другую историю; броски не повторятся (domain-notes §4).

**Варианты.**
- A. Record-replay: каждый вызов LLM и каждый бросок записываются как событие (`llm.output`, `dice.rolled`); replay не вызывает LLM и не бросает кости, а читает записанное. Seed бросков = hash(event_id).
- B. Replay только для «детерминированных» сервисов (entity-manager), нарративные сервисы восстанавливаются только из снапшота, история после снапшота теряется.
- C. Отказаться от replay как гарантии; хранить только снапшоты.

**Рекомендация.** A — единственный вариант, при котором «полная история, replay» из ARCH — правда; это же даёт аудит промптов и воспроизводимые тесты. Оформить ADR.
**Статус.** решено — A: выводы LLM и броски записываются как события (record-replay), replay не вызывает LLM повторно; снапшот — истина (раунд 2). ADR — за архитектором. См. BR-04, FR-021, FR-022, FR-032, US-011, US-017, US-018.

### OQ-D-02. Модель прогрессии культивации [БЛОКИРУЮЩИЙ]

**Контекст.** В коде прогресс — множитель 1.0/1.5 за использование умения; нет реалмов/ступеней, порогов, условий вознесения; любая `ascension.attempt` ведёт на План выше, План Ω достижим за два вознесения, хотя заявлен недостижимым. Жанр (сянься) строится на бутылочных горлышках «накопление + постижение + испытание с риском» (domain-notes §6).

**Варианты.**
- A. Классическая лестница: N реалмов × 4 ступени внутри мира; вознесение на План 1 — только с пика последнего реалма и через испытание оракула с enum-исходами (успех / откат / смерть).
- B. Бесступенчатая «глубина дао»: прогресс — накопление разнообразных актов (умения, выборы, конфликты), порог вознесения — по портрету дао (LLM-оценка + числовой минимум).
- C. Гибрид: ступени внутри мира (детерминированно), переход между Планами — по портрету дао (генеративно).
- Дополнительно: План Ω — (i) недостижим (терминальное испытание всегда проваливается сюжетно), (ii) достижим как «конец персонажа» (ретирмент), (iii) достижим и играем.

**Рекомендация.** C + Ω как (ii): даёт жанровый ритм, ограничивает инфляцию (прирост убывает внутри ступени), сохраняет философию «путь к универсальной сути». Зафиксировать таблицу «что даёт каждый План» в PRD.
**Статус.** решено — C + Ω (ii): гибрид — ступени (реалмы) с бутылочными горлышками внутри мира + «портрет дао» для перехода между Планами; достижение Ω — финал персонажа; не в MVP «Тёмный лес» (раунд 3). Таблица «что даёт каждый План» — в брифе эпика E-C. См. FR-111, FR-112, US-024, US-025.

### OQ-D-03. Возрастной рейтинг и политика насилия [БЛОКИРУЮЩИЙ]

**Контекст.** Документы Living Worlds запрещают «насилие (физическое, психологическое)», при этом продукт — тёмное фэнтези с боем, «Миром Боли», смертью. Фильтров в коде нет. Урок AI Dungeon: без фильтра выхода модель порождает недопустимое даже без умысла игрока; чрезмерная модерация приватных сессий рушит доверие (domain-notes §9). По 436-ФЗ жанру реалистично соответствует 18+.

**Варианты.**
- A. 18+, «стены»: приватная сессия — только жёсткие абсолютные запреты (сексуализация несовершеннолетних, реальные противоправные инструкции), публичный/групповой контент — полный фильтр.
- B. 16+, насилие «без детализации», фильтр выхода на всё.
- C. Без рейтинга и фильтров (только владелец играет) — явно вне объёма до появления внешних игроков.

**Рекомендация.** C для MVP при условии, что в архитектуре есть точка вставки фильтра входа и выхода (один интерфейс), и A как целевая политика. Список абсолютных запретов утвердить сейчас — он влияет на системные промпты.
**Статус.** решено — C для MVP (без фильтров) с точкой вставки фильтра на выходе нарратива и списком абсолютных запретов в системном промпте; A (18+, «стены») — целевая политика (раунд 3). Список утверждён на G1: 7 пунктов BR-08; фильтр категории (a) fail-closed в MVP-1 (2026-09-09). См. FR-050…053, US-016, US-031.

### OQ-D-04. Персональные данные, юрисдикция и право на забвение [БЛОКИРУЮЩИЙ при внешних игроках]

**Контекст.** Регистрация без согласия и без аутентификации; ник, история действий и свободный текст хранятся бессрочно в Redpanda, ChromaDB, Neo4j, MinIO; API удаления нет. 152-ФЗ с 07.2025 требует локализацию первичного сбора в РФ; при аудитории ЕС — GDPR. Event sourcing без крипто-шреддинга делает удаление технически невозможным (domain-notes §10.1).

**Варианты.**
- A. Игроки только из РФ, серверы в РФ, минимизация (ник + технический id), retention по топикам, крипто-шреддинг (ключ на игрока).
- B. Псевдонимизация на входе: game-service хранит соответствие «аккаунт ↔ player_id» отдельно; в шину уходит только псевдоним; удаление = разрыв связи + удаление профиля.
- C. Отложить до внешних игроков.

**Рекомендация.** B сейчас (дёшево, архитектурно правильно), A — при выходе к игрокам. Вопрос пользователю: целевая аудитория по странам.
**Статус.** решено — B: псевдонимизация на входе game-service, внутри только `player_id`, связка с Telegram/Discord ID хранится отдельно и удаляема; юрисдикция РФ по умолчанию (раунд 3). Полное право на забвение — целевое (FR-062, US-035). См. BR-07, FR-060, FR-061, US-009.

### OQ-D-05. Единый список scope-типов [уточняющий, влияет на PRD]

### OQ-D-06. Термин «План» и структура иерархии [уточняющий]

**Контекст.** «План» употребляется как plane (план бытия), как plan (стратегический план в worktree-описании PlanManager, события `plan.created/executed`) и как число `plan_level`. Между Планом 1 и Ω структура не определена; «зона слияния» — то постоянный мир Плана 1, то временная 24-часовая зона, то слияние GM (`gm.merged`).

**Варианты.** A. Закрепить: «План» = plane, события `plane.*`; иерархия фиксирована: 0 → 1 → 2 → Ω; зона слияния = мир Плана 1; временные слияния и `gm.merged` переименовать («конвергенция», «слияние скоупов»). B. Оставить свободную глубину (N планов), генерируемую оракулом генезиса.

**Рекомендация.** A для MVP; B — как расширение через тот же граф.
**Статус.** решено частично — «План» = plane; переход между Планами — по портрету дао; Ω — финал персонажа (раунд 3). Фиксированная глубина иерархии и переименование `plan.*` → `plane.*`, «зона слияния» — на архитектуру/бриф эпика E-C.

### OQ-D-07. Экономика городов: симуляция или описание [уточняющий, блокирует эпик «город»]

**Контекст.** Награды — строки («100 золотых»), репутация — константа, каждый вход в город — welcome-квест. Нет леджера, предметов как сущностей, цен.

**Варианты.** A. Описательная экономика (LLM-текст, без чисел) — только для соло. B. Минимальный леджер: валюта и предметы — сущности, источники/стоки, LLM предлагает награду в лимитах, движок выдаёт. C. Полная симуляция (спрос/предложение, цены).

**Рекомендация.** B; C — после появления групп/торговли между игроками. Для MVP «Тёмный лес» город можно исключить.
**Статус.** открыт → бриф эпика E-D (города). Город исключён из MVP-1; в PRD принята рекомендация B как допущение (FR-113, US-026).

### OQ-D-08. Владелец состояния сущности при пересечении скоупов [уточняющий, влияет на архитектуру]

**Контекст.** NPC может быть одновременно в скоупах города, группы и квеста; GM каждого скоупа публикует `npc.action.*`. Границы консистентности не совпадают: entity-manager — по миру, GM — по скоупу, агенты — по региону.

**Варианты.** A. Единственный писатель — entity-manager; GM/агенты только публикуют предложения (`*.proposed`), entity-manager применяет и разрешает конфликты (версия сущности, optimistic lock). B. Сущность закреплена за одним «домашним» скоупом; остальные — читатели. C. Last-writer-wins.

**Рекомендация.** A (согласуется с OQ-D-01 и OQ-R-11 вариант C); C неприемлем.
**Статус.** решено — A: entity-manager единственный писатель, остальные публикуют предложения (раунд 2). Механизм версии/optimistic lock — архитектура. См. BR-03, FR-030, US-007.

### OQ-D-09. Канон: кто утверждает факты и как сливаются каноны [уточняющий]

### OQ-D-16. Реализация точки вставки фильтра в MVP-1: пустышка или минимальная проверка категории (a) [решено на G1]

**Статус.** решено (G1) — B: минимальная проверка категории (a) по словарю, fail-closed; задержанный ответ → `llm.output` со статусом `quarantined` без хранения `response_raw`. Вариант A снят из PRD. См. FR-050, FR-032, NFR-048, US-016, US-018.

### OQ-A-03 [БЛОКИРУЮЩИЙ] Кто владеет состоянием сущности и нужен ли event replay?
- Почему вопрос: сущности пишут entity-manager и game-service (оба в `entities-{world_id}`), entity-actor хранит своё состояние отдельно; entity-manager не публикует изменений; «snapshot + replay» задекларирован, но replay не реализован и retention Redpanda не настроен. Без ответа нельзя определить границы контекста «Сущности», формат хранения (объект JSON в MinIO vs БД) и гарантии шины.
- Варианты: A) entity-manager — единственный писатель, остальные только через события (`entity.create` команда → `entity.created` факт); хранение остаётся MinIO; replay не требуется, снапшот — источник истины; B) то же, но с event-sourcing (retention «forever», replay при восстановлении); C) перевести сущности в реляционную/документную БД (PostgreSQL/JSONB), MinIO — только бинарники и снапшоты.
- Рекомендация: **A сейчас, с открытой дверью в C** — минимальное изменение, закрывает конфликт владения; event-sourcing (B) не оправдан при отсутствии требований к аудиту/времени восстановления.
- **Статус.** решено — A с дополнением: entity-manager единственный писатель, снапшот — истина, НО выводы LLM и броски записываются как события (record-replay), replay не вызывает LLM (раунд 2). Т. е. лог нужен для догона от снапшота и аудита, не полный event-sourcing. См. BR-03, BR-04, FR-030…034.
- **Статус A3.** решено — **ADR-003**: State в памяти + MinIO объект на сущность (versioning) + снапшот мира с курсором; факты переигрываются, предложения — нет; `seed = SHA-256(event_id ":" roll_index)[0:8]`, RNG `math/rand/v2` PCG; время из `tick.fired`/`round.closed` через `Clock`; режим `--mode=replay` с `RecordedProvider`.

### OQ-A-04 [БЛОКИРУЮЩИЙ] Целевая среда, масштаб и NFR: сколько игроков/миров, какие бюджеты латентности LLM, где деплой?

В матрицу добавлен вариант **E** — одна `Qwen3.8-27B UD-Q3_K_XL` на llama-server (13,1 ГБ весов + KV ≈ 2–4 ГБ при 8–16k → 16–19 ГБ, помещается целиком; проверено по HF `unsloth/Qwen3.8-27B-GGUF`). **Базовая конфигурация теперь: E, если проходит NFR-002/NFR-090; иначе C; иначе A.** Провайдер по умолчанию — `openai_compat` (ADR-005 дополнение 2), блупринты до `baseline.md` задают E. Управление процессом llama-server — OQ-A-21.

### OQ-A-21 [решён архитектором; уточняющий] Стратегия управления llama-server: служба Windows / ручной запуск по скрипту / из compose через host
- Почему вопрос: по U-8 основной LLM-рантайм — нативный процесс вне Docker; нужно решить, кто и как его запускает, чтобы `make up`, замер F-8 и runbook были однозначны. Пользователь запускает `llama-server.exe` вручную с длинной командной строкой.
- Варианты: A) **скрипт `scripts/llm-server.ps1` с зафиксированными параметрами + `make llm-up/llm-down/llm-health`; `make up` процесс не запускает, только проверяет `GET $MV_LLM_URL/health` и предупреждает**; B) служба Windows (NSSM/Task Scheduler) с автозапуском; C) контейнер llama.cpp в compose (профиль `gpu`) через WSL2 GPU.
- Рекомендация и **решение (system-architect, 2026-09-09, не требует владельца)**: **A** для MVP-1 — один оператор, ручной запуск по runbook, параметры зафиксированы в скрипте (воспроизводимость замера), `mmap+mlock` держит модель резидентной; B — при появлении внешних тестеров (E-H); C не берём (WSL2-виртуализация GPU, лимит RAM `.wslconfig`, дубль рантайма при уже установленном нативном). Семплинг по умолчанию в скрипте не задаётся — шлюз передаёт параметры фазы на запрос (non-thinking профиль). Router-режим (`--models-dir` без `-m`) — отдельный вариант скрипта для конфигураций A/E+.
- **Статус.** решено архитектором (ADR-005 дополнение 2 п. 7); пользователь может переопределить на G3 без влияния на код (`MV_LLM_URL` и скрипт).

### OQ-A-19 [уточняющий] Retention журнала и место на диске
- Почему вопрос: ADR-007 задаёт retention доменных топиков 30 дней (≥ окна сводки FR-127 и ≥ 3 интервалов снапшота), `llm_records` 90 дней, `analytics_events` 180 дней; оценка объёма ≈ 3 МБ на сессию (журнал + записи LLM) — при 8 сессиях/месяц это десятки МБ, но при `LLM_STORE_PROMPTS=true` полные промпты в MinIO дают ещё ≈ 1–2 МБ/сессия. Нужно подтверждение, что 30/90/180 дней и хранение полных промптов по флагу устраивают оператора.
- Варианты: A) 30/90/180 дней, промпты по флагу (по умолчанию выкл.); B) короче (7/30/90) — теряется сводка фона при паузе > 7 дней; C) «навсегда» — растущий диск, нужен ручной контроль.
- Рекомендация: **A**.
- **Статус.** решено (пользователь, 2026-09-09) — **A**: 30/90/180 дней, полные промпты в MinIO по флагу `MV_LLM_STORE_PROMPTS` (по умолчанию выкл., ILM 30 дней). Внесено в ADR-007 дополнение п. 1–2 (с `segment.ms=1d`, без которого retention не срабатывает) и `infrastructure.md` §5.1.

### OQ-A-20 [к G2] Объектное хранилище: MinIO из исходников на MVP-1 или замена сервера уже в EPIC-001
- Почему вопрос: после ADR-004 выяснилось (devops, проверено 2026-09-09), что MinIO Inc. прекратила публикацию Docker-образов и бинарников (последний образ `RELEASE.2025-09-07`; фикс CVE-2025-62506 — только исходниками; в феврале 2026 репозиторий архивирован). Пин на замороженный образ = хранилище без security-обновлений. Платформа использует от S3 только Put/Get/Stat/List/Delete; bucket versioning — необязательная страховка (откат — ротация снапшотов). Сервер слушает только `127.0.0.1` на одной доверенной машине — эксплуатационный риск низкий, но стек в `.dev-team.json` («MinIO») формально меняется при замене.
- Варианты (ADR-021): A) **сборка MinIO из исходников последнего тега** (`build/minio.Dockerfile`, CVE закрыт; будущих фиксов не будет; `objstore` минимальный, замена сервера позже по триггерам — CVE ≥ 7 без патча, несобираемость на новом Go, первый внешний клиент); B) заменить на **SeaweedFS** уже в EPIC-001 (живой upstream, S3 versioning есть; +spike и новая технология в волне 0 при одном разработчике); C) community-форк MinIO (образы публикуются; зависимость от стороннего форка).
- Рекомендация: **A** — дизайны EPIC-002/003/004 не меняются, волна 0 не растёт; путь к B подготовлен интерфейсом `objstore` и триггерами ADR-021.
- **Статус.** открыт → пользователь (G2); до решения EPIC-001 F-5/F-6 планируются по A.
