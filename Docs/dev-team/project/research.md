# Часть 1. Исследование аналогов (бизнес-аналитик)

**Автор:** бизнес-аналитик (dev-team)

Цель: понять, какие сценарии и функции считаются обязательными у сравнимых

## Что типично для LLM-GM платформ (по обзорам 2026 года)

| Функция | Наблюдение | Что это значит для multiverse-core |
|---|---|---|
| Разделение механики и нарратива | Сильнейшие системы бросают кубики/применяют правила на сервере, LLM только описывает результат (обзор Dungeons Deep, StoryRoll) | Совпадает с принципом Living Worlds и Agent GM; подтверждает выбор «механика решает, LLM рассказывает» |
| Постоянная память кампании | Ключевой дифференциатор: NPC и факты не «забываются» между сессиями; для этого используется многомодельная оркестрация (лор, состояние персонажей, позиция, нарратив как отдельные задачи) | Semantic memory + Neo4j — уже есть основа; нужна явная модель «канона» и памяти NPC о игроке |
| Форма ввода | AI Dungeon: команды Do / Say / Story; др. платформы — свободный текст с серверной интерпретацией | Гибрид «свободный текст + явный тип действия» — рабочий компромисс для OQ-R-07 |
| Мультиплеер | Обычно малые группы (до 6 игроков синхронно), асинхронные кампании через Discord-ботов | Массовый мультиплеер (1000/шард) — не норма для жанра; см. OQ-R-05 |
| Клиент | Веб, Discord-бот, реже — скачиваемый движок | Discord/Telegram-бот — дешёвый способ получить клиент без UI-разработки; см. OQ-R-06 |
| Реальные статы и смерть | Часть платформ ведёт HP числами, позицию в сцене, перманентную смерть | Совпадает с Rule Engine / Entity-Actor; требует решения об уровне строгости (OQ-R-11) |
| Пользовательские сценарии | Библиотеки сценариев сообщества, скриптинг для продвинутых | Аналог — блупринты в Markdown (SC-07) |

## Выводы

1. Направление проекта (сервер-механика + LLM-нарратив + постоянная память) совпадает
   с тем, что рынок считает «правильной» архитектурой; уникальность — в эволюции
   правил и иерархии миров, а не в самом GM.
2. Рынок не требует массового мультиплеера; одиночный режим и группа до 6 —
   достаточная планка для MVP.
3. Самый дешёвый способ получить «интерфейс игрока» без UI — бот в мессенджере
   поверх существующего WebSocket/REST.

## Типовой набор возможностей в нише

Обязательный минимум, без которого продукт не воспринимается как игра:

1. Ввод игрока на естественном языке → распознавание намерения/действия.
2. **Детерминированный слой механики** (HP, инвентарь, позиция, броски) — ведётся кодом, не LLM.
3. Персистентная память трёх видов: лор мира, состояние сущностей, эпизодическая история (с суммаризацией).
4. Генерация нарратива с заданным тоном/настроением, локализованная.
5. Сохранение/восстановление сессии.
6. Контроль стоимости: кэш, маршрутизация моделей, маленькие модели для рутины.
7. Базовая политика контента (хотя бы для публикуемого контента).

Дифференциаторы (за это платят или остаются): память и непрерывность; агентность — действия игрока необратимо меняют мир, и это видно; авторский контроль над лором/правилами; мультиплеер/партия; живой мир «за кадром» (NPC/фракции действуют без игрока).

## За что ценят и чего избегают

**Ценят:** непрерывность и память; ощущение, что мир «настоящий» (правила соблюдаются); отзывчивость; приватность; авторские инструменты; понятную цену.

**Избегают / за что уходят:** дрейф персонажей и противоречия; GM-«поддакиватель», который разрешает всё; задержки в несколько секунд и больше без обратной связи; непредсказуемую модерацию; счета за токены; необходимость самому «чинить» память промптами.

## Известные грабли (сведено по источникам)

| Область | Грабли | Как обходят лучшие |
|---|---|---|
| **Консистентность мира** | LLM забывает/переписывает факты; предметы появляются из ниоткуда; раны заживают | Состояние в структурированном хранилище (граф/БД), LLM получает его как вход и не является источником истины; изменения — как «патчи»; символическая валидация выхода |
| **Стоимость LLM** | Один вызов на каждое событие каждого агента → счёт растёт линейно с числом агентов × событий | Уровни детализации (LOD), кэш, правила без LLM для рутины, маленькие локальные модели, LLM только для «важных» моментов |
| **Латентность** | Двухфазные конвейеры и цепочки агентов складываются в секунды | Асинхронный нарратив, потоковая выдача, короткие ответы механической фазы, честные SLA (секунды, не миллисекунды на локальной модели) |
| **Модерация** | Либо перегибы фильтра, либо скандал; ручная модерация приватного — недопустима | Разделить приватное/публичное; политика объявлена заранее; фильтр на публикацию, а не на игру |
| **Монетизация / аудитория** | Подписки работают у AI Dungeon/F&F, но при облачных моделях маржа съедается инференсом; «платформа без игры» не находит аудиторию | Узкая цепляющая механика → аудитория → платформа; локальные модели/self-hosted как способ обнулить переменные затраты |
| **Авторская нагрузка** | Чем больше пространство состояний, тем больше контента надо написать | Процедурный контент из состояния (LLM как «рендерер» состояния), а не canned-тексты |
| **Инженерный перебор** | Инфраструктура раньше игрового цикла | Все успешные примеры начинали с одной комнаты/одного региона и одного сквозного цикла |

## Что это значит для multiverse-core (выводы PO)

1. **Идея проекта совпадает с передним краем**: гибрид «символический мир + LLM-рендер», иерархия агентов, граф памяти — это то, к чему пришли Friends & Fables, Hidden Door, NeSyS/AriGraph. Направление верное.
2. **Главный риск — не технология, а отсутствие сквозного играбельного цикла.** 15 сервисов, два поколения GM (narrative-orchestrator и Agent GM Core), Living Worlds с TinyML — при этом в документах нет ни одного описанного и подтверждённого прохождения «игрок вошёл → что-то случилось → игрок увидел результат → мир это запомнил». Все аналоги, дошедшие до аудитории, начинали с этого.
3. **Часть метрик в документах не является измеренными** (Living Worlds: «+31% retention», «92% сокращение балансировки», «production ready» при отсутствии игроков и продукта). Для видения и приёмки их использовать нельзя; нужны собственные, проверяемые критерии.
4. **NFR-цели вроде «LLM-фаза < 100 мс p95» нереалистичны для локального Qwen3** (~80 ток/с) и должны быть пересмотрены на продуктовом уровне: что считается «приемлемо быстро» для текстовой игры — секунды, а не миллисекунды.
5. **Ниша даёт готовый ответ на «что такое MVP»**: один мир, один регион, один игрок, детерминированная механика, LLM-нарратив, память, восстановление. Всё остальное (планы, вознесение, эволюция правил, 1000 агентов) — следующие горизонты.

## Варианты решения

### Вариант A (минимальный) — «Один живой регион»

Один мир, один регион («Тёмный лес» из пилота agent-gm), один игрок, текстовый клиент (CLI / простой веб / Telegram-бот поверх существующего game-service API). Сквозной цикл: ввод на естественном языке → намерение → детерминированная механика (HP/инвентарь/позиция) → нарратив от локального Qwen3 → ответ игроку → мир запомнил (семантическая память) → после рестарта всё на месте. Один GM (Agent GM Core), остальные сервисы либо участвуют в цикле, либо честно заморожены.

- **Плюсы:** превращает набор сервисов в игру за один цикл; даёт первый настоящий критерий приёмки; выявляет мёртвый код и лишнюю инфраструктуру; нулевые переменные затраты (локальная модель).
- **Минусы:** не показывает «мультивселенную» — планы, вознесение, онтологии остаются за кадром; часть уже написанного кода в цикл не попадёт.
- **Риски:** соблазн «по дороге» дотянуть всё; латентность локальной модели потребует пересмотра ожиданий (секунды).
- **Что потребуется:** решение по одному GM; определение «минимальной механики» (5–10 правил); клиент; тест-сценарий «30 ходов без противоречий»; фиксация NFR в секундах.

### Вариант B (целевой) — «Платформа живых миров с авторским контролем»

То же ядро, что A, плюс: онтологии → генерация миров (US-001…US-004), Overseer/Ban of World как символический валидатор, иерархия агентов Global→Domain→Task с LOD, семантическая память с явными связями (plans/explicit-event-relations), блупринты в MD как инструмент автора мира, малый мультиплеер (scope `group`, 2–6 игроков), публичный API для внешних фронтов. Продукт — «движок + API», к которому можно подключить фронт и который автор мира настраивает без кода.

- **Плюсы:** соответствует заявленной философии и уже принятым архитектурным решениям; открывает две аудитории — игроки и авторы миров; даёт основу для open-source сообщества.
- **Минусы:** 3–5 циклов работы для одного разработчика; авторские инструменты (блупринты) требуют документации и примеров.
- **Риски:** без A сначала — превращается в бесконечную платформизацию; стоимость LLM при мультиплеере; удержание консистентности между агентами.
- **Что потребуется:** A как первый инкремент; реестр эпиков с чёткими контрактами; решение о судьбе Living Worlds; политика контента.

### Вариант C (амбициозный) — «Самоэволюционирующая мультивселенная»

Полная картина README + Living Worlds: иерархия планов до Источника, культивация/вознесение через Oracle, Entity-Actors с обучаемыми весами, эволюция правил через Evolution Watcher, кросс-мировое обучение, 1000 игроков/шард, подписочная монетизация.

- **Плюсы:** уникальное позиционирование; исследовательская ценность на уровне Project Sid; потенциально сильный портфолио-проект.
- **Минусы:** ни один аналог такого масштаба не является продуктом с аудиторией; для одного разработчика горизонт — годы; заявленные метрики не проверяемы без игроков.
- **Риски:** стоимость и латентность растут с числом агентов; эволюция правил ломает баланс и консистентность (сами документы это признают); высокая вероятность «вечного прототипа».
- **Что потребуется:** команда, GPU-парк или облачный бюджет, аудитория для измерения метрик, длительный горизонт.

### Рекомендация

**Принять B как целевое видение, A — как обязательный первый инкремент (MVP), C — зафиксировать как долгосрочный горизонт без обязательств.** Обоснование: (1) все дошедшие до аудитории аналоги начинали с одного заземлённого цикла; (2) единственный разработчик — узкое место, и A первым даёт проверяемый результат; (3) B не противоречит уже сделанным архитектурным решениям, а упорядочивает их; (4) C нельзя принять или отклонить, пока нет игроков и измерений — значит, он не может быть целью текущего цикла.

Для текущего цикла (PROJECT) продукт — ясность: подтверждённое видение, реестр эпиков под B с A внутри, реестр открытых вопросов.
