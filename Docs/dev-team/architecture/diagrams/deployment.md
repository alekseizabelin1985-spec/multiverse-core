# Развёртывание

**Вопрос читателя: что и где слушает, какие профили композиции что поднимают и что наружу не публикуется?**

Дата: 2026-09-11 · system-architect#1
Иллюстрирует: [`../infrastructure.md`](../infrastructure.md) §1.2–§1.4, §5, [`../overview.md`](../overview.md) §13, ADR-001 (число процессов — параметр деплоя), ADR-005 дополнение 2 (нативный рантайм модели), ADR-021 (MinIO из исходников).
Проверено по дереву: `docker-compose.yml`, `docker-compose.bot.yml`, `docker-compose.legacy.yml`, `build/versions.env`, `build/{Dockerfile,minio.Dockerfile,redpanda-init.sh,minio-init.sh}`, `Makefile`, `scripts/compose-lint.sh`, `scripts/llm-server.ps1`.

Все публикуемые порты привязаны к `127.0.0.1` — это правило проверяется линтером композиции, а не соблюдается на глаз. Наружу машины не смотрит ничего.

## Что публикуется и что нет

| Что | Порт | Публикуется |
|---|---|---|
| gateway | 8088 | да, только на `127.0.0.1` |
| core | 8090 | **нет**, только `expose`; доступ — через прокси шлюза |
| memory | 8082 | да, профиль `memory` |
| telegram-bot, здоровье | 8089 | да, профиль `bot` (будущее) |
| Redpanda, внешний слушатель | 19092 | да, для `go run` и `mvctl` на хосте |
| Redpanda, админ | 9644 | да |
| Redpanda, внутренний слушатель | 9092 | **нет**, только сеть композиции |
| Redpanda Console | 8092 | да, только профиль `dev` |
| MinIO API | 9000 | да |
| MinIO Console | 9001 | **нет** |
| Qdrant | 6333, 6334 | да, профиль `memory` |
| Neo4j Bolt | 7687 | да, профили `memory` и `legacy` |
| Neo4j Browser | 7474 | **нет** |
| Ollama | 11434 | да, профиль `gpu` |
| llama-server | 1234 | вне композиции, слушает `127.0.0.1` |
| init-контейнеры, chromadb, narrative-orchestrator | — | **ничего** |

Консоли MinIO и Neo4j не публикуются вовсе, потому что публикация порта не умеет зависеть от профиля: сервис у консоли общий с рабочим портом, и выбрана строгая трактовка правила о консолях. Оператору остаётся `docker compose port` (с `COMPOSE_ENV_FILES=.env,build/versions.env` в оболочке — без неё compose не видит версий образов, T-412) или собственный локальный файл переопределения, который не в Git.

## Правила, зашитые в линтер композиции

1. У каждого образа явный тег из `build/versions.env`, никакого «последнего».
2. Каждый публикуемый порт привязан к `127.0.0.1`.
3. Никаких паролей по умолчанию: секрет появляется только как обязательная переменная.
4. Токен бота доходит только до сервиса бота.
5. Плагины Neo4j отсутствуют, список источников Ollama не подстановочный, адрес Ollama не «все интерфейсы».
6. Сервиса `llama-server` в композиции нет, а адрес модели указывает на петлевой интерфейс, `host.docker.internal`, сервис композиции или частную сеть — никогда на публичный адрес.
7. Файл, который загружается всегда, должен интерполироваться на чистой машине; всё, что требует чужого секрета, — в файл своего профиля.

## Что здесь будущее

- **Профиль `bot`** — сервис описан, бинарника нет; `make up PROFILES=bot` поднимет стек и упадёт на старте контейнера бота.
- **Профиль `legacy`** — не поднимается, пока не выбран тег образа Chroma. Это осознанный громкий отказ, а не забытая строка.
- **Содержимое `gateway`, `core`, `memory`** — процессы поднимаются и отвечают на проверку здоровья, но контексты внутри пусты, кроме механики.

Формулировки, записанные при рисовании (до сверки):

1. **Профили `bot` и `legacy` живут в отдельных файлах** (`docker-compose.bot.yml`, `docker-compose.legacy.yml`), и Makefile добавляет нужный файл сам, когда профиль активен. `overview.md` §13 и `infrastructure.md` §1.3 перечисляют профили так, будто все они в одном файле.
2. **Адрес HTTP-сервера у всех трёх процессов берётся из `MV_CORE_ADDR`.** Compose дублирует туда `MV_GATEWAY_ADDR` и `MV_MEMORY_ADDR`; сам бинарник вторых двух переменных не читает. Документы называют три переменные как три источника.
3. **`MV_MODE` и `MV_BUS` передаются в контейнеры и не читаются.** Режим и вид шины `cmd/multiverse` берёт из флагов `--mode` и `--bus`, а compose флагов не передаёт. Словари значений тоже разные: манифест объявляет `MV_BUS=redpanda`, флаг принимает `kafka` или `memory`.
4. **`MV_LLM_URL` обязателен и не имеет значения по умолчанию** — намеренно, чтобы адрес модели не оказался третьим источником истины. `overview.md` §13 приводит его как готовое значение.
5. **Тома целевого стека названы иначе, чем as-is** (`redpanda-data` против `redpanda_data` и так далее), чтобы старые данные, включая учётные записи прежнего MinIO, не примонтировались молча при первом запуске. В `overview.md` §19 это описано как шаг миграции, но не как правило именования, а именно оно и защищает.
6. **Проверка здоровья контейнера — сам бинарник.** В образе нет ни оболочки, ни `curl`, поэтому `multiverse health --url ...` проверяет процесс сам. Это влияет на диагностику: контейнер, не сумевший собраться, не даст никакого вывода проверки.
