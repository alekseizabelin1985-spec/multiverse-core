Правило: **любое изменение контракта из этого файла — только через системного архитектора** (раздел «Запросы на изменение контракта» в `plan/ownership.md`) с оценкой влияния на все команды-потребители. Внутри эпика команда свободна.

**Правило приоритета при расхождении контракта и принятого кода (v0.5).** Когда контракт и реализация, прошедшая ревью и приёмку, расходятся, спор решается по существу, а не по старшинству документа: побеждает та форма, у которой есть доказательство (тест, мутация, зонд на живом стенде). Если побеждает код — правится **этот файл**, и правка сопровождается объяснением «почему так, а не иначе», чтобы следующий исполнитель не восстановил прежнюю форму «по документу». Если побеждает контракт — заводится задача на код с меткой `contract-change`. Молча оставлять расхождение нельзя: тестовый набор не может закреплять поведение, о котором контракт молчит.

## 1. C-01 · EPIC-001 → все: конверт события, реестр типов, библиотека шины и журнала

Тип: общая модель + библиотека · Версия: 1 (v1.1 — дополнения 2026-09-09; **v1.2 — границы старта и остановки, сведение волны 0**; **v1.3 — состав `Deps` по коду и приватность `dead_letters`, T-409**; v1.3a — текст про `Deps` по T-410; **v1.4 — `Dedup.Has/Add`, id из причины, источники конструкторов, таймеры шины, место `membus`; T-416, ADR-027**; **v1.5 — кодирование id из причины, генератор при опции, перехват паники обработчика; T-425**; v1.5a — «Заглушка» и §17 приведены к T-418) · Владелец: EPIC-001 (после — system-architect)

### Интерфейс
- `eventbus.Event{ID, Type, Timestamp, Source, World *WorldRef, Scope *ScopeRef, Meta Meta, Payload map[string]any, Relations []Relation}`; `Meta{SchemaVersion int, CorrelationID, CausationID, CausationType string, ActorKind string, Agent *AgentRef, Replay bool, Locale string, GMPath string}` (ADR-007 п. 1).
- Конструкторы: `NewRoot(type, source, worldID string, scope *ScopeRef, actorKind string, payload map[string]any) Event`; `Derive(parent Event, type, source string, payload map[string]any, opts ...DeriveOption) Event` (копирует `Meta.CorrelationID`, `ActorKind`, `Locale`, `GMPath`; ставит `CausationID = parent.ID`; `WithAgent(AgentRef)`). **v1.4 (ADR-027):** `WithCauseID(parts ...string) DeriveOption` — id события выводится из причины: UUIDv5 в пространстве имён платформы (константа `eventbus`) от `causation_id`, типа и `parts`. Одна и та же причина, тип и части дают один id при повторе публикации, после рестарта и в replay (NFR-061), независимо от `--id-source`. Опция — для события, которое издатель публикует не более одного раза на `(причина, тип, части)`: обязательна для `narrative.output` (T-229) и `encounter.started/ended` (`parts` — id встречи, C-05 v1.4 п. 4–5), рекомендуется для фактов State (`parts` — id сущности), для `dice.rolled` допустима только с индексом броска в `parts`. В `NewRoot` опция — ошибка программиста (паника в конструкторе): у корня нет причины. *Почему:* двухшаговый `Dedup` не снимает дубль при потерянном подтверждении публикации — повтор уходит под новым id, и потребитель, гасящий дубли по id, его не узнаёт (ревью #2 T-220, зонд P4). **v1.5 (T-425; ADR-027, «Уточнение исполнения» п. 1–2).**
  - **Кодирование.** Имя UUIDv5 — компоненты `causation_id`, тип, `parts…` по порядку, каждый записан как `<длина в байтах UTF-8>:<компонент>`, в пространстве `eventbus.CauseIDNamespace` (`46a1a952-5297-584b-9430-d9895b6db112`). Разделителя нет: части — произвольные строки, и любой разделитель внутри части склеил бы `("a|b")` с `("a", "b")`. Кодирование — часть контракта: его держат семь golden-значений `cause_id_test.go`. Смена кодирования или пространства имён меняет id всех производных событий и ломает побайтный replay записанных журналов (NFR-061), поэтому она допустима только с новым пространством имён и ADR.
  - **Генератор.** `Derive` применяет опции до генератора и берёт `nextID()` только при пустом id. С опцией генератор не вызывается, и повторы и перестроения не сдвигают последовательность id остальных событий процесса.
  - **Причина без id.** Паника опции на причине без id остаётся: у корня это ошибка программиста. Обработчик, который может работать без валидации при чтении, проверяет `ev.ID != ""` до `Derive(…, WithCauseID(…))`: запись `Error` и отказ от ответа. Последняя линия — перехват паники в `Delivery` (гарантии ниже).
- Шина: `Bus{Publish(ctx, Event) error; Subscribe(ctx, topic, group string, h Handler) error; Close() error}` — топик выбирается реестром по типу; `Handler func(ctx, Event) error` — ошибка → повтор ×3 (100/500/2000 мс) → `dead_letters`.
- **Журнал (новое, v1.1)**: `Journal{ReadRange(ctx, topic string, from, to int64, h Handler) (next int64, err error); Tail(ctx, topic string, from int64, h Handler) error; End(ctx, topic string) (int64, error)}` — чтение по офсетам без consumer group (State — свой курсор, ADR-011 п. 4; Swarm и Gateway — догон с курсора снапшота, C-14). `End` = офсет следующего сообщения (high watermark): признак «конца журнала» для выхода из `replay` в `live` = `позиция ≥ End − 1` по всем читаемым топикам; отдельного `Bus.Lag()` **нет** (запрос gateway §14 п. 9 закрыт этим методом). `Position{Topic, Offset}`; `PositionFromContext(ctx) (Position, bool)` — адаптер кладёт позицию перед вызовом handler (и в `Subscribe`, и в `Journal`). Реализации: kafka-go (`SetOffset`/`ReadLastOffset`), `membus` (индексы очередей) — одна семантика, общий contract-тест.
- **Дедуп (новое)**: `eventbus.Dedup` (LRU по `event.id`, по умолчанию 10 000; `Seen(id) bool`; сериализуется в снапшот потребителя) — production-пакет; `testkit.Dedup` — псевдоним. **v1.4 (ADR-027):** рядом с `Seen` — двухшаговая форма `Has(id) bool` (спросить, окно не меняется) и `Add(id)` (запомнить). Потребитель, у которого побочный эффект — одна публикация, запоминает событие только после её успеха; иначе упавшая публикация теряется без следа — ни текста, ни `dead_letters`, ни лога (ревью #1 T-220, Mi-1). `Seen` остаётся для тех, кому запоминание до обработки — меньшее зло (агент встречи: повтор задвоил бы кости). Предусловие двух шагов — обработчик не вызывается конкурентно для одного события; обе реализации шины это соблюдают. Своё окно без `IDs`/`Restore` у stateful-потребителя — дефект (C-14 v1.2).
- Реестр: `contracts.Lookup(type) (Spec{Topic, SchemaVersion, Schema, Policy}, bool)`; `contracts.Validate(Event) error`; `contracts.OwnershipRules` (см. C-02); список типов и топиков — ADR-007 п. 4; схемы — `schemas/events/<type>.v<n>.json`, JSON Schema 2020-12, библиотека **`github.com/santhosh-tekuri/jsonschema/v6`** (as-is `xeipuuv/gojsonschema` — только draft-07, не переносится).
- **Валидация при чтении (новое, SEC-16)**: `Subscribe` валидирует конверт и payload по схеме с флагом `MV_BUS_VALIDATE_ON_READ=true` (по умолчанию включено; невалидное → `dead_letters` без вызова handler). Политики топика (`Spec.Policy`): `player_events` — `actor_kind ∈ human|ci|sim`, `meta.agent == nil`; `llm_records`, `system_events(tick.*, agent.*)` — `meta.agent` обязателен для типов роя.
- Чтение payload: `event.Path()` (`shared/jsonpath`) без изменений; `eventbus.GetWorldIDFromEvent`, `GetScopeFromEvent` без изменений.
- Часы и рантайм (foundation §3–4): `shared/clock.Clock{Now()}`, `Timers{After, Every}`; `shared/runtime.Deps{Bus, Journal, Contracts, Clock, Timers, Mode, IDs, Log, Mux}` (**v1.3**), `runtime.Context{Name, DependsOn, Start, Stop, Health}`; необязательный `runtime.Routes{Routes(mux)}` вызывается до `Start`. **Полей `Store` и `Env` в `Deps` нет (v1.3, T-409).** Контекст, которому нужно объектное хранилище, сам создаёт клиент `objstore.New` со своими настройками, а переменные читает через объявления манифеста `shared/env` (`env.MinIOEndpoint.String()` и т. п.), никогда не через `os.Getenv`. *Почему так:* хранилище у контекстов разное — State пишет `entities-{world}` и `snapshots-{world}/state`, gateway только читает указатель, memory хранилище не нужно вовсе, — и общий экземпляр в `Deps` означал бы либо общие настройки, либо пустое поле с отказом в `Start`; окружение уже доступно через пакетные объявления манифеста, и второй путь через `Deps` стал бы вторым источником истины. `Mux` в контракт внесён, потому что уже используется: `serve.go` отдаёт контекстам mux своего единственного HTTP-сервера (`deps.Mux = srv.Mux`), на нём `swarm`, `state` и `memory` монтируют `/v1/admin/*` и `/v1/context/*` (C-06, C-09). Доказательство — тип `Deps` в `shared/runtime/runtime.go` и `cmd/multiverse/serve.go`; решение оркестратора 2026-09-11 (T-409). `serve.go` заполняет все поля `Deps` (T-410). `Contracts` — `contracts.Default()`. `Bus` и `Journal` — один и тот же транспорт, выбранный `MV_BUS`/`--bus`: `kafka` → `eventbus.NewKafka` по `MV_KAFKA_BROKERS`, `memory` → `membus` с полным списком топиков реестра; у обоих `SkipValidateOnRead = !MV_BUS_VALIDATE_ON_READ`. Транспортом владеет процесс: контекст его не закрывает, процесс закрывает его после `Stop` последнего контекста на каждом пути выхода через `return`, включая неудачный старт; паника в `Start` — исключение до `recover` в `runtime.StartAll` (T-415). *(v1.3a, T-410: правка текста, а не контракта — Go-API `Deps` не менялся, а C-01 v1.3 уже требовал это состояние и называл пустые поля пробелом кода.)* `time.Now()` в `internal/*` запрещён линтером; `EventClock`/`NullTimers` для replay — `internal/replay` (EPIC-002), внедряет `cmd/multiverse`.
- **Источники конструкторов (v1.4).** `NewRoot`/`Derive` берут id, время корня и версию схемы из глобальных источников пакета: `SetIDSource`, `SetClock`, `SetRegistry` (`shared/eventbus/sources.go`). Их ставит процесс (`cmd/multiverse`) один раз до `Start` первого контекста — из тех же объектов, что кладёт в `Deps` (`IDs`, `Clock`, `Contracts`), а в `--mode=replay` — `EventClock` (T-060). Контекст их не ставит и не меняет; тест ставит свои через те же функции. *Почему записано:* сегодня процесс их не ставит. `--id-source=sequence` меняет только `Deps.IDs`, которым не пользуется ни один конструктор, — настройка применяется молча не туда, класс T-408. Пока контексты пустые, это безвредно; сломается на первой схеме v2 (версия схемы по умолчанию 1) или в replay (время и id корней — с настенных часов и из UUID). Правка — EPIC-002 **T-055**: срок — первый настоящий издатель, файл `cmd/multiverse` — через tech-lead#1; T-060 заменяет часы источника на `EventClock` в replay.
- **Таймеры повторной доставки (v1.4).** Паузы повтора обработчика (100/500/2000 мс) шина отмеряет транспортными таймерами. Процесс даёт шине реальные таймеры (`clock.RealTimers`) в любом режиме, а `NullTimers`/`EventClock` — только контекстам. Тест вправе дать шине ручные таймеры и двигать их сам. Паузы не входят в байты событий, число попыток и порядок — входят и сохраняются. *Почему:* в replay доменное время идёт от событий, и таймер, который никто не двигает, превращает первую повторную доставку после ошибки обработчика в зависание до отмены (ревью #1 T-410). Освободить шину от доменного времени дешевле, чем учить `NullTimers` отпускать паузы шины. Правка — EPIC-002 **T-060**: из двух вариантов её DoD выбран «шина освобождена».

### Гарантии
At-least-once; порядок внутри топика (одна партиция); публикация неизвестного/невалидного типа → ошибка (не публикуется); reader `MinBytes=1, MaxWait≤100ms`; дедуп по `Event.ID` — обязанность потребителя (`eventbus.Dedup`); `Journal.ReadRange` возвращает события строго по возрастанию офсета; `End` монотонен.

**Паника обработчика (v1.5, T-425; редакция «паника не ловится» заменена).** `Delivery.Deliver` перехватывает панику обработчика (`recover` вокруг вызова `h`) — и в `Subscribe`, и в `Journal`, у обеих реализаций, потому что обе читают через `Delivery`. Паника — дефект (NFR-012), а не временный сбой:
1. **Не повторяется.** Повтор выполнил бы обработчик ещё раз над состоянием, которое паника могла оставить наполовину изменённым, а детерминированная паника повторилась бы четыре раза.
2. **Событие сразу паркуется в `dead_letters`.** `attempts` — номер вызова, в котором была паника; ошибка — `eventbus.ErrHandlerPanic` (текст `eventbus: handler panic: <значение>`). Стек в `dead_letters` не пишется.
3. **Лог уровня `Error`** с полями события, `panic`, `stack` и `handled=false`. Это след, который считает метрика `service_panics` (NFR-012, `metrics.md`): сессия с паникой по-прежнему провалена. Перехват меняет последствие дефекта, но не прячет его.
4. **Офсет** после успешной записи в `dead_letters` коммитится, как у любого запаркованного события. Запись не удалась — ошибка, офсет не коммитится, как сегодня.

Перехват стоит только на границе доставки. Паника вне обработчика (в цикле чтения адаптера, в `Start` контекста — там `recover` даёт `runtime.StartAll`, T-415) по-прежнему роняет процесс. **Stateful-контекст**, который не может доказать целостность своего состояния после паники в своём обработчике, ставит собственный `recover` на своей границе и останавливает себя (`/health fail`), как State (`state-and-mechanics.md`, «Паника в worker'е»): шина не знает, чьё состояние испорчено, и решает только, что делать с событием.

*Почему не «падать со стеком»:*
- (а) at-least-once без коммита: событие, уронившее процесс, после рестарта доставляется снова и роняет его снова. Одна «ядовитая» запись кладёт процесс в цикл рестартов, а по ADR-001 в процессе живут все контексты, включая State. `dead_letters` заведён ровно для того, чтобы одно плохое событие не блокировало топик (ADR-007 п. 6).
- (б) путь по данным есть: `Derive(…, WithCauseID(…))` от конверта без id при `MV_BUS_VALIDATE_ON_READ=false` (ревью #1 T-417, Mi-2).
- (в) крэш-луп оставляет только стек в логах контейнера, а перехват — `Error`, метрику и само событие с причиной в `dead_letters`.

Код — задача EPIC-001 «перехват паники в `Delivery`» (`contract-change`): комментарий `Handler` в `bus.go`, README пакета («Паника не ловится», «Id из причины») и `foundation.md` §5 правятся вместе с кодом.

**Приватность `dead_letters` (v1.3, T-409).** Обёртка `DeadLetter` несёт исходное событие **целиком**, включая текст игрока (`player.said.text`), и ограничивает только размер тела, которое не удалось прочитать: без исходного события инцидент не разобрать. Поэтому топик разбора живёт по правилам приватности доменных топиков — только `player_id`, никаких внешних идентификаторов, — и скан NFR-041 проверяет его наравне с ними. *Почему записано здесь:* перечень политик топиков этот топик не называл, и он выглядел служебным, то есть вне правил (`diagrams/dfd.md`).

**Старт подписки (v1.2).** Подписка **новой** consumer group начинает чтение с **первого офсета** топика, а не с конца. Это гарантия контракта, а не свойство одной реализации: kafka-адаптер задаёт `StartOffset: kafka.FirstOffset`, `membus` держит курсор группы, начинающийся с нуля, — обе половины C-01 ведут себя одинаково, и contract-тест шины это закрепляет. Следствие, ради которого гарантия и названа: потребителю **не нужно** рукопожатие «подписка готова» — событие, опубликованное между вызовом `Subscribe` и моментом регистрации группы, будет доставлено. Рукопожатие в контракт **не** вводится (канал готовности в `Subscribe` был бы самым дорогим из рассмотренных вариантов); подробности и условия пересмотра — ADR-022. *Почему так:* без этой гарантии каждый потребитель городил бы свой опциональный интерфейс готовности, который ни одна реализация шины не реализует, — ровно это и произошло в `testkit/state` и оттуда удаляется.

**Остановка (`Close`, v1.2).** `Close` — упорядоченная остановка, а не аварийный обрыв: каждая подписка `Subscribe` и каждый `Tail`, идущие в этот момент, возвращают **`nil`**, а не ошибку. Три вещи контракт **сознательно не обещает**, и потребитель не имеет права на них опираться:
1. **Сколько событий будет доставлено после вызова `Close`** — от нуля до размера буфера предвыборки реализации. Измерено на одном и том же сценарии (40 событий в хвосте, `Close` под работающим чтением): `membus` доставляет 3 из 40, брокер — 40 из 40 (kafka-go дочитывает очередь до `QueueCapacity`≈100). Обе реализации соответствуют контракту, обе возвращают `nil`. Тестовый набор **не должен** закреплять число: свойство, которое он вправе проверять, — «все подписки вернули `nil`» и «событие, опубликованное после возврата `Close`, не доставлено никому».
2. **Коммит события, обработчик которого вернул `nil` при отменённом контексте.** `membus` коммитит всегда, kafka-адаптер в измерении дал 3 перевыдачи из 5 (гонка `select` в kafka-go). Это чистый at-least-once: «обработчик вернул `nil`» ≠ «офсет зафиксирован». Обработчик обязан быть идемпотентным (`eventbus.Dedup`) — на этом уже стоит вся платформа.
3. **Отмена контекста обработчика при `Close`.** Контекст, переданный в `Handler`, при `Close` **не** отменяется по контракту (заявка отклонена на MVP-1 — ADR-023): обработчик посреди PUT в объектное хранилище должен доводить запись до конца, иначе C-02 «факт публикуется после успешной записи» перестаёт держаться.

**Детерминированный якорь для тестов (v1.2).** Если тесту нужна точка «прочитано ровно до сюда», её даёт журнальная половина контракта, которую реализуют обе шины: `End` → `ReadRange(from, End)` (либо `Tail` с закреплённым офсетом), а не `Close` и не подсчёт доставок подписки. *Почему так:* `Subscribe` блокируется до конца подписки, момент регистрации группы находится внутри невернувшегося вызова, и выразить его через `Bus` нельзя вовсе; связка «закрепить офсет → просигналить → читать с него» окна потери не имеет и правки контракта не требует.

### Заглушка для потребителей
**Статус `membus` (v1.4, T-416; ADR-001 доп. 2026-09-11).** `membus` — **вторая реализация C-01, а не двойник**. Его гоняет тот же contract-тест, что kafka-адаптер, и он же — транспорт поддерживаемого режима бинарника `--bus=memory` (`foundation.md` §2, ADR-010). Реализация живёт рядом с другой реализацией: пакет переехал в **`shared/eventbus/membus`** (T-418, метка `contract-change`; на момент переезда — 15 импортёров: 14 тестов и `cmd/multiverse/bus_memory.go`). Узкое временное исключение линтера для `bus_memory.go` (ровно пакет `shared/testkit/membus$`) снято тем же T-418: правило «production не импортирует `shared/testkit`» снова знает одно исключение — хук `cmd/multiverse/fake_contexts.go` (T-255), уходящий с EPIC-003 I1. *Почему переезд, а не узаконенное исключение:* иначе у одного пакета остаются два статуса — «заглушка для потребителей» по этому блоку и «транспорт режима» по `foundation.md` §2, — а карта владения называла единственным импортом testkit файл, которого нет. Такое расхождение должен развести контракт, а не `.golangci.yml`, тем более что исключения depguard сравниваются по префиксу и уже дважды оказывались шире заявленного (ревью #1 T-410 Mi-3; правила `shared-testkit-*`, T-415). Для потребителей ничего не меняется, кроме пути импорта.
`membus` (`shared/eventbus/membus`, с T-418) — in-memory шина **и журнал** с той же семантикой (порядок, офсеты, дубли по флагу `--chaos=duplicate`, `End`); `contracts` со схемами доступен с первой волны EPIC-001 — команды пишут свои схемы в `schemas/events/` (владелец типа) и регистрируют через PR в `shared/contracts/registry.go` (ревью system-architect). ## 2. C-02 · EPIC-002 → EPIC-003, EPIC-004: предложения и факты состояния

Тип: события · Версия: 1 (v1.1 — уточнения семантики; v1.2 — `forget`/`abandoned`; **v1.3 — правило «одна сущность — один набор изменений»**; **v1.4 — таблица владения одним файлом, связка «путь ↔ причина», статус в то же значение; T-409**) · Владелец: EPIC-002

### Интерфейс
- Вход State: `entity.create.proposed`, `entity.update.proposed` — payload по `api-contracts.md` §2.3.4 (`proposal_id`, `changes[]{entity, expected_version?, ops[]{op: set|inc|append|remove, path, value}}`, `atomic`, `cause`); `meta.agent` обязателен от агентов; `meta.actor_kind` наследуется.
- Выход State: `entity.created {entity, version:1, attributes}`, `entity.updated {entity, version, changed[]{path, old, new}, cause, proposal_id, applied_at}` (по одному на сущность), `entity.update.rejected {proposal_id, reason, entity?, details{expected_version, actual_version, invariant_id}}`; `reason ∈ version_conflict | unknown_entity | level_violation | law_violation | invalid_op | dead_entity | duplicate_entity` (`duplicate_entity` — для `entity.create.proposed` с уже существующим id; расширение enum, совместимо).
- **Семантика (v1.1)**: `rest` предлагает gateway (`cause=rest`, `set hp = hp_max`), State отклоняет при активной встрече (`law_violation inv-…`); `atomic=false` — отказ по каждой сущности отдельно (по одному `rejected`), `atomic=true` — один `rejected` на пакет; `applied_at` и `timestamp` фактов = `timestamp` предложения (время из событий, ADR-003 п. 6); для `append` путь в `changed[]` — путь элемента (`inventory[n]`); `expected_version` обязателен для путей `hp`, `status`, `inventory`, `position` игрока/NPC в бою (ADR-013 п. 1).
- Правило владения (кто что может предлагать) — `data-model.md` §4; проверка `level_violation` по `meta.agent.level` и `owned_entity_types`; **`contracts.OwnershipRules`** (`shared/contracts/ownership.go`) — **единственный источник (v1.4, ADR-025)**: копии нет, теста равенства нет — сравнивать не с чем. `shared/agent/levels.go` (EPIC-003, T-202) своей таблицы владения не держит: вид «какие типы сущностей у уровня» валидатор блупринтов получает от вызывающего, собранный из `contracts.OwnershipRules`. State читает только `contracts.OwnershipRules`. Порядок изменения строк — §16 п. 6. *Почему так:* прежняя редакция называла истиной `shared/agent/levels.go`, которого в дереве нет, а фактической истиной служила «копия» — ровно то, что процедура запрещала; кроме того, в таблице есть строки без агента (`gateway`, `author`, `system`), которым не место в пакете роя, а «экспорт при сборке реестра» развернул бы зависимость фундамента на пакет роя (`diagrams/domains.md`).
- **Связка «путь ↔ причина» (v1.4).** Таблица — декартово произведение путей и причин, поэтому она шире нормы: строка `gateway` формально пропускает `set status` с `cause=move`. Норма — текст C-02: `status` — только переход `alive → abandoned` с `cause=forget`, `hp` — только с `cause=rest`, вне встречи и не выше `hp_max`. Каждая реализация State проверяет её **поверх** таблицы — так и сказано в комментарии `ownership.go`; таблица, прочитанная без этого абзаца, выглядит самодостаточной, и это ловушка для автора `internal/state/ownership.go` (T-056; `diagrams/seq-onboarding.md`).
- **Покинутый персонаж (v1.2, З-2, FR-061)**: `cause` дополнен значением `forget`. Переход `status: alive → abandoned` предлагает **только gateway** (`entity.update.proposed {changes: [{entity: player, expected_version, ops: [{op: set, path: status, value: abandoned}]}], atomic: true, cause: forget}`, без `meta.agent`, `meta.actor_kind` сессии) в каскаде `/forget` (C-04); строка gateway в `OwnershipRules` дополнена `Character.status → abandoned` и `Group.leader_id`. State: предложение от агента (`meta.agent` есть) → `level_violation`; над `dead`/`ascended_final` → `dead_entity` (терминальные не переходят в `abandoned`; `dead` уже исключён из scope и целей — FR-023); `abandoned` — терминальный статус: правило `dead_entity`, inv-01 (`dead_does_not_act`), `NPCTarget` и таблица видимости стража трактуют `status ∈ dead|abandoned|ascended_final` одинаково (C-03: `Actor.Status ≠ alive` исключается из целей). Факт — `entity.updated {changed: [{path: status, old: alive, new: abandoned}], cause: forget}`; потребители (swarm, gateway read-model, memory) обрабатывают его как `status=dead` в части scope/целей/раундов, но `narrative.output kind=death` **не** генерируется. Если персонаж в момент `/forget` в статусе `creating`, gateway публикует то же предложение при получении `entity.created` для `player_id` без связки.
- **Одна сущность — один набор изменений в одном предложении (v1.3, сведение волны 0).** Пакет `changes[]`, называющий одну сущность (по `entity.id`) дважды, State отвергает **целиком** — `entity.update.rejected {reason: invalid_op, entity: <повторённая>}`, независимо от `atomic`. Издатель обязан слить операции этой сущности в один набор. *Почему так:* у такого пакета нет исхода, разрешённого C-02. Применить наборы по очереди — значит опубликовать два `entity.updated` на одну сущность, причём под одной версией (зонд ревью #1 T-017: два набора по `player-A` — `inc hp -1` и `inc hp -2` — дали hp 8, версию 2 и два факта, первый из которых сообщал 10→9, второй 10→8), что нарушает «версия строго +1 на сущность» и «один факт на сущность» (§4.5 п. 12). Применить как один — значит молча потерять то, о чём просил первый набор. Схемой правило не выразимо: JSON Schema не умеет требовать уникальность по вложенному полю (`uniqueItems` сравнивает элементы целиком, а два набора по одной сущности различаются операциями), поэтому реестр такой пакет принимает и отвергнуть его обязана **каждая** реализация State — заглушка это уже делает, T-056 встретит то же предложение. Детали шага — `state-and-mechanics.md` §4.5 п. 1а.
- Read-model: потребители строят проекции из `entity.created/updated`; прямого HTTP к State нет. Начальная загрузка проекции — чтение указателя `snapshots-{world}/state/latest.json`, затем объекта снапшота через `shared/objstore` (только чтение; C-14).

### Гарантии
Факт публикуется после успешной записи в MinIO; `version` строго +1 на сущность при непустом `changed[]` (при `changed=[]` версия не меняется, факт публикуется — ход засчитан); `atomic=true` — все или ничего; повтор предложения с тем же `proposal_id` не применяется второй раз (факты досылаются, если не были опубликованы); латентность применения p95 ≤ 50 мс при ≤ 50 сущностей/scope (без учёта шины).

**Статус в то же значение (v1.4, T-409).** `set status` в значение, которое у нетерминальной сущности уже стоит, — не отказ: изменения нет, факт публикуется с пустым `changed[]`, версия не меняется — ход засчитан, движения не было, по тому же правилу, что любое предложение без изменений (C-04 v1.2). Матрица переходов статуса применяется только к **изменениям**, то есть к тому, что осталось после `ApplyOps`. Для терминальной сущности (`dead|abandoned|ascended_final`) по-прежнему действует `dead_entity`. *Почему так:* повтор действия — второй `/forget`, пришедший раньше факта первого, или пакет агента, предложенный заново после конфликта версий (C-05 v1.3), — не должен превращаться в ошибку игроку. **Код расходится:** `entity.StatusTransitionAllowed(x, x)` отвечает `false`, и это закреплено тестом (`shared/entity/entity_test.go`, строка `alive→alive`). Двойник State правилу уже соответствует, потому что `ApplyOps` отбрасывает `set` без изменения до проверки матрицы (`shared/testkit/state/apply.go`, `statusRefusal`), — ловушка ждёт настоящую реализацию, если та позовёт матрицу на операциях предложения, а не на изменениях. Правка кода — EPIC-002 **T-056** (метка `contract-change`): `StatusTransitionAllowed(x, x) = true` для нетерминального `x`, строка теста `alive→alive` меняет ожидание, `abandoned→abandoned` остаётся `false`.

### Заглушка для потребителей
`testkit/state.FakeState` — применяет предложения в память и публикует факты в `membus` без инвариантов (флаг `WithInvariants()` включает набор inv-01…inv-10).

### История изменений
v1 — 2026-09-09: по `api-contracts.md` §2.3.4 (ADR-003). v1.1 — 2026-09-09: семантика `rest`/`atomic=false`/`applied_at`/`append`, `duplicate_entity`, источник `OwnershipRules`. v1.2 — 2026-09-09 (сведение 3): `cause=forget`, переход `alive → abandoned` от gateway, `abandoned` терминальный, строка gateway в `OwnershipRules`. **v1.3 — 2026-09-11 (сведение волны 0, architect#1): пакет, называющий одну сущность дважды, отвергается целиком (`invalid_op`); правило нормативно для всех реализаций State, схемой не выражается.** **v1.4 — 2026-09-11 (T-409, architect#1): единственная истина таблицы владения — `shared/contracts/ownership.go` (ADR-025); связка «путь ↔ причина» нормативна поверх таблицы; `set status` в то же значение у нетерминальной сущности — факт без изменений (правка кода — T-056).**

## 3. C-03 · EPIC-002 → EPIC-003: библиотека механики и RNG (Go-контракт)

Тип: общая модель (Go API) · Версия: 1 (v1.1 — совместимые дополнения; **v1.2 — сигнатуры приведены к реализованным формам `state-and-mechanics.md` §5.1, ADR-024**) · Владелец: EPIC-002

### Интерфейс
```go
package mechanics
type Rules struct{ … }                                   // загружено из rules/dark-forest.yaml (RulesDocument, data-model §6.3)
func Load(path string) (*Rules, error)
func LoadBytes(b []byte) (*Rules, error)                                 // v1.1
type Actor struct{ ID, Type string; HP, HPMax, Atk, Def int; Dmg, Flee string
                   Status string /* alive|dead|abandoned|ascended_final */
                   Participation string /* active|idle|out_of_combat; "" = active; только player */
                   LastDamager string /* только npc */ }   // v1.1: Participation, LastDamager
func (a Actor) Alive() bool                                              // Status == alive; три терминальных статуса отвечают одинаково (C-02 v1.2)
type Action struct{ Kind string /* attack|flee|npc_attack|rest|free_attack */; Actor, Target string; LivingEnemies int }   // v1.2: LivingEnemies (порог побега)
type Outcome struct{ Hit, Critical, Fumble, TargetDead bool; Natural, Damage, Threshold int; Success *bool; HPBefore, HPAfter int; Loot []Item; FreeAttack bool }   // v1.2: FreeAttack
type Roll struct{ Index int; Formula string; Seed uint64; Result, Natural int; Purpose string }
type ProposedChange struct{ Entity entity.Ref; ExpectedVersion *int64; Ops []entity.Op; Cause string }   // v1.2

func (r *Rules) Resolve(causeEventID string, rollIndexStart int, a Action, actors map[string]*Actor) (Outcome, []Roll, error)
func (r *Rules) NPCTarget(npc *Actor, candidates []*Actor) (*Actor, error)   // v1.2: канал ошибки; last_damager → min_hp → player_id asc; исключая idle/out_of_combat/dead|abandoned
func (r *Rules) Roll(causeEventID string, rollIndex int, formula, purpose string) (Roll, error)   // v1.2: ошибка; броски вне боя (шанс встречи, таблицы фона)
func (r *Rules) Stats(kind string) (Actor, bool)                        // v1.1: базовые статы NPC из rules
func Seed(eventID string, rollIndex int) uint64                          // SHA-256(eventID+":"+idx)[:8] BigEndian
func NewRNG(seed uint64) *rand.Rand                                      // math/rand/v2 PCG(seed, 0)
func (r *Rules) Invariants() []Invariant                                 // NFR-020 inv-01…inv-10; Invariant{ID, Where []string, Check func(StateView, touched) []Violation}  // v1.1: Where, StateView, Violation
func ActorFromEntity(e *entity.Entity, enc *entity.Entity) (*Actor, error)   // v1.2: сущность встречи вторым аргументом (nil — вне боя)
func ChangesFor(a Action, o Outcome, attacker, target *Actor, factEventID string) ([]ProposedChange, error)   // v1.2: ops для entity.update.proposed
func DiceRolledPayload(roll Roll, roller entity.Ref) map[string]any      // v1.2: ссылка на сущность вместо строки
```
Вызывающий (агент встречи EPIC-003) публикует `dice.rolled` на каждый `Roll` (тип принадлежит EPIC-002, схема общая) через `Derive(cause, "dice.rolled", DiceRolledPayload(...))` **до** `combat.decided`, затем `combat.decided` (тип EPIC-003, §2.3.6) и `entity.update.proposed` из `ChangesFor` (рекомендация: один atomic-пакет на раунд; допускается по одному предложению на `combat.decided`).

**Почему сигнатуры v1.2 именно такие** (разбор ревью #1 T-015, решение оркестратора 2026-09-10, ADR-024; в спорных местах прав детальный дизайн §5.1, а v1.1 местами противоречил сам себе):
- `Roll` **возвращает ошибку**: формула и назначение приходят из блупринта региона (фоновые таблицы, `encounter_chance`), а не из кода под ревью, и могут быть невалидны. Функция без канала ошибки вынуждена была бы либо паниковать, либо возвращать «нулевой бросок», который вызывающий опубликует как настоящий.
- `ActorFromEntity` **принимает сущность встречи и возвращает ошибку**: `Participation` и `LastDamager`, которые v1.1 сам же и добавил в `Actor`, — факты **встречи**, а не игрока; из одной сущности игрока их не прочитать (две встречи ответят про одного волка по-разному). Ошибка — потому что актор без `hp`/`def` не должен молча получить ноль: это превратило бы дефект создателя сущности в бой по другим правилам. `nil` вторым аргументом — законное «вне боя».
- `DiceRolledPayload` **принимает `entity.Ref`, а не строку**: `dice.rolled.roller` по схеме — пара `{id, type}` (`EntityWithName`); из строки тип не выводится, и конструктор строил бы заведомо невалидный payload.
- `ChangesFor` **возвращает предложения и ошибку — в ОБОИХ документах**. `[]entity.Change` из v1.1 — это `changed[]` факта `entity.updated`, то есть результат, а не запрошенные операции; предложению нужны `ops` + `expected_version` + `cause`, это `ProposedChange`. Канал ошибки нужен и после реализации (T-053): функция может получить исход, несовместимый с действием, — трофей при живой цели, урон без попадания.
- `NPCTarget` **получает канал ошибки**: без него `nil` заглушки неотличим от «целей нет» (UC-008 A2), и вызывающий не может отличить «некого кусать» от «механика ещё не написана». **Это единственный пункт правки, требующий изменения кода** — задача EPIC-002 **T-053**.

**Состояние реализации на 2026-09-11 (T-409).** Форма v1.2 совпадает с кодом, содержание — пока не везде: `Resolve` и `ChangesFor` возвращают `ErrNotImplemented`, у `NPCTarget` ещё нет канала ошибки, у всех записей `Invariants()` `Check == nil`. Это задачи EPIC-002 **T-053** (`Resolve`, `ChangesFor`, `NPCTarget`) и **T-054** (проверки инвариантов); до них исход боя даёт `testkit/mechanics.FixedMechanics`, и форма предложения закреплена двойником встречи, а не механикой — при появлении `ChangesFor` их придётся сверить. Гарантия детерминизма уже держится на `Seed`/`NewRNG`, они написаны и покрыты тестом.
**Отдых — действие механики, а не боя.** `Action.Kind` знает пять видов (`attack|flee|npc_attack|rest|free_attack`), схема `combat.decided.action` — четыре, без `rest`. Отдых предлагает gateway (`entity.update.proposed cause=rest`, C-02 v1.1), и `combat.decided` он не порождает; издатель, опубликовавший решение боя об отдыхе, получит отказ схемы — это закреплено невалидной фикстурой (T-214) и является правилом, а не дефектом. «Действие» в схеме решения боя и «действие» в C-03 — разные множества (`diagrams/seq-combat-solo.md`).

### Гарантии
Чистые функции, без I/O и часов; детерминизм по `(causeEventID, rollIndex)`; `rules_version` в `Rules`; изменение чисел правил — правка YAML, не кода; сигнатуры **v1.2** (не v1) не меняются — форма, зафиксированная здесь, совпадает с реализацией `internal/mechanics` и с `state-and-mechanics.md` §5.1, и расхождение любого из трёх мест — дефект.

### Заглушка
`rules/dark-forest.yaml` с числами приложения A PRD доступен с первой волны EPIC-002; до готовности `Resolve` EPIC-003 использует **`testkit/mechanics.FixedMechanics`** (табличные исходы по seed) — подпакет `shared/testkit/mechanics`, не `shared/testkit/state` (см. §17).

### История изменений
v1 — 2026-09-09 (ADR-003). v1.1 — 2026-09-09: дополнения по ADR-012 (state §14 п. 3). **v1.2 — 2026-09-11 (сведение волны 0, architect#1): `Roll`, `ActorFromEntity`, `ChangesFor`, `DiceRolledPayload` приведены к формам §5.1 (реализованы в T-015); `NPCTarget` получил канал ошибки (правка кода — T-053); `ProposedChange` внесён в контракт; двойник механики — `shared/testkit/mechanics`. ADR-024.**

## 4. C-04 · EPIC-004 → EPIC-003, EPIC-002: действия игрока, группа, раунд

Тип: события · Версия: 1 (v1.1 — лидерство и каскад `/forget`; **v1.2 — `scope` не предлагается при движении**; **v1.3 — конец встречи для потребителя, T-416**) · Владелец: EPIC-004

### Интерфейс
`player.entered_region`, `player.left_region`, `player.looked`, `player.attacked`, `player.flee_attempted`, `player.rested`, `player.said`, `player.defended {cause: player|round_timeout}` — payload §2.3.1; `group.created/joined/left/leader_changed/disbanded`, `group.entered_region/left_region` — §2.3.2 (перемещение группы — **только** `group.entered_region`, ADR-007/overview §20 п. 7); `round.opened {scope, encounter, round{seq}, expected[], deadline_at}`, `round.closed {round{seq, close_reason}, acted[], auto_defended[], idle[], closed_at}` — §2.3.3. Все — `meta.correlation_id = id` (корень), `meta.actor_kind` сессии, scope игрока/группы.
Сопутствующие предложения от gateway: `entity.create.proposed` (player, group), `entity.update.proposed` (position, scope, group_id, members, `members[].participation`) — по C-02; `rest` — `entity.update.proposed cause=rest` (C-02 v1.1).
**`scope` не путешествует вместе с `position` (v1.2, сведение волны 0).** При движении (`player.entered_region`/`left_region`, `group.entered_region`) предлагается **только** `position`. *Почему так:* `scope` соло-игрока — это `{id: player-X, type: solo}`, и вход в регион его не меняет; `scope` участника группы — `{id: g-N, type: group}`, и перемещение группы его тоже не меняет. Предложить `scope` значило бы отправить набор изменений, который ничего не меняет: State опубликует факт с пустым `changed[]` и той же версией (C-02), потребители read-model получат «событие ни о чём», а версия перестанет быть признаком движения. `scope` меняется **вместе с членством в группе** — `group.created/joined/left/disbanded`, одним atomic-пакетом с `group_id` и `members[]`, где inv-06 (`scope ⇔ group_id ⇔ members`) как раз и требует согласованности. Заглушка `testkit/gateway.Harness` реализует это правило.
**Семантика раунда (уточнение)**: открывающие действия — `attack | flee | defend | group.leave`; `say` в scope `group` **не** открывает раунд и не входит в `acted[]` (UC-016 E2; BA закрепляет в FR-025); `group.leader_changed {cause: death}` при смерти лидера — старейший `alive` по `joined_at` (предложение ADR-020 п. 8, BA — BR-13).
**Лидерство и группа без лидера (v1.1, З-4, BR-13 v0.4)**: `cause` в `group.left`/`group.leader_changed` ∈ `leave | death | forget`; если после выхода/смерти/отвязки лидера живых (`alive`) участников нет — gateway предлагает `set leader_id = null` (`entity.update.proposed`, тот же atomic-пакет) и публикует `group.leader_changed {leader: null, cause}`; группа остаётся без лидера до `group.disbanded`; `enter`/`leave` группы (перемещение) при `leader_id = null` → `409 no_leader` (проверяется раньше `not_leader`); личный `group.leave` участника допустим. `dead`/`abandoned` участники остаются в `members[]` (история), но исключаются из `expected[]`/`acted[]`, целей NPC и `participation=active` (координатор — `OnParticipantsChanged` по `entity.updated status`).
**Каскад `/forget` (v1.1, З-2, FR-061 п. 1–3; реализует `ForgetHooks`, порядок публикаций обязателен)**: (1) `outbox.DropForPlayer` (`pending → dropped`); (2) если персонаж `alive`: один `entity.update.proposed atomic=true cause=forget` — игрок `set status=abandoned` (+`expected_version`), а если он лидер группы — группа `set leader_id = <старейший alive | null>`; затем, если в группе, — `group.left {cause: forget}` и при смене лидера `group.leader_changed {cause: forget, leader: …|null}`; если участников-`alive` не осталось — по BR-13 (без лидера; `group.disbanded` — при выходе последнего участника); во встрече gateway ничего дополнительно не делает — агент встречи видит `entity.updated status=abandoned` и завершает встречу `players_out`, если игроков `alive` нет; (3) `session.End(forget)` → `analytics.session.ended {end_reason: forget}` (C-10); (4) физическое удаление связки (`links.db`). Персонаж `dead` — шаги (2) пропускаются (терминальный статус, FR-023); `creating` — см. C-02 v1.2.
**Конец встречи для потребителя (v1.3, T-416; C-05 v1.4 п. 4–6, ADR-026).** Read-model шлюза и координатор считают встречу законченной по первому из двух событий: факт сущности встречи со `state=resolved` или `encounter.ended`. В журнале факт всегда раньше события, но читатель двух топиков может увидеть их в любом порядке. Встреча, объявленная `encounter.started` раньше, чем пришёл `entity.created`, держится как «объявлена, сущности ещё нет»; это состояние всегда временное, потому что начало публикуется только после факта. Конец может прийти при открытом раунде — так уже бывает, когда смертельный удар нанесён первым действием раунда, — и без действия группы (существо убито вне встречи, C-05 п. 6). Координатор обрабатывает оба случая одним путём. Этот путь — часть дизайна раундов EPIC-004 (T-350/T-351); новых значений `close_reason` правило не вводит.

### Гарантии
Действие опубликовано только после валидации (§1.4) и идемпотентности `action_key`; `round.opened` публикуется до `202` на открывающее действие; `round.closed` публикуется до любых действий по раунду и содержит всё, что нужно механике (порядок `acted[]` — по времени приёма); `player.defended cause=round_timeout` публикуются до `round.closed`; в `solo` раунд = ход и `round.*` **не** публикуются; `player.said.text ≤ 500`, без внешних ID; `player_events` — только `actor_kind ∈ human|ci|sim`, без `meta.agent` (политика C-01).

### Заглушка
`testkit/gateway.Harness` — Go-клиент HTTP API и генератор `player.*` в `membus` для тестов EPIC-003/002 до готовности gateway; фикстуры `player-A/B/C`.

### История изменений
v1 — 2026-09-09. Уточнения 2026-09-09: `say` и раунд, лидерство при смерти (без изменения схем). v1.1 — 2026-09-09 (сведение 3): `cause=forget`, `leader: null`, `409 no_leader`, каскад `/forget` (расширение enum и nullable-поле до реализации схем в T-301). **v1.2 — 2026-09-11 (сведение волны 0, architect#1): `scope` не предлагается вместе с `position`; схемы без изменений, правило нормативно для T-301.** **v1.3 — 2026-09-11 (T-416, system-architect#1): конец встречи для потребителя — первое из «факт сущности встречи `state=resolved`» и `encounter.ended`; конец при открытом раунде и без действия группы — тот же путь, что смертельный удар первым действием раунда (ADR-026); схемы без изменений.**

## 5. C-05 · EPIC-003 → EPIC-004: нарратив и результаты механики для доставки

Тип: события · Версия: 1 (v1.1 — опциональные поля; **v1.2 — вид нарратива на `player.looked`**; **v1.3 — правила агента встречи: повтор при конфликте версий, след в сущности встречи, молчание на непринятое действие, порядок `encounter.started`; T-409**; **v1.4 — жизненный цикл встречи после факта, участие и пакет, ждущий потребитель, один NPC — одна встреча, признак конца обмена, порядок смерти, «Заглушка» по T-220; T-416, ADR-026**; **v1.5 — отказ не по гонке, отсрочка на время создания, «активна» и «занят», причины событий жизненного цикла и пакета Б1, «Заглушка» по T-419; T-425**) · Владелец: EPIC-003

### Интерфейс
`narrative.output` — §2.3.11 (`recipients[]`, `text`, `generated_by: llm|template`, `fallback_reason?`, `kind: turn|round|world_event|entry|death`, `round?`, `llm_output{event}`, `based_on[]`, `absence?`, `background_refs[]`, `filter{applied,status,filter_version}`, `locale`, `laws_version`, **`narrative_event_id?`** (= `id` события; дубль для удобства gateway, v1.1)); `meta.agent.level ∈ task` (personal-gm или group-narrator). `combat.decided` — §2.3.6 (gateway строит `Delivery kind=mechanics` из `outcome`/`hp`). `encounter.started/ended` — §2.3.7; **`encounter.started.round{timeout: "60s", idle_after_missed: 2}`** (опц., v1.1) — параметры раунда из блупринта `encounter-*` (`round` в `rules/dark-forest.yaml`); gateway использует их для таймера раунда, при отсутствии — `MV_GATEWAY_ROUND_TIMEOUT`/`MV_GATEWAY_ROUND_IDLE_AFTER_MISSED` как значения по умолчанию. Gateway обновляет read-model `encounter` и открывает первый раунд группы по `encounter.started`.

**Вид нарратива на осмотр (v1.2, сведение волны 0): `player.looked` → `kind=entry`.** Так говорят дизайн EPIC-001 §5 и задача, так это сделано и закреплено тестом в `testkit/swarm.FakeNarrator`; прежняя строка блока «Заглушка» (`turn`) — ошибка документа. *Почему так:* `turn` в C-05 описывает **исход схватки** (нарратив по `combat.decided`), а осмотр ходом боя не является: он не открывает раунд, не входит в `acted[]` и не порождает `combat.decided`. Правило распространяется на настоящую реализацию EPIC-003 (C4), а не только на заглушку: замена `FakeNarrator` не должна переоткрывать этот вопрос. Виды `turn`/`death`/`world_event` и их издателей закрепляет EPIC-003 в T-220.

**Агент встречи: конфликт версий, след действия, молчание, порядок (v1.3, T-409; решения оркестратора 2026-09-11).** Правила ниже распространяются на настоящего агента встречи EPIC-003, а не только на `FakeEncounter`, который им уже следует (T-219).
1. **Повтор при конфликте версий.** Агент встречи отвечает на действие по своему представлению о мире, которое пополняет фактами `entity.updated` по отдельной подписке. Получив на свой пакет `entity.update.rejected {reason: version_conflict}`, он обновляет представление по пришедшему факту и предлагает заново — ограниченное число раз (двойник: три попытки всего) и **под тем же `proposal_id`**: это та же попытка ответить на то же действие, кости не перебрасываются, `dice.rolled` и `combat.decided` повторно не публикуются, правило «одно действие — один пакет» сохраняется. Повторяется **только** `version_conflict`; остальные причины отказа — дефекты, а не гонки, и дефект, исчезающий на третьей попытке, хуже дефекта, видного сразу. Сдавшись, агент откатывает неприменённую попытку из своего представления. *Почему так, а не «дождаться, пока агент догонит журнал»:* порядок между топиками контракт не гарантирует (C-01: порядок — только внутри топика), поэтому момент «догнал» невыразим, и дизайн на это уже опирается — `round.closed` сделан самодостаточным именно затем, чтобы агент не ждал события из чужого топика. Оптимистическая блокировка (`expected_version`, ADR-013) для того и существует. Замер на двойнике: 7 гонок на 960 боях, после правила все 7 пакетов доходят до State с первой же повторной попытки (`journal.md` 2026-09-11, T-219 итерация 3).
   - **1а. Конфликт принадлежит пакету, а не действию.** Отказ относится к пакету по `proposal_id`. Потребитель, который ждёт реакции на действие, засчитывает конфликт и продлевает ожидание **только** для своего пакета — того, чей `proposal_id` пришёл под корреляцией действия; чужой отказ под той же `correlation_id` он не считает. *Почему:* иначе чужой конфликт продлевает ожидание, а на сроке диагноз винит в исчерпании повторов издателя, который ничего не публиковал (ревью #2 T-400, Mi-1, зонд G2 — `epics/EPIC-001-foundation/review.md`).
   - **1б. Повтор гаснет с первым фактом под своим `proposal_id`; отказ дедуплицируется по `event.id`.** Как только пришёл `entity.updated` с `proposal_id` пакета, пакет решён и отвечать на отказ больше не о чем; сам `entity.update.rejected` проходит тот же `eventbus.Dedup`, что и действия. *Почему:* at-least-once (C-01) на настоящей шине доставляет дубль при перебалансировке. Без этих двух условий дубль отказа запускает повтор уже применённого пакета: State молча отбрасывает его как повтор `proposal_id`, а представление агента учитывает урон второй раз и расходится с состоянием, и следующее действие гарантированно проигрывает гонку (ревью #2 T-219, Ma-1, зонды S2 и S2b — `epics/EPIC-003-swarm-llm-laws/review.md`).
   - **1в. Повтор, меняющий, кто жив, не предлагается (v1.4, T-416; ADR-026).** Если между попытками цель ранил или вылечил кто-то другой и пересчитанный пакет меняет, кто жив, относительно решённого исхода (удар, не смертельный в первой попытке, в повторе добивает — или наоборот), агент пакет **не** предлагает. Он сдаётся с записью уровня `Error` «мир ушёл дальше решения» и откатывает попытку из своего представления (п. 1г). Конец встречи к этому моменту ещё не опубликован — он идёт только после факта закрывающего пакета (п. 5). Поэтому встреча остаётся открытой и в представлении агента, и в State, а следующее действие решается от фактов. *Почему не «пересчитать исход»:* решения обмена (`dice.rolled`, `combat.decided`) уже опубликованы: на несмертельный удар уже ответил укусом тот, кого удар не убил, а смертельный уже объявлен в `combat.decided.outcome.target_dead`. Пакет, меняющий, кто упал, отвечал бы на другое действие. Редакция v1.3 разрешала этот вариант двойнику, но при смертельном ударе оставляла опубликованным `encounter.ended npc_dead` с убийцей над живым волком: встреча в State навсегда `active`, повторный вход открывал вторую (ревью #3 T-219, зонд S4). Противоречие снято не правилом повтора, а порядком публикации конца (п. 5). **Остаточная цена:** опубликованное решение может описывать исход, которого State не применил («волк повержен» над живым волком). При соблюдении п. 6 путь достижим только через `/forget`, пришедший, пока пакет в полёте; условие пересмотра — в ADR-026.
   - **1г. Участие — часть пакета, а не решения (v1.4).** Урон участника (`damage_dealt`), последний ударивший (`last_damager`) и состояние участия откатываются вместе с неприменённой попыткой (агент сдался или мир ушёл дальше) — так же, как здоровье и статус. Номер раунда соло — часть решения: он уже опубликован в `combat.decided.round.seq` и не откатывается; сущность встречи догоняет его следующим принятым пакетом (`set`, не `inc`). *Почему:* участие живёт только в пакете и в сущности встречи. Оставленное в представлении, оно попадает в следующий пакет абсолютным значением: `damage_dealt` в State навсегда включит удар, которого State не применял, а `last_damager` поменяет выбор цели NPC (C-03 `NPCTarget`: `last_damager` проверяется первым). Номер раунда, наоборот, самоисправляется и уже назван в опубликованном событии; его откат дал бы два решения с одним номером (приёмка T-219, N-1 ревью #3 → DoD T-230).
   - **1д. Ждущий потребитель при отказе агента получает только срок (v1.4).** Когда агент сдался или не предложил пакет (п. 1, 1в), события отказа в шину не публикуется (п. 3). Потребитель, ждущий факта по действию, видит лишь истечение своего срока, а решение (`combat.decided`) к этому моменту может быть уже доставлено игроку. Срок — не признак «никто не слушает»: диагноз называет «издатель не довёл пакет до факта (повторы исчерпаны или мир ушёл дальше решения) — смотрите лог издателя». Для шлюза EPIC-004 это значит: встреча продолжается (п. 5), и следующее действие игрока принимается как обычно.
   - **1е. Отказ не по гонке выбрасывает пакет с откатом (v1.5, T-425; ADR-026, «Уточнение исполнения» п. 2).** Пакет, отвергнутый по причине, которая не гонка (`unknown_entity`, `invalid_op`, `dead_entity`, `duplicate_entity`, в настоящем State — и `level_violation`), не повторяется и выбрасывается сразу, как пакет, на котором агент сдался: попытка откатывается из представления вместе с участием (п. 1г), пишется `Error`, отложенные действия решаются (п. 5). Закрывающий пакет — `encounter.ended` не публикуется, встреча продолжается. Пакет создания — встречи нет (п. 4). Закрытие по чужому факту (п. 6), отвергнутое State, повторно на том же факте не предлагается, и встреча отвечает на действия как любая открытая. *Почему:* пакет атомарен, и State не применил из него ничего. Держать закрывающий пакет «в полёте» после пришедшего отказа значит подвесить бой и все отложенные действия навсегда (ревью #1 T-419, Mi-1: бой висел активным над мёртвым волком). Держать попытку в представлении значит привязать следующее действие к версии, которой State не достигал. Буква v1.3 («сдавшись, агент откатывает») называла только исход после исчерпанных повторов; двойник T-419 распространил его на все отказы, и оркестратор с двумя ревью это приняли.
2. **Каждое принятое действие оставляет след в сущности встречи.** Пакет обмена содержит набор изменений и для сущности `encounter`: как минимум номер раунда; участников — если участие изменилось (иначе State опубликует факт с пустым `changed[]`); при конце боя — состояние, исход и ссылку на событие закрытия. *Почему:* обмен, в котором никто не попал, иначе неотличим от «никто не слушал», и встреча выглядит незакрытой. Таблица владения это разрешает уровню `task` (ревью #1 T-219, Critical-1; `journal.md` 2026-09-11).
3. **Встреча не отвечает на действие, которое не принимает.** Атака после `encounter.ended`, атака без живых целей, действие вне региона встречи или в чужом мире — агент встречи молчит: события отказа в C-05 нет и не вводится. Потребитель различает состояние встречи по `encounter.started`/`encounter.ended` и обязан отвергнуть такое действие сам, до публикации: gateway — синхронной ошибкой предусловий (C-08, коды `api-contracts.md` §1.6), харнесс e2e — немедленной ошибкой сценария. *Почему:* эти случаи — не события среды, а ошибки вызывающего; новый тип события ради отказа понадобился бы только заглушке, которую снимет EPIC-003 (решение по Critical-2 ревью T-219, `journal.md` 2026-09-11). **Уточнение v1.4:** состояние встречи потребитель берёт из `encounter.started`/`encounter.ended` **или** из факта сущности встречи (`entity.updated` со `state=resolved`) — что придёт раньше (п. 5, C-04 v1.3).
4. **`encounter.started` публикуется после `entity.created` встречи (v1.4, ADR-026; редакция v1.3 заменена).** Издатель (GM региона; двойник — в его роли) предлагает создать встречу, ждёт факта `entity.created` по её id и только затем публикует `encounter.started` с id из причины (`eventbus.WithCauseID`, `parts` — id встречи; C-01 v1.4). Если создание отвергнуто (`entity.update.rejected` по `proposal_id`), `encounter.started` не публикуется вовсе: встречи нет, озвучивать нечего. Издатель пишет отказ в лог на уровне `Error` — при соблюдении п. 6 отказ создания встречи является дефектом. Потребитель, читающий два топика, всё ещё может увидеть `encounter.started` раньше `entity.created`: порядок между топиками не гарантирован (C-01). Такую встречу он держит как «объявлена, сущности ещё нет», но теперь это состояние всегда временное: факт в журнале уже есть. *Почему не `encounter.ended {abandoned, rounds: 0}` и не нарратив по `entity.created`:* первый вариант вводит пару событий жизненного цикла для встречи, которой не было, и не отзывает уже сказанное нарратором «из тени выходит волк». Второй переносит повод нарратива с события встречи на факт State и оставляет шлюзу открывать первый раунд группы по событию о несуществующей встрече. Цена — задержка `encounter.started` на один оборот State (C-02: p95 ≤ 50 мс плюс шина).
   - **Причина `encounter.started` (v1.5, T-425; ADR-027, «Уточнение исполнения» п. 3).** `WithCauseID` берёт причиной событие, от которого строится предложение создания: вход игрока у двойника, у GM региона — событие, по которому он решил открыть встречу (`tick.fired` или вход). Факт `entity.created` причиной быть не может: id нужен до факта, его пишет `opened_by_event_id` в самом предложении.
   - **Действия во время создания откладываются (v1.5, T-425; ADR-026, «Уточнение исполнения» п. 3).** Пока создание в полёте, действия персонажа, для которого открывается встреча, ждут ответа State, как в п. 5. Встреча создана — они решаются как действия во встрече. Создание отвергнуто — как действия вне встречи (п. 3). *Почему:* удар, отправленный сразу за входом, иначе теряется. Решать его не с чем, и по п. 3 агент молчит, хотя встреча появится через оборот State. Ревью #1 T-419 доказало: без отсрочки краснеют стенды двойника и процессные тесты T-255. Кто держит очередь в настоящем рое — GM региона (T-232) или агент встречи (T-230), — решает дизайн EPIC-003. Контракт требует одного: действие не теряется и не решается до ответа State. Очередь ограничена, переполнение — громкий отказ, а не молчание (DoD T-230).
5. **`encounter.ended` публикуется после факта закрывающего пакета (v1.4, ADR-026).** Событие конца строится **до** пакета: пакет называет его id в `closed_by_event_id`, а id выводится из причины (`WithCauseID`, `parts` — id встречи). Публикуется оно, когда агент увидел `entity.updated` сущности встречи со `state=resolved` под `proposal_id` этого пакета. Пакет выброшен (агент сдался, мир ушёл дальше, отказ не по гонке — п. 1е) — конец не публикуется, встреча продолжается.
   - **Причина `encounter.ended` (v1.5, T-425; ADR-027, «Уточнение исполнения» п. 3)** — событие, на которое отвечает закрывающий пакет: действие игрока (соло) или `round.closed` (группа). Если конец наступил не по обмену — чужой факт: `entity.updated` NPC, ставшего терминальным (п. 6), или `entity.updated status=abandoned` последнего игрока (C-04 v1.1). У такого конца scope конверта — scope встречи (`eventbus.WithScope`), как в п. 6. Причиной не может быть ни факт сущности встречи — id нужен до него, его называет `closed_by_event_id`, — ни `combat.decided`: решений на обмен два, а обмен один. Одна причина закрывает не больше одной встречи, `parts` — id встречи, поэтому повтор пакета и перестроение после рестарта дают тот же id. Выброшенный пакет своё событие не публикует, а следующее закрытие строится от другой причины.
   - **Конец встречи для потребителя состояния** (read-model шлюза, харнесс) — факт сущности встречи со `state=resolved`. `encounter.ended` — событие жизненного цикла для нарратива, роя (`agent.child_resolved`) и аналитики; оно несёт причину и убийцу. В журнале факт всегда раньше события, но читатель двух топиков может увидеть их в любом порядке — концом считается то, что пришло первым.
   - **Действие по встрече, чей закрывающий пакет в полёте,** агент откладывает до решения пакета. Пакет применён — встреча закрыта, и действие получает молчание по п. 3. Пакет выброшен — действие решается по обычным правилам. Отвечать по представлению, включающему неприменённый пакет, нельзя: иначе молчание достанется действию во встрече, которая продолжается.
   - **После рестарта** агент сверяет свои встречи с State (C-14 v1.2). Встреча `resolved` с `closed_by_event_id`, а события с этим id в журнале нет — агент публикует его с тем же id. Для `encounter.started` так же: сущность встречи есть, события нет — публикуется. Повтор, успевший уйти до падения, потребители гасят по id.
   *Почему так:* событие, объявляющее изменение, которого State не принял, отозвать нельзя. Все четыре вопроса волны 1 к этому контракту (п. 1в, отказ создания, существо, убитое чужой рукой, участие) выросли из одного корня: двойник объявлял жизненный цикл встречи до факта. Решения обмена (`dice.rolled`, `combat.decided`) остаются до пакета (C-03): это решения, а не факты, и потребитель состояния берёт здоровье из фактов.
6. **Один NPC — одна активная встреча; существо, убитое чужой рукой (v1.4, ADR-026).** Правило модели данных (`data-model.md` §3.7, атрибут `scope` встречи) нормативно для открывающего: GM региона не открывает встречу с NPC, который уже участвует в активной встрече. Он единственный открывающий в регионе, поэтому гонки нет. State это правило не проверяет — его нет среди inv-01…inv-10.
   Если NPC встречи всё же стал терминальным по чужому факту (сегодня источника нет; появятся Entity-Actor и пробой законов, EPIC-006/007) и живых противников не осталось, **встречу закрывает агент встречи сам**. Он предлагает пакет закрытия сущности встречи без трофея (`state=resolved`, `resolution=npc_dead`, участники выходят из боя), затем по п. 5 публикует `encounter.ended {reason: npc_dead}` **без `killer`** — схема это допускает. Причина здесь — чужой факт, поэтому scope конверта агент ставит явно: scope встречи (`eventbus.WithScope`). Так адресаты нарратива и шлюз находят игроков встречи без `participants[]` в событии. Нарратив на такой конец в MVP-1 **не обязателен**: при соблюдении правила путь недостижим. Когда появится источник, вид — `world_event` по scope конверта.
   **Причина пакета закрытия по чужому факту — `resolve` (v1.5, T-425; ADR-026, «Уточнение исполнения» п. 1).** Пакет трогает только сущность встречи: `state`, `resolution`, `closed_by_event_id` и `participants[]`, через которые участники выходят из боя. Смерть существа уже записана своим фактом со своей причиной, а удара этой встречи не было. `death` дал бы вторую запись одной смерти, `combat` — обмен без бросков. `resolve` есть в enum `cause` схем `entity.*.proposed` и в строке владения встречи уровня `task` (`shared/contracts/ownership.go`, любой путь). Строки игрока и NPC `resolve` не знают, и пакет их не касается, поэтому настоящий State не ответит `level_violation`. `proposal_id` строится от чужого факта.
   **«Активна» и «занята» (v1.5, T-425; ADR-026, «Уточнение исполнения» п. 4).** Встреча **активна** от факта `entity.created` до факта закрывающего пакета. Пока закрывающий пакет в полёте, она всё ещё активна: State держит её открытой. До `entity.created` встреча **открывается**: она не активна, но уже **занимает** своего NPC. Для правила этого пункта NPC занят от предложения создания до факта закрытия или отказа в создании — иначе два открытия в полёте взяли бы одного волка. Молчание п. 3 («атака после конца») относится к встрече после факта закрытия. Действие во время открытия или закрытия откладывается (п. 4–5).
   *Почему закрывает агент, а не нарратор или координатор:* жизненный цикл встречи принадлежит агенту встречи (`api-contracts.md` §2.3.7), и так же он уже закрывает встречу по `abandoned` последнего игрока (C-04 v1.1). Координатору раундов случай не нов (C-04 v1.3). *Почему правило открывающего записано здесь:* двойник его нарушает — двое игроков в одном регионе открывают две встречи против одного волка, — и именно это делало достижимыми зонды S3/S4 ревью T-219 и «встречу над трупом».
7. **Признак конца обмена в `combat.decided` (v1.4).** В схему `combat.decided.v1.json` добавляется совместимое опциональное поле `exchange{index, last}`. `index` — порядковый номер решения в обмене, начиная с 0 (решение по действию игрока — 0, ответ существа — 1). `last` — признак последнего решения обмена. Настоящий агент встречи заполняет поле всегда и ставит `last=true` ровно на одном решении обмена. Нарратор хода закрывает ход по `exchange.last`. Вывод из `action`/`target_dead`/`success`/`free_attack`/`living_enemies` остаётся только для издателя без поля — для двойника до его задачи. *Почему:* издатель знает форму обмена, а потребитель её угадывает. Правило угадывания сегодня верно ровно для обмена «действие + ответ одного NPC» и молча сломается на нескольких NPC и в группе. `index` делает пропуск решения видимым, а не «незакрытым ходом» (ревью #1 T-220, вопрос (в)). Изменение совместимое, `schema_version` не меняется (§16 п. 1); схему правит владелец типа, EPIC-003.
8. **Порядок смерти и удара в `narrative_output` (v1.4).** `narrative.output kind=death` выводится из факта (`system_events`), а текст хода — из решения (`game_events`), поэтому нарратор, читая два топика, может получить смерть раньше удара. Зонд ревью #1 T-220: при задержке чтения `game_events` на 20 мс так было в 8 боях из 8; на стенде как есть — ни разу на 21 смерть. Правило для издателя нарратива: если факт смерти пришёл из пакета боя (в `entity.updated.cause` — причина боя или бегства), смерть публикуется **после** нарратива хода с той же `correlation_id`. Ожидание ограничено таймаутом фазы нарратива; по его истечении смерть публикуется без хода, с записью `Warn`. Смерть не из пакета боя публикуется сразу. Потребитель порядок не восстанавливает: шлюз доставляет игроку тексты в порядке `narrative_output` (C-08: доставки строго по порядку на `player_id`). *Почему на стороне издателя:* топик `narrative_output` один, и порядок в нём задаёт один издатель. Переупорядочивать в шлюзе по `based_on[]` значит учить причинности каждого клиента. Для I1-α и `FakeNarrator` инверсия допустима (решение оркестратора), правило — для настоящего GM (T-233).

### Гарантии
Один `narrative.output` на ход соло и один на раунд группы (`narrative_event_id` общий); `recipients[]` — только игроки scope (включая `idle`); текст прошёл фильтр (a) (`filter.status=pass`) или заменён шаблоном; p95 от `combat.decided` до `narrative.output` — порог после замера (NFR-002); при недоступности LLM — `generated_by=template` в пределах таймаута фазы; текст не содержит разметки, требующей `parse_mode` (бот отправляет как plain text, SEC-10). **v1.4:** `encounter.started` и `encounter.ended` публикуются после факта State, который они объявляют (п. 4–5); смерть персонажа из пакета боя — после текста хода с той же `correlation_id` (п. 8); у настоящего агента встречи ровно одно решение обмена несёт `exchange.last=true` (п. 7). **v1.5:** действие, пришедшее во время создания или закрытия встречи, не теряется и решается после ответа State (п. 4–5); пакет, отвергнутый не по гонке, выбрасывается с откатом и не подвешивает бой (п. 1е); id `encounter.started/ended` выводится из события, от которого строится пакет (п. 4–5).

Соло-удар порождает `turn`, смерть персонажа — `death`, начало встречи — `world_event`. Текстов 22 — по таблице на вид и на каждый исход хода. Вывод из полей решения (`closesExchange`) остаётся только для решения без поля (T-419). Событие запоминается как отвеченное только после успешной публикации: окно — `eventbus.Dedup`, `Has` до обработки, `Add` после успешной `Publish`; своего окна у двойника нет (T-419 п. 7). Цена позднего запоминания названа: при потерянном подтверждении публикации текст уйдёт дважды (ревью #2 T-220, зонд P4). У двойника нарратора id — от генератора, поэтому эта цена у него остаётся. У настоящего рассказчика её снимает id из причины (ADR-027, T-229). **SEC-10 для имён:**
  - имя персонажа проверяет шлюз (`api-contracts.md`, код `name_invalid`: 2–32 символа — буквы, цифры, пробел, дефис);
  - разметку в любом тексте обезвреживает бот, который шлёт текст без `parse_mode` (ADR-006 доп. п. 4, ADR-018 п. 4);
  - имена регионов и NPC из фикстур и блупринтов — авторский контент под ревью владельца, и их не проверяет никто. Гарантия «текст без разметки» относится к шаблонам, а не к подставленным значениям (`TestNoTextNeedsAParseMode` проверяет шаблоны); последний барьер для подстановок — бот.
- **`FakeEncounter`** — заглушка Phase 1 для I1-α. **Форма после T-419 (v1.5):**
  - на `player.entered_region` — `entity.create.proposed encounter` (NPC занят с этого момента), затем, после `entity.created`, — `encounter.started{round{60s,2}}` с id из причины;

  - действие или факт без `id` пропускается с записью `Error`. **Делает EPIC-003 как первую единицу I1a (C4)**; подпакет `shared/testkit/swarm` вливается в `integration/mvp-1` сразу после приёмки tech-lead#2 (ранний merge, до I1-α) — не дожидаясь остального I1a.   | окно нарратора — своё | `eventbus.Dedup` в два шага |

  Три отступления T-419 от буквы v1.4 подтверждены и стали текстом v1.5:
  - отказ не по гонке — п. 1е;

  Историческая запись v1.4: «Прав контракт.» Тесты двойников не должны закреплять прежний порядок сверх этой задачи. Задача проходит до T-230: двойник — образец формы для настоящего агента, и сегодня он показывает прежний порядок. Вместе с двойником правится харнесс (`shared/testkit/gateway`): конец боя он признаёт и по факту сущности встречи со `state=resolved`, иначе после переноса конца за факт он пошлёт следующий удар раньше, чем увидит `encounter.ended`.

## 7. C-07 · EPIC-003 → EPIC-005, EPIC-002 (replay): записи LLM

### Интерфейс

## 14. C-14 · EPIC-002, EPIC-003, EPIC-004 → все: снапшоты и протокол восстановления

Тип: события + объекты · Версия: 1 (v1.1 — уточнения; **v1.2 — окна дедупликации и события жизненного цикла встречи при восстановлении, T-416**) · Владелец: EPIC-002 (формат), реализуют все stateful-контексты.
`snapshot.created {component: state|swarm|gateway, snapshot{id, seq, taken_at, cursor{topic: next_offset}, laws_version, state_hash, size_bytes, key}}` — **значения `component` по этому контракту** (не `api-contracts.md` §2.3.12; system-analyst правит на планировании). Объекты: `snapshots-{world}/{component}/{ts}-{seq}.json` (полный снапшот) + **`snapshots-{world}/{component}/latest.json` — указатель** (метаданные + `key` объекта; ADR-011 п. 2), пишется после успешного PUT объекта; потребители читают указатель, проверяют `state_hash`, затем объект. Префиксы: `state/` — EPIC-002, `swarm/` — EPIC-003, `gateway/` — EPIC-004 (курсоры и проекции; `gateway.db` остаётся истиной для сессий/раундов/outbox). Режим `--mode=replay`; `analytics.replay.completed` — одна схема `schemas/events/analytics.replay.completed.v1.json` (владелец файла EPIC-002; поля `mode=test`, `events_hash_match` добавляет EPIC-005 — совладение, `plan/ownership.md`). Порядок старта: `state` догоняет журнал (`Journal.ReadRange` с `cursor` до `End`) → публикует `replay.completed mode=recovery` → `swarm` и `gateway` строят проекции от `state/latest.json` и догоняют `entity.updated` с `cursor.system_events` через `Journal`; «конец журнала» = `End` по всем читаемым топикам (C-01).
**Уточнение v0.4 (TL2-6)**: (а) **`testkit/state.FakeState` v0 (F-10/T-017) публикует `analytics.replay.completed {mode: recovery, replay{run_id, snapshot_id: null, events_replayed: 0, llm_calls: 0, dice_rolled_new: 0, duration_ms, state_hash_after, incomplete_record: false}}`** сразу после подписки на `system_events` — заглушка соблюдает протокол старта, а не потребители подстраиваются под заглушку; (б) ожидание сигнала потребителем ограничено таймаутом — `swarm`: `MV_SWARM_REPLAY_WAIT` (по умолчанию `120s`, = RTO), по истечении контекст стартует и отмечает `/health degraded {state_replay: missing}` (та же ветка нужна в production при падении `state`); `gateway` — аналогично, если его дизайн ждёт сигнал (`MV_GATEWAY_REPLAY_WAIT`). **Обе переменные объявляются в манифесте `shared/env` тем же изменением, которое вводит их чтение** (EPIC-003 для `swarm`, EPIC-004 для `gateway`), а не заранее (T-409). *Почему так:* манифест держит только читаемые переменные — объявленная и никем не читаемая настройка выглядит применённой и молча не применяется, ровно этот класс дефекта закрыла T-408 (`MV_MODE`, `MV_BUS`, `MV_GATEWAY_ADDR`). До появления читающего кода их отсутствие в `shared/env/vars.go` — не расхождение. То же правило — для `MV_TELEGRAM_CLOUD_FLAG_TTL` (C-08 v1.2) и для переменной журнала воспроизведения, если она понадобится `internal/replay`. Издатели типа в реестре: `state` (EPIC-002), харнесс EPIC-005 (`mode=test`), `testkit/state` (§0).
**Уточнение v1.2 (T-416; ADR-026, ADR-027).**
- (а) **Окна дедупликации stateful-потребителя входят в его снапшот** (`eventbus.Dedup`: `IDs` → снапшот, `Restore` ← снапшот). Сюда относятся окно «уже ответил» роя (нарратор, агент встречи) и окно отказов агента встречи. Окно без сериализации у stateful-контекста — дефект: после рестарта повтор уже выполненной работы (второй текст хода, второй пакет) проходит молча. Своё окно у двойника `FakeNarrator` допустимо — он не stateful-контекст C-14.
- (б) **Восстановившись, агент встречи сверяет свои встречи с State.** Сущность встречи есть, а `encounter.started` с id из причины в журнале нет — агент публикует это событие. Встреча `resolved` с `closed_by_event_id`, а события с этим id нет — публикует `encounter.ended` с тем же id (C-05 v1.4 п. 4–5). Id выводится из причины (C-01 v1.4), поэтому повтор, успевший уйти до падения, потребители гасят по id.

### Гарантии
Снапшот содержит `cursor` по всем читаемым топикам; после восстановления `state_hash_after == hash(снапшот + факты)`; разрыв журнала (retention) → восстановление из объектов сущностей + `/health degraded {log_gap}`; RTO ≤ 2 мин на одной машине (после замера). Хранение снапшотов не зависит от bucket versioning (ротация K=5 в коде; ADR-021).

### История изменений
v1 — 2026-09-09. v1.1 — 2026-09-09: `latest.json` указатель, `component` enum, префикс `gateway/`, совладение схемы `replay.completed`, независимость от versioning. Уточнение v0.4 — 2026-09-09 (сведение 3): `FakeState` v0 публикует `replay.completed`, таймаут ожидания. **v1.2 — 2026-09-11 (T-416, system-architect#1): окна дедупликации входят в снапшот stateful-потребителя; при восстановлении агент встречи дописывает события жизненного цикла, чей факт в журнале есть, а события нет, — с тем же id (ADR-026, ADR-027).**

## 15. C-15 · EPIC-003 → EPIC-013 (E-H облако), EPIC-005 (эмбеддинги): интерфейс провайдера LLM

Тип: Go API · Версия: 1 (v1.1 — сведение A4-2, U-8) · Владелец: EPIC-003 · Потребители: EPIC-003 (шлюз), EPIC-005 (`Embed`/`Models` из `internal/memory` — импорт `llm.Provider`/`providers.Registry` разрешён ADR-001 доп. п. 7), EPIC-013 (облако).

### Интерфейс
```go
package llm
type Provider interface {
    Generate(ctx context.Context, req Request) (Response, error)
    Embed(ctx context.Context, model string, texts []string) ([][]float32, error)
    Health(ctx context.Context) Status            // ok | loading | degraded(model_not_resident) | unavailable
    Models(ctx context.Context) ([]string, error) // имена моделей провайдера (валидатор C-11 п. 7а, /health.llm)
}
type Request struct {
    Phase, Model, System string; Messages []Message
    Schema json.RawMessage                        // JSON Schema 2020-12 ответа (structured output); nil — свободный текст
    Params Params                                 // v1.1: Temperature, TopP, TopK, MinP, PresencePenalty, MaxTokens float/int; Think bool (по умолчанию false)
    Timeout time.Duration; CorrelationID string
}
type Response struct {
    Content string                                // текст (JSON при Schema)
    ReasoningLen int                              // v1.1: длина отброшенного reasoning_content (в llm.output.parse{}); сам текст не сохраняется
    Tokens struct{ Prompt, Completion, Cached int } // v1.1: Cached — из prompt_tokens_details.cached_tokens (0, если нет)
    LatencyMs int64; Provider, Model string
}
```
Реализации (`providers.Registry`, имя = значение `MV_LLM_PROVIDER`): **`openai_compat`** — по умолчанию (llama-server или любой OpenAI-совместимый сервер; адрес — **только** `MV_LLM_URL`, обязательный и без значения по умолчанию, например `http://127.0.0.1:<порт>`; значение принимается и с `/v1` на конце, и без — хвост `/v1` отбрасывается, путь дописывает вызывающий; порт `llama-server` обвязка выводит из того же значения, отдельной переменной порта нет. *Почему так (T-404):* второй источник адреса — `MV_LLM_PORT` — разошёлся с первым на стенде владельца, сервер слушал 8888, а проверка стучалась в 1234; а умолчание `1234` давало при удалённой из `.env` строке два разных ответа — платформа молча шла в 1234, обвязка говорила «адреса нет»; `/v1/chat/completions` с `response_format: {type: json_schema, json_schema: {name, schema}}`, `chat_template_kwargs: {enable_thinking: Params.Think}` — thinking выключен для всех фаз MVP-1 (llama.cpp #20345: грамматика не применяется при thinking), семплинг из `Params` на запрос; `/v1/embeddings`; `/v1/models`; `/health` 503 → `loading`); **`ollama`** — native `/api/chat`/`/api/embed`/`/api/tags`/`/api/ps` (`MV_OLLAMA_URL`); **`anthropic`** — целевое (E-H); **`recorded`**, **`fake`** — тесты. Облако — `openai_compat` с внешним `MV_LLM_URL` + `MV_LLM_API_KEY`: провайдер отказывает в старте при не-локальном host без `MV_LLM_CLOUD_ENABLED=true` (ADR-005 доп. 2 п. 3). Middleware (бюджет, запись, парсер, язык, фильтр, страж) — вне провайдера и общие для всех. Блупринт провайдера не выбирает; модель блупринта ∈ `Models()`.

### Гарантии
`Generate` не имеет побочных эффектов в шине (запись `llm.output` — обязанность шлюза); отмена `ctx` закрывает соединение (ADR-014 п. 2); `Tokens` из ответа провайдера (погрешность ≤ 5 %, NFR-052), при отсутствии — оценка по длине с пометкой; сигнатуры v1 не меняются (новые поля `Params`/`Response` — с нулевыми значениями по умолчанию).

### Заглушка
`providers/fake` (таблица `(phase, matcher) → Response`, `Embed` — детерминированный хэш-вектор для EPIC-005), `providers/recorded` (replay). Живой llama-server/Ollama — только стенд.

### История изменений
v1 — 2026-09-09 (ADR-005). v1.1 — 2026-09-09: `openai_compat` по умолчанию, `Params`/`Response` поля, потребитель `internal/memory` (сведение A4-2, U-8).

## 16. Правила изменения контрактов

1. Совместимые изменения (новое опциональное поле, новый тип события, новый эндпоинт, новый код ошибки): владелец добавляет схему/OpenAPI + запись в реестр в своём эпике, уведомляет архитектора в отчёте; `schema_version` не меняется.
2. Несовместимые (удаление/переименование поля, смена семантики, новый обязательный аргумент Go-API): запрос в `plan/ownership.md` → оценка влияния system-architect (список потребителей из реестра) → `schema_version+1` (события) или `/v2` (HTTP) → задачи командам-потребителям; потребители принимают `n` и `n-1` один инкремент.
3. Изменения `shared/*` (C-01, C-03, C-15, `clock`, `runtime`, `objstore`) — только через system-architect; PR помечается `contract-change`.
4. Тест `contracts` в CI: схемы валидны; каждый тип имеет владельца-издателя и ≥ 1 потребителя (исключения: `world.law_breach.*`, `rules.change.*` до E-B/E-A); OpenAPI ↔ маршруты; политики топиков (§0) проверяются на фикстурах.
5. Переменные окружения — часть контракта процесса: объявляются через `shared/env.Declare` с префиксом `MV_`; `.env.example` сверяется с манифестом в CI (NFR-074).
   - **Адреса сервисов сети compose (v0.7, T-416).** Умолчание в compose, называющее сервис своей сети (`redpanda:9092`, `http://core:8090`), — это значение **другого контекста запуска**, а не второй источник того же значения. Манифест отвечает за процесс на хосте, compose — за контейнер в своей сети; так и записано в шапке `shared/env/vars.go`. Второго поля умолчания в манифесте не вводим. Такое переопределение законно ровно для явного набора из шести переменных: `MV_KAFKA_BROKERS`, `MV_MINIO_ENDPOINT`, `MV_CORE_URL`, `MV_QDRANT_ADDR`, `MV_NEO4J_URI`, `MV_TELEGRAM_GATEWAY_URL`. Значение обязано иметь ту же форму, что умолчание манифеста (схема ↔ схема, `host:port` ↔ `host:port`). Набор живёт в правиле 8 линтера композиции (`infrastructure.md` §3.1.1) вместо эвристики «адресная переменная — по форме умолчания», которая ошибается в обе стороны: `MV_CORE_ADDR` — адрес прослушивания, а не сервиса, но проходил как адрес (ревью #2 T-411, N-4). Новая сетевая переменная, не внесённая в набор, краснит линтер — забытое добавление громкое. `MV_MEMORY_URL` в набор не входит: пустое умолчание значит «память выключена», и compose передаёт его как есть.
   - **Сторонние переменные с умолчанием платформы (`OLLAMA_*`, v0.7).** Процесс платформы их не читает, поэтому умолчание манифеста для них — только документ, а в контейнер значение приносит compose (`${OLLAMA_X:-v}`). Ключ без значения здесь не годится: он отдал бы умолчание образа, а не наше. Поэтому манифест берёт значения настройки `infrastructure.md` §6.4 и loopback-origins SEC-15 как умолчания (`DeclareExternal` с умолчанием, без `RequiredWhen`), а правило 8 проверяет, что умолчание compose равно умолчанию манифеста и для `DeclareExternal`. Вариант «compose требует их через `:?`» отвергнут: он заставил бы оператора копировать шесть строк ради профиля `gpu` и сломал бы правило 7 для файла, загружаемого всегда. Для нативной Ollama значения манифеста — рекомендация: сервер читает переменные окружения ОС, а не `.env`. Правка — **T-413**: `shared/env/infra.go`, тест в `shared/env/env_test.go` (сегодня он ждёт ошибку без `OLLAMA_MAX_LOADED_MODELS`), комментарии `.env.example`, `scripts/compose-lint.sh`.
6. **Таблица владения — один файл (v0.6, ADR-025; редакция v0.4 TL2-3 отменена).** Единственная истина — `shared/contracts/ownership.go` (`contracts.OwnershipRules`), созданный в EPIC-001 по `data-model.md` §4 (включая строку gateway `Character.status → abandoned`, `Group.leader_id`). Копии и теста равенства нет. Строку меняет владелец её семантики — уровни роя EPIC-003, строку `gateway` EPIC-004, строки `author`/`system` EPIC-002 — PR с меткой `contract-change`, ревью system-architect и tech-lead#1 (EPIC-002 — единственный потребитель, который по таблице отказывает, узнаёт из отчёта PR). `shared/agent/levels.go` (EPIC-003, T-202) своей таблицы владения не держит: вид «типы сущностей уровня» валидатор блупринтов получает от вызывающего, собранный из `contracts.OwnershipRules`. *Почему так:* v0.4 объявлял истиной `shared/agent/levels.go`, которого в дереве нет, и требовал блокирующего теста равенства с копией, сравнивать которую не с чем, — фактической истиной служила копия, ровно то, что процедура запрещала. К тому же в таблице есть строки без агента (`gateway`, `author`, `system`), а «экспорт при сборке» разворачивал бы зависимость фундамента на пакет роя (`diagrams/domains.md`, ADR-025). **Подтверждено system-architect#1 (T-416, 2026-09-11)** — ADR-025, раздел «Подтверждение»: в описании PR, меняющего строку, автор перечисляет затронутые блупринты; тест таблицы покрывает строки всех трёх групп (рой, `gateway`, `author`/`system`).
7. **Издатели типа (v0.4, TL2-2/TL2-5).** Владелец типа поддерживает `Spec.Publishers` в реестре; добавление издателя — совместимое изменение (п. 1) с уведомлением system-architect; job `contracts` проверяет `source ∈ Spec.Publishers` на фикстурах и в e2e; источники `testkit/*` — только на `membus`/`MV_SWARM_FAKE=true`.
