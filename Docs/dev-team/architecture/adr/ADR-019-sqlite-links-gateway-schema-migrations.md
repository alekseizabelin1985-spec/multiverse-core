# ADR-019: SQLite в gateway — `modernc.org/sqlite`, два файла с разными PRAGMA, миграции `goose` из embed, единственный писатель, физическое удаление при `/forget`

Статус: предложено (к утверждению на G2 с планом EPIC-004) · Дата: 2026-09-09 · Автор: architect#3 (TEAM-3, EPIC-004) · Уровень: реализация блока
Связи: ADR-004 п. 2 (SQLite, два файла — не пересматривается; здесь — схема, PRAGMA, миграции), ADR-006 п. 3 (outbox), ADR-009 п. 2 (`links.db` — единственная копия, физическое удаление); FR-060, FR-061, FR-085, BR-07; NFR-010, NFR-013, NFR-041, NFR-042; `data-model.md` §5; `components/gateway-and-bot.md` §4, §8.

## Контекст

ADR-004 выбрал SQLite через `modernc.org/sqlite` (CGO-free) с двумя файлами: `links.db` (ПДн-связки) и `gateway.db` (сессии, ходы, раунды, ключи идемпотентности, outbox) и оставил команде «схемы SQLite и миграции (`golang-migrate` или встроенные SQL-файлы)». Требования: физическое удаление строки при `/forget` (после которого поиск по внешнему ID пуст и файл не содержит ID даже в свободных страницах); порядок доставок на игрока и голова очереди; идемпотентность `action_key` 24 ч; восстановление сессий/раундов/outbox после рестарта; ни одного внешнего ID вне `links.db`; один разработчик — минимум инструментов. Замечание системного архитектора: схемы и миграции — предмет этого ADR; идемпотентность `POST /v1/characters` содержит внешний ID в ключе.

## Решение

1. **Драйвер** `modernc.org/sqlite` v1.58.0 (пин); открытие через `store.OpenLinks(path)` / `store.OpenGateway(path)` с DSN `file:<path>?_pragma=journal_mode(WAL)&_pragma=foreign_keys(ON)&_pragma=busy_timeout(5000)&_pragma=synchronous(FULL|NORMAL)`; для `links.db` дополнительно `secure_delete(ON)`, `auto_vacuum(INCREMENTAL)`; `SetMaxOpenConns(1)`, `SetConnMaxLifetime(0)`. Права: `links.db` создаётся с `0600` в каталоге `0700` (`GATEWAY_DATA_DIR`); ошибка старта, если права шире.
2. **Миграции** — `goose` v3.28.0 как библиотека: `internal/gateway/migrations/links/NNNN_*.sql` и `…/migrations/gateway/NNNN_*.sql` (embed, `//go:embed`), `goose.NewProvider(goose.DialectSQLite3, db, fsys)` → `Up(ctx)` при старте контекста; отдельная таблица версий в каждом файле. Нумерация — только EPIC-004 (ownership.md); `Down` не пишутся (откат — восстановление файла из бэкапа); CLI `goose` не используется.
3. **Схема** — `components/gateway-and-bot.md` §4 (`links`, `character_requests`; `sessions`, `turns`, `rounds`, `group_participation`, `idempotency_keys`, `pending_characters`, `deliveries`, `processed_events`, `cursors`). Инварианты: уникальный частичный индекс `player_id` в `links`; `ux_sessions_active` — одна активная сессия на scope; `ux_rounds_open` — один открытый раунд на scope; `ix_deliveries_event (event_id, player_id)` — идемпотентная постановка; `json_valid` CHECK на JSON-полях; всё время — ISO-8601 UTC `TEXT`.
4. **Внешние ID** — только `links.db` (`links.external_id`, `character_requests.external_id`); в `gateway.db` ни одного поля с внешним ID; `Delivery.route` формируется из `links.RouteFor(player_id)` в момент выдачи и не сохраняется. Тест NFR-041 включает `strings`-скан обоих файлов и WAL.
5. **`/forget`** — одна транзакция в `links.db`: `DELETE FROM links WHERE …` (каскад `character_requests`); затем хуки в `gateway.db` (outbox → `dropped`, сессия → `ended leave`, выход из группы через события). *(Порядок заменён: хуки — до `DELETE`, «Дополнение 2» п. 1; изм. T-456.)* Sweeper раз в час: `PRAGMA incremental_vacuum` и `PRAGMA wal_checkpoint(TRUNCATE)` на `links.db` — чтобы удалённые байты не оставались в WAL.
6. **Транзакционная модель consumer'а**: обработка события шины = одна транзакция `gateway.db`: `INSERT processed_events` (дубль → выход без эффектов) → эффекты (outbox, turns, rounds, sessions) → `UPDATE cursors`; коммит → ответ `Bus` «обработано». Ошибка → откат и ошибка обработчику (повтор ×3 → DLQ, C-01).
7. **Retention** (sweeper 60 с): истёкшие `idempotency_keys`/`character_requests` (24 ч); `deliveries` `pending` старше `expires_at` → `dropped`; `delivered/dropped` старше 7 дней — удаление; `processed_events` старше 24 ч; `sessions/turns/rounds` не чистятся в MVP-1 (≤ 1 000 строк/сессия; при необходимости — задача E-G).
8. **Бэкап** — файлы целиком (`sqlite3 .backup` или копия при остановленном процессе); `links.db` — по политике DevOps/security (шифрование, ≤ 30 дней), `gateway.db` — вместе с томами Redpanda/MinIO (`infrastructure.md`).

## Последствия

- Позитивные: один путь сборки без CGO; ПДн физически в одном файле с отдельной политикой; миграции версионируются и тестируются как обычный Go-код; outbox и идемпотентность — SQL, а не самописные структуры.
- Негативные: две зависимости (`modernc.org/sqlite`, `goose`) — обе чистый Go; `MaxOpenConns(1)` исключает параллельные чтения — при росте нагрузки достаточно второго read-only пула (WAL это допускает) без изменения схемы; `synchronous=NORMAL` на `gateway.db` допускает потерю последних миллисекунд при сбое ОС — компенсируется идемпотентностью и повтором событий.
- Что придётся сделать: EPIC-004 I1 — `store`, миграции `0001_init.sql` для обеих БД, интеграционные тесты миграций и `forget`; DevOps — том `GATEWAY_DATA_DIR`, права, бэкап; security-engineer — проверка `secure_delete`/WAL-checkpoint в threat-model.

## Дополнение после G2 (2026-09-09, сведение `consolidation.md` §3/§6; статус ADR — принят на G2)

1. **`/forget` — checkpoint и vacuum сразу, не по расписанию (T-8, SEC-04/05; уточнение п. 5)**: `links.Store.Forget` в одном вызове выполняет `DELETE FROM links …` (транзакция, каскад `character_requests`), затем `PRAGMA wal_checkpoint(TRUNCATE)` и `PRAGMA incremental_vacuum` — до ответа клиенту *(порядок уточнён: сначала `incremental_vacuum`, затем checkpoint; неудача — `503 forget_incomplete`; «Дополнение 2» п. 2–3, изм. T-456)*; для этого `links.db` открывается с `auto_vacuum=INCREMENTAL` (п. 1). Sweeper раз в час (`Store.Compact`) остаётся страховкой (например, после аварийного завершения между DELETE и checkpoint). Интеграционный тест: `strings`-скан файла **и** `-wal` сразу после ответа `/forget` = 0.
2. **Идемпотентность `POST /v1/characters` по `link_id` (T-2, SEC-03; уточнение п. 3–4)**: в `links` добавляется колонка `link_id TEXT NOT NULL UNIQUE` (ULID, присваивается при первом `resolve`, неизменна); `character_requests` перепроектирована с ключом `(link_id, action_key)` и `FOREIGN KEY (link_id) REFERENCES links(link_id) ON DELETE CASCADE` — внешнего ID в ключе нет. Таблица остаётся в `links.db` ради каскадного удаления. В `gateway.db` ни `external_id`, ни `link_id` не хранятся; тест миграций сверяет имена колонок `gateway.db` с запретом подстроки `external`. Схема — `components/gateway-and-bot.md` §4.1 v0.2.
3. **Env**: `GATEWAY_DATA_DIR` читать как `MV_GATEWAY_DATA_DIR` (G-11).
4. Совместимость: миграция `0001_init.sql` ещё не применялась нигде — изменения входят в неё, без `0002`.


## Дополнение 2 (2026-09-13, T-456, system-architect#1): незавершённое стирание при `/forget`

Основание — решение system-architect#1 по T-303 (ревью #1) и код T-303 в `epic/EPIC-004-gateway-bot`: `internal/gateway/links/forget.go`, `internal/gateway/store/compact.go`, `internal/gateway/context.go`. Контракт — C-08 v1.5.

1. **Порядок `/forget`** (уточняет п. 5 решения). Найти связку → хуки `ForgetHooks` в порядке C-04, если у связки есть персонаж → `DELETE FROM links WHERE link_id = ? AND player_id IS ?` (каскад `character_requests`) → `store.CompactLinks` до ответа. Ошибка хука останавливает каскад до удаления: связка остаётся, повтор `/forget` выполняет все хуки заново, поэтому хуки идемпотентны. Шаги до ошибки могли выполниться; ответ — `500 internal`, с T-355 при сбое шины — `503 bus_unavailable` (C-08 v1.5; итерация 2). *Почему не «удаление, затем хуки»:* после удаления игрока не найти по внешнему ID, и хук, упавший после `DELETE`, оставил бы персонажа без `abandoned` и сессию открытой без способа повторить каскад.
2. **`CompactLinks`** (уточняет доп. 1 п. 1): `PRAGMA incremental_vacuum`, затем `PRAGMA wal_checkpoint(TRUNCATE)`. Vacuum сам пишет в WAL, и только checkpoint последним оставляет WAL пустым, а файл сжатым. Checkpoint с `busy != 0` — ошибка: удалённые байты остались в WAL.
3. **Незавершённое стирание.** `CompactLinks` не удался после закоммиченного `DELETE` (читатель вне процесса дольше `busy_timeout` 5 с или истёк дедлайн запроса) — ответ `503 forget_incomplete` с `Retry-After: 5`, стор ставит отметку «сжатие отложено» в памяти процесса. Пока отметка стоит, любой `/forget` отвечает 503, кроме вызова, который сам завершил сжатие; `200 {deleted:false}` после 503 — конец того же забвения. Данные не объявляются удалёнными, пока файл и WAL не очищены (доп. 1 п. 1).
4. **Кто доделывает без клиента.** `Start` контекста — безусловное `Compact` до маршрутов и sweeper'а, в любом режиме: новый процесс не знает об отметке прежнего. Неудача ставит отметку и старт не валит. Sweeper в `live` — `Sweep` раз в минуту доделывает отложенное, `Compact` раз в час — страховка п. 5 решения. `Stop` — `Compact` при отметке, если sweeper остановлен. `/health` gateway — `degraded` с `links_compaction: pending`.
5. **Эксплуатация.** `links.db` открыт одним соединением (п. 1), и под удерживающим читателем каждая попытка сжатия занимает его до 5 с: `resolve`, `consent` и `RouteFor` ждут. Бэкап живого `links.db` (п. 8) удерживает читателя всё время копирования, и `/forget` на это время отвечает 503; бэкап делать коротким `sqlite3 .backup` или при остановленном процессе. Клиент `forget_incomplete` сам не повторяет (C-08 v1.5).
6. **Отвергнуто.** `200` с отложенным стиранием — нарушает доп. 1 п. 1. `500 internal` — это не дефект кода, а внешняя блокировка, и клиент `500` не повторяет. Ожидание читателя без предела внутри запроса — держит единственное соединение и все маршруты связок.
7. **Известное окно.** Успешный `Compact` sweeper'а может снять отметку, поставленную параллельным `/forget` с неудачным сжатием. Страховка — часовое сжатие и сжатие при старте. Закрыть мьютексом «`DELETE` + сжатие» или счётчиком поколений отметки — T-306, запасной путь — T-314.
