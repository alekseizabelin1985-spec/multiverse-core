# ADR-005: LLM-шлюз — абстракция провайдера, structured output, размещение моделей на RTX 4090, облако за флагом (доп. 2: llama-server `openai_compat` по умолчанию, Ollama — второй)

Статус: предложено (к утверждению на G2) · Дата: 2026-09-09 · Автор: system-architect#1
Связи: OQ-A-05 (часть LLM/эмбеддинги), OQ-D-13, OQ-P-07, OQ-R-10, OQ-A-18 (новый: базовая конфигурация моделей); FR-015, FR-032, FR-034, FR-050, FR-051, FR-070…FR-072; BR-14, BR-15; NFR-002, NFR-004, NFR-006, NFR-007, NFR-022, NFR-046, NFR-050…NFR-053, NFR-076, NFR-090; `integrations.md` §2; `domain-review.md` DR-22.

## Контекст

As-is: четыре LLM-клиента (`shared/oracle`, `shared/intent`, `orchestrator/oracle.go`, `oracle_llm_adapter.go`), все через OpenAI-совместимый `/v1/chat/completions`, без учёта токенов, бюджета, записи ответов; модели в блупринтах `qwen:7b/72b` (нет в линейке Qwen3). Решения: локальный Ollama по умолчанию, облако через абстракцию; две модели Qwen3 одновременно (8b + 30b-a3b/32b) на RTX 4090 24 ГБ; structured output и `thinking off` для Phase 1 (DR-22); пороги — после замера.

Проверка размеров (Q4_K_M, публичные данные Ollama/HF, сентябрь 2026): `qwen3:30b-a3b` ≈ 18,6 ГБ веса + KV-кэш ≈ 2–4 ГБ при 8–16k контекста; `qwen3:8b` ≈ 5,2 ГБ; `qwen3:14b` ≈ 9,0 ГБ; `qwen3:32b` ≈ 20 ГБ. Ollama грузит модель в VRAM целиком, если помещается, иначе молча выгружает часть слоёв в RAM (`num_gpu` управляет вручную); `OLLAMA_MAX_LOADED_MODELS` (по умолчанию 3) и `keep_alive` держат модели резидентными. Structured output (`format` = JSON-схема) поддерживается с Ollama 0.5; для Qwen3 есть открытые issue о «преамбуле» перед JSON на части версий — нужен парсер с восстановлением.

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| API Ollama | OpenAI-совместимый `/v1/chat/completions` | один клиент на локаль и облако | нет `think`, `keep_alive`, `format`-схемы (частично), `num_gpu` |
| | **native `/api/chat` для Ollama + отдельные адаптеры для облака** | полный контроль (`think:false`, `keep_alive`, `format`, `options`) | два формата запросов (скрыто за интерфейсом) |
| Размещение моделей | 8b + 30b-a3b полностью в VRAM | как решено р5 | ≈ 24–28 ГБ с KV-кэшем — не помещается |
| | 8b + 30b-a3b, MoE частично в RAM | «две модели» формально | скорость Phase 2 зависит от выгрузки; замер |
| | **одна 30b-a3b на нарратив и тики** | помещается; 3B активных — тики дёшевы; одна модель в прогреве | нет «малой модели» для Phase 1 с LLM (в MVP-1 Phase 1 без LLM — не нужна) |
| | 8b + 14b | помещается с запасом | качество русского у 14b — замер |
| Фильтр (a) | вне шлюза (в Gateway при доставке) | ближе к клиенту | `response_raw` успел бы записаться (NFR-048) |
| | **в шлюзе до записи `llm.output`** | fail-closed до сохранения | шлюз знает о контенте (приемлемо: это его middleware) |

## Решение

1. **Интерфейс** `internal/llm`:
   ```go
   type Provider interface {
       Generate(ctx, Request) (Response, error) // Request{Phase, Model, System, Messages, Schema json.RawMessage, Params{Temperature, MaxTokens, Think bool}, Timeout, CorrelationID}
       Embed(ctx, model string, texts []string) ([][]float32, error)
       Health(ctx) Status                       // модели загружены/резидентны
   }
   ```
   Реализации: `providers/ollama` (native `/api/chat`, `/api/embed`, `format`=схема, `think`, `keep_alive=-1`, `options.num_ctx`), `providers/openai_compat` (OpenAI, DeepSeek; `response_format: json_schema`), `providers/anthropic` (целевое), `providers/recorded` (replay), `providers/fake` (тесты). Выбор — конфигурацией `LLM_PROVIDER=ollama|openai|deepseek|anthropic`, модель — из блупринта на фазу/уровень.
2. **Конвейер шлюза (middleware, порядок фиксирован)**: бюджет (окно по `(world, level, phase)`; фон — `B`/час/мир; облако — денежный лимит) → провайдер с таймаутом фазы (ориентиры: phase1 5 с, phase2 20 с, tick 30 с; уточняются замером) и повторами `attempt ≤ retries` → парсер JSON с восстановлением (обрезка преамбулы/код-блоков, повтор при `schema_invalid`) → проверка языка (0 CJK, латиница ≤ порога) → **фильтр категории (a)** (словарь/регулярные выражения из `config/absolute-limits.yaml`, fail-closed) → запись `llm.output` (при `quarantined`/`filter_error` — без `response_raw`, плюс `content.incident.recorded`) → страж (`guardian`: сущности существуют и видимы, нет `player.*`, типы ∈ `allowed_event_types`, сущности ∈ `owned_entity_types`, инварианты законов, `laws_version` актуальна) → результат конвейеру агента. `llm.output.rejected` публикуется на каждый отклонённый элемент/вызов с `reason` из перечисления FR-034.
3. **Учёт**: `tokens{prompt, completion}` из ответа провайдера, `cost_usd` по таблице цен в конфигурации (0 для Ollama), `latency_ms`, `provider`, `model`, `attempt`; агрегаты доступны `mvctl llm usage` и `/v1/admin/llm/usage` (Should).
4. **Промпт**: секции `<laws laws_version>`, `<canon>`, `<state>`, `<events>`, `<absence>`, `<player_text>` (реплики и имена — как данные, экранированы), `<absolute_limits>` (короткая позитивная формулировка BR-08 из конфигурации), `locale`; `prompt_hash` = SHA-256 полного промпта; полный текст — в `prompts-{world}` по флагу. Основа — `prompt_builder.go` narrative-orchestrator (структурированные секции, тесты) → `internal/llm/prompt`.
5. **Размещение моделей**: базовая конфигурация выбирается **после матрицы замера** (`overview.md` §18.1): A `8b+14b`, B `8b+30b-a3b (частично в RAM)`, C `30b-a3b одна`, D `32b`. Рекомендация архитектора — C при прохождении NFR-002/NFR-090, иначе A; решение фиксируется в `ops/metrics/baseline.md` и блупринтах (OQ-A-18). Compose: `OLLAMA_KEEP_ALIVE=-1`, `OLLAMA_MAX_LOADED_MODELS=2`, `OLLAMA_NUM_PARALLEL=1`, прогрев моделей в `make up` (`/api/generate` пустой промпт) — NFR-004.
6. **Облако** (BR-15, NFR-046): включается `LLM_CLOUD_ENABLED=true` + ключ в env; при числе связок с `alive`-персонажем > 1 требуется `LLM_CLOUD_ALLOW_EXTERNAL_PLAYERS=true` — факт включения пишется в `system_events` (`config.cloud_enabled {by: operator}`); в промпт уходят только `player_id` и имена персонажей; лимит `LLM_CLOUD_BUDGET_USD_PER_DAY` → `budget_exceeded` → локальный провайдер/шаблон.
7. **Деградация** (BR-14, FR-015): любой `error`/таймаут после повторов → `ErrUnavailable` → конвейер агента публикует `narrative.output generated_by=template fallback_reason=…`; тики — LOD 1; `/health.llm=unavailable`; восстановление без рестарта.

## Последствия

- Позитивные: один клиент вместо четырёх; учёт и бюджет в одном месте; record-replay и фильтр — гарантированно до использования ответа; смена модели — правка блупринта.
- Негативные: native API Ollama — отдельный адаптер (≈ 300 строк); риск «преамбулы» у Qwen3 — парсер с восстановлением и золотой набор NFR-065.
- Что придётся сделать: EPIC-001 — матрица замера и `baseline.md`; EPIC-003 — шлюз, провайдеры `ollama`/`recorded`/`fake`, страж, фильтр (a), `config/absolute-limits.yaml`; E-H — `openai_compat`/`anthropic` как рабочие опции.

## Дополнение 2 — 2026-09-09 (сведение A4-2; решение пользователя U-8 «LLM нативно на llama.cpp»)

Контекст: на целевой машине LLM обычно запускается **нативно** через `llama-server.exe` (llama.cpp) с моделью `D:\Models\unsloth\Qwen3.8\Qwen3.8-27B-UD-Q3_K_XL.gguf` на `127.0.0.1:1234` (`--n-gpu-layers 99 --flash-attn on --jinja --kv-offload --kv-unified --reasoning on --models-dir D:\Models\ --slot-save-path … --load-mode mmap+mlock`, семплинг `--temp 1 --min-p 0.01 --top-p 0.95 --top-k 20`); Ollama тоже установлен. Проверено 2026-09-09 (README `tools/server` llama.cpp, HF `unsloth/Qwen3.8-27B-GGUF`, issue ggml-org/llama.cpp#20345):
- llama-server даёт OpenAI-совместимые `POST /v1/chat/completions` (structured output — `response_format: {type: json_schema, json_schema: {name, schema}}`, grammar-sampling по схеме), `POST /v1/embeddings`, `GET /v1/models`, `GET /health` (`200 {"status":"ok"}` / `503 Loading model`), `GET /slots`, `GET /props`; ответ содержит `usage{prompt_tokens, completion_tokens, prompt_tokens_details.cached_tokens}` и `timings{prompt_ms, predicted_ms, …}`; reasoning модели отдаётся отдельным полем `message.reasoning_content` (`--reasoning-format`), включение на запрос — `chat_template_kwargs: {"enable_thinking": false}`; серверные `--reasoning on|off|auto`, `--reasoning-budget N`.
- **Известный дефект** (#20345, открыт с 2026-03): при включённом thinking грамматика `json_schema` **не применяется** — модель может вернуть markdown-обёртку или чужие поля. Следствие: для всех фаз со схемой шлюз обязан выключать thinking на уровне запроса.
- Router-режим (`--models-dir`, переключение моделей по `model` в запросе, `--models-max`, `POST /models/load|unload`) активен **только без `-m`**; при заданном `-m` сервер в single-model режиме и поле `model` игнорируется (модель одна, `GET /v1/models` возвращает её имя).
- `Qwen3.8-27B` — dense, 64 слоя, 24 Q-головы / **4 KV-головы**, `head_dim` 256; файл `UD-Q3_K_XL` = **13,1 ГБ** (`UD-Q4_K_XL` 17,6 ГБ, `UD-Q2_K_XL` 9,8 ГБ). KV-кэш f16 = 2 × 64 × 4 × 256 × 2 Б = **256 КиБ/токен** → ≈ 2 ГБ при 8k, ≈ 4 ГБ при 16k (q8_0 — вдвое меньше). Итого ≈ 16–19 ГБ VRAM при 8–16k — помещается в 24 ГБ с запасом на compute-буферы. Рекомендованный семплинг Unsloth: thinking — `temp 1.0, top_p 0.95, top_k 20, min_p 0`; **non-thinking — `temp 0.7, top_p 0.8, top_k 20, presence_penalty 1.5`**.

1. **Провайдер по умолчанию — `openai_compat`** (llama-server): `MV_LLM_PROVIDER=openai_compat`, `MV_LLM_URL=http://127.0.0.1:1234` (из контейнеров — `http://host.docker.internal:1234`), `MV_LLM_API_KEY` (необязателен локально). Реализация `providers/openai_compat`: `Generate` → `/v1/chat/completions` с `response_format json_schema`, `chat_template_kwargs.enable_thinking = Params.Think` (по умолчанию `false` для всех фаз MVP-1 из-за #20345), параметры семплинга **на запрос** из блупринта (`temperature, top_p, top_k, min_p, presence_penalty, max_tokens`; серверные значения `--temp 1 …` — thinking-профиль, шлюз их переопределяет non-thinking-профилем `0.7/0.8/20/0/1.5` как значениями по умолчанию фазы), `stream:false`; `Embed` → `/v1/embeddings`; `Models` → `GET /v1/models`; `Health` → `GET /health` (503 = `loading`, не `unavailable`) + `Models` (модель блупринта присутствует → `ok`, иначе `degraded(model_not_resident)`); токены — из `usage`, задержка — из `timings` (при отсутствии — по часам шлюза); `reasoning_content` в `llm.output` не пишется (только длина в `parse{}`), стратегия парсера `strip_think` (ADR-016) сохраняется как страховка.
2. **Порядок реализаций** (уточнение п. 1 решения): `openai_compat` — первым (EPIC-003 единица **B3a**), `ollama` native — вторым (**B3b**, тот же интерфейс `Provider`, включается `MV_LLM_PROVIDER=ollama` + `MV_OLLAMA_URL`); облако — **та же реализация `openai_compat` с другим `MV_LLM_URL`/`MV_LLM_API_KEY`** (OpenAI, DeepSeek и любой OpenAI-совместимый шлюз); `anthropic` — отдельный адаптер, целевое (E-H). Значения `MV_LLM_PROVIDER`: `openai_compat | ollama | anthropic | recorded | fake` (имена `openai|deepseek` больше не используются как имена провайдера — это только URL/ключ).
3. **Гейт облака (п. 6 без изменений по сути, уточнение механизма)**: «облако» определяется **не именем провайдера, а адресом**: если host `MV_LLM_URL` не loopback, не `host.docker.internal` и не RFC1918 — провайдер отказывается стартовать без `MV_LLM_CLOUD_ENABLED=true`; при `true` контекст `llm` публикует `config.cloud_enabled {by: operator, provider: openai_compat, endpoint_host}` (без ключей). `cost_usd` — по `config/llm-prices.yaml` по ключу `(endpoint_host, model)`; для локальных адресов 0.
4. **Выбор модели**: поле `model` запроса = имя из `GET /v1/models` (для `--models-dir` — stem файла, например `Qwen3.8-27B-UD-Q3_K_XL`); валидатор C-11 (правило 7а) сверяет модель блупринта со списком провайдера — при single-model режиме список из одного имени. Переключение моделей по имени (конфигурация A — две модели) требует router-режима (`llama-server` без `-m`, `--models-dir`, `--models-max 2`) или второго процесса; это фиксируется в `scripts/llm-server.ps1` по итогам F-8.
5. **Матрица F-8 — вариант E** (OQ-A-18 уточнён пользователем): **E = одна `Qwen3.8-27B UD-Q3_K_XL` на llama-server** на нарратив и тики (≈ 13,1 ГБ + KV 2–4 ГБ). **Базовая конфигурация: E, если проходит NFR-002/NFR-090; иначе C (`qwen3:30b-a3b`, Ollama или GGUF на llama-server); иначе A (`8b + 14b`).** B и D — материал замера. Дополнительно фиксируется E+ (27B + `qwen3-8b` для тиков в router-режиме, ≈ 18–22 ГБ) — только как материал. `ops/metrics/bench-matrix.json` получает `provider` на конфигурацию; скрипт замера ходит в `/v1/chat/completions` (для C/A через Ollama — в его OpenAI-совместимый эндпоинт или native, на выбор devops), метрики те же. Блупринты MVP-1 до `baseline.md` задают **E** (`model: Qwen3.8-27B-UD-Q3_K_XL`, `thinking: false`). **Читать с поправкой дополнения 3 (2026-09-12):** правило выбора — «проходит пороги **и** даёт нужную длину нарратива»; E — базовая на переход, целевая конфигурация нарратива — `Qwen3.6-35B-A3B`, порядок запасных — `E → Qwen3.6 → C → A`.
6. **Прогрев и резидентность (NFR-004)**: для llama-server прогрев не нужен — модель загружена при старте процесса (`mmap+mlock`), `keep_alive` не применяется; `/health` = 503 до окончания загрузки → `make up`/`make health` ждут `200`. `--kv-unified` и один слот — соответствует `OLLAMA_NUM_PARALLEL=1` (интерактив впереди фона обеспечивает планировщик роя, ADR-014). `--slot-save-path` шлюзом не используется (кэш промпта работает автоматически по общему префиксу `system`, см. `cached_tokens`).
7. **Управление процессом llama-server (OQ-A-21, решение архитектора)**: нативный процесс **вне compose**; запуск — `scripts/llm-server.ps1` с зафиксированными параметрами (модель, порт, `--reasoning`, семплинг по умолчанию, `--ctx-size` = `MV_LLM_NUM_CTX` × число слотов) и `make llm-up`/`make llm-down` как обёртки; `make up` процесс **не** запускает — только проверяет `GET $MV_LLM_URL/health` и предупреждает (NFR-072, деградация FR-080). Служба Windows/Task Scheduler — не в MVP-1 (один оператор, ручной запуск по runbook); переход к службе — при появлении внешних тестеров (E-H). Ollama остаётся **опциональным** вторым рантаймом (профиль `gpu` в compose и нативная установка) для конфигураций C/A и эмбеддингов, если llama-server их не обслуживает.
8. **Эмбеддинги (C-09/C-15, EPIC-005)**: `Embed` через `/v1/embeddings` того же llama-server требует загруженной embedding-модели (`nomic-embed-text`/`bge-m3` GGUF в router-режиме) — либо `MV_MEMORY_EMBED_PROVIDER=ollama` отдельно от основного провайдера; выбор — architect#1 в 005-memory (Should), решение не блокирует.
9. **Последствия для документов**: C-15 v1.1 (`contracts.md`), `overview.md` §13/§15/§18.1, `infrastructure.md` §4.2/§6 (devops), `components/swarm-llm-laws.md` §9.1 и `design.md` EPIC-003 B3 → B3a/B3b (architect#2/tech-lead#2), `epics.md` F-6/F-8, `open-questions.md` OQ-A-18/OQ-A-21. ## Дополнение 3 — 2026-09-12 (решение пользователя по T-435: правило выбора и целевая конфигурация нарратива)

## Уточнение исполнения (2026-09-12, T-435, architect#1)

Исполнение п. 5 доп. 2 с поправкой доп. 3: на каких данных принята E, с какими отклонениями от методики, что доказывает ячейку платформы и какой потолок длины держит каждая конфигурация. Основание — `ops/metrics/baseline.md` §2–§5 (замер T-402) и `requests[]` отчётов `bench-E-*`, `bench-Q36-A3B-*`.

1. **Базовая на переход — E**: `Qwen3.8-27B-UD-Q3_K_XL`, `openai_compat`, `server_mode: single`, одна модель на тики и нарратив. Ячейка платформы — `MV_LLM_NUM_CTX=8192`, `MV_LLM_SLOTS=1`, KV `f16`. KV `f16` — умолчание llama.cpp: `scripts/llm-server.{sh,ps1}` не передают `--cache-type-*`. Это уже значения `.env.example`, правок нет.
   *Почему:* три зачётных прогона на пути платформы (чистый `llama-server`), все `pass` по `phase2`: p95 2585 / 2916 / 3533 мс. По 30 замерам `phase2` медиана 2470 мс, максимум 3533 мс, выше 5000 — ни одного. B3 и NFR-090 — 1,0. Правило §6.4 п. 2 («разные дни / после перезапуска») выполнено буквально: прогоны 3 и 4 — после перезапуска, прогон 2 — через 2,7 мин после старта сервера.
2. **Два отклонения от методики.** §6.4 п. 3 требует четыре ячейки 8192/16384 × f16/q8_0, а зачётные прогоны шли:
   - в окне **4 × 200 192** — ни одна ячейка матрицы;
   - на KV **`q4_0`** (со слов владельца, 2026-09-12) — такого типа в матрице нет вовсе.

   Оба отклонения приняты для вердикта и не приняты для настройки платформы.
   - *Размещение.* Окно стенда — худший случай по VRAM. Ячейка платформы 1 × 8192 выделяет под KV в ~98 раз меньше токенов, а `f16` дороже `q4_0` на токен примерно в 3,6 раза: итог всё равно в разы меньше. Вся карта вместе с рабочим столом — 19,4 ГБ, в пределах 20 480 МБ.
   - *Латентность и качество на `f16` не измерены.* При 400–530 заполненных токенах вклад внимания мал, но в какую сторону сдвинет переход `q4_0` → `f16` — рассуждение, а не замер. B3 = 1,0 и NFR-090 = 1,0 получены на самом грубом KV; для `f16` это скорее нижняя оценка.
   - Ячейки q8_0 нужны, только если `f16` не помещается, — помещается. Ячейка 16384 нужна, только если промпт длиннее 8k, — в MVP-1 это не так.
   - **Ячейку платформы доказывает контрольный прогон** E (8192 × 1, `f16`, `--alias`) в другой день — прогон 1 сессии T-438. Полная матрица (12 прогонов, 4 перезапуска) не нужна: q8_0 и 16384 отвечают на вопросы, которых у E нет.
   - *Что значит «E прошла» в контрольном прогоне* (один термин на все документы): `verdict=pass` по NFR-002 (p95 ≤ 5000 мс) **и** p95 ≤ 4400 мс **и** медиана ≤ 3000 мс. Две последние границы — признак того, что ячейка платформы (`f16`, 8192) не медленнее зачётных прогонов на `q4_0`: при n = 10 p95 прогона равен его самому медленному запросу, поэтому одна граница по p95 срабатывала бы от единственного выброса при формально `pass`. Медиана (в зачётных прогонах 2470 мс) удерживает решение от зависимости от одного запроса.
   - *Условия пересмотра:* E не прошла в этом смысле. Отказ по NFR-002 (`fail`) и «прошла по порогу, но вышла за 4400 / 3000 мс» — разные вещи: первое закрывает E как базовую, второе — **сигнал к пересмотру**, с разбора «прочего» по `prompt_ms` (T-434) и только затем `decision_order`. Остальные исходы сессии — таблица в T-438.
3. **Незачёт прогона 1 подтверждён.** Матрица определяет E как `server_mode: single` на `llama-server`. Прогон 1 шёл через роутер Unsloth Studio — другой сервер, не router-режим llama.cpp, — на другом билде (b10840) и с другим окном (221 696). Это замер другой конфигурации, а не неудачный прогон E. Цена названа: засчитай его — E не прошла бы (один `fail` → следующая конфигурация). Причина ~6 с в нём не установлена, а Q36 показала хвост и на чистом пути. Поэтому «чистый путь без задержек» — вывод по 90 запросам, а не доказательство. Ловят контрольный прогон и `narrative_latency_p95_ms` в S1/S2.
4. **Потолок длины нарратива — свой у каждой конфигурации.** Формула бюджета: N = (порог − «прочее» − 150 мс на шину и gateway, B1) × скорость генерации на запрос. «Прочее» = латентность клиента − `timings.predicted_ms`.
   - **E (базовая на переход):** (5000 − 850 − 150) × 40,8 ≈ 163 токена → `max_tokens` `phase2` соло — **160**. Здесь 850 мс — максимум «прочего» по 60 нарративным запросам прогонов 2–4, 40,8 ток/с — минимум по запросам `phase2`.
   - **Qwen3.6-35B-A3B (целевая):** считать по её собственному «прочему» — 2801 мс с нынешним хвостом и 1027 мс без него — и её скорости `phase2` 107,2–128,3 ток/с. Отсюда ≈ **220** токенов с хвостом и ≈ **410** без. Окончательное значение — после трёх прогонов T-438.
   - `max_tokens` — жёсткий обрез: обрезанный ответ невалиден, дальше повтор и шаблон. На нормальном ответе он срабатывать не должен (максимум замера — 130 токенов).
   - Длину держит схема, а не обрез: `text.maxLength` ≈ (`max_tokens` − каркас JSON − служебные поля) × символов на токен × 0,9. Принятые величины: **каркас ≈ 30 токенов** (ключи, скобки, `kind`/`tone`), **служебные поля ≈ 36 токенов** — `mentions` `maxItems` 4 и `background_refs` `maxItems` 2, элемент ≈ 6 токенов (идентификатор в кавычках с запятой); вместе вычитается ≈ 66 токенов. Грамматика `json_schema` закрывает строку сама — проверить тестом на стенде. «Символов на токен» измеряется запросом `/tokenize` (шаг 5 сессии T-438); до измерения — допущение 2,5 символа кириллицы на токен. Отсюда воспроизводимо: E (160 − 66) × 2,5 × 0,9 ≈ **210** символов; Qwen3.6 (220 − 66) × 2,25 ≈ **345** с хвостом и (410 − 66) × 2,25 ≈ **775** без него. Меняются `maxItems` — меняется и `maxLength`, формула та же.
   - **Группа.** Пока действует справочный порог 5000 мс, потолок группы для Qwen3.6 считан по её данным группы: ≈ 226 токенов с хвостом и ≈ 418 без. Для E взята **оценка по соло — 163 токена — как более строгая**: по данным группы у неё выходит 169 (её «прочее» 854 мс и 42,3 ток/с). При ориентире «не хуже двух соло» (10 с) — E ≈ 367 по соло (≈ 380 по группе), Qwen3.6 ≈ 760 и ≈ 950. Порог группы фиксирует T-140 (BA). Потолки промптов замера (320 у `phase2`, 512 у группы) — свойство замера, а не цель: под 5000 мс на E не проходит ни один из них.
   - Бюджет посчитан на промптах ~420 токенов. Длиннее реальный промпт — больше «прочего», и N пересчитывается по `prompt_ms` (T-434).
   - Сегодня КД EPIC-003 §13.3–13.4 задаёт `player-gm phase2 max_tokens: 700` и `narrative.json text.maxLength: 1500` плюс массивы; 700 токенов на E — ~17 с генерации. Адресат правки — **T-439** (architect#2): КД §13.3–13.4, стартовая модель в `:735` и `:977`, а также то, что делает T-203, если стартует раньше T-438.
5. **Qwen3.6-35B-A3B — запасной № 1 и целевая конфигурация нарратива** (доп. 3 пп. 2–3), `decision_order` E → Qwen3.6 → C → A.
   *Почему перед C:* тот же класс, что C (MoE, ~3 млрд активных), но на пути платформы (`llama-server`, без Ollama), уже на стенде и в справочном прогоне прошла все пороги. У C нет ни одного замера.
   Условие приёма сверх вердикта: три прогона по методике в ячейке платформы (после T-434 и T-437), и «прочее» > 2 с исчезает либо объяснено по `prompt_ms`. Необъяснённый хвост у половины нарративных запросов при `pass` по p95 — это непредсказуемая латентность: с ним Qwen3.6 базовой не становится, и тогда вопрос длины нарратива возвращается владельцу (доп. 3 п. 4). Гипотезу «4 слота: выбор слота или восстановление контекста» ячейка платформы проверяет сама: слот там один.
