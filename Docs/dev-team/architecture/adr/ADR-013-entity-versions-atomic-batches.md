# ADR-013: Версии сущностей и atomic-пакеты — оптимистичная версия на сущность, типизированные ops, дедуп по `proposal_id`, интент-объект как WAL для многосущностных пакетов

Статус: предложено (к ревью system-architect, утверждение на G3) · Дата: 2026-09-09 · Автор: architect#1 (TEAM-1, EPIC-002)
Уровень: реализация внутри блока EPIC-002 (в границах ADR-003 п. 1, overview §14 п. 9 «границы транзакций», C-02, BR-03, BR-13, BR-16 п. 4).
Связи: FR-030, FR-033; NFR-012, NFR-013, NFR-020 (inv-04, inv-06); `state-and-mechanics.md` §3.2, §4.5–§4.7; `api-contracts.md` §2.3.4; UC-015, UC-016 A1.

## Контекст

Overview §14 п. 9: «одна сущность = одна атомарная запись (PUT целиком); пакет `atomic=true` — последовательные PUT после проверки всех версий в памяти». Последовательные PUT не атомарны на диске: падение процесса между PUT группы и PUT участника оставляет объекты в состоянии, нарушающем inv-04, а снапшот + журнал (ADR-011) это состояние узаконят при сверке. Также нужно зафиксировать семантику `ops` (as-is entity-manager: `set/add_to_slice/remove_from_slice/remove` без версий и без ошибок), поведение `expected_version` (опционален по C-02), правило `changed=[]` (UC-011 E2), частичное применение `atomic=false` и дедуп повторных предложений при at-least-once.

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| Атомарность пакета на диске | A. последовательные PUT, при падении — обнаружить дивергенцию и остановиться (`/health fail`) | ничего дополнительного | инвариант нарушен на диске; восстановление — ручное |
| | B. один объект-«транзакция» с копиями всех сущностей пакета + указатели | один PUT | ломает «объект на сущность» (потребители read-model читают объекты); двойное хранение |
| | **C. интент-объект** `entities-{world}/_intents/{proposal_id}.json` с `{changes[]{ref, from_version, to_version, attributes_after}}` перед PUT'ами, удаление после; при старте — roll-forward незавершённых | объект на сущность сохраняется; «все или ничего» достигается доведением до конца (roll-forward), а не откатом; только для пакетов > 1 сущности | +1 PUT и +1 DELETE на пакет (≈ 40 мс); интент — ещё один формат |
| | D. PostgreSQL с транзакциями | настоящая атомарность | отклонено ADR-004 для MVP-1 |
| `expected_version` | A. обязателен всегда | строгий optimistic lock | GM региона/gateway не всегда держат актуальную версию (фоновые изменения) → лишние конфликты |
| | **B. опционален (C-02)**: задан — строгая проверка; не задан — применение к текущей версии с инвариантами | гибко: механика боя задаёт (спорные HP), перемещения/тики могут не задавать | без версии два предложения на одно поле применяются оба (last-writer) — допустимо только для полей, где это не HP/инвентарь/позиция; правило владения ограничивает |
| Ops | A. свободный `set` по любому пути | просто | нельзя выразить «+1» и «добавить предмет» без гонок |
| | **B. четыре типизированных `set|inc|append|remove`** с семантикой из §3.2 (`inc` — clamp для `hp`; `append` — дедуп по `item_id`/`player_id`; `remove` — по ключу элемента) | покрывает MVP-1 и C-13; ошибки — `invalid_op` до записи | `append` с дедупом — неявная семантика (документирована) |

| `atomic=false` с ошибкой части | A. отклонить всё | просто | противоречит смыслу флага |
| | **B. применить проходящие, отклонить остальные по одной сущности** | соответствует C-02 | инварианты пересчитываются по оставшимся |

## Решение

1. **Версия** — `int64` на сущность, строго `+1` на каждый факт с непустым `changed[]`; при `changed=[]` версия и `last_event_id` не меняются, факт публикуется с пустым `changed` (ход засчитан — UC-011 E2). `expected_version` опционален (C-02): задан и не совпадает → `version_conflict {expected_version, actual_version}`; не задан → применение к текущей. Правило для издателей (EPIC-003/004): **обязателен** для путей `hp`, `status`, `inventory`, `position` игрока/NPC в бою; для `world.*`/`region.*` атрибутов тиков и для служебных полей встречи — допускается без версии.
2. **Ops** — `shared/entity.Op{Op, Path, Value}` с семантикой `state-and-mechanics.md` §3.2; применение на копии; `changed[]` строится после всех ops сущности, no-op исключаются; зарезервированные пути → `invalid_op`.
3. **Порядок применения предложения**: разбор → дедуп → существование → версии → мёртвые → владение → ops на копиях → инварианты по overlay-представлению (WorldSet + копии) → решение по пакету → персист → публикация → замена оригиналов (`state-and-mechanics.md` §4.5). Пакет `atomic=true` — любая ошибка отклоняет весь пакет одним `rejected`; `atomic=false` — по сущности.
4. **Интент** для пакетов `atomic=true` с числом изменённых сущностей > 1: `PutIntent{proposal_id, proposal_event_id, world, cause, changes[]{ref, from_version, to_version, attributes_after, changed[]}}` → PUT сущностей по возрастанию `id` → `DeleteIntent`. Roll-forward при старте (после снапшота и фактов журнала): для каждого интента — сущности с `version == from_version` получают `attributes_after`/`to_version` (PUT), сущности уже на `to_version` пропускаются; затем публикуются недостающие факты и интент удаляется. Интент с `from_version` ≠ текущей и ≠ `to_version` — дивергенция (`/health fail`). Пакеты из одной сущности интент не пишут (PUT атомарен).
5. **Дедуп**: `proposal_id` в LRU (10 000; сериализуется в снапшот последними 1000) **или** `last_change.proposal_id` у всех целевых сущностей → предложение считается применённым: если `fact_event_id` пуст — факты дослать, иначе тихий пропуск. Предложения с офсетом до курсора снапшота не читаются (ADR-011 п. 4).
6. **Конфликты между уровнями** (BR-16 п. 4): разрешаются версией; издатель повторяет с актуальной версией ≤ 3 раз (рекомендация EPIC-003: агент встречи держит проекцию версий из `entity.updated` и сериализует предложения на scope, поэтому конфликт внутри агента невозможен).

## Последствия

- Позитивные: инварианты позиции группы и scope не нарушаются на диске ни при каком падении; ops с явной семантикой и ошибками до записи; идемпотентность при at-least-once и после рестарта без внешней БД.
- Негативные: интент добавляет ≈ 40 мс к пакетам из > 1 сущности (перемещение группы, пакет раунда с NPC + игроком + встречей); если замер NFR-001 покажет превышение — вариант B (объект-транзакция) не меняет контрактов; `expected_version` опционален, поэтому дисциплина издателей проверяется ревью и тестом «два удара по волку» (UC-016 A1).
- Что придётся сделать: `shared/entity/ops.go`, `internal/state/{apply,intent,dedup}.go`, схема `entity.update.proposed.v1.json` (ops enum, `expected_version` опционален), тесты матрицы отказов и roll-forward; уточнение C-02 в `contracts.md` (частичное применение при `atomic=false`, `duplicate_entity`, `changed=[]`).
