# ADR-022: Старт потребителя без рукопожатия готовности — «новая группа читает журнал с первого офсета» признано гарантией C-01

Статус: принято · Дата: 2026-09-11 · Автор: architect#1 (TEAM-1, EPIC-001, сведение расхождений волны 0)
Уровень: реализация внутри границ C-01 (ADR-007, ADR-010); гарантия шины, не смена стека и не смена границ блоков.
Связи: C-01 v1.2, C-14 (порядок старта), NFR-013 (RTO), задачи T-005, T-014, T-017; `journal.md` 2026-09-10…2026-09-11 (T-017 ревью #1 Minor-2, ревью #2 Nit-5, поправка ревьюера к итерации 2 T-014).

## Контекст

Потребитель, который перед началом работы должен просигналить «я готов» (`testkit/state.FakeState` публикует `analytics.replay.completed` по C-14 v0.4, и рой с gateway начинают предлагать изменения, увидев этот сигнал), обязан гарантировать порядок «подписка живёт → сигнал». Иначе на брокере, где новая consumer group начинает чтение **с конца** журнала, событие, опубликованное между сигналом и регистрацией группы, не будет доставлено никогда.

Средствами интерфейса `Bus` этот момент невыразим: `Subscribe` блокируется до конца подписки, и регистрация группы происходит **внутри невернувшегося вызова**. Исполнитель T-017 обошёл это опциональным интерфейсом `readySubscriber` (шина, знающая момент регистрации, отчитывается каналом), который **ни одна** реализация в дереве не реализует, — то есть в бою всегда работала запасная ветка. Задача прошла четыре ревью, из них два — вокруг этого места.

Поправка ревьюера, снявшая проблему: свойство «новая группа читает с первого офсета» принадлежит **обеим** реализациям C-01 — kafka-адаптер подписывается с `StartOffset: kafka.FirstOffset`, `membus` держит курсор группы, начинающийся с нуля. Значит потерянного окна нет ни на одной из них.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Оставить опциональный интерфейс `readySubscriber` в потребителе | ничего не меняется | ветка, которую не выбирает ни одна реализация; выбор делается приведением типа, которое не проверяет компилятор; каждый следующий потребитель напишет свой такой же интерфейс |
| B. Поднять интерфейс готовности в `shared/eventbus` | одно место вместо N | интерфейс без реализаций — мёртвый код в общем пакете; не решает ничего сегодня |
| C. Добавить канал готовности в `Subscribe` | строгий порядок по построению | самый дорогой: несовместимая правка C-01, обе реализации, все вызывающие; ради свойства, которое обе шины уже дают |
| **D. Признать «новая группа читает с первого офсета» гарантией C-01 и закрепить contract-тестом** | рукопожатие не нужно **никому**; `readySubscriber` удаляется целиком; проверка одна и общая для обеих шин | гарантия сужает выбор транспорта: брокер без этого свойства (или тема с политикой `latest`) потребует вернуться к варианту B или C |

## Решение

1. **C-01 v1.2**: подписка новой consumer group начинает чтение с **первого офсета** топика. Это гарантия контракта, проверяемая общим contract-тестом шины на `membus` и на kafka-адаптере (testcontainers), а не свойство одной реализации.
2. Рукопожатие «подписка готова» в контракт **не** вводится. Опциональный интерфейс `readySubscriber` и его запасная ветка в `shared/testkit/state` **удаляются целиком**; порядок «подписаться → просигналить» в коде потребителя сохраняется как дешёвая дисциплина, но больше ни на чём не держится.
3. Если тесту нужна не «готовность подписки», а точка «прочитано ровно до сюда», её даёт журнальная половина C-01, которую реализуют обе шины: `End` → `ReadRange(from, End)` либо `Tail` с закреплённым офсетом. Связка «закрепить офсет → просигналить → читать с него» окна потери не имеет вовсе (ADR-023 §«Якорь»).
4. **Условие пересмотра**: появление транспорта или конфигурации темы, где новая группа стартует с конца (`auto.offset.reset=latest`, брокер без сохранения офсета группы). Тогда — вариант B, и только если он не закрывает случай — вариант C.

## Последствия

- Позитивные: из потребителя уходит ветка, которую никто не выбирает, и приведение типа, которое не проверяет компилятор; следующий потребитель (рой, gateway) не изобретает своё рукопожатие; свойство проверяется один раз для обеих шин.
- Негативные: гарантия ограничивает выбор транспорта и конфигурации топиков — политику `latest` для топиков платформы применять нельзя, это надо помнить при настройке Redpanda и при появлении второго брокера.
- Что придётся сделать (задача EPIC-002/EPIC-001 при ближайшем касании `shared/testkit/state`): удалить `readySubscriber`, его ветку и тест-«часовой» о том, что шины дерева готовность не сообщают; добавить в contract-тест шины кейс «группа, созданная после публикации, получает событие с первого офсета» — на обеих реализациях. Правка помечается `contract-change` (§16 п. 3).
