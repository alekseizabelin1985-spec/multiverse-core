# ADR-024: Сигнатуры C-03 приводятся к реализованным формам — ошибка как канал контракта, факты встречи передаются, а не угадываются

Статус: принято · Дата: 2026-09-11 · Автор: architect#1 (TEAM-1, EPIC-002, сведение расхождений волны 0)
Уровень: реализация внутри блока «Состояние и механика» (в границах ADR-003 п. 5, ADR-012, C-03); Go-API общей библиотеки, стек и границы блоков не затрагиваются.
Связи: C-03 v1.2, C-02 (предложения и факты), `state-and-mechanics.md` §5.1, §5.4, §5.6; задачи T-015 (сделано), **T-053 (правка кода)**, T-056; `journal.md` 2026-09-10 (ОВ T-015, ревью #1 code-reviewer#1, решение оркестратора), 2026-09-11 (итог приёмки, п. 3).

## Контекст

T-015 реализовала типы и правила `internal/mechanics` по детальному дизайну `state-and-mechanics.md` §5.1. По четырём функциям §5.1 и C-03 v1.1 расходились, и код пошёл за §5.1. Ревьюер разобрал каждую по существу и заключил: прав §5.1, а C-03 местами противоречит сам себе. Пятое расхождение — не в сигнатуре: у `NPCTarget` нет канала ошибки, и `nil` заглушки неотличим от «целей нет».

| Функция | C-03 v1.1 | Реализовано (=§5.1) |
|---|---|---|
| `Roll` | `… ) Roll` | `… ) (Roll, error)` |
| `ActorFromEntity` | `(e entity.Entity) (Actor, error)` | `(e, enc *entity.Entity) (*Actor, error)` |
| `DiceRolledPayload` | `(roll Roll, roller string)` | `(roll Roll, roller entity.Ref)` |
| `ChangesFor` | `(o, a, actors, causeEventID) []entity.Change` | `(a, o, attacker, target, factEventID) ([]ProposedChange, error)` |
| `NPCTarget` | `… ) *Actor` | `… ) *Actor` — форма обоих документов, и она **неверна** |

Отдельно: по `ChangesFor` реализованная форма — **третья**, не совпадающая ни с C-03, ни с §5.1 буквально (в §5.1 не было канала ошибки), поэтому правятся **оба** документа.

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| Кто прав при расхождении | A. контракт по определению, код переделать | формально дисциплинирует | переделка ради формы, у которой нет обоснования; C-03 v1.1 в двух местах противоречит сам себе (сам добавил `Participation`/`LastDamager` в `Actor` — и оставил `ActorFromEntity` с одним аргументом) |
| | **B. побеждает форма с доказательством; расходится — правится документ** | контракт перестаёт врать о коде; исполнитель T-053 не выбирает между двумя истинами | контракт правится «задним числом» — приемлемо только пока у C-03 нет живых потребителей (сегодня их нет, кроме заглушки, которая правится вместе) |
| `NPCTarget` | A. оставить `*Actor`, различать через отдельный предикат | сигнатура v1 не меняется | предикат придётся звать до каждого выбора цели; `nil` по-прежнему двусмыслен |
| | **B. `(*Actor, error)`** | `(nil, nil)` — «некого кусать» (UC-008 A2), ошибка — дефект вызывающего или `ErrNotImplemented` до T-053 | единственное место, где после правки контракта придётся тронуть код |

## Решение

C-03 переходит в **v1.2**; `state-and-mechanics.md` §5.1 и C-03 совпадают дословно. Обоснование по каждой функции — то, ради чего этот ADR и написан:

1. **`Roll` возвращает ошибку.** Формула и назначение броска приходят из **блупринта** региона (фоновые таблицы, `encounter_chance`), а не только из `rules/*.yaml` под ревью, и могут быть невалидны. Функция без канала ошибки обязана либо паниковать внутри хода, либо вернуть «нулевой бросок», который вызывающий добросовестно опубликует как настоящий `dice.rolled`.
2. **`ActorFromEntity` принимает сущность встречи и возвращает ошибку.** `Participation` и `LastDamager` — факты **встречи**: одна и та же сущность волка в двух встречах ответит по-разному, из сущности игрока их не прочитать вовсе. C-03 v1.1 сам добавил эти поля в `Actor` и оставил конструктор с одним аргументом — это и есть внутреннее противоречие. `nil` вторым аргументом — законное «вне боя». Ошибка вместо умолчаний: актор без `hp` или `def` — дефект того, кто создал сущность, а подстановка нуля превратила бы дефект в бой по другим правилам.
3. **`DiceRolledPayload` принимает `entity.Ref`.** Схема `dice.rolled` требует у `roller` пару `{id, type}`; из строки тип не выводится, и единственный конструктор payload строил бы заведомо невалидное событие. (Тем же местом уже поймана ошибка типа: `seed` едет десятичной строкой, потому что `float64` теряет точность на значениях выше 2^53.)
4. **`ChangesFor` возвращает `([]ProposedChange, error)` — в обоих документах.** `[]entity.Change` из C-03 v1.1 — это `changed[]` **факта** `entity.updated`, то есть результат применения, а не запрошенные операции; предложению нужны `ops` + `expected_version` + `cause`. Канал ошибки нужен и **после** реализации (T-053): функция может получить исход, несовместимый с действием, — трофей при живой цели, урон без попадания.
5. **`NPCTarget` возвращает `(*Actor, error)`.** `(nil, nil)` — «некого кусать» (UC-008 A2); ошибка — дефект вызывающего и `ErrNotImplemented` до реализации. Без второго результата вызывающий не отличает «целей нет» от «механика ещё не написана» и тихо пропускает ход NPC.
6. **Тип `ProposedChange`** (`{Entity entity.Ref; ExpectedVersion *int64; Ops []entity.Op; Cause string}`) вносится в C-03: он и есть граница между механикой, которая предлагает, и State, который решает.

## Последствия

- Позитивные: контракт, детальный дизайн и код совпадают дословно, и расхождение любого из трёх мест теперь — дефект, а не «вопрос к архитектору»; исполнитель T-053 не выбирает между двумя формами; каждая функция, читающая данные из-под блупринта, имеет канал отказа.
- Негативные: формально это несовместимое изменение Go-API (§16 п. 2). По факту потребителей у C-03 сегодня нет: единственный — `shared/testkit/mechanics.FixedMechanics`, который правится вместе с `NPCTarget`. Цена правки после появления агента встречи была бы кратно выше — поэтому она делается сейчас, в бридж-блоке.
- Что придётся сделать: **EPIC-002 T-053** — `NPCTarget` → `(*Actor, error)` в `internal/mechanics/target.go`, тот же метод в `shared/testkit/mechanics.FixedMechanics` и в интерфейсе тест-потребителя, который держит подмену компилятором; PR помечается `contract-change`. Остальные четыре формы уже реализованы, правок кода не требуют.
- Оставлено открытым намеренно: чем заполнять `Outcome.Loot`, если трофей берётся по **виду** существа, а `Actor` несёт только идентификатор и тип. Развилка — поле `Actor.Kind` (совместимое дополнение C-03) против отдельного аргумента `ChangesFor`. Решает T-053 на настоящей реализации: сейчас выбор был бы догадкой.
