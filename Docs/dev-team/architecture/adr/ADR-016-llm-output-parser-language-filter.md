# ADR-016: Парсер вывода LLM с восстановлением, проверка языка и фильтр категории (a) как middleware шлюза; без кэша ответов

Статус: предложено (к ревью system-architect#1) · Дата: 2026-09-09 · Автор: architect#2 (TEAM-2, EPIC-003) · Уровень: реализация блока
Связи: ADR-005 п. 2/7, ADR-009 п. 5/6, ADR-003 п. 4, ADR-010 п. 2; FR-032, FR-034, FR-050, FR-051; NFR-022, NFR-048, NFR-065, NFR-090; UC-021…UC-023; C-07, C-15; `components/swarm-llm-laws.md` §9.

## Контекст

ADR-005 фиксирует порядок middleware: бюджет → провайдер с повторами → парсер JSON с восстановлением → язык → фильтр (a) fail-closed → запись `llm.output` → страж. Qwen3 через Ollama на части версий отдаёт преамбулу/`<think>`/код-блок перед JSON даже при `format`=схема; `response_raw` при `quarantined` не сохраняется; повтор — ≤ `retries` из блупринта. As-is парсинг — `json.Unmarshal` без восстановления (`pipeline.go`), а `shared/oracle` вырезает `choices[0].message.content` и не считает токены. В списке задач этапа порядок дан как «бюджет → кэш → фильтр (a) → запись → парсер» — противоречит ADR-005 (фильтр работает по тексту, который извлекается парсером); следуем ADR-005.

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| Восстановление JSON | только `json.Unmarshal` | строго | доля невалидных ответов с первой попытки растёт, каждый повтор — секунды GPU |
| | **ступенчатое восстановление** (trim → `<think>` → код-блоки → сбалансированный `{…}` → trailing commas → схема) с записью стратегии | реальный «grammar leak» чинится без повтора; стратегия в `llm.output.parse` — метрика для замера | нельзя менять содержимое строк (кавычки «» внутри текста не трогаем) — восстанавливаем только структуру |
| | библиотека «json repair» | готово | лишняя зависимость; непрозрачные правки текста нарратива |
| Схема | `encoding/json` в структуру | быстро | нет `enum`/`maxLength`, разные схемы на блупринт |
| | **JSON Schema 2020-12 через `github.com/santhosh-tekuri/jsonschema/v6` (v6.0.2)** | та же схема уходит провайдеру в `format`; `enum` типов тика генерируется из блупринта | компиляция схем при старте (мс) |
| Кэш ответов | кэш `(scope, type, phase)` как в as-is `pipeline.go` | «экономия» | ответ из кэша не имеет `llm.output` → replay и аудит ломаются; одинаковые ответы на разные ходы — дефект продукта |
| | **кэша нет**; в replay — `providers/recorded` | record-replay честный | — |
| Язык | только CJK | просто | латинские ответы («The wolf…») проходят |
| | **0 CJK + доля латиницы ≤ `LLM_LATIN_MAX_RATIO` (0.10, после замера) без учёта идентификаторов** | NFR-090 | порог требует замера |
| Фильтр (a) | ML-классификатор | точнее | нет в стеке; непрозрачен для «0 ложных срабатываний» |
| | **словарь/RE2 из `config/absolute-limits.yaml` + сочетания «возрастной маркер + сексуальный контекст» в окне 80 символов** | детерминирован, версионирован (`filter_version`), правится без кода | ограниченная полнота (принято на G1: только (a), приватная игра) |
| Повтор при фильтре | повторить генерацию | шанс «чистого» текста | вторая попытка на тот же контекст — тот же риск; текст всё равно не сохраняется; отклонено (шаблон) |

## Решение

1. **Парсер** `internal/llm/parser`: `Parse(raw, schema) (json.RawMessage, Strategy, error)` — стратегии по порядку: `direct` → `strip_think` (`<think>…</think>`, поле `thinking` ответа игнорируется) → `strip_fence` (```` ```json ````) → `balanced_object` (первый `{` до парного `}` с учётом строк/экранирования) → `trailing_commas`; содержимое строк не модифицируется; затем валидация схемой (2020-12). Стратегия и флаг `recovered` пишутся в `llm.output.parse{strategy, recovered}` (опциональное поле, совместимое расширение C-07). Обрезанный ответ (`done=false`/несбалансированный) → `schema_invalid`.
2. **Язык**: `CheckLanguage(texts)` — 0 символов диапазонов Han/Hiragana/Katakana/Hangul; доля латиницы среди букв ≤ порога (идентификаторы `player-*`, `wolf-*`, `region:*` исключаются по шаблону); провал → `validation_status=rejected_language`, повтор с подсказкой в `user`-сообщении, затем шаблон (`fallback_reason=language`).
3. **Фильтр (a)** `internal/llm/filter`: интерфейс `NarrativeFilter{Check(ctx, text) (Decision, error); Version()}`; реализация `CategoryAFilter` по `config/absolute-limits.yaml` (RE2, регистронезависимо, `context_terms` — пары в окне); `block` → `quarantined` без `response_raw` (только `response_hash`, `response_len`), `llm.output.rejected reason=filter_blocked category=a`, `content.incident.recorded` без текста, повтора нет → шаблон; `error` (паника/таймаут реализации) → `filter_error`, `response_raw` сохраняется, текст не доставляется (fail-closed). Пустой словарь → предупреждение и встроенный список по умолчанию. Тест золотого набора: 0 ложных срабатываний (NFR-048/065).
4. **Повторы**: `schema_invalid`, `rejected_language`, `error(timeout|unavailable)` → до `1+retries` попыток; каждая попытка — отдельный `llm.output attempt=n`; `system`-промпт неизменен (кэш промпта Ollama), подсказка добавляется в `user`. `filter_*` и `budget_exceeded` не повторяются.
5. **Порядок побочных эффектов — по ADR-005 п. 2** (провайдер → парсер → язык → фильтр → запись `llm.output` → публикация отклонений стража); оценка стража — чистая функция, вычисляется до записи, чтобы `validation_status` записи был окончательным (`valid|partially_rejected|invalid`). Кэш ответов в шлюзе не вводится.
6. **Провайдер Ollama**: native `/api/chat`, `stream:false`, `format`=схема, `think:false`, `keep_alive` из `LLM_KEEP_ALIVE` (-1), `options{temperature, num_predict, num_ctx, seed?}`; токены `prompt_eval_count/eval_count` → `tokens{prompt, completion}` (NFR-052); клиент на `net/http` без зависимости от модуля `ollama`; отмена контекста закрывает соединение (нужно ADR-014 п. 2).

**Пометки об устаревании (2026-09-11, T-409; основание — C-07 v1.2 и ADR-017 доп. 1, `diagrams/states-llm-output.md`):**
- **п. 2 и п. 4** — статуса `rejected_language` больше нет. Провал проверки языка даёт `validation_status=invalid` и `llm.output.rejected {reason: language}`; повтор и шаблон — как написано. Почему: статус описывает исход конвейера, причина живёт только в `rejected.reason`; перечень статусов сужен до шести значений.
- **п. 3, ветка `error`** — `response_raw` при `filter_error` **не сохраняется** (C-07 v1.2: «при `quarantined`/`filter_error` — без `response_raw`»). Почему: фильтр, который упал, не доказал, что текст допустим, а записанный в журнал текст категории (a) уже нельзя стереть — fail-closed относится и к записи, не только к доставке.

**Пометки (2026-09-13, T-457, system-architect#1; основание — ADR-029, подтверждён; C-07 v1.5):**
- **п. 1** — для `Kind=narrative` после валидации схемой парсер проверяет `text` на ярлык вызова выражением `(^|[^0-9A-Za-z_])[eb][1-9][0-9]?([^0-9A-Za-z_]|$)`. Совпадение — `validation_status=invalid`, `llm.output.rejected {reason: schema_invalid}` без `element`. Содержимое строки по-прежнему не правится. Схема нарратива `schemas/agent/narrative.json` статична (элементы массивов — строки с `pattern` ярлыков) и компилируется при старте, как записано в п. 1: на вызов она не сужается, кэш схем не нужен. См. ADR-029 п. 3–4.
- **п. 4** — ярлык в `text` повторяется как `schema_invalid`: подсказка в `user`, затем шаблон. См. ADR-029 п. 4.

## Последствия

- Позитивные: доля `valid_first_try` растёт без лишних вызовов; стратегия восстановления измерима; контент (a) не попадает на диск даже при сбое фильтра; язык гарантирован до доставки.
- Негативные: `balanced_object` может «починить» ответ с мусором после JSON — допустимо (схема ограничивает содержимое); порог латиницы — после замера; словарь (a) требует ревью с юристом для категории (d) (вне MVP-1).
- Что придётся сделать: `internal/llm/{parser,filter,providers/ollama}`; корпус `testdata/llm/preamble/`; `config/absolute-limits.yaml`; зависимость `github.com/santhosh-tekuri/jsonschema/v6` в `go.mod` (пометка в отчёте tech-lead#1).
