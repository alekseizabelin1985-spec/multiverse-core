# ADR-011: Хранение состояния — объект на сущность как commit-record, снапшот с курсором и указатель `latest.json`, собственный курсор журнала у State

Статус: предложено (к ревью system-architect, утверждение на G3) · Дата: 2026-09-09 · Автор: architect#1 (TEAM-1, EPIC-002)
Уровень: реализация внутри блока EPIC-002 (в границах ADR-003 п. 2–3, ADR-004 п. 1, C-02, C-14).
Связи: FR-030, FR-031, FR-033, FR-087; NFR-010, NFR-011, NFR-013; `state-and-mechanics.md` §4.3–§4.4, §4.8–§4.9; `data-model.md` §8; UC-025.

## Контекст

ADR-003 задаёт: State держит мир в памяти, PUT объекта на сущность **до** публикации факта, снапшот мира с `cursor` и `state_hash`, восстановление = снапшот + факты журнала. Открытыми на уровне реализации остались: (1) что именно лежит в `latest.json` и в объекте сущности; (2) как гарантировать, что факт, не опубликованный из-за падения между PUT и `Publish`, не потеряется (RPO = 0); (3) как State отслеживает позицию в журнале при at-least-once, чтобы повторно доставленное старое предложение не породило ложный `version_conflict`; (4) как потребители read-model (gateway, swarm) стартуют от снапшота State.

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| `latest.json` | A. полный снапшот под фиксированным ключом | одно чтение для потребителей | двойная запись ≤ 1 МБ; при падении между записью объекта и `latest` — два разных «последних»; история версий MinIO хранит и полные копии |
| | **B. указатель** `{snapshot{key, seq, cursor, state_hash, …}}` | атомарная замена маленького объекта; ротация K=5 без дублей; потребитель проверяет хэш объекта | два GET при старте потребителя (незначимо) |
| Потерянный факт после PUT | A. ничего не хранить в объекте; при рестарте доверять журналу | проще | факт потерян навсегда: объект уже v+1, в журнале факта нет → read-model потребителей расходится |
| | **B. объект несёт `last_change{proposal_id, changed[], fact_event_id}`** (commit-record) | при рестарте объект с `fact_event_id=""` и версией `mem+1` → факт дослать; дедуп повторного предложения по `last_change.proposal_id` без отдельного хранилища | +≈ 200 байт на объект |
| | C. отдельный outbox-объект на факт | явный outbox | лишний PUT на каждое изменение (+20 мс на критическом пути) |
| Позиция State в журнале | A. consumer group (`core.state`) как у остальных | стандартно | офсет группы и `cursor` снапшота расходятся; после рестарта старые предложения переигрываются → нужны фильтры по офсету, а `Handler` их не видит |
| | **B. собственный курсор** (`Journal.ReadRange/Tail` с `cursor` из снапшота) | курсор снапшота = единственная истина; предложения до курсора не читаются вовсе; тот же путь для recovery и live | нужен `Journal` в C-01 (запрос §14 компонента); State не получает retry/DLQ-обёртку группы — реализует сам (повтор ×3 внутри worker'а, ошибки применения не «ретраятся», а становятся `rejected`) |
| Хэш состояния | A. по HP/инвентарю/позиции/статусу (metrics.md) | компактно | новый атрибут — правка хэша; расхождение по другим полям невидимо |
| | **B. по `{id,type,version,attributes}` всех сущностей, канонический JSON** | покрывает всё доменное состояние; пересчитывается из снапшота + `changed[]` | — |

## Решение

1. **Объект сущности** `entities-{world}/{type}/{id}.json` = `shared/entity.Entity` целиком: `version`, `attributes`, `last_event_id`, `last_change{proposal_id, proposal_event_id, fact_event_id, cause, changed[], applied_at, atomic, batch_size}`, `history` (≤ 50). PUT объекта — точка фиксации изменения; факт публикуется после PUT; `fact_event_id` дописывается в память и попадёт в объект при следующем изменении или в снапшот. *(Уточнён: дополнение 2026-09-14, п. 3.)*
2. **Снапшот** `snapshots-{world}/state/{ts}-{seq}.json` = все сущности (с `last_change`) + `applied_proposals` (последние 1000) + метаданные `{id, seq, taken_at, cursor{topic: next_offset}, laws_version, rules_version, state_hash, size_bytes, entities_count, reason}`; **`latest.json` — указатель** на него (те же метаданные + `key`), записывается после успешного PUT объекта. Ротация — последние 5. `state_hash = sha256(канонический JSON [{id,type,version,attributes}] по (type,id))` — формат `sha256:<hex>`.
3. **Восстановление** (порядок обязателен): `latest.json` → объект (проверка хэша; при несовпадении — предыдущий из списка; нет целых → `/health fail`) → `ReadRange(system_events, cursor, End)` только фактов `entity.created/updated` (версия строго +1, иначе `state_divergence` → `/health fail`) → сверка с `ListEntities`: объект `version == mem+1 ∧ fact_event_id == ""` → принять и дослать факт; `version > mem+1` → дивергенция → roll-forward интентов (ADR-013) → `analytics.replay.completed` → `Tail` предложений с `End`. Разрыв журнала (retention) → восстановление из объектов, `/health degraded {log_gap}`.
4. **State не использует consumer group** для `system_events`: читает `Journal.Tail` со своего курсора; курсор персистится только в снапшоте (между снапшотами — в памяти; после рестарта всё после курсора перечитывается, факты идемпотентны, предложения дедуплицируются по `proposal_id`/`last_change`). `analytics_events` (триггер снапшота по `session.ended`) читается обычной группой `core.state.triggers`.
5. **Потребители read-model** (gateway, swarm) стартуют от `latest.json` State: читают указатель и объект через `shared/objstore` (только чтение), проверяют `state_hash`, догоняют `entity.updated` с `cursor.system_events` через `Journal` — C-14.
6. **Снапшот не блокирует** обработку: worker копирует срез сущностей и фиксирует курсор синхронно, сериализация и PUT — в горутине; параллельно может идти не более одного снапшота на мир. *(Заменён: дополнение 2026-09-14, п. 1.)*

## Последствия

- Позитивные: RPO = 0 без отдельного outbox (commit-record в объекте); один путь кода для recovery и live (курсор); указатель `latest.json` даёт потребителям целостный снапшот всегда; дедуп предложений без БД.
- Негативные: `Journal` — дополнение к C-01 (совместимое, но требует реализации в kafka-адаптере и membus в волне 0); объект сущности растёт на `last_change`/`history` (≤ 10 КБ на сущность — незначимо); State сам реализует повторы на ошибках I/O.
- Что придётся сделать: `shared/entity.LastChange`; `internal/state/{store,snapshot,recovery,dedup}.go`; запрос в C-01 (`Journal`, `Position`); тесты recovery (a)–(g) из `state-and-mechanics.md` §11; `mvctl session-report --audit` (EPIC-005) считает тот же `entity.StateHash`.

## Дополнение 2026-09-14 (T-057, system-architect#1): синхронный снапшот, блок метаданных, досылка факта

Основание: код T-057 (`internal/state/{snapshot,intent,dedup,context}.go`), фикстура seq 0 и тест `TestSnapshotObjectHoldsTheSameWorld` (T-016), решение Ma-1 T-055, КД State v0.4 §4.4, §4.9, §9, §18. Контракты C-02 и C-14 не меняются.

1. **П. 6 заменяется.** Снапшот пишется целиком на worker'е мира. Сущности, окно `applied_proposals` и курсор берутся между двумя предложениями. Затем идут PUT объекта, PUT `latest.json`, ротация и `snapshot.created` — всё до следующего предложения мира. Двух снапшотов одного мира одновременно не бывает по построению.
   - *Почему не горутина.* `snapshot.created` публикуется в `system_events` среди фактов. Из горутины его место относительно фактов следующих предложений зависит от латентности MinIO, и два прогона одной записи дают разный порядок событий — нарушается NFR-061. Удержать порядок из горутины можно только очередью публикаций worker'а, то есть той же синхронностью с лишним механизмом.
   - *Цена.* Одно предложение из `MV_SNAPSHOT_EVERY_FACTS` (200) ждёт записи снапшота (≤ 1 МБ: List, два PUT, ротация). Это меньше 0,5 % предложений: p95 NFR-001 и p95 применения C-02 не сдвигаются, RTO не меняется.
   - *Когда пересмотреть.* p95 `duration_ms` снапшота в логе стенда больше 200 мс или объект больше 1 МБ. Тогда worker копирует и сериализует, PUT идёт в горутине, а `snapshot.created` публикуется очередью worker'а после PUT. Контракты при этом не меняются.
2. **П. 2 уточняется: блок метаданных.** Объект и указатель несут один блок, кроме `size_bytes`. Его несёт только указатель: объект не может назвать собственную длину, не изменив её. `rules_version`, `entities_count` и `reason` есть и в объекте, и в указателе. `snapshot.created` — блок указателя без этих трёх полей (схема закрыта). `seq` — следующий за наибольшим объектом снапшота в хранилище.
3. **П. 1 уточняется: что на диске.** Объект сущности всегда записан с пустым `last_change.fact_event_id`. Запись идёт до публикации, а повторного PUT после неё нет. Слова «попадёт в объект при следующем изменении» не действуют: следующее изменение пишет новую `last_change`. Подтверждённый id факта есть в памяти и в снапшоте, а на диске признак неподтверждённого факта — версия объекта выше восстановленной (п. 3).
4. **П. 3 уточняется: досылка.** Неподтверждённый факт публикуется через рестарт один раз. Путь — повтор предложения: оно не фиксируется, пока ответ не вышел целиком. Дедуп идёт по `last_change.proposal_id`, id и `applied_at` берутся из первого вывода (`last_change.proposal_event_id`, `applied_at`). Recovery принимает висящий объект в память без публикации. Ошибка `Publish` ответа не пропускается: то же событие повторяется до успеха или до `Stop`, после `Stop` мир получает `publish_failed` (КД §9).
