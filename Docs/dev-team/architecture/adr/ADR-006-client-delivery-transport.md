# ADR-006: Доставка клиенту — Telegram long polling, outbox с long-poll и ack между ботом и gateway; WebSocket — позже

Статус: предложено (к утверждению на G2) · Дата: 2026-09-09 · Автор: system-architect#1
Связи: OQ-R-06/OQ-P-04 (бот — эталонный клиент), OQ-A-14 (auth — целевое); FR-003, FR-004, FR-009, FR-052, FR-060; NFR-003, NFR-041, NFR-092; `api-contracts.md` §1.5; `integrations.md` §1.

## Контекст

Аналитик описал два эквивалентных транспорта доставки `Delivery` (long-poll outbox с ack и WebSocket-стрим) и оставил выбор архитектору; способ получения обновлений от Telegram (long polling / webhook) — нейтрален. Условия: один экземпляр бота, машина без публичного адреса, доверенный контур, `ack ≤ 300 мс`, outbox переживает недоступность бота, порядок доставок одному игроку строгий, внешний ID не покидает бота и хранилища связок.

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| Telegram → бот | **long polling `getUpdates` (`timeout=25–30 с`)** | без домена/TLS/reverse-proxy; один пуллер (409 при втором — защита от дублей) | один экземпляр бота; латентность ≤ времени опроса (незначимо) |
| | webhook | ниже задержка, масштабируется | нужен публичный HTTPS-адрес; повтор доставки при медленном ответе → дубли |
| Бот ↔ gateway | **long-poll `GET /v1/clients/{id}/deliveries?after&wait_ms` + `POST …/ack`** | outbox уже нужен; курсор возобновляется после рестарта любой стороны; нет состояния соединения | одно висящее соединение на клиента (одно) |
| | WebSocket `GET /v1/clients/{id}/stream` | push | состояние соединения, переподключения, тот же ack всё равно нужен |
| | оба сразу | гибко | два пути тестировать |

## Решение

1. **Telegram**: long polling, `timeout=25 с`, `allowed_updates=[message]`; бот — отдельный процесс `cmd/telegram-bot`, единственный экземпляр (второй получит 409 — сознательно). Webhook — E-H при появлении публичного адреса (интерфейс `UpdateSource` в боте).
2. **Бот → gateway**: HTTP JSON по `api/gateway.openapi.yaml` (§1 api-contracts). `action_key` = односторонний хэш `(bot_instance_salt, update_id)` — не обратим, идемпотентен при повторе обновления. Заголовки `X-Client-Id: telegram-bot`, `X-Actor-Kind: human`.
3. **gateway → бот**: только long-poll outbox: `GET /v1/clients/{client_id}/deliveries?after=<cursor>&limit=100&wait_ms=25000` → `POST /v1/clients/{client_id}/deliveries/ack {ids}`; без ack — повтор через `redelivery_after` (30 с); `Delivery` хранится в `gateway.db` (`state: pending|delivered|dropped`, `expires_at ≥ 24 ч`); порядок по `player_id` — по `created_at`, gateway не выдаёт следующую доставку игроку, пока предыдущая не подтверждена (голова очереди на игрока). `route.external_id` подставляется из `links.db` **в момент выдачи**; после `/forget` доставки игрока переводятся в `dropped`.
4. **Ack действия**: `202 {correlation_id}` возвращается после валидации и успешной публикации в шину (при недоступности шины — `503 bus_unavailable`, действие не принято); бот отвечает «принято» — NFR-003.
5. **Сообщения игроку**: механика и нарратив — отдельными сообщениями (`kind: mechanics|narrative`), нарратив с пометкой `generated_by` (шаблон — «упрощённый режим»); групповая доставка — каждому в личный чат (по умолчанию) или в общий чат группы (конфигурация бота); `narrative_event_id` один для всех адресатов.
6. **WebSocket-стрим** (`/v1/clients/{id}/stream`) — зарезервирован в OpenAPI как целевой (E-H, внешние фронты), в MVP-1 не реализуется; контракт `Delivery` и `ack` общие.
7. **Аутентификация** — MVP-1 нет (доверенный контур, `X-Client-Id` из списка конфигурации); при первом внешнем клиенте — токен клиента (E-H, OQ-A-14).

## Последствия

- Позитивные: ноль сетевой инфраструктуры (домен, TLS); один путь доставки для бота, CI-харнесса и будущего Discord-бота; потери при рестартах исключены outbox-ом.
- Негативные: задержка доставки ≤ 1 цикла long-poll (миллисекунды при висящем запросе); один экземпляр бота.
- Что придётся сделать: EPIC-004 — outbox в SQLite, эндпоинты deliveries/ack, бот с `UpdateSource`; тест-харнесс использует те же эндпоинты (`X-Client-Id: ci-harness`).

## Дополнение 2026-09-09 (сведение A3 шаг 4)

1. **Allowlist игроков — решение пользователя (SEC-06/07)**: бот принимает команды только от Telegram user id из `MV_TELEGRAM_ALLOWED_USER_IDS` (список через запятую; пустой список = бот отвечает всем «доступ по приглашению» и **не** вызывает gateway); проверка — первая в цепочке обработки `Update`, до любого вызова gateway и до FSM онбординга; отказ — одно сообщение без деталей, лог без ID (счётчик `bot_denied_total`). Инвайт-коды — E-H. Правило переносится и на будущий Discord-бот.
2. **Только личные чаты в MVP-1 (п. 5 уточнение)**: групповые чаты Telegram отклоняются («пишите в личные сообщения», ADR-018 п. 3); «общий чат группы» требует хранения `chat_id` группы в боте, что нарушает принцип «бот без хранилища» — **E-H**. Связка — по `from.id`; `chat_id == from.id` для личных чатов, отдельно не хранится.
3. **Редакция токена (SEC-08)**: URL Telegram Bot API содержит токен — `privacy.Handler` бота редактирует в любом сообщении лога/ошибки подстроку `bot<digits>:<token>` → `bot<redacted>` (regexp), включая `409 Conflict` и сетевые ошибки библиотеки; `WithDebug` запрещён; тест NFR-041 проверяет логи бота на фрагмент токена.
4. **Без `parse_mode` (SEC-10)**: бот отправляет UGC/LLM-текст как plain text (`parse_mode` не задаётся); заголовки «Механика»/«Рассказчик» — префиксом строки, не разметкой пользовательского текста.
5. **Логи бота (ADR-009 п. 4 уточнение)**: retention реализуется ротацией по объёму (`json-file`, `max-size 10m`, `max-file 3`), а не по времени — «≤ 7 дней» становится ориентиром, потому что логи не содержат ПДн по построению (`privacy.Handler`), и буквальный срок не даёт дополнительной защиты; внешний cron/`lumberjack` не вводятся (простота важнее буквальных 7 дней).
