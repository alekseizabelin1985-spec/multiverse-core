# ADR-029: Ответ нарратива ссылается ярлыками вызова `eK`/`bK`, а не id; выдуманный ярлык отбрасывает страж поэлементно

Статус: **предложено**; поправки к ADR-016 (п. 4 ниже) и ADR-017 (п. 5 ниже) — на подтверждение system-architect#1 · Дата: 2026-09-13 · Автор: architect#2 (TEAM-2, EPIC-003; задача T-439, итерация 2 по ревью #1)
Уровень: реализация блока EPIC-003 — сборщик контекста, парсер, страж, роли нарратива. Схемы событий не меняются. Для одной ветки `unknown_entity` нужен запрос C-07 v1.4 (п. 6); до его решения действует временная форма. Стек и границы блоков не затрагиваются.
Связи: ADR-005 доп. 3 и «Уточнение исполнения» п. 4; ADR-016 п. 1, 2, 4; ADR-017 п. 1–3, 5 и доп. 1; ADR-028 УИ п. 1; C-07 v1.3; `ops/metrics/baseline.md` §5; NFR-002, NFR-021, NFR-061, NFR-080; US-017, US-018; КД `components/swarm-llm-laws.md` §3, §9.2, §10.2, §11.2, §11.4, §13.4, §13.4.1, §13.4.2; design EPIC-003 §9, риск 8. Задачи: T-203, T-209, T-212, T-213, T-217, T-218, T-233, T-235, T-237, T-247, T-248, T-260. Диаграмма: `diagrams/seq-swarm-llm-laws-narrative-labels.md`.

## Контекст

Потолок ответа нарратива считается по формуле ADR-005 УИ п. 4: `text.maxLength` = (N − каркас − служебные поля) × символов на токен × запас. Служебные поля там — шесть элементов (`mentions` ≤ 4, `background_refs` ≤ 2) по ≈ 6 токенов, «идентификатор в кавычках с запятой». На базовой конфигурации E потолок N = 160 токенов.

Шесть токенов верны только для коротких ссылок. В платформе ссылки длинные:
- id события — UUID (`shared/eventbus/sources.go` — v4, `cause_id.go` — v5);
- id встречи — `encounter-<id события>` (ADR-028 УИ п. 1), у NPC респауна — производный id.

Такой id занимает ≈ 20–25 токенов. Цена id:
- **в ответе** — при `maxItems` 4/2 массивы займут ≈ 140 из 160 токенов, на текст почти ничего не останется; даже два `background_refs` — ≈ 50 токенов;
- **в промпте** — 20 событий `<absence>` с id добавляют ≈ 500 токенов «прочего». Бюджет замера посчитан на промптах ~420 токенов, и каждое удлинение промпта уменьшает N (ADR-005 УИ п. 4, T-434).

Формулировка T-439 в индексе EPIC-001 говорит об элементах-id. Решение ниже от неё отступает, меняет правило 3 ADR-017 для нарратива, добавляет проверку в парсер ADR-016 и меняет смысл полей C-07. Поэтому оно оформлено ADR (ревью #1 T-439, Ma-1).

## Рассмотренные варианты

| Вопрос | Вариант | Плюсы | Минусы |
|---|---|---|---|
| Чем модель ссылается на сущность и фоновое событие | id как есть | таблица не нужна; `response_raw` читается без восстановления | ≈ 20–25 токенов на элемент: формула ADR-005 не держится; промпт длиннее на сотни токенов |
| | объекты `{"entity":{"id","type"}}`, как в фикстуре `llm.output.v1.*` | та же форма, что у событий шины | ≈ 15–18 токенов на элемент даже с короткими id, `maxLength` на E ≈ 110 символов; тип от модели не доверенный — страж всё равно берёт его из `View` |
| | **ярлык вызова `eK`/`bK`** | ≈ 6 токенов на элемент, формула держится; промпт короче; id модель не пишет вовсе | таблица ярлыков на вызов; replay и аудит должны её восстанавливать (п. 7–8) |
| Схема ответа | сужение на вызов: `items.enum` выданных ярлыков, `maxItems: 0` без отсутствия (итерация 1 T-439) | под грамматикой `json_schema` модель не выдумает ярлык | схема собирается на вызов: компиляция и кэш вопреки ADR-016 п. 1. Выдуманный ярлык на провайдере без грамматики — `schema_invalid` на весь ответ и повтор (≈ 5 с), а не отброс элемента. Под грамматикой модель, «задумавшая» чужой ярлык, вынуждена выбрать выданный: ошибка ссылки становится невидимой. `enum: []` при пустой таблице спорен |
| | сужение только в грамматике провайдера, парсер — по статической схеме | на `openai_compat` ярлык не выдумывается; парсер компилирует схему при старте | у одного вызова две схемы; невидимая ошибка ссылки — та же |
| | **статический `pattern` в файле схемы; таблицу проверяет страж** | одна схема на роль, компиляция при старте (ADR-016 п. 1 не меняется); поведение одинаково на любом провайдере; выдуманный ярлык — отброс элемента, текст остаётся (ADR-017, правило 3) | модель может выдумать ярлык в пределах `e1…e99` — это видно как отброс; для события отброса нужна ветка C-07 без id (п. 6) |
| Replay: пересобранный контекст дал другие ярлыки | не сверять | просто | `eK`/`bK` молча разрешаются в другие id, ссылка приписана не тому |
| | расхождение `prompt_hash` — ошибка записи | расхождение видно | любая правка текста промпта ломает все записи `testdata/recordings`, а перезапись — только на стенде; design EPIC-003 §9 риск 8 прямо задаёт «расхождение — предупреждение» |
| | ярлык из хеша id (`e7k2`) | дрейф контекста ярлык не переназначает | 3–5 токенов на ярлык вместо 1–2, коллизии, случайные строки модель копирует хуже |
| | **расхождение — предупреждение; ярлыки ответа при расхождении не разрешаются** | ни ложной атрибуции, ни поломки записей от правки текста | при правке одного текста промпта ссылки ответа теряются до перезаписи |

## Решение

1. **Где.** Ярлыки — только в вызовах `Kind=narrative` (`player-gm`, `group-narrator`). Вызовы тика несут id, как прежде.

2. **Выдача ярлыков — сборщик контекста (T-235).**
   - Сущности, выведенные в `<state>`, получают `e1…eN` в порядке id (байтовое сравнение строк). События `<absence>` — `b1…bM` в порядке `at`, при равенстве — по id. Одинаковый контекст даёт одинаковые ярлыки и одинаковый `prompt_hash`.
   - Пределы: N ≤ 99 — предел `pattern`. По NFR-080 в scope не больше 50 сущностей, поэтому предел недостижим; если всё же больше — сущности сверх 99 выводятся без ярлыка (сослаться на них нельзя) и пишется лог `warn`. M ≤ 20 — лимит `Absence` (КД §11.2).
   - Края: N = 0 или M = 0 — таблица пуста, схема та же. Сборщик отдаёт таблицу всегда: пустая карта — не `nil` (`nil` означает «таблицу не передали», п. 5). Ярлык в ответе при пустой таблице — выдуманный, его отбрасывает страж (п. 5).
   - Форма в промпте — ярлык в квадратных скобках после имени: `Альфа-волк [e3]`, `[b2] Буря повалила мост`. Id в промпт нарратива не попадает. В `<events>` сущность названа именем и, если она есть в `<state>`, ярлыком.
   - Ярлыки живут только в `user`. `system`, включая `<format>`, от набора ярлыков не зависит: префикс остаётся общим, и кэш промпта llama-server (`cached_tokens`) сохраняется (ревью #1, Mi-4).

3. **Схема — `schemas/agent/narrative.json` (T-203).** Элементы массивов — строки с `pattern` `^e[1-9][0-9]?$` и `^b[1-9][0-9]?$`, `maxItems` — по таблице КД §13.4.1. Схема статична: на вызов не сужается, компилируется при старте, та же схема уходит провайдеру в `response_format`. Кэш скомпилированных схем не нужен. Грамматика llama-server строит правило строки из `pattern` вида `^…$`; если провайдер `pattern` не применит, ответ с id вместо ярлыка поймает парсер по той же схеме (`schema_invalid`, повтор) — поэтому доля `valid_first_try` нарратива проверяется на стенде (T-260). `<format>` — статичный текст (T-218): «на сущности и события ссылайся только ярлыками из промпта; в `text` ярлыков не пиши, называй по имени; сослаться не на что — пустой массив».

4. **Ярлык в `text` — ошибка формата (поправка к ADR-016 п. 1 и 4).**
   - После валидации схемой парсер для `Kind=narrative` проверяет `text` выражением `(^|[^0-9A-Za-z_])[eb][1-9][0-9]?([^0-9A-Za-z_]|$)`.
   - Совпадение — `validation_status=invalid`, `llm.output.rejected reason=schema_invalid` без `element`, повтор с подсказкой в `user`, затем шаблон.
   - Текст не правится: ADR-016 не меняет содержимое строк, а вырезанный ярлык оставил бы фразу без подлежащего.
   - `CheckLanguage` ярлыки не исключает: до неё ответ с ярлыком в `text` не доходит (ревью #1, Mi-5).

5. **Страж (поправка к ADR-017 п. 1 и правилу 3 для нарратива).**
   - `guardian.Input.Mentions map[string]string` (ярлык → id сущности) и `AbsenceEventIDs map[string]string` (ярлык → id события; прежде `map[string]bool`, множество id) заполняет роль из таблицы сборщика.
   - Правило 3 для нарратива — по элементу:
     - ярлык есть в таблице и сущность видима — элемент остаётся;
     - ярлык есть в таблице, но сущность не видима по КД §10.3 (дефект сборщика) — элемент отброшен, `unknown_entity`, `entity` — id, тип и имя из `View`;
     - **ярлыка в таблице нет (выдуман)** — элемент отброшен, текст остаётся, статус `partially_rejected`. Так правило 3 и работало с выдуманным id: поэлементный отброс сохранён.
   - `background_refs[i]` из таблицы видимы по построению: в `<absence>` попадают только события индекса своего мира и региона.
   - Ответ нарратива с непустыми массивами при `Input.Mentions == nil` и `AbsenceEventIDs == nil` (таблицу не передали; пустая таблица — не `nil`, п. 2) — ошибка программы, а не ответ модели: весь ответ `invalid`, `reason=other` без `element`, лог `error` (ревью #1, N-3).
   - Статусы стража, порядок эффектов и повторы не меняются.

6. **Событие отброса выдуманной ссылки — запрос C-07 v1.4 к system-architect#1.**
   - C-07 v1.3 требует для `unknown_entity` `element` и одно из двух: `entity` (`EntityRef` с обязательным `type`) или `background_ref{event{id}}`. У выдуманного ярлыка нет ни id, ни типа.
   - Пробел у двух массивов разный *(уточнено при приёмке T-439, ревью #2 Mi-9)*:
     - **`mentions` и тик — пробел прежний, не от ярлыков.** `EntityRef` требует `type`, а у выдуманной сущности типа нет. Схемы тика дают только `entity?: {id}` и `affects?: [{id}]` (КД §13.4), и выдуманный id тика — `npc-999` из US-018 — сегодня тоже нельзя опубликовать, не придумав тип.
     - **`background_refs` — пробел создан ярлыками.** C-07 v1.3 ввёл `background_ref{event{id}}` как раз для выдуманной фоновой ссылки, и `EventRef` требует только `id`: с id такая ссылка публиковалась как `unknown_entity` с `background_ref`. У ярлыка `b7` id нет, поэтому до v1.4 она уходит в `other`.
   - Запрос: третья ветка `oneOf` для `unknown_entity` — опциональное поле `ref`, строка ссылки в том виде, в каком её написала модель (id в тике, ярлык в нарративе). Расширение совместимое: новое необязательное поле и ослабленное условие.
   - **До решения по v1.4** шлюз (T-213) публикует отброс выдуманной ссылки как `reason=other` с `element{index, type}` — схема v1.3 это допускает — и пишет лог `warn` с ярлыком. Поведение стража (элемент, а не весь ответ) от формы события не зависит; после v1.4 меняется одна функция отображения вердикта в событие.
   - **Влияние на NFR-021 и US-018 (запись для business-analyst).** Критерий NFR-021 «только зарегистрированные `entity_id`» для нарратива усиливается: id в события ставит роль по таблице, модель id не пишет. Метрика `guardian_rejections_per_100` по `unknown_entity` до v1.4 недосчитывает выдуманные ярлыки — они идут под `other` (и ссылки тика без типа — тоже). В US-018, критерий 2, для нарратива «ссылка на `npc-999`» читается как «ярлык вне таблицы вызова, например `e7`»; «отсутствующая ссылка» в событии — `ref` после v1.4. До v1.4 критерий 2 US-018 и ADR-017 доп. 1 п. 4 («`reason=unknown_entity` с отсутствующей ссылкой») для выдуманных ссылок нарратива буквально не выполняются: проверка «по `reason`» (NFR-021, `project/metrics.md`) увидит `other` *(уточнено при приёмке T-439, ревью #2 Mi-9)*. Как считать `other` с `element` в отчёте `guardian_rejections_per_100` и срок v1.4 — решение system-architect#1 и business-analyst (T-457), не этого ADR.

7. **Смысл полей C-07 без смены схем (пометку в `contracts.md` вносит system-architect#1).**
   - `llm.output.response_raw` нарратива содержит ярлыки, а не id; `llm.output.rejected.element.index` — индекс в массиве ответа.
   - `llm.output.rejected.entity` — сущность из `View` (существует, но агенту не видима), тип — из `View`, а не «названный моделью». Несуществующая ссылка — `ref` (п. 6).
   - `narrative.output.background_refs` — id событий. Ярлыки разрешает роль (T-233, T-247), повторы одного ярлыка схлопываются с сохранением порядка. Во внешних событиях ярлыков нет.
   - Таблица ярлыков в `llm.output` не пишется: поля для неё нет, а заводить его — смена схемы ради аудита, который закрывается и так. Аудит (US-018, «отлаживать промпты») читает ярлыки так:
     - при `MV_LLM_STORE_PROMPTS=true` сохранённый промпт (`prompts-{world}/…`) содержит `Имя [eK]` — таблица читается из него;
     - при выключенном флаге таблица восстанавливается правилом п. 2 из контекста на момент причины (replay журнала до `meta.causation_id`), совпадение подтверждает `prompt_hash`;
     - всё, что вызов изменил в мире или показал игроку, уже несёт id: `narrative.output.background_refs`, `llm.output.rejected.entity`.

8. **Replay и восстановление по записи (ревью #1, Mi-6).**
   - В `mode=replay` и при нарративе из записи после рестарта (КД §8.4) шлюз сверяет `prompt_hash` пересобранного промпта с `llm.output.prompt_hash` записи.
   - Совпал — запись используется как есть.
   - Не совпал — лог `warn` `llm_replay_prompt_drift` с `agent`, `phase`, `attempt`:
     - `Kind=tick` и нарратив с пустыми массивами — только предупреждение (design EPIC-003 §9, риск 8, без изменений);
     - нарратив с непустыми `mentions`/`background_refs` — ярлыки ответа **не разрешаются**: массивы считаются пустыми, `text` используется. Расхождение контекста не приписывает ссылку другому id молча. Цена — потерянные ссылки до перезаписи.
   - Оговорка I2 (`NopMemory` в replay против живого `AbsenceSummary`, T-248) — частный случай расхождения.
   - Новых `llm.output` и `llm.output.rejected` в replay нет (C-07).

9. **Длина — связанные решения (КД §13.4.1).**
   - Служебные поля — 6 токенов на ярлык в кавычках с запятой, 66 токенов вместе с каркасом при `maxItems` 4/2.
   - N округляется вниз до десятков, в том числе для Qwen3.6: 210 и 400 вместо «≈ 220» и «≈ 410» ADR-005 УИ п. 4 (ревью #1, Mi-1). 220 токенов при 107,2 ток/с — это 5003 мс, выше порога.
   - `text.maxLength` = (N − 66) × min(0,9 × c; c_min), округление вниз до кратного 5. c — ожидаемые символы на токен (до калибровки 2,5), c_min — нижняя граница плотности (до калибровки 2,0). E: 185 символов, а не 210 (ревью #1, Mi-2). До калибровки запас дешевле ошибки: 25 символов текста против обреза `max_tokens`, повтора и шаблона именно на самых длинных ответах.
   - Тест T-203 проверяет согласованность N, `maxLength`, `maxItems`, c и c_min, записанных рядом с числами, и то, что `maxLength` из медианы c не выходит за c_min. Запас держит отдельная константа c_min, а не тот же c: поэтому тест падает именно на той ошибке, которую нашло ревью, — `maxLength` 210 итерации 1 даёт 66 + ⌈210 / 2,0⌉ = 171 > 160. Верно ли само значение c_min, CI не видит: реальную плотность модели проверяет только стенд (T-260 в сессии T-438).

## Последствия

- **Позитивные.**
  - Формула ADR-005 держится: на E текст — 185 символов, а не ≈ 110 и не «ничего».
  - Промпт нарратива короче на сотни токенов — меньше «прочего» в NFR-002.
  - Модель не пишет id: ссылка в событии всегда взята из таблицы, которую построил код.
  - Одна статическая схема на роль; ADR-016 п. 1 (компиляция при старте) не меняется.
  - Выдуманная ссылка стоит отброса элемента, а не повтора на 5 с.
- **Негативные.**
  - Таблица ярлыков — ещё одно состояние вызова: сборщик, страж, роль и replay должны видеть одну и ту же.
  - До C-07 v1.4 выдуманная ссылка видна в метрике под `other`, а не `unknown_entity`.
  - Аудит `response_raw` без сохранённых промптов требует пересборки контекста.
  - Ярлык в `text` стоит повтора на весь ответ.
  - Правка одного текста промпта при replay теряет ссылки в ответах с ярлыками до перезаписи.
- **Что сделать** (строки DoD — `epics/EPIC-003-swarm-llm-laws/tasks.md` и отчёт tech-lead#2 по T-439):
  - T-203 — статическая схема с `pattern`, числа E, c и c_min рядом с числами, тест инварианта, длина в `## phase2`; фикстуры `llm.output.v1.*` с ярлыками;
  - T-209 — проверка ярлыка в `text` (п. 4), компиляция при старте без сужения;
  - T-212 — сверка `prompt_hash` в replay (п. 8), вызов проверки п. 4 на шаге парсера;
  - T-213 — отображение выдуманной ссылки в событие (п. 6), `reasons[]`;

## Условия пересмотра

- Доля **попыток** нарратива с ярлыком в `text` (ответ отвергнут парсером, п. 4) выше 2 % на стенде (T-260) или в прогонах S1/S2. Принятого ответа с ярлыком в `text` не бывает по построению, поэтому мерится доля попыток *(уточнено при приёмке T-439, ревью #2 Mi-10)*. Тогда меняется форма ярлыка в промпте либо вырезание ярлыка из `text` становится допустимым.
- Выдуманных ярлыков (ярлык ответа вне таблицы промпта; в платформе — отброс стражем, п. 5–6) больше 5 на 100 вызовов нарратива на стенде (T-260) или в прогонах S1/S2. Тогда сужение `enum` в грамматике провайдера стоит своей цены.
- Провайдер без грамматики (`anthropic`, E-H) становится основным для нарратива: пересчитать обе доли выше на нём.
- `llm_replay_prompt_drift` с потерей ссылок в CI чаще раза на запись. Тогда в C-07 нужно поле хеша таблицы ярлыков, и расхождение становится точным.
- Появляется удаление сущностей (после MVP-1): тип из `View` может пропасть, и таблица должна нести тип.
- NFR-080 поднимает предел сущностей в scope выше 99: расширяется `pattern`.
- Аудит без сохранённых промптов становится регулярной операцией: таблица ярлыков пишется в `llm.output` (смена C-07).
