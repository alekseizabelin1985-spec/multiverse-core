# ADR-027: Идентификатор производного события выводится из причины; окно дедупликации — в два шага

Статус: принято · Дата: 2026-09-11 · Автор: system-architect#1 (T-416, ревизия контрактов волны 1)
Уровень: общий код C-01 (`shared/eventbus`: совместимые дополнения Go-API) и уточнение C-14. Стек и границы блоков не меняются.
Связи: C-01 v1.4, C-05 v1.4 п. 4–5, C-14 v1.2; ADR-023 (at-least-once, коммит не гарантирован); ADR-026 п. 1, п. 10; NFR-013, NFR-061. Задачи: T-220 (принята), T-229 (DoD уже требует id из причины и окно в снапшоте), T-230, T-232, T-236, EPIC-002 T-055/T-056, новая задача EPIC-001 «C-01 v1.4 в коде». Источники: ревью #1 T-220 (Mi-1, зонд P1), ревью #2 T-220 (Mi-3, зонды P4 и P5, сравнение окна и `Dedup`), `journal.md` 2026-09-11.

## Контекст

У нарратора один побочный эффект — публикация текста, поэтому событие он должен запоминать как отвеченное только после успешной публикации. Иначе упавшая публикация теряется бесследно: нет ни нарратива, ни `dead_letters`, ни лога (зонд P1). `eventbus.Dedup.Seen` спрашивает и запоминает одним шагом, поэтому T-220 завела собственное окно. У него вытеснение FIFO вместо LRU и нет `IDs`/`Restore`, то есть его нельзя положить в снапшот C-14. Для заглушки это допустимо, для настоящего GM (T-229) — дефект.

Второй шаг сам по себе не спасает. Если запись в брокер прошла, а подтверждение потерялось, шина вернёт ошибку, обработчик повторится, и текст уйдёт второй раз. `Derive` каждый раз берёт новый `nextID()`, а шлюз гасит дубли по `id` (`narrative_event_id` = `id`, C-05 v1.1). У второй публикации id другой, и шлюз её не погасит — игрок увидит текст дважды (зонд P4). Отдельно ADR-026 требует после рестарта опубликовать `encounter.ended` с тем же id, который назвал закрывающий пакет. Со случайным id это невозможно.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только двухшаговый `Dedup` (`Has` + `Add`) | упавшая публикация повторяется, окно одно и сериализуемо | потерянное подтверждение по-прежнему даёт дубль под новым id |
| B. Идемпотентный продюсер брокера | дубль при повторе внутри сеанса продюсера гасит брокер | клиент `kafka-go` его не поддерживает; не покрывает `membus`, рестарт и replay; решает только часть случаев |
| C. Потребитель гасит дубли по `(causation_id, type)` | ничего не менять у издателя | каждый потребитель учит правило «одно событие типа на причину», которое знает только издатель; id перестаёт быть единственным ключом дедупликации, на котором стоит вся платформа |
| **D. Id производного события выводится из причины + двухшаговый `Dedup`** | повтор, рестарт и replay дают тот же id, и существующая дедупликация по id потребителей гасит дубль; replay побайтно совпадает независимо от `--id-source` (NFR-061); ADR-026 п. 10 становится выразимым | опция применима только там, где издатель публикует не больше одного события на `(причина, тип, части)`; неверно выбранные части склеят два разных события в одно |

## Решение

1. **`eventbus.WithCauseID(parts ...string) DeriveOption`** (C-01 v1.4). Id события — UUIDv5 в пространстве имён платформы (константа пакета `eventbus`) от `causation_id`, типа события и `parts` через разделитель, которого нет в id. Одна и та же причина, тип и части дают один и тот же id. В `NewRoot` опция — ошибка программиста: у корня нет причины, и конструктор паникует, как `runtime.Registry.Register` на повторном имени. Ошибка видна в первом тесте, а не тихо в бою.
2. **Где обязательна.** `narrative.output` (T-229): `parts` — вид нарратива, если на одну причину возможны разные виды. `encounter.started` и `encounter.ended` (ADR-026): `parts` — id встречи.
   **Где рекомендована.** Факты State (`entity.created`/`entity.updated`, `parts` — id сущности). Тогда «факты досылаются, если не были опубликованы» (C-02) перестаёт давать дубли у потребителей. Решение принимает EPIC-002 в T-055/T-056.
   **Где запрещена.** События, которых на одну причину и тип может быть несколько, если `parts` их не различают. Пример — `dice.rolled`: там `parts` обязан содержать индекс броска.
3. **Двухшаговое окно** (C-01 v1.4). `Dedup.Has(id) bool` спрашивает и окно не меняет. `Dedup.Add(id)` запоминает. `Seen` остаётся атомарной парой для потребителей, у которых запоминание до обработки — меньшее зло (агент встречи: повтор задвоил бы кости). Предусловие двух шагов — обработчик не вызывается конкурентно для одного события. Обе реализации шины это соблюдают: подписка отдаёт топик по одному событию (зонд P5 достижим только прямым конкурентным вызовом).
4. **Окно — в снапшоте** (C-14 v1.2). Stateful-потребитель сериализует свои окна `Dedup` (`IDs` → снапшот, `Restore` ← снапшот), включая окно «уже ответил» роя. Собственное окно без сериализации у stateful-контекста — дефект.
5. **Чего решение не делает.** Потребитель без дедупликации по id по-прежнему видит дубль: дедупликация остаётся его обязанностью (C-01). Нерешённым остаётся и дубль при конкурентной доставке одного события — это нарушение предусловия п. 3, а не случай, который решение покрывает.

## Последствия

- **Позитивные.**
  - Потерянное подтверждение, рестарт и replay дают один id, и дубль гасится тем механизмом, который уже есть у каждого потребителя.
  - Replay производных событий не зависит от источника id.
  - Одно окно дедупликации вместо своих окон в каждом контексте.
- **Негативные.**
  - Издатель обязан правильно выбрать `parts`, и ошибка тихая: два разных события получат один id, и второе будет погашено как дубль. Защита — таблица применимости в п. 2 и тест, что разные `parts` дают разные id, а одинаковые — одинаковые.
  - Добавляется одна опция и два метода в общий пакет (`contract-change`).
- **Что придётся сделать.**
  - Новая задача EPIC-001 «C-01 v1.4 в коде» (S, метка `contract-change`): `Dedup.Has`/`Add`, `WithCauseID`, тесты — детерминизм, различие частей, паника в `NewRoot`, валидность id по `_envelope.json` (строка, `minLength` 1), README пакета. Срок — до T-229 (подволна 1.9).
  - T-229, T-230, T-232 применяют опцию.
  - Задача «двойники по C-05 v1.4» заменяет окно `FakeNarrator` на двухшаговый `Dedup`.
- **Условие пересмотра.** Появится издатель, которому нужна идемпотентность без естественной причины, например событие по таймеру вне `tick.fired`. Тогда id выводится из ключа идемпотентности, переданного явно, — той же опцией с другим набором частей, без нового механизма.

## Уточнение исполнения (2026-09-11, T-425, system-architect#1)

Решение не меняется. Ниже — как оно исполнено в T-417 и T-419 и что из этого нормативно. Основание — решения оркестратора по T-417 и T-419 (`journal.md` 2026-09-11), ревью #1 T-417 и ревью #2 T-419. Там, где текст п. 1–2 выше расходится с этим разделом, действует этот раздел.

1. **Кодирование имени UUIDv5 — префикс длины у каждой части, а не разделитель (к п. 1).** Имя — конкатенация по компонентам `causation_id`, тип события, `parts…` в этом порядке; каждый компонент записан как `<длина в байтах UTF-8, десятичная>:<компонент>`. Id — `uuid.NewSHA1(CauseIDNamespace, имя)`. `CauseIDNamespace` = `46a1a952-5297-584b-9430-d9895b6db112` — сам UUIDv5 от URL `https://multiverse-core.io/eventbus/cause-id` в стандартном пространстве URL, поэтому его можно воспроизвести, а не принимать на веру.
   *Почему не разделитель, как было написано в п. 1:* части — произвольные строки (id сущности, вид нарратива, кириллица), и любой разделитель может оказаться внутри части. Тогда `("a|b")` и `("a", "b")` дают одно имя и один id, и потребитель молча гасит второе событие как дубль — ровно та тихая ошибка, которую п. 2 называет главной ценой решения. Префикс длины однозначен: различаются и пустые части, и их число (`("a","b")` ≠ `("a","b","")`). Проверено ревью #1 T-417 — перебор 248 820 кортежей с пустыми частями, цифрами, двоеточиями и кириллицей, коллизий 0.
   **Кодирование — часть контракта C-01, а не деталь реализации.** Его закрепляют семь golden-значений в `shared/eventbus/cause_id_test.go`, в том числе длина в байтах, а не в рунах, и кодирование каждой части, а не только первой. Сменить кодирование или пространство имён значит сменить id каждого производного события: журнал, записанный до смены, перестанет повторяться побайтно (NFR-061). Поэтому смена допустима только с новым пространством имён и отдельным ADR.
2. **С опцией `WithCauseID` генератор id не вызывается (к п. 1).** `Derive` сначала применяет опции и берёт `nextID()` только тогда, когда id после опций пуст. Следствие нормативно: число событий с id из причины — повторы публикации, перестроения после рестарта — не сдвигает последовательность id остальных событий процесса. Иначе при `--id-source=sequence` повтор одной публикации менял бы id всех следующих корней, и replay расходился бы с записью. Разовое следствие — у процессного теста T-255 сместилось распределение исходов после перехода двойников на опцию. Ревью #2 T-419 доказало: причина только в генераторе, правила не менялись — мутант, возвращающий прежний расход id, возвращает и прежнее распределение.
3. **Причина для событий жизненного цикла встречи — событие, от которого строится пакет, а не факт State (к п. 2; ADR-026 п. 1).** Id нужен до факта: его пишет само предложение — `opened_by_event_id` в предложении создания, `closed_by_event_id` в закрывающем пакете. Поэтому в `Derive(причина, …, WithCauseID(id встречи))` причина такая:

   | Событие | Причина (`causation_id`) |
   |---|---|
   | `encounter.started` | событие, от которого строится предложение создания: вход игрока (двойник); у GM региона — событие, по которому он решил открыть встречу (`tick.fired` или вход) |
   | `encounter.ended` по обмену | событие, на которое отвечает обмен: действие игрока (соло), `round.closed` (группа). Не `combat.decided`: решений на обмен два, а обмен один |
   | `encounter.ended` по чужому факту | этот факт: `entity.updated` NPC, ставший терминальным (Б1, ADR-026 п. 7), или `entity.updated status=abandoned` последнего игрока |

   Однозначность: одна причина закрывает не больше одной встречи, а `parts` — id встречи. Выброшенный закрывающий пакет своё событие не публикует, а следующее закрытие строится от другой причины и получает другой id. Публикация по-прежнему только после факта (ADR-026 п. 1).
4. **Причина без id (к п. 1).** Паника опции на причине без id остаётся: у `NewRoot` это ошибка программиста. Но `Derive` от конверта без id достижим по данным при `MV_BUS_VALIDATE_ON_READ=false`, поэтому издатель проверяет `ev.ID != ""` до `Derive(…, WithCauseID(…))`: запись `Error` и отказ от ответа вместо паники. Так уже сделано в двойнике (T-419 итерация 3), и это требование DoD T-229 и T-230. Последняя линия защиты — перехват паники обработчика в `eventbus.Delivery` (C-01 v1.5, T-425): событие уходит в `dead_letters`, процесс не падает. Проверка в обработчике этой линии не заменяется — без неё действие не получает ответа, а виден будет только `dead_letters`.

## Уточнение исполнения 2 (2026-09-11, T-431, system-architect#1)

Решение не меняется. Основание — запрос architect#2 (design EPIC-003 §14.1, «Запрос system-architect») и проверка design EPIC-003 §14 (там же, §14.5). Если текст п. 3 выше расходится с этим разделом, действует раздел.

5. **Пример у `Seen` в п. 3 устарел (к п. 3).** Читать п. 3 так: «`Seen` остаётся для потребителя, чей побочный эффект нельзя сделать идемпотентным: для него запоминание до обработки — меньшее зло, чем повтор эффекта». Пример «(агент встречи: повтор задвоил бы кости)» снят. Агент встречи делает ответ идемпотентным по построению: у всех событий ответа id из причины, и ответ собирается один раз (design EPIC-003 §14.1). Поэтому он использует `Has`/`Add`.
   - *Почему решение не меняется:* п. 3 оставлял выбор формы потребителю по признаку «что меньшее зло», и агент встречи этот признак соблюдает.
   - После §14.1 повтор его ответа не задваивает ни кости, ни события.
   - Раннее запоминание, наоборот, теряло бы полуопубликованный ход на каждом плановом рестарте, потому что окно лежит в снапшоте (C-14 v1.2).
   - Та же правка — в C-01 v1.6 («Дедуп»).
6. **Посредник не гасит повтор раньше получателя (к п. 3–4).** Двухшаговое окно получателя работает, только если повтор до него доходит. Поэтому посредник, который раздаёт событие получателям внутри процесса (Router роя), запоминает событие в своём окне только после того, как все получатели ответили без ошибки. Ошибку получателя он возвращает шине (C-01 v1.6). Иначе раннее запоминание у посредника воспроизводит у получателя ту самую потерю без следа, от которой его избавляет п. 3.
7. **Прочтение C-05 п. 1: «`dice.rolled` и `combat.decided` повторно не публикуются» значит «не решаются заново»** (C-05 v1.6). На повторе при конфликте версий новых бросков и решений нет. Повтор публикации того же события с тем же id — дубль at-least-once, и его гасит дедупликация по id (п. 5 «Чего решение не делает» не меняется).
