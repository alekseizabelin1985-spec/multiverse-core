# ADR-027: Идентификатор производного события выводится из причины; окно дедупликации — в два шага

Статус: принято · Дата: 2026-09-11 · Автор: system-architect#1 (T-416, ревизия контрактов волны 1)
Уровень: общий код C-01 (`shared/eventbus`: совместимые дополнения Go-API) и уточнение C-14. Стек и границы блоков не меняются.
Связи: C-01 v1.4, C-05 v1.4 п. 4–5, C-14 v1.2; ADR-023 (at-least-once, коммит не гарантирован); ADR-026 п. 1, п. 10; NFR-013, NFR-061. Задачи: T-220 (принята), T-229 (DoD уже требует id из причины и окно в снапшоте), T-230, T-232, T-236, EPIC-002 T-055/T-056, новая задача EPIC-001 «C-01 v1.4 в коде». Источники: ревью #1 T-220 (Mi-1, зонд P1), ревью #2 T-220 (Mi-3, зонды P4 и P5, сравнение окна и `Dedup`), `journal.md` 2026-09-11.

## Контекст

У нарратора один побочный эффект — публикация текста, поэтому событие он должен запоминать как отвеченное только после успешной публикации. Иначе упавшая публикация теряется бесследно: нет ни нарратива, ни `dead_letters`, ни лога (зонд P1). `eventbus.Dedup.Seen` спрашивает и запоминает одним шагом, поэтому T-220 завела собственное окно. У него вытеснение FIFO вместо LRU и нет `IDs`/`Restore`, то есть его нельзя положить в снапшот C-14. Для заглушки это допустимо, для настоящего GM (T-229) — дефект.

Второй шаг сам по себе не спасает. Если запись в брокер прошла, а подтверждение потерялось, шина вернёт ошибку, обработчик повторится, и текст уйдёт второй раз. `Derive` каждый раз берёт новый `nextID()`, а шлюз гасит дубли по `id` (`narrative_event_id` = `id`, C-05 v1.1). У второй публикации id другой, и шлюз её не погасит — игрок увидит текст дважды (зонд P4). Отдельно ADR-026 требует после рестарта опубликовать `encounter.ended` с тем же id, который назвал закрывающий пакет. Со случайным id это невозможно.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только двухшаговый `Dedup` (`Has` + `Add`) | упавшая публикация повторяется, окно одно и сериализуемо | потерянное подтверждение по-прежнему даёт дубль под новым id |
| B. Идемпотентный продюсер брокера | дубль при повторе внутри сеанса продюсера гасит брокер | клиент `kafka-go` его не поддерживает; не покрывает `membus`, рестарт и replay; решает только часть случаев |
| C. Потребитель гасит дубли по `(causation_id, type)` | ничего не менять у издателя | каждый потребитель учит правило «одно событие типа на причину», которое знает только издатель; id перестаёт быть единственным ключом дедупликации, на котором стоит вся платформа |
| **D. Id производного события выводится из причины + двухшаговый `Dedup`** | повтор, рестарт и replay дают тот же id, и существующая дедупликация по id потребителей гасит дубль; replay побайтно совпадает независимо от `--id-source` (NFR-061); ADR-026 п. 10 становится выразимым | опция применима только там, где издатель публикует не больше одного события на `(причина, тип, части)`; неверно выбранные части склеят два разных события в одно |

## Решение

1. **`eventbus.WithCauseID(parts ...string) DeriveOption`** (C-01 v1.4). Id события — UUIDv5 в пространстве имён платформы (константа пакета `eventbus`) от `causation_id`, типа события и `parts` через разделитель, которого нет в id. Одна и та же причина, тип и части дают один и тот же id. В `NewRoot` опция — ошибка программиста: у корня нет причины, и конструктор паникует, как `runtime.Registry.Register` на повторном имени. Ошибка видна в первом тесте, а не тихо в бою.
2. **Где обязательна.** `narrative.output` (T-229): `parts` — вид нарратива, если на одну причину возможны разные виды. `encounter.started` и `encounter.ended` (ADR-026): `parts` — id встречи.
   **Где рекомендована.** Факты State (`entity.created`/`entity.updated`, `parts` — id сущности). Тогда «факты досылаются, если не были опубликованы» (C-02) перестаёт давать дубли у потребителей. Решение принимает EPIC-002 в T-055/T-056.
   **Где запрещена.** События, которых на одну причину и тип может быть несколько, если `parts` их не различают. Пример — `dice.rolled`: там `parts` обязан содержать индекс броска.
3. **Двухшаговое окно** (C-01 v1.4). `Dedup.Has(id) bool` спрашивает и окно не меняет. `Dedup.Add(id)` запоминает. `Seen` остаётся атомарной парой для потребителей, у которых запоминание до обработки — меньшее зло (агент встречи: повтор задвоил бы кости). Предусловие двух шагов — обработчик не вызывается конкурентно для одного события. Обе реализации шины это соблюдают: подписка отдаёт топик по одному событию (зонд P5 достижим только прямым конкурентным вызовом).
4. **Окно — в снапшоте** (C-14 v1.2). Stateful-потребитель сериализует свои окна `Dedup` (`IDs` → снапшот, `Restore` ← снапшот), включая окно «уже ответил» роя. Собственное окно без сериализации у stateful-контекста — дефект.
5. **Чего решение не делает.** Потребитель без дедупликации по id по-прежнему видит дубль: дедупликация остаётся его обязанностью (C-01). Нерешённым остаётся и дубль при конкурентной доставке одного события — это нарушение предусловия п. 3, а не случай, который решение покрывает.

## Последствия

- **Позитивные.**
  - Потерянное подтверждение, рестарт и replay дают один id, и дубль гасится тем механизмом, который уже есть у каждого потребителя.
  - Replay производных событий не зависит от источника id.
  - Одно окно дедупликации вместо своих окон в каждом контексте.
- **Негативные.**
  - Издатель обязан правильно выбрать `parts`, и ошибка тихая: два разных события получат один id, и второе будет погашено как дубль. Защита — таблица применимости в п. 2 и тест, что разные `parts` дают разные id, а одинаковые — одинаковые.
  - Добавляется одна опция и два метода в общий пакет (`contract-change`).
- **Что придётся сделать.**
  - Новая задача EPIC-001 «C-01 v1.4 в коде» (S, метка `contract-change`): `Dedup.Has`/`Add`, `WithCauseID`, тесты — детерминизм, различие частей, паника в `NewRoot`, валидность id по `_envelope.json` (строка, `minLength` 1), README пакета. Срок — до T-229 (подволна 1.9).
  - T-229, T-230, T-232 применяют опцию.
  - Задача «двойники по C-05 v1.4» заменяет окно `FakeNarrator` на двухшаговый `Dedup`.
- **Условие пересмотра.** Появится издатель, которому нужна идемпотентность без естественной причины, например событие по таймеру вне `tick.fired`. Тогда id выводится из ключа идемпотентности, переданного явно, — той же опцией с другим набором частей, без нового механизма.
