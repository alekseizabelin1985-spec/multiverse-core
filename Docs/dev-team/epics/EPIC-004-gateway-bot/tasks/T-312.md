### Что сделано

**`cmd/telegram-bot/internal/deliver`** (новый пакет, `loop.go`):
- `Loop.Run(ctx)` — цикл доставки в своей горутине; `Loop.Once(ctx)` — один оборот: ack того, что осталось с прошлого раза, затем `Deliveries(cursor, limit=100, wait=25s)`, затем доставки ответа по одной в порядке шлюза, затем один `Ack` на все отработанные.
- Решение об ack — только по типу ошибки `Sender` (DoD Mi-1 ревью T-310): отправлено, `ErrBlocked`, `ErrChatNotFound`, `ErrRejected` → ack; `ErrUnavailable`, неизвестная ошибка, отмена `ctx` → без ack; `ErrUnauthorized` → без ack, остаток ответа не отправляется. Повторы `429`/`5xx` — внутри `sender.Telegram` с `DefaultPolicy` (3 попытки, пауза `retry_after`).
- Доставка из нескольких частей (текст длиннее 4096) уходит подряд, до следующей доставки; ack — после всех частей.
- Доставка без маршрута Telegram (нет `route`, другая платформа, нечисловой `external_id`) подтверждается без отправки — см. «Решения».
- Курсор — поле `Loop`, нигде не сохраняется (КД §16 п. 5). Не принятый шлюзом ack держится в памяти (без дублей, не больше 1000 id) и повторяется перед следующим опросом. При остановке — последний ack под своим контекстом, до 5 с.
- Ошибка long-poll (сеть, `409 poll_in_progress`, `5xx`) → пауза 1, 2, 4 … 30 с на `clock.Timers`, строка лога на каждую, строка при восстановлении.
- Лог: ключи `kind`, `reason`, `count`, `error` (через `privacy.Redact`), `pause`; ни чата, ни внешнего ID, ни текста.

**`cmd/telegram-bot/main.go`, `serve.go`, `health.go`** (пакет бинарника):
- `main` → `os.Exit(run(ctx, args, environment))`, `ctx` отменяется `SIGINT`/`SIGTERM`. Без аргументов — бот (так его запускает compose); `health [--url]` — healthcheck; иное → код 2.
- `serve`: логгер `shared/logging` (`MV_LOG_LEVEL`, `MV_LOG_FORMAT`) → `config.Load` (ошибка → stderr без значений, код 1) → `build` → `bot.run`.
- `build` (сборка зависимостей):
  - один логгер `slog.New(privacy.NewHandler(logging…, privacy.NewRedactor(cfg.Secrets()...)))` — для `access`, `flow`, `deliver`, `updates` и ошибок библиотеки;
  - `sender.NewTelegram` с `DefaultPolicy` и клиентом 30 с — циклу доставки; `WithPolicy(sender.ReplyPolicy)` того же отправителя — `flow`;
  - `sender.NewBestEffortTelegram` со своим клиентом 5 с — `access.Gate`;
  - два клиента шлюза `client.New(cfg.GatewayURL, "telegram-bot")`: `flow` — `HTTP.Timeout` 6 с и `Backoff{Retries: 1, 200 мс}`; цикл доставки — 35 с (`client.DefaultHTTPTimeout`) и `DefaultBackoff`;
  - `updates.NewTelegram` с `PollTimeout` из конфигурации.
- `bot.run`: слушает `/health` на `MV_TELEGRAM_HEALTH_ADDR`, запускает цикл доставки в горутине, обработчик обновлений `gate.Wrap(flow.Handle)` — в `Source.Start`; после его возврата останавливает цикл (ack отправленного), закрывает `/health`, пишет причину в лог и stderr через `Redactor`, возвращает `updates.ExitCode(err)`: `ErrConflict` → 3, `ErrUnauthorized` (и `getMe`, и `401 getUpdates`) → 1, остановка сигналом → 0.
- `GET /health` → `{"status":"ok","details":{"bot_denied_total","bot_not_private_total","bot_too_often_total"}}` из `access.Counters`.
- `telegram-bot health [--url]`: умолчание из `MV_TELEGRAM_HEALTH_ADDR` (пустой хост, `0.0.0.0`, `::` → `127.0.0.1`, как `defaultHealthURL` в `cmd/multiverse/health.go`); код 0 только при 200 и `status: ok`; проба без прокси окружения, таймаут 3 с. `docker-compose.bot.yml` не менялся.

### Решения по ходу
1. **Доставка без маршрута Telegram — ack без отправки.** КД §8.2 и C-08 такого случая для клиента своей платформы не описывают (шлюз не выдаёт `route` чужой платформе и роняет доставки без связки). Неподтверждённая она 24 ч (TTL) выдавалась бы каждые 30 с и держала бы очередь игрока (одна в лизинге). Выбран ack со строкой лога `reason=no_route`; вопрос в «Открытых вопросах».
2. **`ErrUnauthorized` останавливает отправку остатка ответа.** DoD требует только «без ack»; остальные сообщения того же ответа получили бы тот же `401`. Отправленное до него подтверждается.
3. **Неудачный ack не теряется** — повторяется перед следующим опросом; при остановке — последний ack до 5 с. Уменьшает повторы сообщений после сбоя шлюза или `SIGTERM`; вне DoD, но внутри «пакетный ack» КД §10.4.
4. **Отдельные клиенты с явными лимитами** (`limits` в `serve.go`): отказ — 5 с без повторов; `flow` → шлюз — 6 с (шлюз обрывает обычный запрос на `api.RequestTimeout` 5 с) и один повтор через 200 мс, итого ≤ ~12 с на команду; цикл доставки → шлюз — 35 с. Telegram для `flow` и цикла — один клиент 30 с, разные политики (DoD M-2 требует отдельного клиента только шлюзу отказов).
5. **`/health` без `shared/runtime`.** Свой маленький `http.Server` с тем же форматом `{status, details}`: `shared/runtime` притянул бы в бинарник бота `shared/contracts`, JSON-схемы и `shared/recording`. `status` всегда `ok`, пока процесс жив — доступность Telegram и шлюза не отражает (в рисках).
6. **Подкоманда `health` ходит без прокси** (`Transport{Proxy: nil}`): проба спрашивает соседний процесс; в `cmd/multiverse` та же проблема решена заменой пустого хоста, здесь — и тем же, и отключением прокси.
7. **Новых переменных нет.** `X-Client-Id` — константа `telegram-bot` (умолчание `MV_GATEWAY_CLIENT_IDS`), ожидание long-poll — `client.MaxPollWait` 25 с, таймауты клиентов — константы. КД §11.3 называет `MV_BOT_CLIENT_ID` и `MV_BOT_DELIVERY_WAIT`; в манифест они не вносились — объявлять переменную ради значения, которое не меняется, значит расширять compose и `.env.example` без нужды. Для devops: передавать в `docker-compose.bot.yml` нечего сверх уже известного по T-463 (`MV_TELEGRAM_ACTION_KEY_SALT`, `MV_TELEGRAM_COMMANDS_PER_MIN`).
8. **Коды выхода:** 1 — конфигурация, токен, занятый порт `/health`; 2 — командная строка (как у `cmd/multiverse`); 3 — `409`.

### Риски
- При `SIGTERM` может потеряться одно обновление, уже взятое в обработку (`WithUpdatesChannelCap(0)`): остаток пачки Telegram отдаёт повторно, повтор гасится `action_key`. Записано в runbook §6 и README.
- Повтор сообщения игроку: доставка ушла, а ack не дошёл (сбой шлюза дольше 30 с, падение процесса) — после истечения лизинга шлюз выдаст её снова. Для доставки из нескольких частей сбой на второй части повторит первую.
- `/health` бота — `ok`, пока процесс жив: зависший Telegram или недоступный шлюз compose не перезапустит.
- Цикл доставки стартует одновременно с проверкой токена (`getMe`): при отозванном токене он успеет взять доставки в лизинг; они не подтверждаются и вернутся через 30 с.
- В тестах `main` на Windows httptest-сервер не видел разрыва удерживаемых запросов после остановки бота и ждал их в `Close`; моки освобождают удерживаемые запросы в `Cleanup` до `Close`.
