### Дополнение оркестратора (ревью #1 T-312)
1. **Поздний ack.** `Ack` принимает доставку клиента, пока она `pending` и `leased_by` — этот клиент, независимо от `leased_until`. `ReleaseExpiredLeases` снимает только `leased_until` и оставляет `leased_by`. Если доставку снова взял **другой** клиент, поздний ack первого — `unknown`. Если снова взял **тот же** клиент, поздний ack подтверждает её, и вторая выданная копия сообщения становится лишней. Тест `TestALateAckIsTakenUntilTheDeliveryIsLeasedAgain`, мутант M4 («release стирает `leased_by`») — красный. КД §8.4 (`WHERE id IN (...) AND leased_by=:client`) и §8.2 (кандидаты — «без действующего лизинга») этому не противоречат.
2. **Пустой ответ раньше `wait`.** В шлюзе он бывает только при остановке сервера процесса (`runtime.ShuttingDown`, C-01 v1.8, КД §5.1 п. 8). В replay long-poll не отвечает пустым раньше срока: ожидание идёт по настенным часам (решение 3), лизинг работает. Отмена запроса клиентом ответа не даёт. **Как клиенту держать темп:** пустой ответ, пришедший заметно раньше `wait_ms`, означает остановку процесса. Следующий long-poll — после паузы порядка секунды, лучше с нарастанием, как после сетевой ошибки; иначе цикл доставки бота будет повторять запросы к останавливающемуся процессу, пока не получит сетевую ошибку. КД §8.3, §10.4 и C-08 темп клиента не определяют — вопрос 5.

### Решения по ходу
1. **Id доставки выводится, а не берётся из генератора** (КД §4.2: `d-<ULID>`): `d-` + UUID v5 от длинно-префиксной записи ключа. Причины: (а) `Deps.IDs` при `--id-source=sequence` выдаёт `link_id` и `player_id`, и каждая доставка сдвигала бы их в e2e — порядок consumer и HTTP недетерминирован; (б) уникальный `id` сам даёт идемпотентность `Enqueue` без нового индекса; (в) ключ перехода встречи (`encounter_id`, `opened`, `player_id`) делает доставку открытия идемпотентной после рестарта без миграции `0002_*`. Ключ события включает `kind`: одно событие может дать игроку доставки двух видов.
2. **Одна доставка в лизинге на игрока — строже SQL КД §8.2:** `NOT EXISTS` проверяет любую другую действующую доставку игрока (`x.seq <> d.seq`), а не только более раннюю.
3. **Ожидание long-poll — по настенным часам в любом режиме** (`clock.RealTimers{}` в `context.go`, в тестах — управляемые): в replay процесс даёт контекстам `replay.NullTimers`, и long-poll без данных не закончился бы никогда. Основание — то же, что у `runtime.SetDeadlines` (C-01 v1.8): время соединения, не домена. Лизинг и `created_at` — по `Deps.Clock`. Вопрос 4.
4. **Доставка с маршрутом другой платформы → `dropped`**, как без маршрута: `Lease` фильтрует по платформе постановки, и клиент платформы связки её не увидит никогда.
5. **Платформа клиента — таблица в коде** `handlers.ClientPlatforms` (`telegram-bot → telegram`), по рекомендации КД §5.1. Клиент без платформы получает пустой список после `wait_ms` и `unknown` на ack. Вопрос 1.
6. **Ack — одна транзакция на вызов** (КД §8.4). Сбой публикации завершения хода откатывает весь вызов → `503 bus_unavailable`; эталонный клиент повторяет `503`.
7. **Отказ State ищет игрока сначала по ходу** (`turns.Load` по `correlation_id`), затем по `entity` отказа: ход записывается после публикации пакета (`context.WithoutCancel`, T-305), и отказ может прийти раньше. Без хода и без `entity` отказ пропускается с `Warn` — риск ниже. Текст выбирается по `action_type` хода, без хода — общий «Действие не выполнено».
8. **Адресаты `combat.decided` в группе** — живые участники плюс игроки, о которых решение (удар, убивший защитника, — новость и для него). Групповой бой — I2, путь проверен только unit-тестом.
9. **Доставка `world_event` на открытие встречи** адресуется участникам встречи в проекции (из `encounter.started` или из сущности), живым.
10. **Звонок до коммита.** `Enqueue` звонит внутри транзакции consumer; ждущий long-poll лизингует на том же единственном соединении и видит строки только после коммита, откат будит его впустую.
11. **`api` не импортирует `shared/runtime`** (КД §3: вне stdlib только `shared/clock`, пакет импортирует бот) — `Config.SetDeadlines` получает функцию от контекста.

### Отклонения от дизайна и DoD
- Решение 1 — формат id доставки (`d-<UUID v5>` вместо `d-<ULID>`).
- Решение 2 — условие «одна в лизинге» строже SQL КД §8.2.
- Решение 3 — ожидание long-poll по `clock.RealTimers{}` вместо `Deps.Timers`; КД §11.2 говорит, что в replay «лизинг outbox не работает», а лизинг работает во всех режимах (вопрос 4).
- `Store.Enqueue` принимает транзакцию и время (`Enqueue(ctx, q, now, ds...)`), `Lease` — без `after` (КД §6): `after` дублирует условие лизинга и влияет только на `cursor` пустого ответа. `Renderer` — функции пакета, а не интерфейс.
- Групповые доставки (`group.*`, `round.opened`, `player.said`) из КД §8.1 не делались — T-352/T-353, в описании T-307 их нет.

### Риски и допущения
- Сбой брокера → откат ack → повторная выдача сообщений игрокам (вопрос 2).
- Отказ State без хода в `gateway.db` и без `entity` в payload пропускается с `Warn`: игрок не узнает об отказе. Схема `entity.update.rejected` поле `entity` не требует; `FakeState` пишет его, когда знает сущность.
- Поздний ack того же клиента после повторной выдачи подтверждает доставку, вторая копия уже ушла игроку: дубль возможен, но не повторяется бесконечно.
- Клиент без платформы держит слот `pollguard` весь `wait_ms`, ничего не получая.
- В replay ожидание long-poll идёт по настенным часам, а лизинг — по часам процесса. Если часы replay стоят, лизинг не истекает, и доставка без ack не выдаётся повторно.
