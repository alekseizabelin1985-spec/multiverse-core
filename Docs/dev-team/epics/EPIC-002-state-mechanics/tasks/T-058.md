### Решения по ходу и отклонения
1. **Источник предложений** — не открытый вопрос: КД §4.10 (изм. T-444) и C-02 v1.5/v1.8a уже решили `source=mvctl`, предлагающий `author`, `cause=init`, `actor_kind=system`; строка `system` пуста. Код следует им.
2. **Идемпотентность.** State гасит повтор применённого предложения **без ответа** (§4.5 п. 2, T-056), поэтому ждать нечего. `Bootstrap` сначала читает журнал `[0, End)`: сущность, чей `entity.created` с тем же `proposal_id` уже там, не предлагается и попадает в `Skipped`. Отказ `duplicate_entity` (сущность есть, окно и запись коммита bootstrap уже не называют) — тоже `Skipped`. Строка КД §4.10 «`duplicate_entity` с тем же `proposal_id` = дедуп → тихий пропуск» описывает State не так, как он работает — вопрос 1.
3. **`--force` над миром со снапшотами** — *(итерация 2: заменено решением system-architect — очистка объектов State мира, снапшот seq 0; ниже — текст итерации 1)* ~~принят `seq > 0`, `state/` не чистится.~~ Снапшот `bootstrap` получает номер за наибольшим объектом (`nextSeq`, T-057), прежние уходят ротацией K=5; команда ничего не удаляет. Строку «снапшот seq 0» читать как «первый снапшот нового мира» — вопрос 3.
4. **Снапшот `shutdown` State внутри команды.** `Context.Stop` пишет снапшот `shutdown` (§4.9), и `latest.json` ушёл бы с `bootstrap` seq 0 на `shutdown` seq 1 того же мира. Команда даёт State обёртку хранилища `sealable`: после снапшота `bootstrap` — и после неудачного bootstrap или снапшота — запись и удаление отклоняются `errSealed`. Снапшот `shutdown` не пишется, эту ошибку `Stop` команда отбрасывает (`unexpected`), остальные возвращает. После неудачного bootstrap `latest.json` нет, следующий `init` не упирается в «инициализирован». Отклонение от буквы §4.9 для короткоживущего State — вопрос 2, предложение в бэклог 1.
5. **`--store` по умолчанию** — `memory` (DoD-команда работает без стека). ~~Мир в MinIO через State внутри команды — `--bus memory --store minio`.~~ *(итерация 2, Ma-1 и решение system-architect: при `--bus memory` допустимо только `--store memory`, иначе `exit 2`; мир в MinIO создаёт путь `--bus kafka`.)*
6. **`--bus kafka`** отказывает `exit 2` до открытия хранилища и публикаций: иначе сущности были бы предложены, а снапшота и указателя не было бы, и следующий `init` не отказал бы.
7. **Курсор.** Строка приёмки T-057 говорит «сверяет курсор с `End` журнала после bootstrap». `Applier` ставит курсор на офсет предложения + 1, то есть на факт последнего предложения, `End − 1` до `snapshot.created`. Тест сверяет точное значение по журналу и главное свойство: в `[cursor, End)` нет предложений.
8. **Код выхода 2** для «мир инициализирован» — по DoD и КД §4.10, хотя в `cli` код 2 — «вызов неверен». Скрипт отличает случай по тексту stderr.
9. **`BootstrapOption`** (вариативный хвост сигнатуры КД): тест таймаута без 10 с реального ожидания. Вызовы по сигнатуре КД не меняются.
10. **Логи State и шины внутри команды** — в `slog.DiscardHandler`. Оператору команда сообщает сама: отказ с причиной, ответ не пришёл — вместе с `Health()` State, снапшот не записан.
11. **`LoadFixtures` в `internal/state`** повторяет `shared/testkit/state.LoadFixtures`: production-код не импортирует `shared/testkit` (depguard). Предложение в бэклог 2.
12. **`world status`** сверяет указатель с объектом (сверх DoD, строго по порядку чтения §4.4): иначе `status` показывал бы `state_hash`, который объект не подтверждает.

### Открытые вопросы (к system-architect через оркестратора)

Если retention `system_events` унесёт `entity.created`, а State ещё помнит bootstrap в записи коммита, повтор не получит ответа и закончится таймаутом. Нужен ли State ответ на повтор применённого создания или `world init` при `--bus kafka` проверяет мир иначе?

### Вопросы исполнителя
1. **Идемпотентность `Bootstrap`: прав код, текст КД исправлен.** C-02 v1.6 уже говорит «State гасит по нему повтор создания», то есть без ответа. Строка КД «`duplicate_entity` с тем же `proposal_id` = дедуп → тихий пропуск» описывала ожидание, которого у State нет. Новый комментарий `Bootstrap` в КД §4.10: «повтор идемпотентен и ответа на уже применённое не ждёт: сущность, чей `entity.created` с тем же `proposal_id` уже есть в `system_events` `[0, End)`, не предлагается — State гасит повтор применённого предложения без ответа (§4.5 п. 2, C-02 v1.6); ответ `duplicate_entity` (сущность есть, а окно и `last_change` этот `proposal_id` уже не называют) — тоже пропуск; иной отказ или нет ответа — `ErrBootstrap`, созданное остаётся». Сигнатура в КД дополнена `opts ...BootstrapOption`, отступление 9 принято. Строка §4.5 «с тем же `proposal_id` — дедуп» описывает State и не меняется. Код не меняется.
2. **Снапшот `shutdown`: принято закрытое хранилище (`sealable`), признак в `state.Config` не вводится.**
   - Короткоживущий State есть только у этой команды, поэтому правило живёт рядом с единственным вызывающим.
   - Закрытие покрывает и путь неудачи. Без него `Stop` после оборванного bootstrap записал бы `latest.json` половины мира, и следующий `init` отказал бы.
   - Признак потребовал бы правки `Config` и цикла снапшота `shutdown` в `Stop`. В рабочей папке T-059 изменены обе эти части `context.go`, так что конфликт гарантирован без выигрыша.
   - Проверено против кода T-059: снапшот PUT не повторяет, отказ закрытого хранилища мгновенный. `Stop` T-059 пропускает мир `uninitialized`, и это дополняет закрытие, а не заменяет его: мир, где создана сущность мира, но не NPC, уже не `uninitialized`.

   Правило внесено в КД §4.10. Предложение в бэклог 1 исполнителя отклонено; пересмотр — когда появится второй вызывающий короткоживущего State. **Условие приёмки:** после слияния T-059 в ветку эпика тесты `cmd/mvctl/internal/world` прогоняются заново на новом `Start`, который при `Objects` восстанавливает мир.
3. **`--force`: очистка и снапшот seq 0; вариант `seq > 0` поверх старого мира не принят.**
   - В рабочей папке T-059 `Start` при `Config.Objects` вызывает `Applier.Recover`, и старый мир поднимается вместе с окном `proposal_id`.
