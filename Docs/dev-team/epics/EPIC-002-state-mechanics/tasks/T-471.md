### Что сделано
1. **Законы в процессе.** `cmd/multiverse/contexts_state.go`: фабрика `newStateWithTheLaws` читает книгу правил из `MV_RULES_PATH` (`mechanics.Load`) и строит `state.New(state.Config{Invariants: rules.Invariants()})`. Имя и умолчание `rules/dark-forest.yaml` взяты из `design.md` эпика, §4.3 «Путь правил» и §7. Путь считается от рабочей папки процесса. Переменная объявлена в `shared/env/vars.go`, строка добавлена в `.env.example`. Если книга не читается или не компилируется, фабрика возвращает контекст `lawless`. Его `Start` отказывает, `/health` отвечает `fail`. Текст отказа называет переменную, путь, рабочую папку (для относительного пути) и причину: `start context state: state: the laws of the world are not loaded from MV_RULES_PATH="rules/dark-forest.yaml" (relative to the working directory …), and state does not run without them: mechanics: read rules: open rules/dark-forest.yaml: …`. Книгу без законов уже отвергает `mechanics.Load` («no laws»), поэтому своей проверки нет. Книга читается при сборке контекстов, а не в `init`: так же `newSwarm` читает `MV_SWARM_FAKE`.
2. **Образ.** `build/Dockerfile`: в итоговой стадии заданы `WORKDIR /home/nonroot` и `COPY rules/ ./rules/`. Рабочая папка задана явно, а не взята из базового образа, поэтому относительное умолчание указывает на эту копию. `.dockerignore` каталог `rules/` не исключает.
3. **Норма rest (C-02 v1.8 п. 3).** В `internal/state/ownership.go`:
   - `normAllows`, первая ветка: набор шлюза с `cause=rest` пишет только корень `hp`, иначе `level_violation` на шаге 6;
   - `restRefusal` проверяет по порядку: встреча (`encounter_id` сущности до операций) → `law_violation` без `invariant_id`; `hp` не целое → `invalid_op`; нет целого `hp_max` или `hp > hp_max` → `law_violation {inv-02}`; `hp < hp_max` → `level_violation`.

   Порядок по C-02: путь → встреча → вид `hp` → значение. `apply.go` не менялся.
4. **Строка `system` (C-02 v1.8 п. 6).** В `shared/contracts/ownership.go` строка теперь `{Proposer: ProposerSystem}`: пустая, как у `object` и `monitor`. Константа `ProposerSystem` осталась. Комментарии о предлагающих и о норме rest приведены к v1.8.
5. **Тестовое окружение процесса.** Тесты `cmd/multiverse` запускаются из папки пакета, где `rules/` нет. Поэтому `onLoopback` (`serve_test.go`) задаёт `MV_RULES_PATH` абсолютным путём к `rules/` дерева через помощник `withTheRuleBook` (`contexts_state_test.go`). `emptyWorldEnv` (`test/e2e/empty_world_test.go`) передаёт дочернему процессу тот же абсолютный путь. Стенд I1-α и тесты `/health` делают `t.Chdir` в корень, поэтому идут на умолчании.
6. В `tasks/T-056.md` пункт DoD «`system` proposer и источник bootstrap» в двух таблицах закрыт ссылкой на T-471 с пометкой «на ревью». Индекс `../tasks.md` не трогал: это запрет промпта.

### Решения по ходу и отклонения
- **Где читается книга.** Книга читается в фабрике контекста (`runtime.New` у `serve`), отказ приходит из `Start`. Держать загрузку в `internal/state` (поле `Config` с путём) означало бы править `context.go` рядом с T-057, а в «Файлах» T-471 его нет. Тесты `cmd/multiverse` проверяют тип `*state.Context`, поэтому ленивой обёртки над ним нет.
- **Строка матрицы T-056 «rest inside an encounter that erases encounter_id in the same set»** теперь ожидает `level_violation`, а не `law_violation`: по C-02 v1.8 п. 3 путь проверяется раньше встречи. Свойство Mi-1 ревью #1 T-056 (встреча читается до операций) через `Applier` больше не наблюдается. Его держит прямой тест `restRefusal` и мутант M14.
- **Строка «rest below zero»** в `plan_test.go`: inv-02 → `level_violation` (T-470, «Передать»).
- **Мутант порядка.** В индексе он назван «встреча после вида `hp`», в T-470 — «встреча раньше нормы пути». Проверены оба (M5, M6).
- **Название переменной.** В строке T-471 индекса сказано: «каталог `rules/` рабочей папки или переменная через `shared/env` — выбор с tech-lead#1». Взята переменная из `design.md` эпика. Нужна отметка tech-lead#1 (вопрос 1).

### 2. Порядок отдыха: `append hp` во встрече → `invalid_op` раньше встречи
**Решение: прочтение ревью #1 («Риски» п. 3) и приёмки верное, это ошибка формы пакета. Текст п. 3 уточнён — C-02 v1.8a.**

Как в коде. `plan` (`apply.go:391-408`) проверяет по порядку:
1. шаг 6 — `mayChange` вместе с `normAllows`;
2. шаг 7 — `entity.ApplyOps`, ошибка даёт `invalid_op`;
3. `statusRefusal`;
4. `restRefusal`: встреча по `before`, затем вид `hp`, затем значение.

`append` к числу `hp` возвращает `ErrInvalidOp{ReasonNotList}` (`shared/entity/ops.go:343-345`). По комментарию типа это «операция, которая не применима ни к одной сущности», а решения о состоянии мира из `ApplyOps` не выходят.

*Почему это форма, а не «вид `hp`»:*
- Абзац «Причина отказа по связке» оставляет `invalid_op` за формой пакета: неизвестная операция, путь не того типа. Пакет, который нельзя применить, ошибочен при любом мире. Диагноз не должен зависеть от того, открыта ли встреча.
- Так же устроен п. 2: грамматика пути отвечает раньше дедупликации и владения.
- «Вид `hp`» из п. 3 проверяет результат, который шаг 7 пропустил: `set hp "10"`, `set hp 5.5`, `remove hp` (после операций `hp` нет). Это часть нормы отдыха, и она идёт после встречи.
- Издатели (`BuildRestProposal`, `Harness.Rest`) публикуют один `set hp = hp_max`, поэтому поведение не меняется.

*Что изменено в C-02 v1.8a п. 3:*
- порядок теперь такой: норма пути (шаг 6) → применение операций (шаг 7) → встреча → вид `hp` → значение;
- всё, что отвергает шаг 7, — `invalid_op`, и этот отказ приходит раньше проверки встречи;
- «вид `hp`» — то, что шаг 7 пропустил;
- записано заранее: после T-472 значение чужого вида в корне `hp` отвергает шаг 7.

*Следствие для T-472.* T-472 переносит виды атрибутов в `shared/entity`. По её DoD `ApplyOps` начнёт отвергать `set hp "10"` и `set hp 5.5`. Тогда отдых во встрече с таким значением получит `invalid_op` на шаге 7, а не `law_violation`. Правки для T-472 — в п. 6.

### 5. Вопросы architect#3 (T-309, EPIC-004)
**5.1. Кто ждёт State при старте.** Решение: **ждёт только `swarm`**. Рекомендация architect#3 принята, текст — C-14 v1.4.
- *Почему шлюз не ждёт.* Проекция шлюза — это снапшот State и факты журнала. Факты, которые State допубликует при восстановлении, придут подпиской и лягут по правилу версии, так что ожидание не сделает проекцию вернее.
- *Почему рой ждёт.* Рой сам решает, что предложить (тики, спавн). Без сигнала он решал бы по миру, который State ещё не восстановил.
- *Что исправлено в `contracts.md`.* В C-14 — фраза «Порядок старта». В v0.4 (б) зачёркнута фраза о `MV_GATEWAY_REPLAY_WAIT`. Добавлено «Уточнение v1.4». `diagrams/seq-recovery.md` уже рисует шлюз без ожидания, её не правил.
- *КД State §7.3 в этой ветке не правил*: здесь в КД меняются только строки с пометкой. Текст для отдельной правки — в ветке T-057 или после её слияния, решает оркестратор:
  > Порядок старта в одном процессе (`--contexts=all`): `state` → ждёт своего `replay.completed` → `swarm`/`laws`/`llm` → `gateway` → `memory`. В разных процессах сигнала `analytics.replay.completed` ждёт только `swarm` (таймаут `MV_SWARM_REPLAY_WAIT`, 120 с → `/health degraded {state_replay: missing}`); `gateway` не ждёт и сразу строит проекцию из `state/latest.json` и журнала (C-14 v1.4).
- *Найденная граница* — открытый вопрос EPIC-002, не блокирует.
  - По КД §4.8 («Что пропускается») State при восстановлении пропускает `*.proposed` в `[cursor, End)`.
  - В compose `gateway` и `core` — разные процессы. Шлюз может опубликовать предложение, пока `core` перезапускается. Такое предложение ляжет раньше `End`, который State возьмёт при старте, и останется без ответа: игрок получит `turn.completed status=timeout`.
  - Ожидание при старте шлюза это не закрывает: шлюз переживает рестарт `core` и сам заново не стартует. Граница записана в C-14 v1.4.
  - Вариант A. После догона State решает предложения из `[cursor, End)`, на которые в том же диапазоне нет ни факта, ни отказа. Первый проход собирает `proposal_id` ответов. Неотвеченные предложения решаются как пришедшие поздно, по миру на `End`.
  - Вариант B. Оставить как есть: издатель узнаёт о потере по своему сроку, игрок повторяет действие. Записать в runbook.
  - Рекомендация: A — отдельной задачей EPIC-002 после T-057, до неё — B. Сначала tech-lead#2 проверяет, что код T-057 делает §4.8 именно так.

**5.2. `snapshot.created` в replay и NFR-061.** Решение: **рекомендация architect#3 принята с уточнением**, текст — C-14 v1.4.
- В `--mode=replay` `snapshot.created` публикует только `state`. `swarm` и `gateway` в replay снапшоты не пишут и событие не публикуют. Шлюз уже так делает (T-309). Для роя это правило задаче снапшотов EPIC-003: кода ещё нет, `git grep` на кончике EPIC-003 находит только строку реестра.
- Тип служебный. В сравнение NFR-061 (ADR-010 п. 3, `mvctl golden check`) он не входит при любом `component`: EPIC-005 отфильтровывает его по типу.
- Уточнение. Место события State в журнале всё равно детерминировано: по решению T-057 снапшот пишется на worker'е между предложениями. Это нужно не для хеша, а шлюзу: по этому событию он снимает `projection=stale` (T-309, И2-1). От этого момента зависит проекция, по которой шлюз проверяет следующие действия в replay.
- *Почему вне сравнения.* Payload зависит от развёртывания и хранилища: частоты `MV_SNAPSHOT_EVERY_FACTS`, `seq` и `key` из содержимого бакета, `size_bytes` из формата сериализации. Эталон краснел бы от смены настройки. Детерминизм мира и так проверяют факты.
- *Отклонено* «State в replay тоже не публикует»: протокол State один для обоих режимов (§4.8), и снятие `stale` у шлюза в replay осталось бы без триггера.
