### Вердикт

**ВЕРНУТЬ** — Critical 2, Major 1, Minor 4, Nit 1.

Заглушка сделана хорошо и подробно: пакет на сущность, дедуп переизданного действия, проекция
мира по фактам State, три конца встречи, трофей один раз, всё публикуемое проходит валидацию схем.

Возвращаю за то, что **решение оркестратора «одно действие — ровно одно атомарное предложение»

### Замечания по серьёзности

#### Critical

**Cr-1. `fake_encounter.go:770-780` (`propose`) — при обмене, в котором никто не попал, заглушка
не публикует НИЧЕГО, и харнесс упирается в таймаут. Это прямое расхождение с решением
оркестратора от 2026-09-11 (вариант «б»).** Код:

```go
sets := pending.sets()
if len(sets) == 0 {
    e.log.Debug("nothing changed", "event_id", cause.ID, "type", cause.Type)
    return nil
}
```

Решение оркестратора: «каждое разрешённое встречей действие порождает ровно одно атомарное
предложение… Промах не меняет здоровья, но меняет УЧАСТИЕ — а без записи участия раунд невозможно
закрыть ни по „все походили“, ни по порогу пропущенных ходов… Промах расходует ход, и это доменная
правда, а не удобство теста». В коде участие не записывается: сущность встречи после создания не
обновляется вовсе (собственное отклонение 3 в `dev-log.md`), а именно она — тот механизм, которым
решение обосновано.

Доказательство запуском. Прицельно, подобранный идентификатор `probe-53`
(`Verdict(id,0)=miss`, `Verdict(id,2)=miss`):

```
double-miss cause event id: probe-53 (attack=miss, counter=miss)
entity.update.proposed published for the double-miss attack: 0 (decision: exactly 1)
```

На полном боевом пути, 60 прогонов `solo-skirmish`:

```
runs=60 ok=35
timeout: step 4 (attack player-A)  x8
timeout: step 5 (attack player-A)  x9
timeout: step 6 (flee  player-A)   x8
```

Текст отказа харнесса: `nobody resolved the attack of player-A on wolf-alpha within 5s: an
encounter answers every action it takes with one proposal of change, and none arrived`.
Тот же ноль-пакетов у бегства: провал побега без свободной атаки (или со свободной атакой мимо)
изменений не даёт.

Как исправить. Пакет без операций State действительно отвергает, поэтому «публиковать пустое» не
годится — и оркестратор это учёл. Правильный пакет у заглушки есть чем наполнить: §4.6 даёт
уровню `task` право менять сущность встречи по любому пути с `cause=combat|flee`. Достаточно на
каждое разрешённое действие класть в `pending` набор для сущности встречи — `round_seq` и
`participants[].state`/`acted` — и публиковать его вместе с ранениями, когда они есть, и одного —
когда их нет. Это заодно закрывает отклонение 3: сущность встречи перестанет быть замороженной
на момент создания.

**Одновременно снять `fake_encounter_test.go:313` `TestAMissChangesNothing`** — он утверждает
`0 proposals for an exchange that changed nothing`, то есть охраняет ровно то поведение, которое
решением отменено. На его место — тест «промах тоже даёт ровно один пакет, и в нём ход участника».

**Cr-2. `fake_encounter.go:339-369, 963-975, 984-1008` — действие, которое заглушка решила не
отрабатывать, остаётся БЕЗ ЛЮБОГО ответа, и отличить это от «никто не слушает» нельзя.**
Веток четыре, и все выходят с `nil` молча: встреча уже закрыта (`fightOf` → «action outside an
encounter»), целей не осталось (`targetOf` → пусто), вход без региона, действие чужого мира.

Для боевого пути главная — первая. Встреча закрывается, как только волк или игрок упал, а скрипт
`solo-skirmish` (T-400) бьёт дважды и потом бежит. Детерминированно, волк на 1 hp:

```
encounter.ended reason=npc_dead
attack after encounter.ended -> nobody resolved ... within 2s (waited 2s)
flee   after encounter.ended -> nobody resolved ... within 2s (waited 2.001s)
```

DoD задачи требует «0 действий без ответа». Сегодня это не выполняется: действие без ответа —
штатный исход трёх ветвей из четырёх.

Как исправить. Тут не нужен пакет изменения — нужен **явный отказ вместо тишины**. C-05 уже даёт
заглушке право закрыть встречу событием; симметрично ей нужен способ сказать «твоё действие не
принято и не будет». Наименьшая правка, не трогающая контракт: на `player.attacked`/
`player.flee_attempted` вне живой встречи публиковать `combat.decided` невозможно (нет встречи),
поэтому договорённость должна лечь в C-05 отдельным пунктом. До неё — сторона харнесса (Ma-1
ревью T-400): подписка на `encounter.ended` и мгновенный отказ. Прошу оркестратора решить, где
проводить границу; **любое из двух решений закрывает Cr-2, но пока не принято ни одно, сквозной
сценарий не исполним.**

#### Major

**Ma-1. `fake_encounter.go:57, 928-940` — встреча создаётся от имени агента уровня `task`, а §4.6
такого права не даёт: создание встречи принадлежит уровню `domain` с `cause=spawn`.**
Подтверждаю решение оркестратора и уточняю радиус поражения: это **единственное** предложение
заглушки, которое таблица владения отвергнет. Зонд прогоняет бой целиком (вход, четыре удара,
смерть волка с трофеем, бегство) и сверяет каждое предложение с `contracts.OwnershipRules()`:

```
DENY create encounter cause=spawn level=task
     -> no rule of §4.6 lets proposer=task change a encounter with cause=spawn (create=true)
OK   update player   cause=combat level=task paths=[hp]
OK   update npc      cause=combat level=task paths=[died_at hp killed_by loot_claimed_by status]
OK   update player   cause=combat level=task paths=[inventory]
OK   update player   cause=flee   level=task paths=[position]
```

Расхождений два, не одно: у уровня `task` для сущности `encounter` нет ни `Create`, ни причины
`spawn` (разрешены `combat, flee, group, death, resolve`). У уровня `domain` для `encounter` есть
и то и другое.

Как исправить: `encounterAgent` должен отдавать уровень по роли момента. При создании встречи —
`domain` (заглушка в этот момент действует как GM региона), при последующих изменениях — `task`.
Идентификатор агента `fake-encounter:solo:<player>` при этом менять не надо: §4.6 смотрит на
`meta.agent.level`, а не на имя. Заодно `AgentLevelTask` перестанет быть единственной константой
уровня в файле — рядом нужна `AgentLevelDomain`.

### Замечания по серьёзности

#### Major

**Ma-1 (новое). `fake_encounter.go:1262-1302` (`refused`), `:1286-1296`, `:1308-1315` (`awaiting`) —
дублирующая доставка отказа `version_conflict` запускает повтор пакета, который уже применён, и
представление заглушки расходится с State.** Причины две:
- `enc.pending` снимается только в ветке «сдался»: факт успешного повтора его не гасит;
- сам отказ не дедуплицируется.

Доказательство — зонд S2, детерминированно:

```
after the refusal:            offers=2; offer2 wolf hp=9 pinned v1
[State применил offer2: факт wolf hp 10→9, v2, proposal prop-sw-14]
after the DUPLICATE refusal:  offers=3 (want 2)
offer3 proposal_id=prop-sw-14 (same=true) wolf hp=8 pinned v2   ← урон снят второй раз
next action's package:        wolf pinned v3, wolf hp->3         (State: v2, hp=9)
```

`FakeState` отбрасывает третье предложение молча, как уже применённое (`testkit/state/apply.go:188-191`:
ни факта, ни отказа). Но заглушка уже сложила его в своё представление (`apply`), и оно разошлось с
State. Следующее действие гарантированно проигрывает гонку и тратит попытку. Если фантомный урон
доводит NPC до нуля, `targetOf` вернёт пусто: следующий удар останется без ответа (харнесс — «none
arrived» по сроку), а встреча не закроется.

Дубль подряд, до факта (S2b): один отказ, доставленный дважды, тратит **две** попытки из трёх
(`offers=3`).

Утверждение записи итерации 3 (§9: «дублирующая доставка отказа даст лишнее предложение, но не лишнее
применение») верно для State и неверно для самой заглушки.

Достижимость: на `membus` дубль возможен только после ошибки обработчика; на Kafka — при ребалансе
или перезапуске. `FakeContext` монтируется в процесс ядра поверх настоящей шины (T-255).

Как исправить:
1. В `Observe` при факте с `proposal_id`, равным `pending.proposalID()`, гасить `enc.pending`: пакет
   решён, отвечать на отказ больше не о чем.
2. Дедуплицировать `entity.update.rejected` по `ev.ID` тем же `eventbus.Dedup`, что и действия.

Достаточно п. 1; п. 2 дёшев и закрывает S2b. Тест: отказ → факт повтора → тот же отказ ещё раз ⇒
предложений по-прежнему 2; отказ дважды подряд ⇒ 2.

### 1. Порядок «запомнить после публикации» — где он даёт дубль

Зонд P1 и три режима, в которых дубль мог бы появиться.

| Сценарий | Как воспроизведён | Нарративов | Вывод |
|---|---|---|---|
| P1: один отказ `Publish`, через подписку | обёртка над `membus`, `player.looked` в топик | 1 (попыток 2) | как заявлено |
| P1: всегда отказ | то же | 0; DLQ 1, `attempts` 4 = попыток публикации 4 | как заявлено |
| P1: повторная доставка после успеха | `membus.Chaos{Duplicate: true}`: осмотр, удар, ответ волка — каждый в топике дважды | различных `id`: 2 (entry 1, turn 1), `based_on` = `[удар, ответ]` | дубля нет |
| P1: ход, отказ один раз на ответе волка, через подписку | — | 1, `based_on` полный | как заявлено |
| **P4: публикация записалась, но шина вернула ошибку** | `Publish` пишет запись, затем отвечает ошибкой (потерянный ack) | **2**, `id` `pe-2` и `pe-3`, у обоих `causation_id` `pe-1` | **дубль**, см. Mi-3 |
| **P5: две конкурентные доставки одного события** | два `Narrate` одного осмотра, публикация ждёт обоих (барьер) | **2**; то же для закрывающего решения хода — **2 хода** | дубль, но с шинами репозитория недостижим, см. ниже |

**Чем окно защищено от гонки `has` → publish → `add`.** Не мьютексом окна, а тем, что обработчик одного топика не
вызывается конкурентно. `membus` держит курсор группы через всю `Deliver` (`membus.go:287-309`). `kafka` читает одним
циклом `FetchMessage` → `deliver` → `CommitMessages` (`kafka.go:187-205`). `Delivery` повторяет обработчик
последовательно (`delivery.go:97-113`). Второй `Start` отвергается (`fake_narrator.go:253-256`), а `FakeContext`
создаёт один нарратор (`fake_context.go:149`). `id` принадлежит одному топику, а `Narrate` (три топика) и
`Observe` (`system_events`) работают с разными `id`. Значит, P5 достижим только прямым конкурентным вызовом
экспортированного обработчика. В итерации 1 атомарный `Dedup.Seen` это покрывал, итерация 2 — нет. Предусловие
записано в комментарии `window` (`:819-820`), но не у экспортированных `Narrate`/`Observe`.

**P4 реален для настоящего брокера.** Ошибка `WriteMessages` по таймауту после того, как брокер принял запись, и
есть потерянный ack. Шлюз гасит дубли по `id` события (`narrative_event_id` = `id`, C-05 v1.1), а у повторной
публикации `id` новый: `Derive` всегда берёт `nextID()` (`types.go:182`), опции задать `id` нет. Игрок увидит текст
дважды. Для заглушки на `membus` путь почти недостижим: запись атомарна, разве что в режиме `Chaos.Duplicate`. Но это
цена at-least-once, и её надо назвать, а не отрицать.

### 2. Буфер хода при постоянном отказе

Зонд P6 через подписку. Действие A (удар и ответ волка): публикация хода всегда отказывает, ответ волка уходит в DLQ.
Затем отказы выключены, и действие B (промах и ответ волка) рассказано. Итог: DLQ 1 (ответ волка A); нарративов 1,
`based_on` = ровно `[удар B, ответ B]`. Решений A в нём нет, склейки нет. В логе `ERROR` «dropped untold». Текст B:
«Удар уходит в пустоту. Альфа-волк отвечает — 1; Вася держится: 7 из 10.»

Внутренний зонд, длинный бой: 11 000 действий подряд, текст каждого хода отказан (4 вызова, как у `Delivery`).
`exchanges` = 1 запись с 2 решениями, окно = 10 000 (ёмкость). Памяти не течёт: буфер — не больше одного хода на
персонажа, и он заменяется при следующем действии. Остаётся только запись персонажа, который больше не
действует (сбежал или погиб). Это одна запись на персонажа, для заглушки допустимо.

Попутно: для этого случая сообщение лога неточно — см. N-3.

### 3. Своё окно рядом с `eventbus.Dedup`

| | `Dedup` | `window` |
|---|---|---|
| Ёмкость | 10 000 (`DefaultDedupCapacity`), `≤0` → по умолчанию | та же константа; `newWindow(0)` паникует (`index out of range`), но единственный вызов — с константой |
| Вытеснение | LRU: повторное попадание освежает | FIFO по времени ответа: `has` не освежает |
| Снапшот C-14 | `IDs`/`Restore` | нет |

Зонд: после `a, b, c, (дубль a), d` у `Dedup` остаются `[c a d]`, у окна — `b c d`. Для заглушки разница несущественна:
повтор приходит сразу, в пределах `Backoff` и 10 000 событий. Нарратор не stateful-контекст C-14, снапшот ему не нужен.
**Вывод:** для T-220 это нормальная локальная реализация, отдельный вопрос ради неё не нужен. Вопрос о
двухшаговом API `Dedup` оркестратор уже отправил архитектору (journal). По существу он нужен T-229: настоящему GM
понадобятся и два шага, и снапшот, и тогда второй механизм без `IDs`/`Restore` станет дефектом. К вопросу стоит
приложить P4: двухшаговый `Dedup` дубль при потерянном ack не лечит. Лечит его детерминированный `id` нарратива от
причины (например, `id` причины + вид), а это тоже изменение `shared/eventbus` (`Derive`) — в ту же пачку.

### 3. Тесты через `process.run`

- **Путь.** Контексты строит `runtime.New` из реестра пакета `main`, то есть через хук. Процесс запускается
  настоящим `process.run` на транспорте настоящего `openBus`. Снаружи на ту же шину ставятся только двойники того,
  чего в бинарнике ещё нет: `FakeState` и харнесс. Мимо кода `cmd/multiverse` идут только `parseServe`/`serve`/
  `withSignals`, их покрывают свои тесты. Мутант G1 автора (фейк не строится) краснит оба процессных теста.
- **Мой мутант O5**: хук передаёт `FixturesDir: "testdata/fixtures"`. Краснеет `TestTheProcessTellsTheDeath…`
  («0 death narratives…», исход `npc_dead`). Значит, решение «фикстур у процесса нет, мир — из `entity.created`»
  охраняется тестом, пусть и косвенно.
- **Сломанный порядок (зонд O1).** Обёртка транспорта задерживает первую доставку в группу
  `testkit-encounter-system_events` на 3 с: заглушка узнаёт волка позже входа персонажа. Итог — красный, не
  зависание. Каждый бой падает примерно за 3 с с сообщением «step 4 (attack player-A): … nobody resolved the attack
  … within 2s». Причину («заглушка не знала волка при входе») сообщение не называет — N-3. В обычном прогоне гонка не
  проявилась: `-count=10` зелёный, `-shuffle=on -count=3` зелёный.
- **Вероятностный тест смерти.** По `rules/dark-forest.yaml` и таблице `FixedMechanics` (6 hit + 1 critical из 10)
  укус попадает с вероятностью 0,7. Урон `d4` не меньше 1, при 1 hp любое попадание убивает. Скрипт — не больше 8
  ударов (`maxBlows`), и на каждый волк с 1000 hp отвечает укусом. Потом бегство: успех 0,7 (уходит живым), провал
  0,3, и тогда удар вдогонку. Точная вероятность ложного падения — 0,3⁸ · (0,7 + 0,3 · 0,3) ≈ 5,2·10⁻⁵ (1 на ~19 000).
  Оценка автора 0,3⁸ ≈ 6,6·10⁻⁵ — верхняя граница того же порядка, верна. Сообщение при падении проверено зондом O2
  (персонаж бессмертен, 3 прогона). В двух прогонах выведены оба сообщения, в одном — только «0 death narratives,
  want the one of player-A». Пояснение «the wolf missed every bite» приклеено к проверке исхода и не выводится в самом
  вероятном ложном случае (8 промахов, затем удачное бегство, исход `players_out`) — N-2.
- **`t.Chdir` и `testkit.Deterministic`.** `t.Parallel` в пакете нет. Очистки выполняются в обратном порядке:
  сначала останавливается процесс, затем двойники, потом восстанавливаются окружение, каталог и источник
  идентификаторов. `-shuffle=on -count=3` зелёный, утечки нет.

### 2. `WithCauseID` для жизненного цикла

- `encounter.started`: `Derive(вход, …, WithCauseID(enc.id))` (`:727-736`), `enc.id = "encounter-"+вход.ID`.

- Одна причина с разными встречами различается частью `enc.id`.

### Новые замечания

**Mi-A (Minor) — действие без `id` роняет двойник паникой `WithCauseID`; путь Б1 от неё защищён случайно.**
`FakeEncounter.Act` (`fake_encounter.go:599-622`) не проверяет `ev.ID` и доходит до
`Derive(ev, encounter.started, …, WithCauseID(enc.id))` (`:727-736`). Удар или бегство без `id` так же дойдут до
`endEvent` (`:1265-1267`) на закрывающем пакете. `WithCauseID` на причине без `id` паникует (`cause_id.go:48-50`).

Зонд RF: вход с `ID=""` → `panic: eventbus: WithCauseID on "encounter.started", an event without a cause`.

Путь Б1 от паники не падает (зонд RG: факт смерти волка с `ID=""` → `Observe` возвращает `nil`), но только
случайно. Условие Mi-1 сравнивает `enc.orphaned` (`""`) с `enc.downed.ID` (`""`), равенство выключает
закрытие. Мутант Mi1 превращает RG в ту же панику. Без мутанта бой молча не закрывается.

Достижимость узкая, поэтому Minor. `membus.Publish` конверт без `id` не пропускает (`Route` → `ValidateEnvelope`,
`registry.go:150`). При проверке при чтении по умолчанию такой конверт уходит в `dead_letters`. Остаётся
`MV_BUS_VALIDATE_ON_READ=false` и конверт от продюсера без проверки (Kafka, профиль `legacy`). Двойник стоит в
процессе под `MV_SWARM_FAKE=true`, и паника без `recover` роняет процесс со всеми контекстами.

Это регрессия итерации: в `2ac07829` `Derive` без опции не паниковал. Кроме того, это расхождение с правилом
`shared/eventbus/README.md:94-99`: «обработчик, который может работать без валидации при чтении, проверяет
`ev.ID != ""` до `Derive(…, WithCauseID(…))»`. Двойник — образец для T-230, и настоящий агент унаследует
пропуск.

*Как исправить:*
- в `Act` до `acted.Seen` — `if ev.ID == "" { Warn; return nil }`;
- в `downedBy` — явно пропускать факт без `id` с `Warn` вместо случайного `"" != ""`;
- закрепить тестом по зондам RF/RG.

#### Major

**Ma-1 (T-215). `schemas/events/llm.output.v1.json:32, 48, 91–112` — условная обязательность
`response_raw`, `filter` и `error` не выражена.**

Что требуют документы:
- C-07 и `api-contracts.md` §2.3.10: `response_raw` обязателен, кроме `quarantined` и
  `filter_error`;
- `data-model.md` §7.2: `filter` — «при тексте», `error{}` — «при `error`».

В схеме все три поля просто опциональны, условие есть только в сторону запрета (`if/then` на

Чем это опасно: такую запись `providers/recorded` не воспроизведёт. Replay сессии узнает об этом
только на прогоне (`ErrIncompleteRecord`), а не при публикации. Сужать схему дешевле всего сейчас,
пока издателя (T-211) нет. Тем же доводом оркестратор обосновал `pattern` у `provider`
(журнал 2026-09-11).

T-301)»). В dev-log T-215 его нет ни как сделанного, ни как отклонённого. Сам исполнитель вынес
половину пункта (`error{}` при `error`) в открытые вопросы (dev-log §8 п. 5).

*Правка (вариант а, предпочтительный):* заменить одиночный `if/then` на `allOf` из трёх условий:
- `validation_status ∈ valid|partially_rejected|invalid` → `required: [response_raw]`;
- `validation_status ∈ valid|partially_rejected|quarantined|filter_error` → `required: [filter]`.

`valid` без `response_raw`, `error` без `error{}`. Изменение — сужение без издателей: уведомить

### 2. Гейт облака

Классификация (зонд, `IsLocalEndpoint`):
- **локальные:** `127.0.0.1`, `127.10.0.1`, `[::1]`, `[::1%25lo]`, `[::ffff:127.0.0.1]`, `[::ffff:10.0.0.1]`,

- **облако:**
  - адреса «все интерфейсы»: `0.0.0.0`, `[::]`;
  - `169.254.1.1` (link-local, в том числе адрес метаданных облака) и `100.64.0.1` (CGNAT);
