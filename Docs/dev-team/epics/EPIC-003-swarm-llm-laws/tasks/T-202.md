**Отклонения от дизайна и решения по ходу.**
1. **Источник `AllowedEventTypes`** — `api-contracts.md` §2.4, «Белые списки уровней (MVP-1)». В `data-model.md` §4 — владение сущностями, типы событий там не перечислены. `city-gm` получил список `domain`. У `guardian-monitor`/`entity-actor` список пуст.
2. **Сигнатура `EnvFromProject`**: `ownedEntityTypes` — вторым параметром после типов (ревизия 4: «принимает её параметром»). Блупринты берутся из `<root>/blueprints` без рекурсии; файлы, которые не разбираются, пропускаются. Схемы — из `<root>/schemas/agent/**/*.json`. `Tools` пуст. `FileExists` видит только файлы внутри `root` (`filepath.IsLocal`). Файл на месте каталога — ошибка.
3. **`laws_ref`**: ссылка `laws/<мир>@vN` проверяется как файл `laws/<мир>.vN.yaml` (имя из T-205). КД говорит «существует (`env.FileExists`)», но ссылка — не путь.
4. **7а**: `info: models not checked` выдаётся, только если блупринт называет хотя бы одну модель: у `encounter` без моделей эта строка была бы шумом. Запрещённую модель (NFR-071) у провайдера не переспрашиваем. Режим «`warning` в рантайме» из КД не реализован: признака рантайма в составе `ValidationEnv` из задачи нет — см. бэклог.
5. **`provider`** отвергается парсером (`ParseError{Field: llm.phase2.provider, Reason: unknown field}`) и до `Validate` не доходит. Тест корпуса переводит `ParseError` в `Issue`, как это будет делать CLI.
6. **Без каскада**: правило, которое чего-то требует от роли (фаза, `absolute_limits_ref`, `max_instances`, белый список, строка владения, тип scope), не срабатывает, если роль не сходится с уровнем — правило 1 уже отказало.
7. **Обязательность** по `api-contracts.md` §3.1, столбец «Обяз.»: `llm.phase2` у `personal-gm`/`group-narrator`, `llm.tick` у `global-gm`/`region-gm`/`city-gm`; у `global` нет `parent`, `invariants` не пуст. Кроме того: интервалы, `ttl` задачи и `respawn_ttl` — положительные длительности `time.ParseDuration`; `lod_default` ∈ `rule-only|basic`; `phase1.mode` ∈ `rules|llm`; у `phase2` нет `mode: rules`; `fallback` ∈ `template|rules`; `retries` ≥ 0.
8. **Правило 2**, «task — `pattern` или список `type`»: `type` и так обязателен для всех уровней, отдельной проверки нет.
9. **Правило 13** проверяет и `## description`, и пункты `## canon`. У YAML-блупринта поле называется `prompts.<секция>`.

**Предложения в бэклог.**
1. **T-222 (рантайм)**: серьёзность 7а — `warning` в рантайме по КД. Варианты: поле окружения (например, `ModelMissingSeverity`) или понижение находки `llm.*.model` у вызывающего. Решение — architect#2.
2. **T-204**: перевод `ParseError` → `Issue` лежит в тесте (`issuesOfFile`). CLI нужен тот же; кандидат в API пакета.
3. **`api-contracts.md` §3.2**: «`npc_table[].stats_ref` отсутствует в `rules` — ошибка». В окружении нет статов `rules`, поэтому валидатор это не проверяет. Варианты: поле `ValidationEnv` или тест согласованности I1b (§3, «Тест согласованности»).
4. **Документы** (architect#2; `swarm-llm-laws.md` правит только владелец):
   - КД §13.2 — шапка `ValidationEnv` без `OwnedEntityTypes`/`Models`; правило 8 ссылается на `levels.OwnedEntityTypes`; в правиле 10 нет правила «`laws_ref` → файл»;
   - design §3.1 A2 и КД §2 — `AllowedEventTypes` «по `data-model.md` §4», а фактический источник — `api-contracts.md` §2.4;
   - ADR-015 п. 3 — `EnvFromProject(root, contracts.Types(), invariants)`.
5. **Владение по уровню, а не по роли.** Строки `contracts.OwnershipRules` ключуются уровнем. Поэтому `personal-gm` с `owned_entity_types: [player]` проходит валидатор: строка `task` написана для агента встречи. Предложение `entity.update.proposed` у него перекрыто белым списком событий (только `narrative.output`). Если нужна строгость по роли — это вопрос к C-02 (строки ролей), а не к валидатору.
