**Решения по ходу.**
1. **Корень проекта — отдельный параметр `LoadConfig.Root`.** Ссылки блупринта (`laws_ref`, `rules_ref`, `absolute_limits_ref`, `schema_ref`) — пути от корня проекта (КД §13.2), а каталог блупринтов задаёт `MV_SWARM_BLUEPRINTS_DIR` и может лежать не в `<root>/blueprints`. `LoadFromEnv` берёт корнем рабочий каталог процесса, как `MV_LAWS_DIR` и `MV_LLM_PRICES`.

4. **Один источник на отношение в `ScopeIndex`.** Позиция — только `entity.*` (КД §7.2 «только позиция»), состав групп — только `group.*`, встреча scope — только `encounter.*`. `player.entered_region` и `group.entered_region` индекс не читает (КД §5.1 шаг 3 перечисляет `entity.*/group.*/encounter.*`).
5. **Id scope читается в двух формах** — `{type: solo, id: player-A}` (фикстуры, двойники, `shared/entity.Scope`) и `{type: solo, id: solo:player-A}` (тесты `shared/eventbus`, `shared/contracts`): префикс типа снимается.
6. **Payload декодируется через JSON** — событие, собранное в процессе (`[]map[string]any`), читается так же, как пришедшее с шины (`[]any`).
7. **`/health` — ровно ключи КД** (`blueprints` — базовые имена файлов, `llm: model_missing`). Блупринт и фаза без модели — методом `ModelsMissing()`; выводить ли их в `/health` — решит T-239.

1. **Mi-1: вариант (а), перепроверка до неподвижной точки.** `LoadDir` валидирует набор повторно: `env.Blueprints` каждого прохода — имена файлов, не отвергнутых в прошлых проходах. Набор только сужается, а более узкий набор только добавляет находки, поэтому отвергнутый файл остаётся отвергнутым, и цикл завершается не позже чем через один проход на файл. Находки, которых не было в первом проходе (первый проход идёт по всем именам, как в CLI), получают суффикс `; that blueprint is in the directory, but rejected`.
