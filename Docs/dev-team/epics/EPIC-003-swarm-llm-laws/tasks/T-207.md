### Отклонения от дизайна
1. **Агент и попытка — через контекст (`recorded.WithCall`), а не через `llm.Request`.** В C-15 у `Request` есть только `CorrelationID` и `Phase`; ключ C-07 требует ещё `agent.id` и `attempt`. Менять `Request` — правка контракта C-15 (через system-architect) и файла T-206. Контекст не меняет интерфейс и инертен для других провайдеров. Шлюз (T-212) обязан вызывать `WithCall` перед `Generate`; без этого — `ErrNoCallKey`, а не промах.
2. **Чтение `*.jsonl` и журнала `llm_records` из «Что сделать» не реализовано в пакете.** Первая версия содержала адаптеры `JSONL(io.Reader)` и `Journal(eventbus.Journal)`. По сообщению оркестратора (решение architect по T-457, уточняется: формат, чтение и индекс записи — в отдельном пакете `shared/recording`; собственный парсер JSONL у провайдера отклонён) оба адаптера удалены вместе с тестами. Декодирование JSON для проверки ключа на числах `float64` осталось только в тестовом помощнике `overTheWire`. Два наблюдения из удалённого кода — в бэклоге п. 6.
3. **Самостоятельной регистрации в `init` нет**: `fake.Factory`/`recorded.Factory` отдают фабрики, проводка регистрирует их сама. `recorded` из `llm.Config` не собрать — нужен источник.
4. **`Response.Provider` у `recorded` — провайдер записи** (например, `openai_compat`), а не `recorded`: ответ воспроизводится как был записан.
5. **Имена типов** — `fake.Provider` и `recorded.Provider` (идиома Go для пакета `fake`); в DoD, КД и DoD T-212 они названы `FakeProvider`/`RecordedProvider`. Соответствие записано в README.
6. **Записи без текста** (`error`, `quarantined`, `filter_error`) дают отдельные ошибки, а не `ErrIncompleteRecord`: запись есть, но текста нет. Как шлюз воспроизводит такую попытку, решает T-212 через `Lookup`.

Надо собирать события и разбирать после чтения. (б) `ReadRange` у `membus` при остановке возвращает `next < to` без ошибки — неполный индекс надо считать ошибкой.
