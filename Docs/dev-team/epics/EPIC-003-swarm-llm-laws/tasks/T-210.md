**Отклонения от дизайна и решения по ходу.**
1. **Что суммирует лимит.** КД §9.3 называет ключ окна `(world, level, phase, provider)`, а лимиты — по `(world, {global, domain}, tick)` и `(world, task, narrative)`. Окна хранятся по полному ключу, правило суммирует покрытые им ключи мира по всем провайдерам. Иначе смена провайдера или уровня обнуляла бы фон, а КД §7.3 говорит о бюджете «на мир».
2. **Наполнение только через `llm.output`.** Отдельного «зарезервировать вызов» в `Allow` нет. `Allow` и `Observe` — два шага, поэтому два параллельных вызова могут оба пройти окно с одним свободным местом. КД §7.1 даёт шлюзу один воркер LLM; если T-212 пустит вызовы параллельно, ему нужна сериализация или резерв (риск ниже).
3. **Любой `validation_status` — вызов.** `error`, в том числе `yielded`, тоже учитывается: провайдер был вызван.
4. **Фильтр `actor_kind=system` — только для фона** (КД §7.3). Интерактивный вызов — ответ на действие игрока, `Derive` наследует `actor_kind=human`; с фильтром окно интерактива не восстанавливалось бы.
5. **Время вызова — `ev.Timestamp`**, то есть время причины, а не момент ответа провайдера. Поэтому догон видит тот же момент, что и живой прогон; ~~расхождение с «настенным» временем вызова не больше длительности вызова~~. *(Исправлено при приёмке, tech-lead#2, ревью #1 Mi-1.)* Окно отстаёт на всё время от причины до попытки: Phase 1, ожидание в очереди, предыдущие попытки. Для окна `1h` это пренебрежимо (≤ 2,5 %). Для окна `1m` — до десятков секунд: третья попытка нарратива после двух таймаутов по 20 с записана моментом причины и выходит из минутного окна примерно через 15 с. Дальше — вопрос об `llm.output.called_at` к system-architect#1 и строка DoD T-250.
6. **Денежный лимит облака** (`limit_money`, C-07 v1.4) не входит: DoD раздела его не требует, `Kind=cloud` и схема — T-250.
7. Имя типа события — неэкспортируемая `typeLLMOutput`, чтобы не занять имя, которое, возможно, заведёт `Recorder` (T-211).

**Решения владельца эпика по замечаниям ревью #1**
