## Описание и DoD
- **Причина (T-425, C-01 v1.5)**: паника любого обработчика роняет весь процесс ADR-001 со всеми контекстами; при at-least-once без коммита событие после рестарта приходит снова — цикл рестартов. Путь по данным есть: `Derive(…, WithCauseID(…))` от конверта без id при `MV_BUS_VALIDATE_ON_READ=false`.
- **Код**: `recover` вокруг обработчика в `Deliver` и экспортируемая `ErrHandlerPanic`; без повтора — сразу в `dead_letters` с `attempts` = номер вызова; лог `Error` с `panic`, `stack`, `handled=false`; коммит после записи в `dead_letters`, неудачная запись — ошибка; покрыты и `Subscribe`, и `Journal`, обе реализации шины. Метка `contract-change`.
- **Тесты**: паника при первом вызове; паника после ошибки (`attempts=2`); сбой записи в `dead_letters`; путь `Journal`; случай contract-теста на `membus` (на Redpanda — с T-394).
- **Мутанты**: снять `recover`; повтор после паники; `Warn` вместо `Error`; первым — контрольный мутант с синтаксической ошибкой, ключи overlay относительные.
- **Документы**: комментарий `Handler` в `bus.go`, README `shared/eventbus` (абзацы «Паника не ловится» и «Id из причины»), `components/foundation.md` §5.
- **Срок и порядок**: до первой настоящей подписки в бинарнике (T-055 или T-237), не позже интеграции I1-α; после T-418 — обе трогают `membus` и contract-тест.
- **Исполнитель**: developer.

## Выполнение (developer)
developer#1, 2026-09-11. Время начала и окончания в поручении не указаны. Не закоммичено: коммит делает оркестратор после приёмки.

**Что сделано (C-01 v1.5)**
- `Delivery.Deliver`: каждый вызов обработчика идёт через новый метод `call`. В нём `recover` в отложенной функции превращает панику в `ErrHandlerPanic` и пишет лог. Лог пишется там же, потому что только там `debug.Stack` ещё показывает кадры обработчика.
- Паника не повторяется: `Deliver` сразу вызывает `deadLetter` с `attempts` = номер вызова. `ctx.Err()` для паники не проверяется: паника при остановке тоже паркуется, иначе после рестарта она пришла бы снова. Результат `deadLetter` возвращается как есть: `nil` — вызывающий коммитит офсет, ошибка записи — возврат ошибки, офсет не коммитится.
- `ErrHandlerPanic` объявлена в `registry.go` рядом с остальными ошибками пакета. Текст: `eventbus: handler panic: <значение>`. Значение-ошибка оборачивается через `%w`, `errors.Is` находит и её. `panic(nil)` с Go 1.21 даёт `*runtime.PanicNilError` и тоже паркуется.
- Лог уровня `Error` («event handler panicked; the event goes to dead letters»). Поля: `event_id`, `event_type`, `correlation_id`, `topic`, `offset`, `consumer`, `attempts`, `handled=false`, `panic`, `stack`. Поля события вынесены в помощник `eventAttrs`, им же пользуется прежний `log`, формат его строк не изменился. Стек в `dead_letters` не пишется. Логгер процесс передаёт обеим реализациям (`cmd/multiverse/bus.go`, `bus_memory.go`), поэтому строка в эксплуатации есть.
- Покрытие путей. Kafka: `Subscribe`, `ReadRange` и `Tail` → `k.deliver` → `Delivery.Deliver`/`DeliverRaw`. Коммит в `Subscribe` — только после `nil`. `membus`: те же три метода → `b.deliver` → те же функции, курсор группы сдвигается только после `nil`. Утверждение T-418 подтверждено чтением кода, других вызовов обработчика в обеих реализациях нет. Тесты: `membus` — все три пути; kafka — шаг `deliver` без брокера. Сами циклы kafka встретят панику в contract-кейсе на Redpanda (T-394).
- Документы: комментарии `Handler` и `Bus` в `bus.go`, doc-комментарии `Delivery` и `Deliver`. README `shared/eventbus`: пункт «Паника не ловится» заменён пунктом «Паника обработчика перехватывается» со ссылкой на правило C-01 v1.5 для stateful-контекста; абзац «Id из причины» переписан. `components/foundation.md` §5.3.
