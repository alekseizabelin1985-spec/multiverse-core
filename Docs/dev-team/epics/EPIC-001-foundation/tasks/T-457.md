### Часть 1. ADR-029 и C-07

**1.1. Поправки к ADR-016 и ADR-017 — подтверждены.**
- ADR-016 п. 1 и п. 4: схема нарратива статична, элементы — строки с `pattern` ярлыков, компиляция при старте не меняется; ярлык в `text` — `schema_invalid` без `element`, повтор с подсказкой, строка не правится.
- ADR-017 п. 1 и правило 3 для нарратива: `Input.Mentions`/`AbsenceEventIDs` — `map[string]string`, пустая таблица ≠ `nil`, отброс по элементу в трёх ветках.
- *Доводы.* Статичная схема сохраняет ADR-016 п. 1 и даёт одно поведение на провайдерах с грамматикой и без неё. Сужение `enum` на вызов прятало бы ошибку ссылки под грамматикой и стоило бы повтора всего ответа без неё. Поэлементный отброс — прежний смысл правила 3.
- *Уточнение при подтверждении (N-6 ревью #2).* Ветка «таблицу не передали» проверяется по каждому массиву: непустой `mentions` при `Mentions == nil` или непустой `background_refs` при `AbsenceEventIDs == nil`.
- Пометки внесены: ADR-016 (перед «Последствиями»), ADR-017 (в конце, в том числе доп. 1 п. 4).

**1.2. `ref` в C-07 — вариант A, версия C-07 v1.5.**
- Номер: ADR-029 и КД называют «C-07 v1.4», но v1.4 уже занят денежным лимитом (T-449). Изменение идёт как **v1.5**.
- `llm.output.rejected.ref` — опц. строка 1…128. Условие `unknown_entity`: `element` и ровно одно из `entity` | `background_ref` | `ref`; `ref` допустим только при `reason=unknown_entity`.
- Смысл веток: `entity` — существующая, но невидимая сущность, тип и имя из `View`; `background_ref` — существующее невидимое событие (при ярлыках недостижимо); `ref` — ссылка, не разрешившаяся ни во что (id тика `npc-999`, ярлык `e7`/`b7`).
- **Временная форма ADR-029 п. 6 (`other` с `element`) отменена**, в код не идёт: решение принято до старта T-213, как просил ревьюер.
- Вариант B (`reason=other` навсегда) отвергнут. NFR-021 недосчитывал бы выдуманные ссылки, критерий 2 US-018 для нарратива не выполнялся бы буквально, а для `background_refs` это был бы регресс относительно v1.3 (Mi-9).

**1.3. `labels_hash` (Mi-11) — принят в тот же C-07 v1.5.**
- `llm.output.labels_hash` — опц., `sha256:` + 64 hex, есть ровно у `Kind=narrative` (свойство-тест шлюза, не схема). Хеш таблицы ярлык → id; кодирование — префикс длины у каждого компонента, как `WithCauseID`; порядок `e` по номеру, затем `b`; пустая таблица — хеш пустой строки.
- Replay: совпал `labels_hash` — ярлыки разрешаются при расходящемся `prompt_hash` (только `warn llm_replay_prompt_drift`); не совпал — `warn llm_replay_labels_drift`, массивы пустые, `text` используется; запись без поля — правило ADR-029 п. 8 по `prompt_hash`. Аудит подтверждает восстановленную таблицу `labels_hash`.
- *Доводы.* Без поля плановая смена L (T-260), `<facts>` при `NopMemory` (I2) и правка `<format>` гасили бы ссылки нарратива во всех записях — новый регресс NFR-061. Цена — одно опц. поле до первого издателя, а версия C-07 поднимается всё равно. Таблица целиком в запись не пишется: id уже есть во внешних событиях.
- Следствие для ADR-029 (Mi-11 а, б): после v1.5 смена L или `## phase2` перезаписи записей не требует; с `NopMemory` ссылки теряются, только если различается сама таблица (`<absence>`).

**1.4. Смысл полей C-07 при ярлыках (ADR-029 п. 7) — внесён в C-07 v1.5.** `response_raw` нарратива — с ярлыками; `element.index` — индекс в массиве ответа; `narrative.output.background_refs` — id, повторы схлопываются; ярлык встречается только в `response_raw` и `rejected.ref`; прежнее «тип, который назвала модель» у `entity` заменено типом из `View`.

**1.5. N и c_min — подтверждены.** N — потолок латентности, поэтому округление вниз до десятков у всех конфигураций: Qwen3.6 — 210 и 400, а не «≈ 220» и «≈ 410» (220 токенов дают 5003 мс, 410 — 5002 мс). c_min = 2,0 до калибровки T-438 подтверждено: цена на E — 25 символов текста против обреза `max_tokens` и шаблона на самых длинных ответах. В ADR-005 УИ п. 4 внесена только строка «см. ADR-029».

**1.6. Запись для business-analyst (через оркестратора).**
- US-018, критерий 2, для нарратива: «ссылка на `npc-999`» читается как «ярлык вне таблицы вызова, например `e7`»; событие — `llm.output.rejected {reason: unknown_entity, element, ref}`. Для тика `npc-999` — тоже `ref`.
- NFR-021, метрика `guardian_rejections_per_100` по `unknown_entity` считает все три ветки, включая `ref`. Критерий «только зарегистрированные `entity_id`» для нарратива усилен: id в события ставит роль по таблице, модель id не пишет.
- Пробел «выдуманная ссылка без типа» для `mentions` и тика был и в C-07 v1.3. Для `background_refs` его открыли ярлыки (Mi-9), v1.5 закрывает оба.

### Часть 2. Вопросы приёмки T-054

**В1 — вариант А с сужением стороны участников. C-05 v1.8 п. 9.**
- Агент встречи: участник погиб в идущем бою (группа) — тот же пакет пишет `participants[].state = dead`; после факта `abandoned` — `out_of_combat` в ближайшем пакете встречи; последний игрок — встреча закрывается (C-04 v1.1).
- Закон inv-01, сторона участников (б): нарушение, только если терминальный персонаж **затронут тем же пакетом** и ещё участвует в незакрытой затронутой встрече.
- `law_violation` внесён в перечень C-05 п. 1е.
- *Почему сужение, а не буква варианта А.* При букве А гонка `/forget` (зонд P3) давала бы отказ пакету, который трогает только встречу, а в группе — всему atomic-пакету раунда с уже опубликованными решениями остальных игроков. Этот вход асинхронный и законный. Смерть же всегда приходит пакетом, который её причинил, поэтому P2 закон ловит по-прежнему. Непереписанное участие забытого персонажа ловят аудит и тест агента встречи, а `expected[]` шлюза и `NPCTarget` терминальных уже не считают.
- *Почему не Б.* Без проверки участников неверная запись участия в State — источник read-model шлюза после рестарта — не ловилась бы ничем до аудита, а DoD «три статуса — одно нарушение» потерял бы выражение на стороне персонажа.
- Где код: сторона участников — **T-056**, потому что гонка P3 достижима уже в I1, а T-056 закрепляет её тестом. Сторона NPC — T-066.

**В2 — да, законно. C-05 v1.8 п. 9.** Убитый NPC остаётся в `npcs[]` как история, бой идёт против живых. Закон inv-01, сторона NPC (а): незакрытая встреча, `npcs[]` не пуст и **все** NPC терминальны — нарушение на каждом NPC. Для одного NPC это совпадает с сегодняшней проверкой. Код — T-066.

**В3 — `dead_entity`. C-02 v1.5b.**
- Переход терминальной сущности в любой нетерминальный статус отвергает шаг 5 по сущности «до», для всех трёх терминальных статусов, в том числе когда пакет стирает `died_at`/`killed_by`. `law_violation inv-09` на переход не выдаётся. `invariant_id` называет закон, чья проверка ответила на шаге 8.
- *Доводы.* C-02 v1.5 уже называет переход терминальной сущности `dead_entity` частной строкой рядом с общим правилом про инварианты. `Check` перехода не видит, и `invariant_id` без сработавшей проверки ссылался бы на закон, которого никто не проверял. Потребитель обрабатывает обе причины одинаково (дефект, без повтора).
- *Довод ревьюера* («у условия есть инвариант → `law_violation`») учтён: общее правило действует там, где закон проверяет `Check`. inv-09 в `Check` ловит запись смерти у нетерминальной сущности.
- КД State: §4.5 п. 5 — добавлен `abandoned`, переход — `dead_entity`; §4.6 — строка `domain`/`npc`; §5.7 — строки inv-01, inv-09, inv-10.

**В4 — да, вне инварианта.** `players_present` — производная проекция `position` персонажей: на пути предложений она не пересчитывается и может отставать, истина — `position` (inv-10). Проверка проекции отклоняла бы каждый ход шлюза, который меняет `position` без региона. Правка: `data-model.md` §3.2, `diagrams/erd.md`, КД State §5.7 (строка inv-10). Комментарий `attrs.go` — строка DoD T-056.

**Подтверждение без решения (из приёмки).** В `touched` входят и сущности с пустым `changed[]` — согласен с решением tech-lead#2 в DoD T-056.

**Вопрос 1 T-207 — поля `llm.Request.AgentID` и `Request.Attempt`. C-15 v1.4.**
- `Request` несёт все четыре части ключа записи. Шлюз заполняет их перед каждым `Generate`, `Recorder` пишет `meta.agent.id` и `attempt` из того же `Request`, `recorded` строит ключ `recording.LLMOutputKey`. Записанный и искомый ключи совпадают по построению.
- *Почему не `context` (`recorded.WithCall`):* ключ — часть контракта replay (ADR-010 п. 2), а значение `context` не видно в сигнатуре. Новый вызывающий (middleware облака EPIC-013, golden EPIC-005) компилировался бы без него и падал бы только в replay. К тому же ключ делился бы между `Request` и `context`.
- Совместимо: поля с нулевыми значениями, прочие провайдеры их не читают и в тело запроса не переносят. `WithCall` удаляет T-212.

**Вопрос 2 T-207 — источники над `shared/recording`. C-01 v1.9, «Чтение журнала», «Источники записей LLM».**
- Запись — один тип `*recording.Recording` из двух читателей: файл (`Open`/`Read`) и журнал (`ReadJournal`). Провайдер получает `recorded.Events(rec.Events(recording.TypeLLMOutput))`:
  - `--mode=replay` с `--recording` — `Deps.Recording`;
  - `--mode=replay` без записи — `ReadJournal(Deps.Journal, llm_records, 0)`;
  - догон после рестарта в live — `ReadJournal` от начала окна догона; окно — КД роя §4.3 (курсор снапшота), шаблон при промахе — §9.1 (итерация 3).
- Уроки удалённого кода T-207 — правила `ReadJournal`: обработчик только складывает события, разбор идёт после чтения; `next < End` без ошибки (остановка `membus`) или отменённый `ctx` — ошибка.
- Ключ — одна форма в `shared/recording`: индекс по `LLMOutputKeyOf`, вызов — `LLMOutputKey`. `LLMOutputKeyOf` перестаёт усекать дробный `attempt` (`jsonpath.GetInt` отдаёт `1` на `1.5`): провайдер T-207 такую запись отвергает, и формы не разойдутся. Запись без ключа — `ErrMalformedRecord` у провайдера, пропуск у `Index`.
- *Отвергнуто:*
  - `Source` поверх `ReadRange` с обработчиком провайдера — урок 1;
  - свой `recorded.Key` как ключ индекса — вторая форма ключа;
  - перекрёстный тест двух форм вместо одной — ловит расхождение позже, чем его исключает одна функция.
