## Описание и DoD
- **Причина (ревью #1 T-413)**: построчный разбор YAML в compose-lint расходится с compose молча на целом классе записей — пробел перед двоеточием (закрыт точечно в T-413), $ вместо доллара, удвоенная одинарная кавычка, # в блочном скаляре и в многострочной строке в кавычках, поток-маппинг у правила 3; вложенная подстановка в сообщении :? даёт ложный отказ, хотя compose вычисляет его лениво. Относительный путь в -f не от корня даёт ложный отказ правила 7 (было и до T-413).
- **Что сделать**: брать значения для правил 3, 7 и 8 из вывода docker compose config --no-interpolate (значения после разбора YAML, без подстановки) — это снимает весь класс разом; прогон фикстур — параллельно (сейчас около 68 секунд подряд, цель — около 10).

### Итог

Правила 3, 7, 8 и источник образа у правила 1 читают значения из `docker compose config --no-interpolate --no-consistency --format json --profile '*'`. Каждый файл читается отдельно, поэтому находка называет свой файл. Файл профиля — не самостоятельный проект: `telegram-bot` зависит от `gateway` основного файла. Интерполированный `config` одного `docker-compose.bot.yml` отказывает («depends on undefined service "gateway"»; это вскрыл мутант m05), а `--no-interpolate` на v5.2 согласованность не проверяет. `--no-consistency` добавлен для версий compose, которые сначала собирают проект. На v5.2 вывод с ним и без него побайтно одинаков (sha256 для трёх файлов и фикстуры). Построчный разбор YAML (`strip_comment`, `unquote`, `MAPPED`, `entry`, `TOP_LEVEL`/`BLOCK`, построчный `raw_images`) удалён. Скрипт воспроизводит только интерполяцию, и в двух местах теперь так же, как compose:
- сообщение `${VAR:?…}` не проверяется ни правилом 8, ни второй половиной правила 7: compose вычисляет его, только когда уже отказывает;
- `${VAR:-$${X}}` закрывается на второй `}`: compose считает каждую `${`, в том числе внутри `$${`.

Правило 5 (текстовый поиск литерала `OLLAMA_HOST=0.0.0.0`) оставлено на тексте файла сознательно: это «нигде в файле», включая комментарии. Правила 1–6 по-прежнему читают интерполированную модель.

**Формат — JSON.** Его разбирает стандартный `json` Python, который скрипту уже нужен. Для YAML понадобился бы PyYAML, а его нет в стандартной библиотеке, и на машине владельца и раннере он не гарантирован. Модель для правил 1–6 и так была в JSON.

**Безопасность `--no-interpolate`** проверена на своём файле с фиктивными переменными:
- ключ без значения остаётся `null`, значение из окружения процесса или `--env-file` не подтягивается;
- `env_file` в `environment` не вливается;
- проектный `.env` не читается, потому что линтер всегда передаёт `--env-file build/versions.env --env-file .github/ci.env`.

Для сравнения: интерполированный `config` подставляет значение из окружения в ключ без значения и вливает `env_file`. Значит, в отказы нового чтения попадает только текст самих файлов.

**Защита от чужой версии compose.** Compose v5.2.0 в `config --no-interpolate` по профилю не фильтрует вовсе. Без `--profile` он отдаёт все 11 сервисов `docker-compose.yml`, включая `ollama`, а интерполированный `config` без профиля — только 6. Поэтому `--profile '*'` на этой версии ничего не меняет, и мутант m06 ниже эквивалентен. Флаг оставлен для версии, которая фильтрует сырое чтение по профилю. Если такая версия к тому же не понимает `'*'`, сервисы с профилями пропадут из чтения. На этот случай линтер сверяет, что каждый сервис интерполированной модели есть в одном из чтений, и иначе выходит с кодом 2 и объяснением. Защиту проверяет мутант m14 (пустое сырое чтение).

Попутно (замечания ревью T-413, вошедшие в эту задачу):
- относительный `-f` считается от каталога вызывающего, как у compose; несуществующий файл отвергается по имени, с кодом 2 (N-3);
- находка якоря, влитого в несколько сервисов, выводится один раз со всеми местами;
- место находки — путь в модели (`docker-compose.yml services.core.environment.MV_X`) вместо номера строки;
- `PYTHONIOENCODING=utf-8`: без него на Windows Python пишет отказы в кодовой странице консоли, и `§` в `expect-text` не совпадает (мутант m11).

### Вопрос системному архитектору (не решён, передаю)

Литерал `OLLAMA_*` без подстановки (`OLLAMA_NUM_PARALLEL: 4`) правило 8 не проверяет — так же, как литералы `MV_*` (T-408). Варианты:
- (а) оставить как есть, симметрично T-408;
- (б) отвергать любой литерал `OLLAMA_*`, у которого есть умолчание `DeclareExternal`: законна только форма `${OLLAMA_X:-<умолчание infra.go>}`;
- (в) отвергать литерал, только если он отличается от умолчания `infra.go`.

Рекомендация — (б). У литерала `.env` не может переопределить значение, а литерал с другим числом — второй источник, тот самый, что закрывает контракт §16 п. 5. Для `MV_*` T-408 оправдал литерал тем, что адрес, порт и проба — «один факт, записанный один раз». Для настроек Ollama такой причины нет. В нынешних файлах литералов `OLLAMA_*` нет, ложных отказов не будет. После T-429 реализация — несколько строк: значение ключа из `external` без единой подстановки. Это решение контракта, поэтому оставлено архитектору.
