### Итог

1. **`--alias` в обоих скриптах**, только в single-режиме. Аргументы: `-m <файл> --alias <id>`, сразу за `-m`. Порядок одинаков в `.sh` и `.ps1`, это проверено сравнением командных строк, которые получил подставной сервер. В router-режиме (`--models-dir`) алиаса нет.
2. **Правило id — одна функция на реализацию**: `model_alias` в `.sh` и `Get-ModelAlias` в `.ps1`. Правило такое: берётся часть после последнего `/` или `\`, и с неё снимается хвост `.gguf` без учёта регистра. Другие расширения не снимаются.
   - *Почему не «всё после последней точки»*: так работал прежний `[IO.Path]::GetFileNameWithoutExtension` в прогреве `.ps1`. Из `Qwen3.8-27B` он делает `Qwen3`, а `.sh` в прогреве снимал только `.gguf`, то есть двойники уже расходились.
   - *Почему оба разделителя на любой ОС*: `[IO.Path]` на Linux не делит путь `D:\Models\…`, а `basename` в Git Bash не делит по `\`.
   - Это же имя теперь уходит в `model` прогревочного запроса обеих реализаций вместо двух разных вычислений.
3. **Пустой id — отказ до старта.** Пример: `MV_LLM_MODEL_FILE='D:\Models\'`. Обе реализации печатают одну строку `llm: MV_LLM_MODEL_FILE=… names no file, so the server would have no model id to report` и выходят с кодом 1. Без этой проверки сервер поднялся бы с пустым алиасом, и в `/v1/models` снова оказался бы путь или пустое имя.
4. **Новая строка при старте** (одинаковая в двух реализациях): `llm: the model is reported as <id> (--alias, the file stem that blueprints name)`. Оператор видит, под каким именем модель попадёт в `/v1/models`.
5. **Пин `LLAMACPP_BUILD`: `b10441` → `b10878`.**
   - *Откуда число*: `build_info` из `GET /props` = `b10878-4850c7727` у всех зачётных прогонов E (2–4) и у справочного прогона Qwen3.6. Источник — `results` в `ops/metrics/bench-matrix.json` и `baseline.md` §1, на этом билде принято решение T-435. `b10441` — установка владельца на F-6. На момент задачи стенд `:8888` не отвечал (`/health`, `/props`, `/v1/models` → нет соединения), так что сверить билд живьём было нельзя. Число взято из отчётов, как и велел оркестратор.
   - *Формат*: в пин идёт только номер, без хеша. `make llm-health` вытаскивает `bNNNN` из `MV_LLM_BIN --version` (`build[: ]<N>`) и сравнивает строки. С хешем в пине было бы вечное предупреждение.
   - *Что проверяет `make llm-health`* (T-404 п. 2, логику не трогал): если `MV_LLM_BIN` задан, сравнивает билд бинарника с пином и при расхождении выдаёт предупреждение, а не ошибку (§6.2, §9.5). Если не задан, пишет, что рантайм запущен не отсюда и пин его не описывает. `llm-bench` при незаданном `MV_LLM_BIN` берёт `build_info` из `/props` с пометкой `(props)`, пин — только последний откат (T-434).

### Бэклог (найдено, вне DoD — не трогал)

1. **`.ps1` рвёт аргумент с пробелом.** `Start-Process -ArgumentList` склеивает массив через пробел без кавычек. Сценарий S6 `MV_LLM_MODEL_FILE='D:\My Models\…gguf'` даёт у `.ps1` командную строку `-m D:\My Models\…gguf`, то есть два аргумента, а у `.sh` — один. Дефект есть и на `HEAD` (проверено тем же сценарием), он касается `-m`, `--slot-save-path`, `--models-dir` и имени файла с пробелом в `--alias`. На стенде владельца путей с пробелами нет, поэтому это не блокер. Правка — кавычки для элементов с пробелом в `.ps1` плюс сценарий паритета (T-405).
2. **Прогрев в `llm-server.sh` собирает тело JSON строкой оболочки** — тот же класс, что дефект T-434 в `llm-bench.sh`. После T-437 id не содержит `\` и `/`, но `"` в имени файла на Linux допустим и дал бы 500 на прогреве. Правка — сборка тела python-помощником, как в T-434.
3. **`make llm-health` не сверяет `/v1/models` с `LLM_MODEL_DEFAULT`.** Сервер, поднятый вручную без `--alias`, по-прежнему выглядит зелёным. Строка «модель не резидентна» в проверке закрыла бы это на стороне оператора до появления `Health` провайдера (EPIC-003).
