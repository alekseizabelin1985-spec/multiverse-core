# T-412: Голый docker compose не читает COMPOSE_ENV_FILES из .env, а документы обещают обратное

## Описание и DoD
- **Причина (T-411)**: воспроизведено на compose v5.2 — у владельца `docker compose config` без `make` падает на `REDPANDA_IMAGE`, потому что версии из `build/versions.env` подхватываются только через Makefile. Шапка `docker-compose.yml`, `.env.example` и комментарий в Makefile обещают, что голый compose работает.
- **DoD**: либо голый `docker compose config -q` на чистом клоне с заполненным `.env` зелёный, либо все три документа честно говорят «только через make» и называют причину. Выбор — за исполнителем с обоснованием.
- **Исполнитель**: devops-engineer.

## Выполнение (devops-engineer)
2026-09-11, devops-engineer#1. Подробно — запись T-412 в `../dev-log.md`.

- **Воспроизведение.** Чистый клон (экспорт индекса, `.env` из `.env.example`, `[required]` заполнены заглушками), compose v5.2.0: голый `docker compose config -q` — код 1, `required variable REDPANDA_IMAGE is missing a value` плюс предупреждение `GO_VERSION is not set`. Имя переменной в ошибке — первое попавшееся `*_IMAGE`: при повторе было `REDPANDA_CONSOLE_IMAGE`. Причина: compose берёт `COMPOSE_ENV_FILES` только из окружения своего процесса. Переменная называет env-файлы и потому не может прийти из одного из них, так что строка в `.env` не действует. `COMPOSE_PROFILES` из `.env` compose при этом читает — проверено по списку сервисов.
- **Выбор — (б): «только через make», причина названа.** Путь (а) на v5.2 технически есть — обёртка `include: [{path: docker-compose.yml, env_file: [.env, build/versions.env]}]` проходит интерполяцию версий. Но без `.env` (CI, `compose-lint`) она падает жёстко (`.env: The system cannot find the file specified`). Кроме того, основной файл пришлось бы переименовать, а Makefile, правило 7, CI и `docker-compose.override.yml` — перестроить; файлы профилей `bot`/`legacy` через `-f` версий из `include` всё равно не получают. Копировать пины в `.env.example` нельзя: единственный источник версий — `build/versions.env` (NFR-071). Переменная в профиле пользователя — свойство машины, а не чистого клона.
- **Сделано (только комментарии и документы, модель композиции не изменилась).** Шапка `docker-compose.yml`, комментарий над `COMPOSE_ENV_FILES` в Makefile и блок над строкой в `.env.example` говорят: «только через make», объясняют почему и дают форму для ручной команды (`export COMPOSE_ENV_FILES=.env,build/versions.env`, для PowerShell — `$env:`). Попутно исправлены такие же обещания в `build/versions.env`, `.github/ci.env`, `scripts/compose-lint.sh`, в `infrastructure.md` (§1.1 — строка хоста, §4.2, §9) и в README («Запуск за 5 команд» — врезка). В `Docs/ops/runbook.md` — врезка перед разделом 1 и отсылки в разделах 2, 5, 8 у прямых команд `docker compose`. Строка `COMPOSE_ENV_FILES` в `.env.example` остаётся: её объявляет манифест `shared/env/infra.go`.
- **Новых правил линтера нет**, поэтому ни фикстур, ни мутантов не требуется.
- **Проверки.** Чистый клон: голая форма — 1 (как и написано в документах); с переменной в оболочке — 0; через `$(COMPOSE)` Makefile (`make --eval`) — 0; `make compose-lint` — 0. Рабочее дерево: `make compose-lint` — ok, 8 правил, 14 из 14 «плохих» фикстур отвергнуты; `mvctl env check` — 67 переменных, 0. Владелец: `config -q` с `COMPOSE_ENV_FILES=.env,build/versions.env` — 0, sha256 модели `config --format json` до и после — `0870f33d758b0688` (совпали), `up --dry-run --no-build` — 0; `.env` не открывался, контейнеры не трогались. pre-commit и gitleaks — в dev-log.
