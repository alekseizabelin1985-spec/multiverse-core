# Runbook — эксплуатация Multiverse-Core

Источник: `Docs/dev-team/architecture/infrastructure.md` §9 (сведено к фактическому
состоянию репозитория на момент EPIC-001 «Фундамент», подволна 0.7). Аудитория —
оператор стенда (сейчас — владелец проекта, единственная машина: Windows 11,
Docker Desktop, GPU для LLM).

> **Стадия проекта.** Контексты `state`, `mechanics`, `swarm`, `llm`, `laws`,
> `gateway`, `memory` сейчас — заглушки (`cmd/multiverse/contexts.go`), отвечающие
> `/health: ok` без домена. Команды ниже поднимают и проверяют инфраструктуру и
> процессы платформы; игровых сценариев (`mvctl world init`, сессии игрока) на этом
> этапе ещё нет — они появляются по мере эпиков EPIC-002…EPIC-005. Команды `mvctl`
> и `multiverse db`, которых в этом разделе нет (`world`, `blueprint`, `laws`,
> `record`, `golden`, `llm`, `memory`, `report`, `trace`, `db backup|check`),
> зарезервированы в реестре (`cmd/mvctl/main.go`, `cmd/multiverse/db.go`) и
> возвращают код ошибки с именем владеющего эпика — это ожидаемое поведение, не
> баг.

> **Порядок ниже не прогнан целиком.** GNU make не установлен ни на одной
> машине, где шла разработка T-001…T-398 — ни один участник ни разу не
> выполнил ни одной цели `make` по-настоящему; правки `Makefile` проверялись
> построчной эмуляцией оболочки (см. `Docs/dev-team/journal.md`, записи по
> T-397). CI цели `make` тоже не вызывает. Владелец — первый, кто прогоняет
> этот раздел на реальной чистой машине: установить `make` (README, раздел
> «Требования»), затем `make -n up`, `make compose-lint`, и только потом
> настоящий `make up`.

> **Прямые команды `docker compose` в этом runbook** (`exec`, `restart`,
> `logs`, `pull`, `up -d <сервис>`, файл бота) работают, только если в той же
> оболочке задано `export COMPOSE_ENV_FILES=.env,build/versions.env`
> (PowerShell: `$env:COMPOSE_ENV_FILES = ".env,build/versions.env"`). Без этого
> compose не видит `build/versions.env` и падает на первой переменной образа
> (`REDPANDA_IMAGE` или другой `*_IMAGE`) ещё до команды. Эту переменную compose берёт только из окружения своего процесса,
> строку в `.env` он не читает: переменная называет env-файлы и поэтому не может
> прийти из одного из них (проверено на compose v5.2, T-412). Цели `make`
> экспортируют её сами, поэтому стек поднимается и сводится только через `make`.

## 1. Запуск с нуля (после клонирования)

1. `cp .env.example .env`; заполнить переменные, отмеченные `[required]` в
   комментарии над ними в `.env.example` — это обязательный минимум для
   активного набора профилей (`COMPOSE_PROFILES` в примере — `memory`).
   **Пустую переменную комментировать только строкой выше, никогда после `=`**:
   dotenv-парсер `docker compose` обрезает хвостовой комментарий лишь у
   НЕПУСТОГО значения, а у пустого берёт его текстом значения — переменная
   перестаёт быть пустой, `${VAR:?}` молчит, и сервис стартует с мусорным
   значением, хотя `make` (`set -a; . ./.env`) читает ту же строку как пустую
   (T-397). Оставить `COMPOSE_PROFILES=memory` — профиль `bot` пока не
   запускается (бинарник `cmd/telegram-bot` появится в EPIC-004); про профили
   `bot`/`legacy` — ниже.
2. **LLM (опционально).** Проверить в `.env`: `MV_LLM_PROVIDER=openai_compat`,
   `MV_LLM_URL`, `MV_LLM_BIN`, `MV_LLM_MODEL_FILE`, `MV_LLM_MODELS_DIR`; файл
   модели (`.gguf`) должен лежать по указанному пути. `make llm-up` → дождаться
   `/health = 200` → `make llm-health` (печатает `/v1/models` и билд). Без LLM
   платформа тоже стартует — нарратив деградирует (`/health.llm = unavailable`,
   FR-080), это не авария.
3. `make minio-image` (первый раз ≈ 5 минут) → `make up` (поднимает
   `redpanda`, `minio`, `gateway`, `core` плюс профили из `.env`; init-контейнеры
   создают топики и бакеты) → `make health`.
   На свежем стеке `make health` показывает `core degraded` — мир не создан —
   до `mvctl world init` (с `--bus kafka` — после T-475); затем `ok`. Это не
   авария: `degraded` — работающий процесс, контейнер `healthy`, и `make up`
   не падает (зовёт `make health` с `DEGRADED_STRICT=0`). Сам `make health`
   на `degraded` выходит с кодом ≠ 0; `make health DEGRADED_STRICT=0` его
   принимает. Строки таблицы: `ok`, `degraded`, `FAIL` (`fail`, HTTP ≠ 200,
   HTTP 200 со статусом вне перечня или процесс недоступен), `-` (сервис не поднят) (`infrastructure.md` §2.2, §7.2).
4. Проверка вручную: `curl http://127.0.0.1:8088/health` (gateway),
   `curl http://127.0.0.1:8082/health` (memory, если профиль `memory` включён).
   Порт `core` (`:8090`) наружу не публикуется — проверяется изнутри контейнера:
   `docker compose exec core /multiverse health --url http://127.0.0.1:8090/health`.

### Профили

Профили `bot` и `legacy` описаны в собственных compose-файлах
(`docker-compose.bot.yml`, `docker-compose.legacy.yml`) и подключаются
Makefile'ом, только когда профиль реально запрошен: `make up PROFILES=bot`,
`make up PROFILES=memory,legacy` или `COMPOSE_PROFILES=...` в `.env` (Makefile
сам добавляет `-f` нужного файла по активному набору). Причина — `docker
compose` интерполирует файл целиком ДО отбора по профилям, и обязательные
переменные этих сервисов (токен бота, образ Chroma) раньше валили `make up`
всем подряд, включая тех, кто эти профили не поднимает (T-397). **Голый
`docker compose --profile bot up` без Makefile официально не
поддерживается:** без `COMPOSE_ENV_FILES` в оболочке он не поднимет ничего и
откажет на первой переменной образа (`*_IMAGE`, врезка перед разделом 1), а с
переменной, но без `-f docker-compose.bot.yml`, не увидит файл бота и поднимет
стек без бота. Это решение оркестратора, а не пробел. `make up PROFILES=legacy` сам сначала
выполняет `legacy-src` (цель `up` объявляет её своей предпосылкой, срабатывает,
как только `legacy` попал в активный набор) — она делает `rm -rf
build/.legacy-src` и `git archive` из `LEGACY_SRC_REF`, поэтому первый запуск
профиля дольше обычного; отдельно вызывать `make legacy-src` не нужно. Профиль
`bot` сегодня всё равно не запускает контейнер — `cmd/telegram-bot` появится в
EPIC-004.

### Режим, вид шины и адрес процесса — одна настройка, одно место (T-408)

`MV_MODE` (`live|replay`) и `MV_BUS` (`kafka|memory`) в `.env` — **единственный**
источник этих двух решений. Флаги `--mode` и `--bus` существуют для того, кто
запускает процесс руками, и перекрывают переменную, только если переданы явно;
compose флагов не передаёт, значит в контейнерах решает `.env`. Процесс при
старте говорит, что и откуда взял:

```
multiverse dev listening on :8090, contexts: …, mode: replay (MV_MODE), bus: kafka (MV_BUS)
```

В JSON-логе это поля `mode` / `mode_from` и `bus` / `bus_from`. Если в скобках
стоит `--mode`, значит переменную перекрыли флагом. **Если режим в скобках не
тот, что в `.env`, — это видно сразу**; раньше не было видно вообще ничего:
переменные передавались в контейнеры и не читались никем, а выбор делали флаги,
которых compose не передавал.

Адрес прослушивания у процесса один — `MV_CORE_ADDR`, при любом наборе
`--contexts`: `serve.go` создаёт один HTTP-сервер и отдаёт его всем контекстам.
Внутри compose каждому сервису проставлен литерал (`:8088` gateway, `:8090`
core, `:8082` memory), совпадающий с опубликованным портом; проверка здоровья
контейнера (`/multiverse health` без `--url`) выводит адрес из той же
переменной, так что промахнуться мимо своего же порта она не может.

**Миграция существующего `.env` — один раз, ДО следующего `make up`:**

1. `MV_BUS=redpanda` → `MV_BUS=kafka`. Вид шины называется по протоколу, а не по
   продукту: брокеры и так задаются в `MV_KAFKA_BROKERS`, клиент кафковый, а
   Redpanda — одна из реализаций этого API. Старое значение **не** подменяется
   молча: процесс с ним не стартует и печатает, чем его заменить.
2. Удалить строки `MV_GATEWAY_ADDR` и `MV_MEMORY_ADDR` — оба имени отменены,
   адрес у процесса один (`MV_CORE_ADDR`).

Проверить себя до запуска (Git Bash, из корня репозитория):

```bash
(set -a; . ./.env; set +a; go run ./cmd/mvctl env check --env)
```

Команда называет и недопустимое значение, и отменённые имена с заменой; код
возврата ненулевой, пока в `.env` осталась хоть одна такая строка.

## 2. Остановка / перезапуск

- `make down` — останавливает контейнеры, тома сохраняются; это единственная
  цель остановки для любого набора профилей — она подключает тот же набор
  compose-файлов, что и `make up` (см. «Профили» выше). Если стек поднимали с
  `PROFILES=...`, передайте то же значение и в `make down` (либо держите
  `COMPOSE_PROFILES` в `.env` неизменным между `up` и `down`), иначе Makefile
  не подключит файл профиля и не остановит его сервисы.
- Перезапуск одного процесса: `docker compose restart core` (или `gateway`,
  `memory`) — с `COMPOSE_ENV_FILES` в оболочке (врезка перед разделом 1).
- `make reset` — **удаляет тома**; требует свежего `make backup` и подтверждения
  вводом `yes`.

### Том `gateway-data`, созданный до T-303 — проверить и починить один раз

С T-303 контекст `gateway` при старте открывает `links.db` и `gateway.db` в
`/data` (`MV_GATEWAY_DATA_DIR`) и отказывается работать в каталоге, открытом
группе или остальным (ADR-019 п. 1), и с файлом базы шире `0600`. Образ
платформы создаёт `/data` владельцем `nonroot` (65532) с правами `0700`, и
**пустой** именованный том получает их при первом монтировании. Том
`gateway-data`, созданный прежними `make up`, остался `root` `0755` и прав
образа уже не унаследует: gateway не стартует, контейнер `unhealthy`, в логе
(`make logs SERVICE=gateway`) —
`gateway: data directory /data (MV_GATEWAY_DATA_DIR): … mode 0755, want 0700 or narrower`
или `permission denied`. При признаке `mode 0755` данных в томе нет: шлюз
отказывает до создания первого файла. `permission denied` или `mode 0644` у
файла бывают и у тома **с данными** — например, если `links.db` вернули в том
распаковкой архива от `root`. Поэтому сначала — только проверка (Git Bash, из
корня репозитория; команды для оператора, агенты их не выполняют):

```bash
export COMPOSE_ENV_FILES=.env,build/versions.env
ALPINE_IMAGE=$(sed -n 's/^ALPINE_IMAGE=//p' build/versions.env)
docker volume ls --filter name=gateway-data  # <COMPOSE_PROJECT_NAME>_gateway-data
docker run --rm -v multiverse_gateway-data:/v:ro "$ALPINE_IMAGE" ls -lan /v   # только чтение
```

**Том пуст** (в выводе только `.` и `..`) — пересоздать его:

```bash
make image                                   # образ с каталогом /data
docker compose stop gateway && docker compose rm -f gateway
docker volume rm multiverse_gateway-data     # имя из docker volume ls выше
make up && make health                       # gateway: ok
```

**В томе есть `links.db`** (или `gateway.db`) — том **не удалять**: это
единственная копия связок игроков. Вернуть владельца и права одной командой
и запустить шлюз:

```bash
make image
docker compose stop gateway
docker run --rm -v multiverse_gateway-data:/v "$ALPINE_IMAGE" \
  sh -c 'chown -R 65532:65532 /v && chmod 0700 /v && find /v -type f -exec chmod 0600 {} +'
docker run --rm -v multiverse_gateway-data:/v:ro "$ALPINE_IMAGE" ls -lan /v   # 65532, drwx------, -rw-------
make up && make health                       # gateway: ok
```

Вне compose (`go run ./cmd/multiverse serve --contexts=all --bus=memory` на
хосте) умолчание `/data` — корень файловой системы: на Linux/macOS без root
старт падает, на Windows создаётся `\data` в корне диска. Каталог задают явно,
вне репозитория (там идентификаторы игроков, в git им не место), например
`MV_GATEWAY_DATA_DIR="$HOME/.multiverse/gateway"`; ошибка старта называет
переменную.

## 3. LLM: старт, проверка, смена модели

**Адрес — один, `MV_LLM_URL`, и правило чтения адреса — тоже одно.**
Переменная **обязательна и умолчания не имеет** (T-404, ревью #2): раньше
манифест подставлял `http://127.0.0.1:1234`, и при удалённой из `.env` строке
платформа считала, что адрес есть, а `make llm-health` — что его нет; для
одного случая было два ответа. Адрес LLM угадать нельзя, поэтому его отсутствие
— ошибка на обеих сторонах: `mvctl env check --env` даёт
`MV_LLM_URL: required and empty`, обвязка — `has no value`.
Отдельной переменной для порта нет (T-404). Из `MV_LLM_URL` берётся и порт,
который слушает локальный `llama-server` (`--port`), и адрес, по которому
стучится `make llm-health`, и адрес, который меряет `make bench`. Само правило
живёт в одном месте на реализацию — `scripts/lib/llm-endpoint.sh` и
`scripts/lib/LlmEndpoint.psm1`, — и все четыре скрипта (`llm-server.*`,
`llm-bench.*`) вызывают его, а не повторяют. До этого правило было размножено
по четырём файлам с тремя разными поведениями, и на стенде владельца
`make bench` объявлял живой сервер мёртвым.

Что именно делает правило:

- **значение можно писать как С хвостом `/v1`, так и БЕЗ него** — обвязка сама
  приводит его к базовому адресу и говорит об этом строкой
  `llm: MV_LLM_URL ends with /v1; …`; править значение руками из-за этого не
  нужно, какую бы форму ни дала документация вендора. Без среза запрос ушёл бы
  в `/v1/v1/models`, и живой эндпоинт числился бы мёртвым. Проверка здоровья
  идёт НЕ под `/v1`: `/v1` в СЕРЕДИНЕ пути (`…/v1/proxy`) не трогается;
- **`host.docker.internal` → `127.0.0.1`** для пробы с хоста: имя резолвится
  только внутри контейнера. Любой другой адрес — включая адрес локальной
  подсети и облако — проверяется как есть;
- **порт `--port` берётся оттуда же**, поэтому проба и сервер не могут
  разъехаться;
- **значение без схемы отклоняется** (`127.0.0.1:8888` — не адрес): HTTP-клиент
  платформы такой строкой пользоваться не может, а обвязка, которая работает
  там, где ломается платформа, показывает зелёный свет несуществующей LLM;
- **пустое значение — не «проверять нечего», а ошибка**: `make llm-health`
  завершается ненулевым кодом. Ненастроенная LLM обязана краснеть;
- **порт для локального адреса указывается явно**: `http://127.0.0.1` — это не
  «порт по умолчанию», а порт, которого никто не выбирал, и такой адрес
  отвергается (иначе `llama-server` получил бы `--port 80`). С T-450 это
  относится к любому локальному адресу, а не только к адресу этой машины:
  `http://192.168.1.10` и `http://ollama` тоже отвергаются. Записанный порт
  считается явным, даже если он совпадает с портом схемы: `http://127.0.0.1:80`
  допустим;
- **`0.0.0.0` и `[::]` — ошибка конфигурации**, а не «адрес этой машины»: на
  этом адресе сервер слушает, а клиент по нему обратиться не может. Раньше
  `make llm-up` поднимал на нём сервер. Теперь все цели отвечают
  `names 0.0.0.0, the any-address …` и завершаются с кодом 1. Нужно писать
  `127.0.0.1` или адрес хоста;
- **`user:pass@` в адресе отвергается**: ключ эндпоинта живёт в
  `MV_LLM_API_KEY`, а не в адресе. Значение при этом не печатается — оно
  содержит секрет. (Раньше учётные данные молча выбрасывались, и проба шла без
  них, тогда как `net/http` платформы построил бы из них Basic-заголовок.);
- **невидимые символы отвергаются**: значение с символом вне печатного ASCII
  (мягкий перенос `U+00AD`, нулевой пробел `U+200B` — обычный результат
  копирования из документации) — ошибка в обеих реализациях. Такой адрес
  платформа и обвязка закодировали бы по-разному;
- **`MV_LLM_API_KEY` с управляющим символом отвергается**: ключ, склеенный из
  двух строк `.env`, в заголовок не помещается — его отправили бы обрезанным, а
  оператор увидел бы `401` и пошёл чинить не то;
- **значение `MV_LLM_PROVIDER` вне списка манифеста отвергается** — тем же
  списком, что проверяет `mvctl env check`;
- **обрезаются только пробелы ASCII** (пробел, табуляция, переводы строки) по
  краям значения. Неразрывный пробел `U+00A0` в конце адреса не срезается
  молча, а отвергается как символ вне печатного ASCII — в обеих реализациях
  одинаково (раньше PowerShell его срезал и проверка зеленела, а bash отвергал,
  T-405).

**Какой адрес «локальный» — одно правило на всех (T-450).** Гейт облака
платформы, `make llm-health`/`make llm-up` и правило 6 `make compose-lint`
отвечают на этот вопрос одинаково. Правило и все его случаи — таблица
`testdata/llm/local-endpoints.tsv`, подробности —
`Docs/dev-team/architecture/infrastructure.md` §6.3.1. Кратко:

| Ответ | Примеры | Что будет |
|---|---|---|
| `local` | `127.0.0.1:8888`, `[::1]:8080`, `localhost:1234`, `host.docker.internal:8888`, имя сервиса compose `ollama:11434`, `192.168.1.10:8080`, `10.*`, `172.16–31.*`, `169.254.*`, `[fd12::1]:8080`, `[::ffff:127.0.0.1]:8888` | гейт облака молчит |
| `cloud` | `api.openai.com`, любое имя с точкой (`ollama.local`, `nas.lan`), `100.64.0.1`, `2130706433`, IPv4 с точкой на конце (`127.0.0.1.:8888`) | без `MV_LLM_CLOUD_ENABLED=true` провайдер не стартует, `make llm-health` краснеет, `make compose-lint` отвергает такой адрес в compose |
| `invalid` | `0.0.0.0:8888`, `[::]:8888`, локальный адрес без порта, порт `0` или `65536`, `?`/`#` в адресе, пробел или `\` в хосте | ошибка конфигурации: все цели завершаются с кодом 1 и печатают причину |

Однословное имя (`ollama`, `core`) правило считает именем сервиса compose, но
само его не резолвит. С хоста такое имя обычно не разрешается, и
`make llm-health` получит «unreachable». Для проверки с хоста указывайте
`127.0.0.1:<порт>`.

> **Риск: однословное имя и `*.localhost` полагаются на резолвер.** Класс
> `local` у них не зависит от DNS, а место, куда уйдёт запрос, — зависит. На
> хосте и в контейнере однословное имя проходит список поиска (`search`)
> резолвера: при корпоративном search-домене `ollama` может разрешиться в
> `ollama.corp.example` за пределами машины. `*.localhost` в loopback
> отправляет не каждый резолвер: RFC 6761 выполняется не везде. Гейт облака
> при этом молчит. Там, где это важно, указывайте IP: на хосте —
> `127.0.0.1:<порт>`, в compose — адрес RFC 1918 сети compose. Точка на конце
> не спасает: `ollama.` — это уже `cloud`, а `127.0.0.1.` — не адрес, а имя
> для DNS, и тоже `cloud`.

**Переходный период:** пока в платформу не влита T-451 (EPIC-003), гейт облака
платформы ещё считает однословное имя облаком. Если
`MV_OLLAMA_URL=http://ollama:11434` не стартует с `MV_LLM_CLOUD_ENABLED=false`,
дело в этом, а не в `.env`. До T-451 **не включайте** `MV_LLM_CLOUD_ENABLED=true`
ради имени сервиса: этот флаг открывает платформе любой облачный адрес. Укажите
адрес RFC 1918 контейнера в сети compose (без закрепления он меняется при
пересоздании контейнера) или дождитесь T-451.

`MV_LLM_HOST` — это НЕ дубликат: он говорит, какой интерфейс слушает локальный
сервер (только loopback, SEC-15), а `MV_LLM_URL` — куда стучаться. Нелокальное
значение `MV_LLM_HOST` теперь не предупреждение, а отказ: `make llm-up` не
поднимет сервер, у которого нет аутентификации, на интерфейсе, видном извне.

Первая строка вывода `make llm-health` всегда печатает оба адреса:
`llm: probing <адрес пробы> (from MV_LLM_URL=<значение>)`. Если в вашем `.env`
осталась строка `MV_LLM_PORT=` — удалите её; об этом теперь говорит и сама цель
(`llm: MV_LLM_PORT=… is retired and ignored …`), и `mvctl env check --env`.

**Проба ходит НАПРЯМУЮ, мимо прокси.** И `curl --noproxy '*'`, и
`Invoke-WebRequest -NoProxy` — решение принято сознательно: платформа на Go
уважает `HTTP_PROXY`, а проверка — нет, потому что прокси умеет отвечать за
эндпоинт (на машине владельца он отвечал `503 «модель грузится»` по адресу, где
не слушал никто). Ложный красный переживаем, ложный зелёный — нет. Следствие:
если ваш облачный эндпоинт доступен ТОЛЬКО через прокси, `make llm-health`
покажет его недостижимым, хотя платформа его дозовётся; это ожидаемо.

**Не всякий провайдер поднимается отсюда.** `make llm-up`/`make llm-down`
управляют только нативным `llama-server` (`MV_LLM_PROVIDER=openai_compat` и
адрес этой машины). Для облачного адреса, `anthropic`, `ollama`, `recorded` и
`fake` цели честно печатают, что запускать и останавливать нечего, и не делают
вид, что что-то сделали; для облака и для `ollama` вместо запуска выполняется
проверка «отвечает ли эндпоинт» (см. таблицу ниже).

**Старт.** `make llm-up` (single-режим) или `make llm-up ROUTER=1` (router,
несколько моделей). Скрипт (`scripts/llm-server.ps1` на Windows,
`scripts/llm-server.sh` в WSL/Linux — Makefile сам выбирает по наличию `pwsh`)
пишет PID в `ops/llm-server.pid` и ждёт готовности по адресу из `MV_LLM_URL`
(до 180 с; `503 Loading model` по пути — норма).

**Проверка.** `make llm-health` — адрес пробы и его источник, код готовности,
список `GET /v1/models`, а для локального `llama-server` ещё билд llama.cpp и
`nvidia-smi` (used/total VRAM). Билд и VRAM для удалённого эндпоинта не
печатаются: они описывают процесс этой машины, а версию чужого рантайма
показывает список моделей.

**Точка, по которой выносится суждение.** Сначала `GET /health`. Если сервер
отвечает на нём `404`, `401`, `403`, `405` или `501` — это не «LLM мёртв», а
«такой точки у сервера нет»: `/health` принадлежит llama.cpp, а контракт
платформы — OpenAI-совместимый интерфейс (ADR-005). Тогда суждение выносится
по `GET /v1/models`, и строка вывода прямо говорит, по какой точке: `... = 200
ok (this server has no /health; judged by the endpoint the contract needs)`.
`503` по-прежнему означает «модель ещё грузится». Так на стенде владельца
проверяется сервер семейства unsloth-studio, у которого `/health` нет.

**Второй `make llm-up` не поднимает второй сервер.** Перед запуском цель
стучится по адресу. Если по нему уже кто-то отвечает, а `ops/llm-server.pid` не
записывает нашего процесса (типичный случай: сервер поднят руками), запуск
ОТКЛОНЯЕТСЯ с объяснением — иначе на занятый порт встаёт второй процесс, а
успехом рапортуется чужой ответ.

**Стоп.** `make llm-down` (по PID-файлу `ops/llm-server.pid`). Битый PID-файл не
роняет цель: строка, которая не является номером процесса, игнорируется, файл
удаляется.

**Номеру из PID-файла больше не верят на слово.** Файл содержит три строки —
номер, `bin=` (путь запущенной программы) и `started=` (время старта, UTC), — и
перед остановкой проверяется, что процесс с этим номером выполняет ту же
программу и стартовал тогда же. Причина конкретная: PID-файл переживает
перезагрузку, Windows переиспользует номера процессов, и при ревью #2 этот код
остановил посторонний живой процесс окружения владельца, номер которого оказался
записан в файле. Что бывает теперь:

| Что в файле | Что делают `llm-up` / `llm-down` |
|---|---|
| номер нашего живого процесса | как раньше: «already running … nothing to do» / останавливают |
| номер, за которым стоит ДРУГАЯ программа или другое время старта | НИЧЕГО не останавливают, печатают, чем этот номер оказался, и удаляют файл |
| номер живого процесса, но сверять не с чем (старый однострочный файл и `MV_LLM_BIN` не задан) или программу процесса прочитать нельзя | НИЧЕГО не останавливают и файл НЕ удаляют: `llm-down` печатает причину и завершается нулём, `llm-up` отказывается стартовать (код 1), пока это не разобрано вручную |

Разбирается это вручную: посмотреть, что за процесс (`Get-Process -Id <n>` /
`ps -p <n>`), и, если сервера действительно нет, удалить `ops/llm-server.pid`.

**Что делает каждая цель при разных `MV_LLM_PROVIDER`:**

| `MV_LLM_PROVIDER` и адрес | `llm-up` | `llm-down` | `llm-health` |
|---|---|---|---|
| `openai_compat`, адрес этой машины (`127.0.0.1`, `[::1]`, `localhost`, `host.docker.internal`) | поднимает `llama-server` на порту из `MV_LLM_URL` | останавливает по PID-файлу | полная проверка: адрес, модели, билд, VRAM |
| `openai_compat`, другой локальный адрес (`10.*`, `192.168.*`, `172.16-31.*`, `169.254.*`, IPv6 ULA, имя сервиса compose) | говорит, что отсюда не запускается (сервер на LAN или в compose — не наш процесс), и проверяет, отвечает ли эндпоинт | говорит, что останавливать нечего | проверка по адресу как есть; гейт облака МОЛЧИТ: это доверенная сеть, а не вендор |
| любой провайдер с адресом, адрес `invalid` (`0.0.0.0`, локальный без порта) | ошибка конфигурации, код 1 | то же | то же |
| `openai_compat`, адрес облака | говорит, что отсюда не запускается, и проверяет, отвечает ли эндпоинт | говорит, что останавливать нечего | проверка по адресу как есть, с ключом `MV_LLM_API_KEY`; при `MV_LLM_CLOUD_ENABLED` не `true` — предупреждение И НЕНУЛЕВОЙ КОД, даже если эндпоинт ответил `200`: провайдер откажется от такого адреса (ADR-005 доп. 2 п. 3), значит платформа LLM пользоваться не сможет |
| `ollama` | говорит, что рантайм свой (`ollama serve` / профиль `gpu`), и проверяет `MV_OLLAMA_URL` | говорит, что останавливать нечего | проверка по `MV_OLLAMA_URL`; пустое значение — ошибка |
| `anthropic` | говорит, что это облако вендора; адреса для пробы у обвязки нет | то же | сообщает, что проверить отсюда нечего; готовность провайдера показывает `deps.llm` в `/health` ядра |
| `recorded`, `fake` | говорит, что провайдер отвечает внутри процесса | то же | то же, код 0 |

**Смена модели.** Положить `.gguf` в `MV_LLM_MODELS_DIR` → `make llm-down` →
поправить `MV_LLM_MODEL_FILE` в `.env` (single-режим) или включить `ROUTER=1`
(модель тогда выбирается полем `model` в блупринте, когда блупринты появятся,
EPIC-003) → `make llm-up` → `make llm-health` (новое имя должно быть в
`/v1/models`) → обновить `LLM_MODEL_DEFAULT` в `build/versions.env`. Имя
модели в single-режиме — имя файла без `.gguf`: его отдаёт `--alias`, который
ставит `make llm-up` (T-437); сервер, поднятый вручную без `--alias`, отдаёт путь
к файлу, и модель блупринта с ним не сверится.

**Обновление билда llama.cpp.** Отдельной задачей: скачать релиз → `make llm-down`
→ заменить бинарник (старый сохранить) → `llama-server --version` → обновить
`LLAMACPP_BUILD` в `build/versions.env` → `make llm-up` → `make llm-health` →
`make test-e2e` (золотой прогон на записях, когда они появятся, EPIC-003) — при
регрессии вернуть прежний бинарник.

**Пути с пробелами.** `MV_LLM_MODEL_FILE`, `MV_LLM_MODELS_DIR` и
`MV_LLM_SLOT_SAVE_PATH` с пробелом (`D:\My Models\…`) доходят до `llama-server`
одним аргументом в обеих реализациях (T-405). Раньше `llm-server.ps1` склеивал
аргументы без кавычек, и путь рвался на два. Значения с обратной косой чертой
в `.env` по-прежнему берутся в кавычки (комментарий над блоком в `.env.example`).

**Правка скриптов `scripts/llm-*` и `scripts/lib/*`.** После любой правки —
`make scripts-parity`: одни и те же входы проходят через `.sh` и `.ps1`, и
стенд сравнивает коды возврата, сообщения, аргументы запуска сервера, запросы,
CSV и JSON замера. Серверу владельца он не мешает: вместо `llama-server`
работает двойник на свободном порту `127.0.0.1`, Docker и сеть не нужны. Строка
`KNOWN-FAILING` в выводе — известное расхождение со ссылкой на бэклог, а не сбой.
Если стенд покраснел на сценарии, который правка не должна была задеть, —
расходятся две реализации, и чинить нужно ту, что отстала. Устройство стенда —
`Docs/dev-team/architecture/infrastructure.md` §3.1.2.

**Диагностика:**

| Симптом | Что смотреть |
|---|---|
| `loading` дольше 3 мин | размер модели vs VRAM (`nvidia-smi`); хватает ли RAM при `mlock` |
| `unavailable` с хоста | процесс жив? `ops/llm-server.pid`; адрес пробы печатает первая строка `make llm-health` — по нему и стучаться вручную |
| `make llm-up` советуют там, где `MV_LLM_BIN` не задан | так больше не бывает: без `MV_LLM_BIN` цель не советует `make llm-up`, а говорит поднять рантайм тем же способом, каким он поднимался раньше |
| `llm-down` говорит «refusing to stop a process this run cannot recognise» | номер в `ops/llm-server.pid` не опознан как наш процесс (см. таблицу выше). Это защита, а не сбой: посмотрите, что за процесс, и удалите файл руками |
| проверка стучится «не туда» | так больше не бывает: адрес один (`MV_LLM_URL`) и правило его чтения одно (`scripts/lib/llm-endpoint.*`), расходиться нечему. Если адрес неверен — он неверен и у платформы, правится в одном месте |
| `make llm-health` = 0, а LLM не работает | так больше не бывает: пустой адрес, закрытый гейт облака и ответ не `200` дают ненулевой код в обеих реализациях |
| `make bench` говорит «the LLM process is not running» при живом сервере | так больше не бывает: замер берёт адрес и правило оттуда же, откуда проверка, включая откат с `/health` на `/v1/models` |
| `unavailable` только из контейнера | `host.docker.internal` (у `core` есть `extra_hosts: host.docker.internal:host-gateway`), правило файрвола Windows для `llama-server.exe` |
| `degraded(model_not_resident)` | `GET /v1/models` vs ожидаемое имя модели |

Логи — `ops/llm-server.log` (перезаписывается при рестарте; `--verbose` не
включаем).

## 4. Резервное копирование и восстановление

Реализовано целями Makefile (`build/versions.env` задаёт образ `ALPINE_IMAGE` для
служебных контейнеров):

```bash
make backup                 # тома minio-data и redpanda-data -> $BACKUP_DIR (по умолчанию ~/multiverse-backups), затем backup-prune
make backup-prune           # удалить копии старше 30 дней (DRY_RUN=1 — только показать)
make restore FILE=<архив>   # восстановить один из них: make restore FILE=minio-<date>.tgz
                            # архив старше 30 дней — только вне $BACKUP_DIR и полным путём (см. ниже)
make archive-legacy         # разово: as-is тома (minio_data, redpanda_data) -> backups/legacy-<date>/
```

`make backup` останавливает `core`/`redpanda` на время снятия архива каждого тома
и запускает их обратно; бакет `prompts-*` исключается из бэкапа MinIO намеренно
(содержит тексты игроков, отдельный жизненный цикл ILM 30 дней). `make reset`
отказывается работать без свежего архива в `$BACKUP_DIR`. Очистка в конце
`make backup` не роняет ни `backup`, ни `make deploy`: если она вернула не `0`
(например, старый архив держит открытым антивирус или Проводник), печатается
`backup: WARNING backup-prune exited <код> …`, архивы при этом уже сделаны, а
очистку повторит ежедневное задание.

**Архив для восстановления старше 30 дней** держите вне `$BACKUP_DIR` — например,
в `%USERPROFILE%\multiverse-restore\` — и передавайте полным путём:
`make restore FILE="$HOME/multiverse-restore/minio-<date>.tgz"`. Внутри
`$BACKUP_DIR` его удалит ближайший запуск очистки (задание Планировщика или
`make backup`), в том числе между копированием и `make restore`.

### Срок хранения копий: 30 дней (T-463)

Копии данных игроков хранятся не дольше 30 дней: решение оркестратора
(`journal.md`, 2026-09-13), ревью безопасности T-318 (M-1, R2-Mi-1), тот же срок,
что у бакетов `prompts-*` (SEC-22). Уведомление FR-009 обещает «ещё до 30 дней в
копиях» — это обещание держит `scripts/backup-prune.sh`.

**Правило — возраст, а не число.** Удаляется всё, что строго старше 30 суток на
момент запуска. «Оставить последние N» и «не трогать последний архив» нет: если в
каталоге остались только старые копии, он очищается от них полностью. Ровно 30
суток и моложе — остаются.

**Что удаляется** (только внутри `$BACKUP_DIR`, по умолчанию
`%USERPROFILE%\multiverse-backups`):

| Копия | Имя файла | Кто пишет |
|---|---|---|
| архив тома MinIO | `minio-<штамп>.tgz` и его строка в `SHA256SUMS` | `make backup` |
| архив тома Redpanda | `redpanda-<штамп>.tgz` и его строка в `SHA256SUMS` | `make backup` |
| копия `links.db` (зашифрована `age`) | `links\links-<штамп>.db.age` | бэкап SQLite, EPIC-004 |
| копия `gateway.db` | `links\gateway-<штамп>.db` | бэкап SQLite, EPIC-004 |

**Формат штампа** — `%Y%m%d-%H%M%S` по местному времени (`date +%Y%m%d-%H%M%S`,
например `20260913-093000`), как у `make backup`. Бэкап `links.db`/`gateway.db`
(EPIC-004) обязан писать имена ровно в этом формате. Возраст берётся из штампа:
копирование файла меняет mtime, а имя — нет. Если у файла с таким префиксом и
суффиксом штамп не разбирается (`minio-copy.tgz`, месяц 13), возраст берётся по
mtime — иначе такой файл жил бы вечно. Штампу, который опережает «сейчас» больше
чем на сутки (часы были неверны во время `make backup`, файл переименован), скрипт
не верит: возраст берётся по mtime, в вывод и журнал пишется
`WARNING <путь>: its stamp is more than a day ahead of now …`. Опережение до суток
включительно — небольшое расхождение часов, штамп остаётся в силе. Если больше
чем на сутки вперёд ушёл mtime (у файла без штампа или со штампом, которому не
поверили), опереться больше не на что: файл живёт до mtime плюс 30 дней, а скрипт
пишет `WARNING <путь>: its mtime is more than a day ahead of now …` (T-463).

**Каталог `--dir`** должен быть абсолютным путём (`/…`, `C:\…` или `C:/…`), не
корнем диска (`/`, `C:\`, `/c`) и содержать слово `backup` в одном из компонентов
пути в любом регистре (`multiverse-backups` подходит). Относительный путь (`.`,
`backups`) отвергается: задание Планировщика разрешило бы его от своего рабочего
каталога (`System32`), и опечатка в `/TR` чистила бы не тот каталог. Проверка
повторяется после разрешения пути: `C:\backups\..` — тоже корень.

**Что не трогается никогда:** файлы с другими именами (`notes.txt`,
`postgres-<штамп>.tgz`, сам `SHA256SUMS`, журнал `backup-prune.log`), строки
`SHA256SUMS` других файлов, любые подкаталоги кроме `links\` (в том числе
`legacy-*`), каталоги и символические ссылки с «подходящим» именем, `links\`,
если это ссылка. Скрипт не переходит по ссылкам и не удаляет по маске: каталог
перечисляется, и каждый файл удаляется по своему полному пути
(`rm -f -- <путь>`). Каждый удалённый файл печатается с возрастом и тем, откуда
он взят (`by its stamp` / `by its mtime`).

Срок — константа `RETENTION_DAYS=30` в скрипте, переменной окружения нет.

Архив старше 30 дней, принесённый в `$BACKUP_DIR` ради восстановления, удалит
ближайший запуск очистки (задание или `make backup`). Держите такой архив вне
каталога (`%USERPROFILE%\multiverse-restore\`): `make restore FILE=<путь>`
принимает любой путь.

```bash
make backup-prune DRY_RUN=1   # что было бы удалено, ничего не удаляет
make backup-prune             # удалить; каталог — BACKUP_DIR Makefile
bash scripts/backup-prune.sh --dir "$HOME/multiverse-backups" --dry-run   # то же без make
```

Код выхода: `0` — успех (в том числе «нечего удалять»), `1` — файл не удалился или
`SHA256SUMS` не переписался (строка неудалённого архива остаётся), `2` — ошибка
вызова, каталога нет или `--dir` отвергнут (относительный путь, корень диска, нет
слова `backup`).

#### Ежедневное задание Планировщика задач

`make backup` вызывает очистку в конце, но срок от этого вызова не зависит: если
бэкапы перестанут делать, старые копии всё равно должны уйти. Поэтому очистку
запускает отдельное ежедневное задание. **Регистрирует его владелец стенда один
раз**, в `cmd.exe` (не в PowerShell: у него своё экранирование кавычек внутри
`/TR`). Путь к клону — свой; `%USERPROFILE%` раскрывается в момент создания:

```bat
schtasks /Create /TN "multiverse\backup-prune" /SC DAILY /ST 10:00 /RL LIMITED /F /TR "\"C:\Program Files\Git\bin\bash.exe\" \"%USERPROFILE%\Documents\Claude\Projects\multiverse\scripts\backup-prune.sh\" --dir \"%USERPROFILE%\multiverse-backups\" --log \"%USERPROFILE%\multiverse-backups\backup-prune.log\""
```

- `bin\bash.exe` из Git for Windows сам добавляет `/usr/bin` в `PATH`, отдельный
  профиль не нужен. Скрипт принимает путь с обратными слешами.
- Строка `/TR` после раскрытия `%USERPROFILE%` не длиннее 261 символа (ограничение
  `schtasks`); при длинном пути к клону — перенести клон или каталог бэкапов ближе к
  корню профиля.
- Без `/RU` задание выполняется от текущего пользователя и только когда он вошёл в
  систему; пароль не сохраняется. Каждый запуск на секунду открывает окно консоли.
- Если `/Create` отвечает «Отказано в доступе» из-за папки `multiverse\` в
  Планировщике, зарегистрируйте задание без папки: `/TN "multiverse-backup-prune"`,
  и то же имя подставляйте ниже в `/Run`, `/Query`, `/Delete`, а в
  `Set-ScheduledTask` — `-TaskPath '\' -TaskName 'multiverse-backup-prune'`.
  Создание папки без повышения прав регистрацией не проверялось.
- Не запускайте `make backup` около 10:00: если задание прочитает `SHA256SUMS` до
  дозаписи сумм свежего архива, а перепишет после, строка свежего архива
  потеряется (окно — доли секунды, архив остаётся; сумму можно пересчитать
  `sha256sum`).
- `schtasks /Create` не умеет «запустить при первой возможности, если запуск
  пропущен» (машина была выключена в 10:00). Включить это (PowerShell, один раз):

  ```powershell
  Set-ScheduledTask -TaskPath '\multiverse\' -TaskName 'backup-prune' -Settings (New-ScheduledTaskSettingsSet -StartWhenAvailable)
  ```

**Проверка после регистрации:**

```bat
schtasks /Run /TN "multiverse\backup-prune"
schtasks /Query /TN "multiverse\backup-prune" /V /FO LIST
```

В выводе `/Query`: «Время прошлого запуска» (Last Run Time) — только что,
«Прошлый результат» (Last Result) — `0`, «Время следующего запуска» (Next Run
Time) — завтра в 10:00. В конце `%USERPROFILE%\multiverse-backups\backup-prune.log`
— строки `backup-prune: run at …` и `backup-prune: done: …`.

**Признаки, что задание не выполнялось** (проверять раз в неделю, раздел 7):

- «Время прошлого запуска» старше суток или `30.11.1999 0:00:00` (так Планировщик
  показывает «ни разу»); «Прошлый результат» `267011` (0x41303) — задание ещё не
  запускалось;
- «Прошлый результат» `1` — файл не удалился или `SHA256SUMS` не переписался,
  `2` — неверный `--dir` (каталога нет, путь относительный, корень диска, нет слова
  `backup`) или аргумент; причина — в `backup-prune.log`;
- в `backup-prune.log` есть `WARNING … its stamp is more than a day ahead of now`
  или `WARNING … its mtime is more than a day ahead of now` — проверить часы
  машины, на которой делали `make backup`; файл с mtime впереди удалится только
  через 30 дней после этого mtime, при необходимости удалить его вручную по полному
  пути;
- последняя строка `backup-prune: run at …` в `backup-prune.log` старше суток или
  журнала нет;
- `make backup-prune DRY_RUN=1` печатает `would remove` с возрастом 32 дня и
  больше — очистка отстала больше чем на сутки (файлы возрастом 30–31 день между
  двумя запусками задания — норма).

Снять задание: `schtasks /Delete /TN "multiverse\backup-prune" /F`.

**Копии в томе `gateway-data`.** Открытые копии `/data/backup/*` внутри тома этот
скрипт не видит и не чистит: их удаляет сама процедура бэкапа SQLite сразу после
`docker cp` на хост (infrastructure.md §5.6; runbook бота и gateway — T-317,
EPIC-004).

**Восстановление после падения (тома целы):** `make up` → `make health`; в логе
`core` — попытка восстановления по журналу (контексты пока заглушки, поэтому
сейчас это просто повторный старт без данных для восстановления).

**Восстановление на чистой машине:** установить Docker Desktop, `git clone`,
`.env` из менеджера паролей владельца → `make minio-image` → `make restore
FILE=minio-<date>.tgz` → `make restore FILE=redpanda-<date>.tgz` → `make llm-up`
(если нужен) → `make up` → `make health`. Архивы старше 30 дней положите вне
`$BACKUP_DIR` (например, `%USERPROFILE%\multiverse-restore\`) и передайте в `FILE=`
полным путём: в `$BACKUP_DIR` их удалит очистка, если на машине уже есть задание
Планировщика или вы успеете сделать `make backup`.

**Онлайн-бэкап SQLite (`links.db`/`gateway.db`) и восстановление памяти
(Qdrant/Neo4j) через `mvctl`/`multiverse db`** — реализуются вместе с
`internal/gateway` (EPIC-004) и `internal/memory` (EPIC-005); сейчас
`multiverse db backup|check` возвращает ошибку «нет базы данных в этом процессе»
— это ожидаемо, компонентов ещё нет.

### Ротация токена

Признаки компрометации: токен попал в публичный репозиторий/чат/скриншот,
бот отвечает на команды, которые оператор не отправлял, либо
`getUpdates`/`getMe` внезапно начали отвечать `401` без смены `.env`
(`cmd/telegram-bot/internal/updates.ErrUnauthorized`, код выхода процесса — 1).

**Не подставлять токен в URL, в аргумент команды или в адресную строку
браузера** — он уйдёт в историю оболочки (`~/.bash_history`, история
PSReadLine), в аргументы процесса и, в браузере, в историю и синхронизацию.
Не выкладывать вывод `docker compose config` и `docker inspect
telegram-bot` — там токен виден открытым текстом.

1. В Telegram открыть `@BotFather` → выбрать бота → `/revoke` (или «API
   Token → Revoke» в меню бота) — выпустить новый токен; старый перестаёт
   действовать немедленно. Формулировку и путь меню сверить с текущим
   интерфейсом @BotFather при сухом прогоне (открытый пункт, см. карточку
   T-317, «Итерация 2»).
2. Заменить значение `MV_TELEGRAM_BOT_TOKEN` в `.env` на новый токен;
   обновить запись `.env` в менеджере паролей владельца (раздел 4) и
   резервные копии `.env` рядом с репозиторием — обновить или удалить.
   Без этого шага восстановление на чистой машине (раздел 4) вернёт
   отозванный токен, и бот выйдет с кодом 1. Токен передаётся сервису
   `telegram-bot` **только** через `environment:` в `docker-compose.bot.yml`
   (D-10, правило 4 `compose-lint`) — не через `env_file` и не хранится
   больше нигде в репозитории.
3. **До перезапуска** проверить веб-хук **нового** токена (не старого —
   после `/revoke` из шага 1 старый токен отвечает `401`, и проверка старым
   токеном ничего не покажет). Непустой webhook означает, что `getUpdates`
   нового процесса ответит `409 Conflict`: бот выйдет с кодом 3
   (`cmd/telegram-bot/internal/updates.ErrConflict`) и уйдёт в цикл
   рестартов. Токен — только через stdin, не в URL и не в аргументе
   команды. Git Bash:
   ```bash
   IFS= read -rs TG_TOKEN            # ввод не отображается и не пишется в историю
   printf 'url = "https://api.telegram.org/bot%s/getWebhookInfo"\n' "$TG_TOKEN" \
     | curl -sS -K -                 # curl -K - читает URL из stdin, не из argv
   # при непустом "url" в ответе — снять webhook тем же приёмом:
   printf 'url = "https://api.telegram.org/bot%s/deleteWebhook"\n' "$TG_TOKEN" \
     | curl -sS -K -
   unset TG_TOKEN
   ```
   PowerShell (Windows PowerShell 5.1 и PowerShell 7). Вызывать именно
   `curl.exe`: в Windows PowerShell 5.1 `curl` — псевдоним
   `Invoke-WebRequest`, и он не понимает `-sS -K -`. Ввод `Read-Host` в
   историю PSReadLine не пишется, в истории остаётся только литерал `$t`:
   ```powershell
   $s = Read-Host -AsSecureString
   $t = [System.Net.NetworkCredential]::new('', $s).Password
   "url = `"https://api.telegram.org/bot$t/getWebhookInfo`"" | curl.exe -sS -K -
   # при непустом "url" в ответе — снять webhook тем же приёмом:
   "url = `"https://api.telegram.org/bot$t/deleteWebhook`"" | curl.exe -sS -K -
   Remove-Variable s, t
   ```
4. Перезапустить бота вместе с остальным стеком или один сервис.
   **`PROFILES=` замещает активный набор, а не дополняет его** (переменная
   `ACTIVE_PROFILES` в `Makefile`) — перечислить весь обычный набор
   оператора вместе с `bot`, а не только `bot` (см. раздел 2, «тот же
   `PROFILES=` у `up` и `down`»):
   ```bash
   make up PROFILES=<обычный набор>,bot   # например: make up PROFILES=memory,bot
   # либо, не трогая остальной стек:
   docker compose -f docker-compose.yml -f docker-compose.bot.yml up -d telegram-bot
   ```
   Если бот всё же вышел с кодом 3 — тот же токен поллит другой экземпляр
   бота или webhook появился снова: остановить сервис, устранить причину
   (шаг 3, [`cmd/telegram-bot/README.md`](../../cmd/telegram-bot/README.md),
   «Коды выхода и `409 Conflict`») и только потом запускать заново.
5. **Токен нигде не логируется** (SEC-08):
   `cmd/telegram-bot/internal/privacy` вырезает `bot<цифры>:<секрет>` из
   любой строки лога и из текста ошибок HTTP-клиента Telegram, включая
   `debug`. Проверить после перезапуска, по всему логу контейнера, а не
   только по последним строкам (утечка при старте может уйти выше хвоста).
   Шаблон ловит обе формы токена — с префиксом `bot` и голую
   `<цифры>:<секрет>`; `bot<redacted>` под него не попадает:
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.bot.yml \
     logs telegram-bot | grep -cE '[0-9]{5,}:[A-Za-z0-9_-]{30,}'   # ожидается 0
   ```
   Ненулевой счёт — считать новый токен скомпрометированным и повторить
   ротацию с шага 1; найденные строки не выкладывать и не пересылать.

Чек-лист (в порядке шагов):
- [ ] Старый токен отозван у `@BotFather` (или заменён по шагу 1) — старый
      перестал действовать.
- [ ] `MV_TELEGRAM_BOT_TOKEN` в `.env` обновлён; запись в менеджере паролей и
      резервные копии `.env` вне репозитория обновлены или удалены — нигде не
      остался отозванный токен.
- [ ] Webhook нового токена пуст или снят — до перезапуска (шаг 3).
- [ ] Сервис `telegram-bot` перезапущен новым токеном (шаг 4).
- [ ] В логе `telegram-bot` токена нет (весь лог, шаг 5, не только хвост).
- [ ] `make health PROFILES=<набор>,bot` показывает `telegram-bot` здоровым
      (проба `127.0.0.1:8089`, `Makefile`, цель `health`), а
      `docker compose ps telegram-bot` — `healthy` (healthcheck —
      `/telegram-bot health` внутри контейнера).

### Правила оператора (условия правдивости уведомления `/start`, T-318)

Текст первого сообщения бота (`/start`, FR-009) обещает игроку автоматическое
удаление его записей и срок хранения бэкапа связки ≤ 30 дней (в резервных
копиях игры записи могут храниться ещё до 30 дней сверх указанных сроков —
У-1). Обещание правдиво только при соблюдении следующих правил — подробности
и источники в
[`cmd/telegram-bot/README.md`](../../cmd/telegram-bot/README.md) («Данные
игроков»), в карточке
[T-318](../dev-team/epics/EPIC-004-gateway-bot/tasks/T-318.md) (раздел
«Условия правдивости У-1…У-9») и в
[КД, gateway-and-bot.md](../dev-team/architecture/components/gateway-and-bot.md):

- профили `memory` и `legacy` не запускаются, пока в
  `MV_TELEGRAM_ALLOWED_USER_IDS` есть кто-то, кроме владельца — проверка, не
  зависящая от набора `-f` у `docker compose`: `docker ps --filter
  label=com.docker.compose.project=<проект> --format '{{.Names}}'` не должен
  показывать `qdrant`, `neo4j`, `memory`, `chromadb`, `semantic-memory`,
  `narrative-orchestrator` для внешних игроков;
- открытых копий тома `gateway-data` не оставлять; копия `links.db` — только
  через `age`;
- копии `links.db` и `gateway.db`, а также архивы `make backup`, не хранятся
  дольше 30 дней (ротация — задача T-463, статус `todo` на момент этой
  страницы: до её выполнения чистка старше 30 дней — вручную);
- `mvctl report` по сессиям живых игроков не запускать до доработки
  EPIC-005 (T-131/T-132): сейчас `ops/metrics/*` может содержать
  идентификатор игрока;
- при изменении сроков retention (30/90/180 дней) или срока хранения
  бэкапа текст `cmd/telegram-bot/internal/render/notice.go` и его тест
  правятся в той же задаче
  (FR-009).

### Другие правила эксплуатации бота

- В `@BotFather` у бота должен быть выключен `/setjoingroups` (**Disable**):
  бота нельзя добавить в группу. В группе бот и так не отвечает и не читает
  сообщения (SEC-07), но выключенная настройка исключает саму возможность
  добавления.
- При `SIGTERM` может потеряться одно обновление, уже взятое в обработку
  (long polling без буфера канала, `WithUpdatesChannelCap(0)`); Telegram
  отдаёт остаток пачки повторно при следующем запуске, повтор гасится тем же
  `action_key` — повторного действия игрока не происходит.
- Отказ постороннему (не из allow-list) — не больше одного ответа «Доступ по
  приглашению.» на чат и не больше 10 таких ответов на весь бот за 60 секунд;
  счётчик отказов (`bot_denied_total`) виден в `/health` бота вместе с
  `bot_not_private_total` и `bot_too_often_total`. `status` в `/health` —
  `ok`, пока процесс работает: недоступность Telegram или шлюза видна не там,
  а в логе (`deliveries not polled`, `answer not delivered`).
- Таймауты клиентов бота (подробно — README бота, «Как устроен процесс»):
  ответы игрокам и вызовы шлюза из обработчика команд — короткие (шлюз: 6 с на
  попытку и один повтор, ответ игроку в Telegram: 10 с на попытку и один
  повтор, отказ постороннему: 5 с без повтора), чтобы один
  зависший вызов не держал команды всех игроков; цикл доставки ждёт шлюз до
  35 с (long-poll 25 с). Ответ игроку под флуд-баном Telegram дольше 3 с
  (`sender.ReplyPolicy`) теряется — игрок повторяет команду; доставки
  (механика, нарратив) при сбое Telegram не подтверждаются и приходят снова
  через 30 с.
- Шаг диалога, `player_id` чата, курсор доставок и отметка «удаление не
  завершено» (`forget_incomplete`) хранятся только в памяти бота. После
  перезапуска: игрок продолжает с `/start`; неподтверждённые доставки приходят
  снова, а сообщение, чей `ack` не дошёл до шлюза, игрок может получить
  дважды; повтор `/forget confirm` после ответа «удаление не завершено» и
  рестарта между ними ответит «нечего удалять», хотя связка и данные уже
  стёрты — оператору это не требует действий.

## 7. Ежедневный / еженедельный чек оператора

- Перед сессией (если нужен LLM): `make llm-up` — процесс не служба, после
  перезагрузки Windows сам не поднимется.
- Регулярно: `make health` (ненулевой код — есть `FAIL`, `degraded` или
  недоступный LLM: смотреть вывод `make llm-health` под таблицей; при
  `LLM_STRICT=1`, это умолчание, он тоже даёт код ≠ 0, а `LLM_STRICT=0` его не
  считает; `degraded` — процесс работает, но ждёт действия, например
  `mvctl world init`); `make backup`
  (еженедельно или перед важными изменениями); `docker system df`.
- Еженедельно: задание `multiverse\backup-prune` выполнялось —
  `schtasks /Query /TN "multiverse\backup-prune" /V /FO LIST` и
  `make backup-prune DRY_RUN=1` без строк `would remove … (32 days old` и старше
  (раздел 4, «Срок хранения копий»).
- После правки `.env`: `(set -a; . ./.env; set +a; go run ./cmd/mvctl env check --env)`
  — переменная с недопустимым или отменённым именем/значением называется здесь,
  а не выясняется падением контейнера после `make up` (T-408).
- Ежемесячно: сверить `build/versions.env` с реестрами образов и релизами
  llama.cpp (раздел 5).

Автоматизированные отчёты (`mvctl report`, `mvctl llm`, инциденты
в `ops/metrics/incidents.csv`) появляются вместе с EPIC-005 (005-ops); сейчас
`ops/metrics/` содержит только заготовки замера LLM из задачи F-8: `README.md`,
`bench-matrix.json` и `baseline.md` (статус — ШАБЛОН, заполняется после прогона на стенде).

## 8. Карточки процессов

| | `gateway` | `core` | `memory` (профиль `memory`) |
|---|---|---|---|
| Команда | `/multiverse --contexts=gateway` | `/multiverse --contexts=state,mechanics,laws,llm,swarm` | `/multiverse --contexts=memory` |
| Порт / health | `127.0.0.1:8088/health` | `127.0.0.1:8090/health` (не публикуется наружу; проверка изнутри контейнера) | `127.0.0.1:8082/health` |
| Данные сейчас | нет (том `gateway-data` зарезервирован, `internal/gateway` ещё не реализован) | нет домена (заглушка); при появлении `internal/state` — MinIO (`entities-*`, `snapshots-*`) | нет домена (заглушка); при появлении `internal/memory` — Qdrant/Neo4j |
| Старт / стоп | `docker compose up -d gateway` / `stop gateway` | `docker compose restart core` | `docker compose up -d memory` (требует профиль `memory`) |
| Логи | `make logs SERVICE=gateway` | `make logs SERVICE=core` | `make logs SERVICE=memory` |
| Типичный сбой | контейнер не стартует → проверить `.env` (обязательные `MV_MINIO_*`) | `llm=unavailable` → раздел 3 | `qdrant`/`neo4j` не healthy → `docker compose logs qdrant neo4j` |

Команды `docker compose` в таблице — с `COMPOSE_ENV_FILES` в оболочке (врезка перед
разделом 1); `make logs` передаёт переменную сам.

Пятая карточка — **`llama-server`** (нативный процесс, не сервис compose):

| | `llama-server` |
|---|---|
| Команда | `make llm-up` (см. раздел 3) |
| Порт / health | адрес из `MV_LLM_URL` (другого источника нет, T-404): `GET /health` (200 `ok` / 503 `loading`), с откатом на `GET /v1/models` |
| Данные | файл модели `.gguf` в `MV_LLM_MODELS_DIR` |
| Старт / стоп | `make llm-up` / `make llm-down`; `make up`/`make down` его не трогают |
| Логи | `ops/llm-server.log` |
| Секреты | нет — локальный сервер работает без `--api-key` |
